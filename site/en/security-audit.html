Scope and method

The reviewed scope was the full diff since the round 10 state (445279ac, July 20, 2026) up to the current working state, including uncommitted changes: 215 commits and 468 files, but only about 3,750 lines of production code across 22 modules — the remainder is tests and refactoring documentation.

  • New UFW sysctl override feature writing to /etc/ufw/sysctl.conf as root
  • New runtime measurement module and its hook into the central command path
  • Large radio refactoring, proven behaviour-preserving via a normalised content diff
  • As-is review of the radio sinks (mpv/ffmpeg invocation, ICY metadata, recording filenames, playlist parsing)
  • Regression re-check of the round 9 and 10 hardening — all intact

Candidates and validation

K1 — stderr contamination in the read-modify-write of /etc/ufw/sysctl.conf [LOW, 6/10, hardened]: the file is read via sudo -n cat through a helper that merges stderr into stdout, so a sudo warning ("unable to resolve host …") arrives with exit code 0 inside the supposed file content and would be written back into a root config file. The reporter's claim that this could disable hardening at boot was refuted empirically: sysctl warns about a malformed line but continues processing the remaining lines and returns 0, and ufw-init ignores errors anyway. The reporter also missed that a write-back only happens on an actual change, and that the same pattern already existed in committed code. The warning text is not attacker-controlled, so there is no injection vector. Hardened regardless with a plausibility gate that aborts the run — at both read sites — as soon as the content contains a line that cannot be a sysctl config line.

K2 — new write sink missing its sister sink's allowlist [LOW, 3/10, hardened]: the key allowlist introduced in round 10 sits deliberately at the write sink as a second line of defense, but the new sink writing to /etc/ufw/sysctl.conf — a file that per its own header overrides /etc/sysctl.conf and /etc/sysctl.d — carried none of those checks. Not exploitable today (the only caller passes a module constant, and no data flow from transfer packages or remote JSON reaches this sink), but a regression against a documented protection decision. The sink now applies the same allowlist and value validation as its sister.

K3 — "sysctl re-apply silently reverts kernel hardening" [REFUTED, 2/10]: the validator extracted the original ufw_0.36.2-6_all.deb and showed that /etc/ufw/sysctl.conf contains no rp_filter at all, so the central premise was wrong. The only real overlap with the NetMon baseline is log_martians — and the code under complaint is precisely the countermeasure for it, since the package ships log_martians=0 against NetMon's target of 1. A downstream value verification also exists: a baseline re-check reads the live kernel values after every step. Finally, the direction of the deviation was misjudged — rp_filter=1 is stricter than NetMon's deliberate 2, so security would rise, not fall. No code change needed.

Implemented hardening

  • Key allowlist and value validation at the UFW sysctl write sink
  • Plausibility gate aborting any read-modify-write whose content contains a non-config line (both read sites)
  • -- option terminator before the mpv media argument, so a playlist entry named --script=payload.lua cannot become an option
  • Handover payload now passes through the stream URL scheme allowlist — the only path that bypassed it
  • mpv IPC socket moved into XDG_RUNTIME_DIR or a private 0700 directory (socket access means mpv's run command)
  • Explicit ffmpeg protocol allowlist without file, so a crafted HLS/concat playlist cannot pull local files into a recording
  • Value-side redaction in the measurement log — previously only metadata keys were checked, not values
  • Measurement log opened with O_NOFOLLOW and mode 0600; rotation skips symlinked paths
  • 26 new regression tests; full suite 2562 passed, 2 skipped
