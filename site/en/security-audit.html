Code Security Review
NetMon Roots v1.1.20

Tenth automated security review based on Claude Fable 5, covering the full code diff since the round 9 state. This round focused on the largest change since 1.1.19: the new security-baseline / sysctl apply stage and the baseline transfer package (import/export between machines), plus the locale-independent UFW parsing, the new data backup, and the test/development infrastructure. Two high-severity issues were confirmed and fixed — a sysctl directive injection via an imported transfer package (a path to root privilege escalation) and, discovered empirically rather than statically, a test suite that really rebooted the host because two tests executed a real systemctl reboot.

Two high-severity issues were confirmed and fixed. F1: the new baseline transfer package passed imported id/ expected fields into an /etc/sysctl.d/ file loaded as root, with no character or allowlist check — a crafted file could set kernel.core_pattern = |/path/script (root code execution on the next crash). F2: two tests let a command generator return a real systemctl reboot without mocking execution — and since an active desktop user may reboot via polkit without a password, every test run actually restarted the host. Both were fixed (strict sysctl allowlist and value validation; defused tests plus a suite-wide guard against destructive commands), regression-tested, and re-verified.

Scope and method

The reviewed scope was the full code diff since the round 9 state (~15,300 new lines), with version consistency across the application, Debian package, and changelog (all 1.1.20). The audit concentrated on the new functionality and on privileged or externally influenced paths.

  • New security-baseline / sysctl apply stage and the baseline transfer package (import/export)
  • Locale-independent UFW and Lynis output parsing
  • New data backup and the "game mode" firewall exceptions
  • Native permission checks (home/critical-file rights, Secure Boot) and the root network service
  • Test / development / CI infrastructure

Confirmed findings

F1 — Sysctl directive injection via imported baseline transfer package [HIGH, 9/10, fixed]: imported id/key/expected fields were only checked for non-emptiness, then written as key = value into /etc/sysctl.d/ and loaded as root via sudo -n sysctl --system. A crafted file could set kernel.core_pattern = |/tmp/evil.sh (root code execution on the next crash) or silently downgrade kernel hardening via embedded newlines. Fixed with an allowlist of the ten documented baseline keys plus strict key/value format validation (no newlines, pipes, or shell metacharacters), deriving the drop-in id only from the validated key, and a second defense-in-depth filter at the write sink.

F2 — Test suite executed a real systemctl reboot (host restart) [HIGH, empirical, fixed]: two tests for the new system actions returned the real ["systemctl","reboot"] without mocking the execution path, so every test run on a desktop system actually rebooted the host (discovered empirically — the audit host restarted reproducibly during test runs). This affects the test/development and CI infrastructure, not the shipped application code (whose release path is guarded by a confirmation dialog, safety phrase, and strict protection). Fixed by defusing both tests and adding a suite-wide guard (tests/conftest.py) that blocks destructive commands at the subprocess level, even behind sudo/pkexec wrappers.

Implemented hardening

  • Sysctl key allowlist and strict value validation for imported transfer packages
  • Suite-wide guard blocking destructive system commands (reboot/poweroff/shutdown/logout) in tests
  • 15 new regression tests (8 for the sysctl allowlist, 7 for the command guard)
  • Regression re-check of the round 7/8/9 hardening — all intact
