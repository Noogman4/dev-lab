# State

## 1. Kurzbeschreibung

State bedeutet Zustand. Bei Software beschreibt er die aktuell relevanten Werte und Bedingungen eines Programms oder Objekts. Ein vereinfachtes Statusmodell kann beispielsweise „bereit“, „scannt“ und „Fehler“ unterscheiden. Der tatsächliche Gesamtzustand umfasst häufig mehr als ein einzelnes Wort. Welche Übergänge zulässig sind, muss bewusst festgelegt werden.

## 2. Was bedeutet der Begriff?

Die Quelle nennt mögliche NetMon-Zustände. Hier dienen solche Namen nur als verständliche Beispiele. Sie sind keine geprüfte Beschreibung vorhandener Programmzustände oder tatsächlich implementierter Übergänge.

Ein Zustandsmodell wählt aus dem großen technischen Gesamtzustand die für eine Aufgabe wichtigen Unterschiede aus. Wenn ein Auftrag läuft, soll beispielsweise kein zweiter gleicher Auftrag unkontrolliert beginnen. Ein Statusname allein verhindert das noch nicht. Die verarbeitenden Stellen müssen die vorgesehenen Regeln auch anwenden.

## 3. Einfacher Vergleich aus dem Alltag

Eine Bestellung ist zunächst aufgenommen, später in Bearbeitung und schließlich abgeschlossen. Bestimmte Handlungen sind nur in passenden Phasen sinnvoll. Ein abgeschlossener Auftrag kann nicht einfach so behandelt werden, als wäre er noch nie begonnen worden.

Die Grenze: Der Zustand ist eine fachliche Modellierung. Ob Rücknahme, Wiederholung oder Teilabschluss möglich sind, hängt vom tatsächlichen Prozess ab. Software kann außerdem parallel laufende Teilzustände besitzen. Drei aufgeschriebene Wörter bilden daher nicht jede reale Situation vollständig ab.

## 4. Wie funktioniert das?

Ein einfacher Zustandsautomat legt Zustände und erlaubte Übergänge fest. Ein Ereignis oder eine Operation kann einen Wechsel anfordern. Vor dem Wechsel wird geprüft, ob er in der aktuellen Situation zulässig ist. Weitere Daten oder Bedingungen können dabei ebenfalls relevant sein.

Die [Qt-Dokumentation zu QStateMachine](https://doc.qt.io/qt-6/qstatemachine.html) beschreibt Zustände, Übergänge und deren gemeinsamen Graphen. Qt bietet dafür einen konkreten ereignisgesteuerten Rahmen. Das folgende kleine Python-Beispiel verwendet diesen Rahmen nicht und besitzt auch nicht dessen Ausführungs- oder Nebenläufigkeitsmodell.

Für feste Namen kann Python eine Enumeration verwenden. Die [Dokumentation zu Enum](https://docs.python.org/3.13/library/enum.html#enum.Enum) erklärt solche benannten Mitglieder. Eine Enumeration verhindert aber nicht von selbst jeden falschen Übergang. Sie stellt zunächst die vorgesehenen Namen bereit; die Übergangsregel wird zusätzlich implementiert.

Viele unabhängig veränderte Ja-Nein-Schalter können widersprüchliche Kombinationen ermöglichen, etwa gleichzeitig „fertig“ und „läuft“, wenn das fachlich ausgeschlossen sein soll. Ein passendes Modell macht solche Regeln sichtbar. Ob ein einzelner Automat genügt oder mehrere Teilzustände gebraucht werden, muss anhand der Aufgabe entschieden werden.

## 5. Wo begegnet mir das unter Linux?

Anwendungen zeigen Verbindungs-, Bearbeitungs- und Fehlerzustände. Die Anzeige sollte zum maßgeblichen Zustand passen. Ein ausgegrauter Knopf allein schützt aber nicht alle anderen Zugriffswege vor einer unzulässigen Operation. Fachliche Prüfungen brauchen einen passenden Ort.

Ein Zustand im Arbeitsspeicher ist außerdem nicht automatisch dauerhaft gespeichert. Nach einem Neustart muss gegebenenfalls ein sinnvoller Zustand neu aufgebaut oder geladen werden. Dieser Eintrag ändert keine vorhandene Konfiguration, startet keinen Auftrag und prüft kein Wiederanlaufverhalten einer Anwendung.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Es verarbeitet ausschließlich eigene Zustandsnamen. „SCANNT“ bezeichnet einen Testwert; es wird kein Netzwerk angesprochen.

```python
from enum import Enum, auto

class Zustand(Enum):
    BEREIT = auto()
    SCANNT = auto()
    FEHLER = auto()

erlaubt = {
    (Zustand.BEREIT, Zustand.SCANNT),
    (Zustand.SCANNT, Zustand.BEREIT),
    (Zustand.SCANNT, Zustand.FEHLER),
    (Zustand.FEHLER, Zustand.BEREIT),
}

def wechseln(aktuell, ziel):
    if (aktuell, ziel) not in erlaubt:
        raise ValueError("Übergang nicht erlaubt")
    return ziel

zustand = Zustand.BEREIT
zustand = wechseln(zustand, Zustand.SCANNT)
zustand = wechseln(zustand, Zustand.BEREIT)
abgelehnt = False
try:
    zustand = wechseln(zustand, Zustand.FEHLER)
except ValueError:
    abgelehnt = True
assert abgelehnt and zustand is Zustand.BEREIT
print("Endzustand:", zustand.name)
print("Unzulässiger Wechsel abgelehnt:", abgelehnt)
```

Geprüfte Ausgabe:

```text
Endzustand: BEREIT
Unzulässiger Wechsel abgelehnt: True
```

Die erste Folge ist im selbst festgelegten Modell erlaubt. Der direkte Wechsel von BEREIT nach FEHLER ist hier bewusst ausgeschlossen. Das ist eine Beispielentscheidung, keine allgemeine Regel für jede Anwendung. Das Programm prüft keine parallelen Aufträge, dauerhafte Speicherung oder GUI-Aktualisierung.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Statusname kann einen ausgewählten Aspekt beschreiben. Der Gesamtzustand umfasst weitere relevante Werte. Ein Zustandsautomat regelt Übergänge. Das gleichnamige State-Entwurfsmuster kann zustandsabhängiges Verhalten auf eigene Objekte verteilen; nicht jede Enum-Liste ist bereits dessen Umsetzung.

## 8. Häufige Missverständnisse

Ein Zustandsname erzwingt noch keine Regeln. Eine Anzeige ist nicht automatisch der maßgebliche Speicherzustand. Enum führt keine erlaubten Übergänge von selbst aus. Und ein erfolgreiches Einzelbeispiel beweist keine korrekte Nebenläufigkeit.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Benenne Zustände und Übergänge fachlich verständlich. Prüfe auch abgelehnte Folgen und Fehlerwege. Dokumentiere, welcher Teil den Zustand ändern darf. Die Übung bleibt bei eigenen Speicherwerten und verändert keine Geräte, Dienste oder Netzwerkeinstellungen.
