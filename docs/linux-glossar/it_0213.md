# Fork

## 1. Kurzbeschreibung

Ein Fork ist im hier gemeinten Git-Projektumfeld eine eigenständig verwaltete Abzweigung eines Repositorys. Auf einem Hostingdienst kann sie als eigenes Repository unter einem anderen Benutzerkonto oder einer Organisation erscheinen. Sie ermöglicht eigene Entwicklung, ohne dafür unmittelbar Schreibrechte im ursprünglichen Projekt zu benötigen. Das Original wird dadurch nicht automatisch verändert.

## 2. Was bedeutet der Begriff?

Die Quelle spricht von einer eigenen Kopie eines fremden Repositorys. Für Plattformen wie GitHub gehört dazu eine vom Dienst verwaltete Beziehung zum Ausgangsrepository. Ein gewöhnlicher lokaler Git-Klon und ein solcher Plattform-Fork sind deshalb nicht einfach derselbe Vorgang.

Die [GitHub-Dokumentation zu Forks](https://docs.github.com/en/pull-requests/reference/forks) beschreibt deren Beziehungen und Plattformregeln. Diese Beschreibung gilt für GitHub, nicht automatisch für jeden Hostingdienst. Der allgemeine Begriff kann außerdem eine langfristige eigenständige Weiterentwicklung eines Softwareprojekts meinen, auch wenn später keine Änderungen mehr zurück vorgeschlagen werden.

## 3. Einfacher Vergleich aus dem Alltag

Du erhältst eine eigene redaktionell betreute Ausgabe eines gemeinsamen Handbuchs. Darin kannst du Vorschläge ausarbeiten, ohne die Ausgabe der ursprünglichen Redaktion direkt zu ändern. Später kannst du anbieten, einzelne Verbesserungen zu übernehmen.

Die Grenze: Eine Plattform verwaltet technische Repository-Beziehungen, Berechtigungen und Sichtbarkeitsregeln. Ein Fork ist deshalb keine beliebig private Papierkopie. Außerdem bleiben Nutzungs- und Lizenzbedingungen relevant. Eine technische Kopiermöglichkeit ist keine pauschale Erlaubnis für jede weitere Verwendung.

## 4. Wie funktioniert das?

Ein Hostingdienst legt den Fork innerhalb seiner Regeln an und verknüpft ihn mit dem Ausgangsprojekt. Anschließend kann eine lokale Arbeitskopie dieses Forks erstellt werden. Eigene Commits werden zunächst lokal erzeugt und gegebenenfalls zum eigenen Fork übertragen.

Soll die Arbeit ins ursprüngliche Projekt gelangen, braucht es einen weiteren abgestimmten Integrationsweg. Der Fork allein schreibt keine Änderungen zurück. Auch neue Änderungen des Ausgangsprojekts erscheinen nicht als allgemeine Git-Regel automatisch in sämtlichen Arbeitsständen des Forks.

Die [GitHub-Anleitung zur Synchronisierung eines Forks](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/syncing-a-fork) unterscheidet eine Aktualisierung auf der Plattform von einem lokalen Ablauf mit Abruf und Integration. Nach einer nur lokalen Aktualisierung muss eine gewünschte Übertragung zum Plattform-Fork gesondert erfolgen. Ein Remote-Name wie `upstream` ist dabei eine übliche lokale Bezeichnung, keine zwingend eingebaute Git-Quelle.

## 5. Wo begegnet mir das unter Linux?

Wer an einem frei zugänglichen Projekt mitarbeiten möchte, arbeitet oft in einem lokalen Klon des eigenen Plattform-Forks. Der Editor sieht dann gewöhnliche Arbeitsdateien. Die Verbindung zwischen Fork und Ursprungsprojekt gehört zusätzlich zur Plattform und ihren Arbeitsabläufen.

Git auf Linux benötigt für lokale Commits keinen Fork bei einem Dienst. Ebenso ist ein Fork keine Voraussetzung für jeden Teambeitrag; mit passenden Rechten kann ein Projekt andere Abläufe verwenden. Die Wahl hängt von Zusammenarbeit und Berechtigungen ab.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenbeispiel wurde nicht auf einer Plattform ausgeführt. Die Namen „Handbuch“ und „Eigene Ausgabe“ sind erfunden. Es wird kein Konto angelegt, kein Fork erzeugt und keine Nachricht an ein Projekt geschickt.

Zuerst besitzt das ursprüngliche Handbuchprojekt einen gespeicherten Stand. Eine Mitwirkende möchte einen Tippfehler verbessern, hat dort aber keine unmittelbaren Schreibrechte. Ein nach den Plattformregeln erlaubter Fork kann ihr einen eigenen Ort für die Entwicklung geben.

Danach erstellt sie eine lokale Arbeitskopie ihres Forks. Dort bearbeitet sie den Text und speichert einen Commit. Erst ein späterer Push überträgt diesen Commit in ihren Plattform-Fork. Die lokale Kopie, der Fork auf dem Dienst und das ursprüngliche Repository sind drei unterscheidbare Orte.

Anschließend kann sie die Änderung zur Übernahme vorschlagen. Das Ausgangsprojekt entscheidet über Prüfung und Integration. Ein Vorschlag ist keine automatische Annahme. Alternativ kann die eigene Ausgabe dauerhaft unabhängig weitergeführt werden, soweit die geltenden Bedingungen das erlauben.

Später enthält das Original eine weitere Verbesserung. Die Mitwirkende muss prüfen, ob und wie diese in ihre eigene Entwicklung passt. Die bloße Herkunftsbeziehung löst mögliche Konflikte oder fachliche Unterschiede nicht selbst. Das Beispiel behauptet weder eine tatsächliche Synchronisierung noch eine geprüfte Plattformintegration.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Clone ist eine Git-Kopie, häufig für lokale Arbeit. Ein Branch ist eine Referenz innerhalb eines Repositorys. Ein Fork ist hier eine eigenständig verwaltete Projektabzweigung. Ein Vorschlag zur Übernahme ist wiederum ein zusätzlicher Zusammenarbeitsvorgang. Der gleichnamige Unix-Prozessbegriff ist ein anderes Thema.

## 8. Häufige Missverständnisse

Ein Fork verändert das Original nicht automatisch. Er ist nicht zwingend privat. Er ersetzt keinen lokalen Commit und keinen Push. Eine Herkunftsbeziehung garantiert außerdem keine dauerhafte Aktualität oder spätere Übernahme der eigenen Änderungen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Kläre die Regeln des konkreten Diensts sowie Sichtbarkeit und Nutzungsbedingungen. Dokumentiere die vorgesehenen Austauschwege. Dieses Dokument bleibt bei der Erklärung; es verändert weder Projektberechtigungen noch Repository-Beziehungen auf einem Hostingdienst.
