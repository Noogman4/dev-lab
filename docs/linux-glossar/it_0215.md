# Conflict

## 1. Kurzbeschreibung

Ein Conflict ist im Git-Kontext eine Situation, in der Änderungen nicht automatisch zu einem eindeutigen Ergebnis zusammengeführt werden können. Häufig verändern zwei Entwicklungszweige dieselbe Textstelle unterschiedlich. Git hält die Integration dann an. Die Beteiligten müssen entscheiden, welcher gemeinsame Inhalt richtig ist, und die Auflösung nach dem vorgesehenen Ablauf bestätigen.

## 2. Was bedeutet der Begriff?

Die Quelle nennt einen Widerspruch beim Zusammenführen. Ein Merge-Konflikt ist ein typischer Fall. Konflikte können aber auch bei anderen Integrationsverfahren auftreten. Außerdem gibt es mehr als widersprüchliche Textzeilen: Beispielsweise können Löschen und Bearbeiten derselben Datei aufeinandertreffen.

Die [offizielle Dokumentation zu git merge](https://raw.githubusercontent.com/git/git/master/Documentation/git-merge.adoc) beschreibt das Anhalten bei Konflikten und die Fortsetzung nach ihrer Auflösung. Ein Konflikt bedeutet nicht automatisch eine beschädigte Repository-Datenbank. Er zeigt zunächst, dass für die betroffenen Änderungen eine zusätzliche Entscheidung nötig ist.

## 3. Einfacher Vergleich aus dem Alltag

Zwei Redakteure ersetzen denselben Satz durch unterschiedliche Fassungen. Beide berufen sich auf denselben früheren Text. Eine dritte Person kann nicht allein aus der Reihenfolge der Blätter ableiten, welche Aussage fachlich gelten soll.

Die Grenze: Git prüft technische Änderungsmuster, keine vollständige Bedeutung. Zwei Änderungen können ohne gemeldeten Konflikt zusammengeführt werden und trotzdem fachlich widersprüchlich sein. Umgekehrt kann eine technisch schwierige Textüberlappung inhaltlich leicht lösbar sein. Die Werkzeugmeldung ersetzt keine Prüfung des gemeinsamen Ergebnisses.

## 4. Wie funktioniert das?

Bei einer konfliktbehafteten Zusammenführung bleiben die betroffenen Pfade als ungelöst vermerkt. In gewöhnlichen Textkonflikten kann Git Markierungen und die beteiligten Fassungen in die Arbeitsdatei schreiben. Die genaue Darstellung hängt von Optionen und Konfliktart ab. Binärkonflikte müssen nicht dieselben sichtbaren Textmarkierungen besitzen.

Nach der bewussten Bearbeitung wird das gewünschte Ergebnis aufgenommen. Bei einem normalen angehaltenen Merge kann danach der Zusammenführungscommit abgeschlossen werden. Das Entfernen von Markierungen allein ist keine fachliche Lösung: Der übrig gebliebene Inhalt muss sinnvoll sein. Auch ein versehentlich vorgemerkter falscher Text kann technisch als aufgelöst gelten.

Die [Dokumentation zu git diff](https://raw.githubusercontent.com/git/git/master/Documentation/git-diff.adoc) erläutert verschiedene Vergleichsformen und die Auswahl nach Änderungsarten. Das Beispiel prüft einen ungelösten Pfad mit dem Filter `U`. Nach dem Abschluss werden zusätzlich Inhalt, Elternzahl und Status kontrolliert.

## 5. Wo begegnet mir das unter Linux?

Konflikte erscheinen im Terminal, im Editor oder in grafischen Merge-Werkzeugen. Diese Oberflächen zeigen unterschiedliche Hilfen zur Auswahl. Eine Schaltfläche für „unsere“ oder „ihre“ Fassung sollte nicht ohne Kenntnis des aktuellen Vorgangs verwendet werden; ihre Bedeutung muss zur Integrationsrichtung passen.

Vor der Integration ist ein sauberer Ausgangsstand hilfreich. Bestehende offene Arbeit kann die Übersicht und Rücknahme erschweren. Hier wird ein Konflikt ausschließlich mit drei selbst erzeugten Textfassungen in einem neuen temporären Repository hergestellt.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel lief mit Python 3.13 und Git 2.52.0. Persönliche und systemweite Git-Konfiguration sind für die Kindprozesse ausgeblendet; das neue Repository übernimmt keine Vorlagen. Der erwartete fehlgeschlagene Merge wird ausdrücklich kontrolliert.

```python
import os
from pathlib import Path
import subprocess
import tempfile

env = {k: v for k, v in os.environ.items() if not k.startswith("GIT_")}
env.update(GIT_CONFIG_GLOBAL="/dev/null", GIT_CONFIG_NOSYSTEM="1")
with tempfile.TemporaryDirectory() as ordner:
    repo = Path(ordner)
    def git(*args, erwartet=0):
        r = subprocess.run(
            ["git", "-c", "user.name=Glossar", "-c",
             "user.email=glossar@example.invalid", "-c",
             "commit.gpgsign=false", *args],
            cwd=repo, env=env, capture_output=True, text=True
        )
        assert r.returncode == erwartet, (r.stdout, r.stderr)
        return r.stdout.strip()
    datei = repo / "notiz.txt"
    def speichern(text):
        datei.write_text(text + "\n", encoding="utf-8")
        git("add", "notiz.txt")
        git("commit", "-m", text)
    git("init", "--template=", "-b", "basis")
    speichern("Name: Probe")
    git("switch", "-c", "variante")
    speichern("Name: Probe A")
    git("switch", "basis")
    speichern("Name: Probe B")
    git("merge", "--no-edit", "variante", erwartet=1)
    assert git("diff", "--name-only", "--diff-filter=U") == "notiz.txt"
    assert "<<<<<<<" in datei.read_text()
    speichern("Name: Probe A und B")
    assert datei.read_text() == "Name: Probe A und B\n"
    assert git("status", "--porcelain") == ""
    assert len(git("rev-list", "--parents", "-n", "1", "HEAD").split()) == 3
    print("Textkonflikt erkannt:", True)
    print("Aufgelöster Inhalt:", datei.read_text().strip())
```

Geprüfte Ausgabe:

```text
Textkonflikt erkannt: True
Aufgelöster Inhalt: Name: Probe A und B
```

Die kombinierte Formulierung ist eine ausdrückliche Entscheidung für diese erfundene Notiz. Sie ist keine universelle Konfliktstrategie. Der Merge endet mit zwei Eltern und sauberem Status. Es werden keine Projektdateien zusammengeführt und keine Daten übertragen; das Übungsrepository wird entfernt.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Konflikt ist kein zusätzlicher Branch und kein eigener Commit. Er kann einen Merge unterbrechen. Ein fachlicher Fehler kann dagegen auch ohne Git-Konflikt bestehen. Ein Rebase-Konflikt gehört zu einem anderen laufenden Verfahren mit dessen eigenem Fortsetzungsablauf.

## 8. Häufige Missverständnisse

Ein Konflikt bedeutet nicht automatisch Datenverlust. Markierungen zu löschen genügt fachlich nicht. Konfliktfreiheit beweist keine Richtigkeit. Und die pauschale Wahl einer Seite kann beabsichtigte Änderungen der anderen Seite verwerfen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Kläre Ausgangslage und Absicht beider Änderungen. Prüfe anschließend die vollständige gemeinsame Fassung. Verwende Fortsetzung oder Rücknahme passend zum laufenden Vorgang. Die Übung testet nur einen gewöhnlichen Textkonflikt, keine Binär-, Lösch- oder Rebase-Konflikte.

## 10. Verwandte Begriffe

[Merge](it_0209.md) kann Konflikte erzeugen. [Branch](it_0208.md) bezeichnet die beteiligten Linien. [Commit](it_0207.md) speichert die Lösung. [Pull](it_0210.md) kann eine Integration anstoßen. [Git](it_0205.md) verwaltet den Vorgang.
