# REST

## 1. Kurzbeschreibung

REST bedeutet „Representational State Transfer“ und bezeichnet einen Architekturstil für verteilte Hypermediasysteme. Er beschreibt zusammengehörige Gestaltungsregeln, nicht ein einzelnes Datenformat oder einen bestimmten API-Pfad. HTTP-basierte Schnittstellen können sich daran orientieren. JSON-Antworten und ein `GET`-Aufruf allein beweisen jedoch keine vollständige REST-Konformität.

## 2. Was bedeutet der Begriff?

Roy Fielding erläutert den Stil in [Kapitel 5 seiner Dissertation](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm). Zu den Bedingungen gehören unter anderem Client-Server-Trennung, zustandslose Kommunikation, Cachebedingungen, eine einheitliche Schnittstelle und ein geschichteter Aufbau. Code-on-Demand ist eine optionale Bedingung.

Die Quellbeschreibung „ein verbreiteter Stil für Web-APIs“ ist als Einstieg brauchbar. Im Alltag wird REST allerdings oft lockerer verwendet als in der Originalbeschreibung. Für eine fachliche Aussage sollte deshalb benannt werden, welche Eigenschaften tatsächlich gemeint oder geprüft sind.

## 3. Einfacher Vergleich aus dem Alltag

Ein öffentliches Informationssystem verwendet gemeinsame Regeln für das Auffinden, Abrufen und Weiterverfolgen von Informationen. Besucher müssen nicht für jedes einzelne Angebot eine völlig neue Bedienungssprache lernen. Verweise zeigen, welche nächsten Schritte möglich sind.

Die Grenze: REST ist kein bloßer grafischer Rundgang und keine Sammlung schöner Adressnamen. Seine Bedingungen betreffen die technische Architektur. Auch garantiert eine einheitliche Schnittstelle nicht, dass jedes Angebot dieselben Daten enthält oder jede Aktion ohne Berechtigung erlaubt ist.

## 4. Wie funktioniert das?

Ressourcen werden identifiziert und über Darstellungen angesprochen. Eine Darstellung ist nicht zwingend die interne Datenstruktur des Servers. Sie enthält die für die Kommunikation vorgesehenen Informationen in einem passenden Format.

Fielding beschreibt für die einheitliche Schnittstelle unter anderem selbstbeschreibende Nachrichten und Hypermedia als Steuerung des Anwendungszustands. Verweise und zulässige Übergänge gehören damit zum Entwurf, statt nur eine Liste fest eingebauter Adressen zu liefern. Ein beliebiges JSON-Objekt erfüllt diese Bedingungen nicht automatisch.

Zustandslosigkeit bedeutet, dass eine Anfrage den nötigen Verständniszusammenhang selbst mitbringt. Sie bedeutet nicht, dass ein Server keine dauerhaft gespeicherten Ressourcen oder Datenbankeinträge besitzen darf. Anwendungsressourcen und auf dem Server vorausgesetzter Sitzungskontext sind verschiedene Dinge.

## 5. Wo begegnet mir das unter Linux?

Programme können HTTP-Schnittstellen verwenden oder bereitstellen. Das Betriebssystem macht daraus nicht automatisch eine REST-Architektur. Entscheidend sind die Gestaltung und die tatsächlich eingehaltenen Bedingungen.

Das Katalogbeispiel `GET /users` zeigt einen möglichen Abrufpfad. Die Bedeutung von `GET` ergibt sich aus HTTP. [RFC 9110 zu sicheren Methoden](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1) beschreibt deren im Wesentlichen lesende Semantik. Daraus folgt nicht, dass überhaupt keine technischen Nebenwirkungen wie Protokollierung auftreten dürfen. Ein solcher Abruf ist außerdem nur ein kleiner Ausschnitt der gesamten Architektur.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenmodell betrifft eine fiktive Notizressource. Es wurde keine API aufgerufen und keine Benutzer- oder Notizdatei angelegt.

```text
Ein Client ruft eine Darstellung der Notiz unter /notizen/7 ab.
Die Antwort beschreibt die Notiz in einem vereinbarten Medientyp.
Passend definierte Verweise können weitere erlaubte Schritte beschreiben.
Eine spätere Anfrage enthält den für ihr Verständnis nötigen Zusammenhang.
Der Server prüft weiterhin fachliche Regeln und Berechtigungen.
```

Die Notiz ist die Ressource; die empfangene Darstellung ist der zugängliche Kommunikationsinhalt. Sie muss nicht das unveränderte Datenbankobjekt sein. Welche Verweise und Aktionen tatsächlich gelten, müsste die Schnittstelle ausdrücklich definieren.

Das Modell behauptet keine vollständige REST-Implementierung. Cacheverhalten, Mediensemantik und weitere Bedingungen werden hier nicht praktisch geprüft. Es zeigt lediglich mehrere Entwurfsfragen, die über einen sprechenden Pfad und JSON hinausgehen. Eine gemessene Konformitätsabnahme findet nicht statt.

## 7. Abgrenzung zu ähnlichen Begriffen

HTTP ist ein Protokoll, REST ein Architekturstil. JSON ist ein mögliches Datenformat. Eine API ist der allgemeinere Zugang zu Funktionalität. Ein aufgerufener Funktionsname mit Netzwerktransport kann wiederum einem anderen Kommunikationsstil folgen, auch wenn HTTP beteiligt ist.

## 8. Häufige Missverständnisse

REST bedeutet nicht „jede Operation ist POST“. Ebenso wenig macht jede Verwendung von `GET`, `POST` und JSON eine Schnittstelle vollständig REST-konform. Zustandslosigkeit verbietet keine gespeicherten Daten. Auch ein öffentlich lesbarer Pfad hebt Berechtigungs- und Schutzanforderungen nicht automatisch auf.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Beschreibe konkrete Architekturzusagen statt nur ein Etikett zu verwenden. Unterscheide Ressourcen, Darstellungen, Methoden und Zustandsübergänge. Dieser Eintrag verändert keine API, sendet keine Anfragen und legt keine Konten oder Datenbestände an.

## 10. Verwandte Begriffe

Die [API](it_0169.md) ist der allgemeinere Schnittstellenbegriff. [HTTP](it_0145.md) stellt verbreitete Kommunikationsregeln bereit. [HTTPS](it_0146.md) ergänzt Schutz. Ein [Service](it_0119.md) bietet Funktionalität, deren Architektur gesondert beurteilt werden muss.
