# Nonblocking

## 1. Kurzbeschreibung

Nonblocking bedeutet bei einer konkreten Schnittstelle, dass sie nicht auf eine bestimmte noch fehlende Bereitschaft wartet. Stattdessen liefert sie ein verfügbares Ergebnis oder eine dafür vorgesehene Rückmeldung. Der aufrufende Code kann danach andere Arbeit erledigen. Das bedeutet weder garantierten Erfolg noch eine feste Echtzeitgrenze für jeden Teil des gesamten Programms.

## 2. Was bedeutet der Begriff?

Die Quelle nennt einen Hintergrundthread, der die GUI reaktionsfähig hält. Das beschreibt einen möglichen Gesamtentwurf. Der im Hintergrund ausgeführte Aufruf kann trotzdem selbst blockierend sein. Ein Worker verlagert das Warten; er verändert nicht automatisch den Vertrag jeder verwendeten Schnittstelle.

Die [Python-Dokumentation zu Queue.get_nowait](https://docs.python.org/3.13/library/queue.html#queue.Queue.get_nowait) zeigt einen unmittelbar passenden Zugriff. Er entspricht dem nicht blockierenden Abruf. Ist kein Eintrag vorhanden, wird Empty gemeldet, statt auf einen zukünftigen Eintrag zu warten. Das ist ein normaler zu behandelnder Ausgang dieses Aufrufs.

## 3. Einfacher Vergleich aus dem Alltag

Du fragst am Schalter, ob ein Dokument schon bereitliegt. Ist es noch nicht vorhanden, erhältst du diese Rückmeldung und erledigst zunächst etwas anderes. Du bleibst nicht unbegrenzt am Schalter stehen, bis das Dokument vielleicht später fertig wird.

Die Grenze: Die Rückmeldung allein erledigt den Auftrag nicht. Es muss geklärt sein, wie eine spätere Bereitschaft erkannt wird. Ein ständiges hektisches Nachfragen kann unnötige Arbeit verursachen. Software braucht dafür einen passenden Folgeablauf statt nur einen anderen Aufrufnamen.

## 4. Wie funktioniert das?

Eine nicht blockierende Operation prüft die aktuell mögliche Aktion. Sind die benötigten Daten oder Kapazitäten verfügbar, kann sie fortfahren. Andernfalls erhält der Aufrufer eine spezifizierte Rückmeldung. Deren Form hängt von Bibliothek und Operation ab, beispielsweise eine Ausnahme oder ein Rückgabestatus.

Bei Netzwerkschnittstellen beschreibt die [Python-Dokumentation zu socket.setblocking](https://docs.python.org/3.13/library/socket.html#socket.socket.setblocking) die Auswahl des Modus. Nicht blockierend ist dort etwas anderes als ein blockierender Aufruf mit einer positiven Wartefrist. Der konkrete Zustand und die Folgeschritte müssen passend behandelt werden. Das Beispiel verwendet jedoch keinen Socket und ändert keine Netzwerkoption.

Der weitere Ablauf kann Ereignisbenachrichtigungen oder eine geeignete Bereitschaftsprüfung nutzen. Eine enge Schleife ohne sinnvolles Warten oder andere Arbeit kann unnötig CPU-Zeit verbrauchen. Nicht blockierend bedeutet also nicht, dass eine Anwendung beliebig schnell immer wieder denselben erfolglosen Versuch ausführen sollte.

Auch der restliche Code zählt. Eine nicht blockierende Abfrage hilft wenig, wenn unmittelbar danach eine lange synchrone Berechnung die zentrale Ereignisverarbeitung aufhält. Reaktionsfähigkeit ist eine Eigenschaft des gesamten passenden Ablaufs, keine automatische Folge eines einzelnen API-Aufrufs.

## 5. Wo begegnet mir das unter Linux?

Netzwerk- und Ereignisprogramme verwenden verschiedene Bereitschaftsmodelle. Worker und asynchrone Tasks können dabei unterschiedliche Aufgaben übernehmen. Diese Techniken sind nicht austauschbar, nur weil eine Oberfläche in allen Fällen reagieren soll.

Für diesen Eintrag genügt eine eigene Speicherqueue. Es wird kein tatsächlicher Socket geöffnet, kein Dienst angesprochen und kein Hintergrundthread benötigt. Der Test kontrolliert den vorgesehenen leeren Fall und den später verfügbaren eigenen Wert.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Zwischen zwei Abrufversuchen wird eine eigene Liste für einen anderen kleinen Verarbeitungsschritt vorbereitet. Es gibt keine Schleife mit ständigem Nachfragen und keine Zeitmessung.

```python
from queue import Empty, Queue

aufgaben = Queue()
noch_nicht_verfuegbar = False
try:
    aufgaben.get_nowait()
except Empty:
    noch_nicht_verfuegbar = True
assert noch_nicht_verfuegbar
andere_daten = [titel.strip() for titel in [" Alpha ", " Beta "]]
assert andere_daten == ["Alpha", "Beta"]
aufgaben.put("Probe")
ergebnis = aufgaben.get_nowait()
assert ergebnis == "Probe"
aufgaben.task_done()
print("Fehlender Eintrag gemeldet:", noch_nicht_verfuegbar)
print("Andere Titel vorbereitet:", len(andere_daten))
print("Späterer Eintrag:", ergebnis)
```

Geprüfte Ausgabe:

```text
Fehlender Eintrag gemeldet: True
Andere Titel vorbereitet: 2
Späterer Eintrag: Probe
```

Der erste Versuch meldet die fehlende Bereitschaft. Anschließend kann der eigene Code fortfahren. Nach dem bewussten Einstellen eines Werts liefert der nächste Versuch das Ergebnis. Der Ablauf prüft den Queue-Vertrag, keine GUI-Reaktionszeit, Netzwerkbereitschaft oder allgemeine Echtzeitfähigkeit.

## 7. Abgrenzung zu ähnlichen Begriffen

Blocking wartet nach seinem Vertrag. Nonblocking meldet gegebenenfalls fehlende Bereitschaft unmittelbar. Async organisiert kooperative Aufgaben. Ein Thread ist ein eigener Ausführungsstrang. Ein Hintergrundthread kann selbst blockierende Arbeit enthalten, während andere Threads weiterarbeiten.

## 8. Häufige Missverständnisse

Nicht blockierend bedeutet nicht immer erfolgreich. Ein Timeout ist nicht dasselbe wie ein unmittelbarer Bereitschaftsversuch. Ein Worker macht nicht jeden Aufruf nichtblockierend. Und eine ständig laufende Abfrageschleife ist keine automatische gute Ereignisverarbeitung.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Lies Rückgabestatus und Folgeablauf der konkreten API. Prüfe leere und verfügbare Fälle mit eigenen Daten. Die Ausführung verändert keine Dateien, Programme, Konten, Dienste oder Netzwerk- und GUI-Konfigurationen.
