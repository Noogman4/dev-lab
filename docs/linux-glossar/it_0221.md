# Plugin

## 1. Kurzbeschreibung

Ein Plugin ist eine Erweiterung, die eine Anwendung über vorgesehene Anschlussstellen um Funktionen ergänzt. Die Anwendung bietet dafür einen vereinbarten Rahmen, das Plugin liefert eine passende Umsetzung. Laden, Erkennen und Aufrufen müssen geregelt sein. Eine beliebige zusätzliche Datei wird nicht allein durch ihren Namen zu einer nutzbaren Erweiterung.

## 2. Was bedeutet der Begriff?

Die Quelle nennt ein denkbares Radio-Modul als Plugin. Dafür müsste die Anwendung festlegen, welche Aufgaben die Erweiterung übernehmen darf und welche Schnittstelle sie erfüllt. Ob ein bestimmter vorhandener Programmteil tatsächlich ein Plugin ist, ergibt sich aus dessen Einbindung, nicht aus dieser Möglichkeit im Glossar.

Die [PyPA-Anleitung zum Erstellen und Auffinden von Plugins](https://raw.githubusercontent.com/pypa/packaging.python.org/main/source/guides/creating-and-discovering-plugins.rst) beschreibt mehrere Python-Ansätze: Namenskonventionen, Namespace-Pakete und Paketmetadaten. Diese sind konkrete Erkennungsverfahren. Sie ersetzen keine fachliche Definition dessen, was eine Erweiterung leisten und zurückgeben soll.

## 3. Einfacher Vergleich aus dem Alltag

Ein Zubehöranschluss erlaubt passende Zusatzgeräte. Ein Zubehör muss mechanisch und funktional zum Anschluss passen. Ein gleich aussehender Stecker genügt nicht, wenn eine andere Spannung oder ein anderes Signal erwartet wird.

Die Grenze: Softwareplugins besitzen oft umfassenden Zugriff auf denselben Prozess wie die Anwendung. Eine Schnittstelle ist daher nicht automatisch eine Sicherheitsisolierung. Ein fehlerhaftes Plugin kann trotz passenden Namens falsche Werte liefern, unerwartete Wirkungen haben oder die Anwendung stören.

## 4. Wie funktioniert das?

Zuerst legt die Anwendung einen Vertrag fest: benötigte Funktionen, zulässige Eingaben, Ergebnisse und Fehlerverhalten. Danach wird bestimmt, wie verfügbare Erweiterungen gefunden werden. Anschließend werden geeignete Kandidaten geladen und bei Bedarf aufgerufen. Diese Schritte sollten auseinandergehalten werden.

Für Python können installierte Pakete sogenannte Entry Points bekannt machen. Die [Python-Dokumentation zu Entry Points](https://docs.python.org/3.13/library/importlib.metadata.html#entry-points) erläutert Namen, Gruppen, Ziele und das Auflösen durch `load()`. Eine Gruppe kann beispielsweise Erweiterungen einer bestimmten Anwendung kennzeichnen. Das Vorhandensein eines Metadateneintrags beweist aber noch nicht, dass das geladene Objekt den fachlichen Vertrag korrekt erfüllt.

Laden kann Code ausführen. Ein Fehler bei der Erkennung ist außerdem etwas anderes als eine Ausnahme während einer späteren Funktion. Die Anwendung muss entscheiden, wie solche Fälle gemeldet werden und ob die übrige Arbeit fortgesetzt werden kann. Versionsverträglichkeit und Lebensdauer gehören ebenfalls zum Entwurf. Ein universelles Pluginformat für alle Linux-Anwendungen gibt es daraus nicht.

## 5. Wo begegnet mir das unter Linux?

Editoren, Medienprogramme und Entwicklungswerkzeuge bieten Erweiterungen. Manche verwenden Python, andere native Bibliotheken oder eigene Sprachen und Protokolle. Eine Erweiterung für Programm A passt daher nicht allein wegen desselben Betriebssystems in Programm B.

Auch „installiert“ und „aktiv“ sind verschiedene Zustände. Ein vorhandenes Paket muss vom betreffenden Programm gefunden und passend eingebunden werden. Dieses Dokument sucht keine installierten Erweiterungen, lädt keinen fremden Code und aktiviert keine vorhandene Funktion.

## 6. Konkretes Beispiel Schritt für Schritt

Das folgende Gedankenbeispiel wurde nicht implementiert oder ausgeführt. Eine erfundene Notizanwendung soll zusätzliche Exportdarstellungen erlauben. Es werden keine Dateien gespeichert und keine Plugins installiert.

Zuerst definiert die Anwendung ihren Vertrag: Eine Exporterweiterung erhält eine Liste von Notiztiteln und liefert einen Text zurück. Sie darf die Liste nicht verändern. Für dieses Beispiel sollen ein leerer Bestand und ein Titel mit einem Zeilenumbruch ausdrücklich behandelt werden.

Danach werden zwei mögliche Erweiterungen entworfen. Eine erzeugt eine nummerierte Textansicht, eine andere eine JSON-Darstellung. Beide benötigen dieselbe Eingabeform, liefern aber bewusst unterschiedliche Darstellungen. Die Anwendung entscheidet, welche ausgewählt ist, und verwendet das zurückgegebene Ergebnis passend weiter.

Als Nächstes wird geklärt, wie die Exporterweiterungen gefunden werden. Python-Entry-Points wären eine mögliche technische Lösung. Das Gedankenbeispiel legt jedoch keine Paketmetadaten an und behauptet keine erfolgreiche Auffindung.

Schließlich prüfen die Beteiligten den Vertrag: Was geschieht bei ungültiger Eingabe, unbekannter Schnittstellenversion oder einem Fehler in der Erweiterung? Eine bloße Liste von Namen beantwortet diese Fragen nicht. Auch ein erfolgreicher Import würde noch keinen korrekten Export beweisen. Dieses Modell liefert deshalb keine Abnahme eines Pluginrahmens oder einer tatsächlichen Erweiterung.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Modul ist ein Codebaustein. Ein Plugin wird über einen vorgesehenen Erweiterungsmechanismus eingebunden. Eine Abhängigkeit kann für den Grundbetrieb nötig sein, während eine Erweiterung zusätzliche Möglichkeiten anbietet. Die genaue Einordnung hängt vom Entwurf der Anwendung ab.

## 8. Häufige Missverständnisse

Ein Dateiname garantiert keine Schnittstellenverträglichkeit. Erkennen ist noch nicht erfolgreiches Ausführen. Eine Plugin-Schnittstelle ist keine automatische Sandbox. Und eine Erweiterung für ein Programm passt nicht universell in alle anderen Programme.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe Herkunft, passende Version und tatsächliche Berechtigungen einer Erweiterung. Dokumentiere Vertrag und Fehlerbehandlung. Das Gedankenmodell führt weder eine Paketinstallation noch eine Aktivierung oder Änderung an Konten, Diensten und vorhandenen Anwendungen aus.
