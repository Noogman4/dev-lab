# Fixture

## 1. Kurzbeschreibung

Eine Fixture stellt die für einen Test benötigten Ausgangsdaten oder Umgebungsbedingungen bereit. Dazu können eigene Dateien, Objekte oder Datenbankzustände gehören. Auch ein geregeltes Aufräumen ist wichtig. Die Fixture soll den Fall nachvollziehbar und wiederholbar machen, statt von zufällig vorhandenen persönlichen Daten oder dem Ergebnis eines anderen Tests abhängig zu sein.

## 2. Was bedeutet der Begriff?

Die Quelle nennt vorbereitete Testdaten und temporäre Dateien. Eine Fixture ist dabei mehr als eine beliebige Beispieldatei: Es muss feststehen, wann sie entsteht, wer sie verwendet und wie lange sie gilt. Manche Werkzeuge verwenden den Begriff zudem für eine spezielle Funktion zur Bereitstellung solcher Ressourcen.

Die [Python-Dokumentation zu unittest.setUp](https://docs.python.org/3.13/library/unittest.html#unittest.TestCase.setUp) beschreibt die Vorbereitung unmittelbar vor einer Testmethode. Das ist eine konkrete Frameworkregel. Andere Testwerkzeuge können zusätzliche Lebensdauerbereiche anbieten. Die allgemeine Idee bleibt, passende Ausgangsbedingungen bewusst zu verwalten.

## 3. Einfacher Vergleich aus dem Alltag

Vor jedem Versuch wird ein eigener sauberer Messaufbau vorbereitet. Material und Einstellungen sind bekannt. Danach wird aufgeräumt, damit der nächste Versuch nicht unbemerkt von Resten des vorherigen beeinflusst wird.

Die Grenze: Nicht jede Ressource lässt sich völlig kostenlos neu aufbauen. Größere gemeinsame Vorbereitungen können sinnvoll sein, benötigen aber klare Regeln gegen gegenseitige Beeinflussung. Auch garantiert ein identischer Aufbau nicht jede gleiche Außenbedingung, wenn beispielsweise ein unkontrollierter entfernter Dienst beteiligt bleibt.

## 4. Wie funktioniert das?

Zunächst wird bestimmt, was der Test wirklich benötigt. Danach erzeugt die Fixture diese Ressourcen in einem geeigneten Bereich. Der Test erhält Zugriff auf den bekannten Zustand. Nach der vorgesehenen Lebensdauer werden eigene Ressourcen entfernt oder geschlossen.

Aufräumen muss auch bei Fehlern bedacht werden. Die [Dokumentation zu unittest.addCleanup](https://docs.python.org/3.13/library/unittest.html#unittest.TestCase.addCleanup) beschreibt registrierte Aufräumfunktionen, die auch nach einer fehlgeschlagenen Vorbereitung ausgeführt werden können, sofern sie bereits angemeldet wurden. Ein späterer Schritt sollte nicht unbemerkt eine zuvor erzeugte Ressource ohne Aufräumweg zurücklassen.

Für eigene Dateibereiche bietet [TemporaryDirectory](https://docs.python.org/3.13/library/tempfile.html#tempfile.TemporaryDirectory) einen temporären Ordner und eine Cleanup-Funktion. Das hilft bei der Begrenzung und Entfernung der Testdaten. Es ist für sich allein keine Sicherheits-Sandbox und beschränkt nicht automatisch sämtliche Prozesszugriffe.

Eine Fixture sollte keine unnötigen Abhängigkeiten schaffen. Wenn ein Test auf der vom vorherigen Fall geänderten Datei aufbaut, kann die Reihenfolge plötzlich wichtig werden. Ein jeweils frischer Zustand verhindert solche Kopplung für den gezeigten Fall. Gemeinsame unveränderliche Daten und veränderliche eigene Ressourcen brauchen unterschiedliche Überlegungen.

## 5. Wo begegnet mir das unter Linux?

Tests verwenden temporäre Verzeichnisse, vorbereitete Datenbanken oder kleine eigene Konfigurationsbeispiele. Vorhandene Benutzerdateien sind dafür keine verlässliche und ungefährliche Standardgrundlage. Welche Ressourcen tatsächlich benötigt werden, folgt aus der Prüfgrenze.

Dieses Glossar erweitert keine vorhandene Testsuite. Das folgende vollständige Skript erzeugt ausschließlich eigene Testdateien in neu angelegten temporären Ordnern. Es benötigt nur die Python-Standardbibliothek und verändert keine Geräte, Konten oder Dienste.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 ausgeführt. Jede Testmethode bekommt eine eigene Datei mit demselben bekannten Ausgangstext. Die Pfade werden nur für die abschließende Kontrolle des Aufräumens gesammelt.

```python
import io
from pathlib import Path
import tempfile
import unittest

angelegt = []

class DateiTest(unittest.TestCase):
    def setUp(self):
        self.ordner = tempfile.TemporaryDirectory()
        self.addCleanup(self.ordner.cleanup)
        basis = Path(self.ordner.name)
        angelegt.append(basis)
        self.datei = basis / "probe.txt"
        self.datei.write_text("Anfang\n", encoding="utf-8")

    def test_lesen(self):
        self.assertEqual(self.datei.read_text(encoding="utf-8"), "Anfang\n")

    def test_aendern(self):
        self.assertEqual(self.datei.read_text(encoding="utf-8"), "Anfang\n")
        self.datei.write_text("Geändert\n", encoding="utf-8")
        self.assertEqual(self.datei.read_text(encoding="utf-8"), "Geändert\n")

suite = unittest.defaultTestLoader.loadTestsFromTestCase(DateiTest)
bericht = io.StringIO()
ergebnis = unittest.TextTestRunner(stream=bericht, verbosity=0).run(suite)
assert ergebnis.wasSuccessful() and ergebnis.testsRun == 2, bericht.getvalue()
assert len(angelegt) == 2 and all(not pfad.exists() for pfad in angelegt)
print("Ausgeführte Testfälle:", ergebnis.testsRun)
print("Temporäre Ordner entfernt:", True)
```

Geprüfte Ausgabe:

```text
Ausgeführte Testfälle: 2
Temporäre Ordner entfernt: True
```

Beide Fälle prüfen ihren eigenen Anfangszustand. Die Änderung im einen Fall beeinflusst den anderen nicht. Nach dem Lauf sind die eigenen Ordner entfernt. Das Beispiel simuliert keinen Fehler im Cleanup selbst und liefert keine Aussage über beliebige externe Testressourcen.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Test enthält die eigentliche Prüfung. Eine Fixture stellt Bedingungen bereit. Ein Mock ersetzt eine Abhängigkeit und kann Teil einer Fixture sein. Ein Cache dient dagegen der Wiederverwendung von Ergebnissen und kann bei unbedachter gemeinsamer Nutzung Tests beeinflussen.

## 8. Häufige Missverständnisse

Eine Fixture ist nicht immer nur eine Datei. Gemeinsame Daten dürfen nicht beliebig unkontrolliert verändert werden. Temporäre Ablage bedeutet keine vollständige Isolation. Und ein erfolgreicher Test entbindet nicht vom Aufräumen eigener Ressourcen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Halte Umfang und Lebensdauer klein genug für den Zweck. Registriere Aufräumwege rechtzeitig und prüfe die Ausgangslage. Die Ausführung entfernt nur selbst erzeugte temporäre Bereiche und keine vorhandenen Projekt- oder Benutzerdateien.

## 10. Verwandte Begriffe

[Test](it_0246.md) beschreibt Erwartungen. [Unit Test](it_0247.md) nutzt begrenzte Bedingungen. [Integrationstest](it_0248.md) kann echte Ressourcen brauchen. [Mock](it_0250.md) stellt Ersatzverhalten bereit. [Sandbox](it_0240.md) ist eine andere Art von Grenze.
