# Clone

## 1. Kurzbeschreibung

Ein Clone legt eine neue lokale Git-Kopie eines Repositorys an. Ein gewöhnlicher Klon enthält Versionsdaten und ein bereitgestelltes Arbeitsverzeichnis. Er ist mehr als ein Download aktueller Projektdateien. Umfang und Form hängen von den Optionen ab; eine bewusst verkürzte Kopie muss beispielsweise nicht die vollständige ältere Historie enthalten.

## 2. Was bedeutet der Begriff?

Das Katalogbeispiel sagt, `git clone` lade ein Projekt herunter. Häufig stammt die Quelle tatsächlich von einem Server. Sie kann aber ebenso ein lokales Repository sein. Entscheidend ist die Übernahme von Git-Daten und die Anlage eines neuen Repositorys, nicht zwingend eine Internetübertragung.

Die [offizielle Dokumentation zu git clone](https://raw.githubusercontent.com/git/git/master/Documentation/git-clone.adoc) beschreibt das neue Zielverzeichnis, Remote-Tracking-Referenzen und einen anfänglich ausgecheckten Branch. Die gewöhnliche Kopie bietet damit eine Grundlage für weitere eigene Commits und den späteren Austausch. Sie ist keine ständig automatisch synchronisierte Ansicht der Quelle.

## 3. Einfacher Vergleich aus dem Alltag

Du erhältst eine eigene Arbeitsausgabe eines Archivs mit nachvollziehbaren abgelegten Ständen. Daraus wird ein bestimmter Stand auf deinem Arbeitstisch bereitgestellt. Du kannst daran arbeiten, ohne dass jede Bearbeitung sofort das ursprüngliche Archiv verändert.

Die Grenze: Ein Klon übernimmt nicht zwangsläufig jede lokale Besonderheit der Quelle. Lose Entwürfe auf deren Arbeitstisch gehören nicht automatisch zur abgelegten Historie. Auch spezielle Klonoptionen können den Umfang einschränken. Der Vergleich ist daher keine Zusage einer vollständigen Datenträgerkopie.

## 4. Wie funktioniert das?

Git richtet im Ziel Versionsdaten und eine passende lokale Konfiguration für den Austausch ein. Bei einem üblichen Klon heißt die Quelle `origin`. Dieser Name kann anders gewählt werden. Ein lokaler Branch wird bereitgestellt; weitere entfernte Branches sind nicht automatisch alle als eigene lokale Arbeitsbranches ausgecheckt.

Optionen wie eine begrenzte Historientiefe, eine Branchbeschränkung oder Filter verändern die übernommenen Daten. Auch Submodule brauchen eine passende gesonderte Behandlung. „Geklont“ bedeutet deshalb nicht pauschal, dass jede denkbare Projektkomponente und jeder historische Inhalt bereits lokal verfügbar ist.

Die [Beschreibung des Git-Repository-Aufbaus](https://raw.githubusercontent.com/git/git/master/Documentation/gitrepository-layout.adoc) unterscheidet Versionsdaten und Arbeitsverzeichnis. Ein normaler Klon stellt einen gespeicherten Stand daraus bereit. Offene Änderungen oder nicht erfasste Dateien im Arbeitsverzeichnis einer lokalen Quelle werden nicht wie bei einem gewöhnlichen rekursiven Dateikopiervorgang automatisch übernommen.

## 5. Wo begegnet mir das unter Linux?

Entwickler beginnen häufig mit einem Klon und öffnen danach dessen Ordner im Editor. Das macht den Code verfügbar, installiert aber nicht automatisch alle Laufzeitabhängigkeiten. Auch ein erfolgreicher Klon ist keine bestandene Programmprüfung.

Ein Quellarchiv als ZIP kann Dateien eines Stands liefern, besitzt aber normalerweise nicht dieselbe Git-Historie und Austauscheinrichtung. Welche Variante sinnvoll ist, hängt vom Ziel ab. Hier werden keine fremden Projekte heruntergeladen oder ausgeführt.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 und Git 2.52.0 ausgeführt. Es verwendet zwei neue lokale temporäre Verzeichnisse. Persönliche und systemweite Git-Konfiguration werden für die Kindprozesse ausgeblendet; Vorlagen werden nicht übernommen.

```python
import os
from pathlib import Path
import subprocess
import tempfile

env = {k: v for k, v in os.environ.items() if not k.startswith("GIT_")}
env.update(GIT_CONFIG_GLOBAL="/dev/null", GIT_CONFIG_NOSYSTEM="1")
with tempfile.TemporaryDirectory() as ordner:
    basis = Path(ordner)
    quelle = basis / "quelle"
    kopie = basis / "kopie"
    quelle.mkdir()
    def git(repo, *args):
        return subprocess.run(
            ["git", "-c", "user.name=Glossar", "-c",
             "user.email=glossar@example.invalid", "-c",
             "commit.gpgsign=false", *args],
            cwd=repo, env=env, check=True, capture_output=True, text=True
        ).stdout.strip()
    git(quelle, "init", "--template=", "-b", "probe")
    datei = quelle / "notiz.txt"
    datei.write_text("Gespeichert\n", encoding="utf-8")
    git(quelle, "add", "notiz.txt")
    git(quelle, "commit", "-m", "Eigener Ausgangsstand")
    datei.write_text("Noch offen\n", encoding="utf-8")
    (quelle / "nur-lokal.txt").write_text("Nicht erfasst\n", encoding="utf-8")
    git(basis, "clone", "--no-local", "--template=", str(quelle), str(kopie))
    assert git(kopie, "rev-parse", "HEAD") == git(quelle, "rev-parse", "HEAD")
    assert (kopie / "notiz.txt").read_text() == "Gespeichert\n"
    assert not (kopie / "nur-lokal.txt").exists()
    assert git(kopie, "status", "--porcelain") == ""
    print("Kloninhalt:", (kopie / "notiz.txt").read_text().strip())
    print("Nicht erfasste Datei kopiert:", (kopie / "nur-lokal.txt").exists())
```

Geprüfte Ausgabe:

```text
Kloninhalt: Gespeichert
Nicht erfasste Datei kopiert: False
```

Die Quelle besitzt beim Klonen offene und nicht erfasste Inhalte. Die Kopie erhält dennoch den gespeicherten Commit. `--no-local` vermeidet hier die besondere lokale Kopieroptimierung; die Quelle bleibt ein lokaler Pfad. Es wird kein Internettransport genutzt. Beide Übungsbereiche werden entfernt.

## 7. Abgrenzung zu ähnlichen Begriffen

Clone legt ein neues Repository an. Pull aktualisiert und integriert in ein vorhandenes. Ein Dateikopiervorgang kann andere Inhalte erfassen. Ein Fork auf einem Hostingdienst ist wiederum eine dort verwaltete Projektabzweigung und nicht automatisch eine lokale Arbeitskopie.

## 8. Häufige Missverständnisse

Clone installiert keine Anwendung. Er kopiert nicht automatisch offene Quelldateien. Ein verkürzter Klon enthält nicht jede Historie. Und spätere Änderungen der Quelle erscheinen nicht ohne weitere Austauschschritte von selbst in der Kopie.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe Quelle, Ziel und gewünschte Optionen. Unterscheide das Bereitstellen von Code von dessen Ausführen. Das Beispiel enthält nur selbst erzeugte Textdateien und verändert keine vorhandenen Repositories, Abhängigkeiten oder Programme.

## 10. Verwandte Begriffe

[Repository Git](it_0206.md) erklärt die Ablage. [Git](it_0205.md) ist das Werkzeug. [Commit](it_0207.md) bezeichnet den gespeicherten Stand. [Pull](it_0210.md) aktualisiert vorhandene Arbeit. [Push](it_0211.md) überträgt eigene Versionsarbeit.
