# Dependency Injection

## 1. Kurzbeschreibung

Dependency Injection bedeutet, dass benötigte Abhängigkeiten von außen an eine Funktion oder ein Objekt übergeben werden. Der verwendende Teil erzeugt die konkrete Abhängigkeit nicht vollständig selbst. So kann seine eigentliche Aufgabe von der Zusammenstellung der Anwendung getrennt werden. Dafür ist nicht zwingend ein besonderes Framework oder ein automatischer Container nötig.

## 2. Was bedeutet der Begriff?

Die Quelle nennt einen Logger, der einer Klasse übergeben wird. Die Klasse benötigt dann beispielsweise nur die Fähigkeit, eine Meldung abzugeben. Ob diese Meldung später gesammelt, angezeigt oder passend gespeichert wird, kann außerhalb entschieden werden.

Die [Microsoft-Dokumentation zu Dependency Injection in .NET](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/overview) beschreibt die Übergabe von Abhängigkeiten und einen integrierten Container. Die dortigen Registrierungen und Lebensdauerregeln sind konkrete .NET-Funktionen. Die allgemeine Idee ist breiter und kann auch in einem kleinen Python-Programm durch eine gewöhnliche Parameterübergabe umgesetzt werden.

## 3. Einfacher Vergleich aus dem Alltag

Eine Person soll Dokumente beschriften und bekommt dafür einen geeigneten Stift bereitgestellt. Sie muss nicht bei jedem Auftrag selbst entscheiden, welchen Laden sie aufsucht und wie sie einen Stift beschafft. Für einen Probelauf kann ein anderes passendes Schreibwerkzeug bereitliegen.

Die Grenze: Softwareabhängigkeiten brauchen einen genauen Vertrag. Ein Gegenstand, der nur „Stift“ heißt, muss nicht dieselben Eigenschaften besitzen. Ebenso reicht eine gleichnamige Methode nicht aus, wenn Fehlerverhalten oder Seiteneffekte anders sind. Die Übergabe beseitigt die fachliche Abhängigkeit nicht; sie macht deren Auswahl sichtbarer.

## 4. Wie funktioniert das?

Zunächst wird geklärt, welche Fähigkeit der verwendende Teil benötigt. Dann wird eine passende Implementierung erzeugt oder ausgewählt. Beim Zusammenstellen wird sie beispielsweise dem Konstruktor übergeben. Der Teil verwendet danach den vereinbarten Vertrag, statt bei jeder Arbeit eine bestimmte konkrete Implementierung selbst anzulegen.

Martin Fowlers [ursprünglicher Fachartikel zu Dependency Injection](https://martinfowler.com/articles/injection.html) beschreibt verschiedene Formen und die Trennung von Zusammenstellung und Verwendung. Er ist eine Primärquelle des Autors zum Muster; seine Java-Beispiele sind keine Python-Syntaxvorgaben. Die Grundentscheidung lässt sich unabhängig von einem bestimmten Container betrachten.

Ein Container kann umfangreichere Objektbeziehungen verwalten. Dann werden zusätzliche Fragen wichtig: Wer besitzt ein Objekt, wie lange lebt es, und wer schließt Ressourcen? Solche Regeln entstehen nicht automatisch durch das Wort Injection. Auch manuelle Übergabe braucht eine passende Zuständigkeit für Lebensdauer und Fehlerbehandlung.

## 5. Wo begegnet mir das unter Linux?

Eine Anwendung kann Zugriff auf Speicherung, Zeit, Meldungen oder andere Dienste übergeben. Bei Tests lässt sich dann eine eigene kleine Umsetzung verwenden. Das kann verhindern, dass ein Test nur wegen einer fest eingebauten konkreten Abhängigkeit einen echten Dienst ansprechen muss.

Ein brauchbarer Ersatz muss trotzdem den relevanten Vertrag abdecken. Ein erfolgreicher Test mit einer einfachen Sammlung beweist beispielsweise noch nicht, dass ein späteres Dateiprotokoll korrekt schreibt. Die Grenzen des eingesetzten Ersatzes müssen klar bleiben.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Die Meldungsfunktion wird übergeben. Im Test sammelt sie nur eigene Texte in einer Liste; es werden keine Dateien geschrieben und keine Dienste verwendet.

```python
class TitelDienst:
    def __init__(self, melden):
        self._melden = melden

    def vorbereiten(self, titel):
        ergebnis = titel.strip()
        if not ergebnis:
            raise ValueError("Titel fehlt")
        self._melden("Titel vorbereitet")
        return ergebnis

meldungen = []
dienst = TitelDienst(meldungen.append)
titel = dienst.vorbereiten(" Probe ")
assert titel == "Probe"
assert meldungen == ["Titel vorbereitet"]
abgelehnt = False
try:
    dienst.vorbereiten("   ")
except ValueError:
    abgelehnt = True
assert abgelehnt and meldungen == ["Titel vorbereitet"]
print("Titel:", titel)
print("Erfasste Meldungen:", len(meldungen))
```

Geprüfte Ausgabe:

```text
Titel: Probe
Erfasste Meldungen: 1
```

Der Dienst kennt die konkrete Liste nicht und erzeugt sie nicht selbst. Er erhält eine aufrufbare Fähigkeit. Geprüft werden Titelverarbeitung, eine Erfolgsmeldung und das Ausbleiben einer weiteren Meldung beim abgelehnten Titel. Eine vollständige Logging-Schnittstelle oder ein Container wird damit nicht implementiert.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine Dependency ist etwas Benötigtes. Dependency Injection beschreibt dessen Übergabe. Ein Plugin ergänzt Funktionen über einen Erweiterungsmechanismus. Bei einem Service Locator fragt ein Teil Abhängigkeiten selbst bei einer zentralen Stelle ab; das ist eine andere Form der Beschaffung.

## 8. Häufige Missverständnisse

Dependency Injection erfordert keinen Container. Sie bedeutet nicht automatisch Netzwerkzugriff. Ein übergebener Ersatz garantiert keine vollständige Kompatibilität. Und das Verwenden vieler Parameter ist allein noch kein guter Entwurf, wenn Verantwortlichkeiten unklar bleiben.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Übergebe gezielt benötigte Fähigkeiten und dokumentiere ihren Vertrag. Halte Zusammenstellung und Verwendung verständlich. Prüfe echte Integrationen zusätzlich, wenn deren Verhalten relevant ist. Das Beispiel nimmt keine Änderungen an vorhandenen Diensten, Anwendungen oder Abhängigkeiten vor.
