# CI

## 1. Kurzbeschreibung

CI steht für Continuous Integration, auf Deutsch kontinuierliche Integration. Gemeint ist eine Arbeitsweise, bei der Änderungen regelmäßig zusammengeführt und durch nachvollziehbare automatische Builds und Prüfungen abgesichert werden. Ein CI-System unterstützt diesen Ablauf. Ein vorhandener Serverjob allein beweist noch keine gelungene Integration oder vollständige fachliche Prüfung jeder Änderung.

## 2. Was bedeutet der Begriff?

Die Quelle fasst CI als automatische Tests bei Änderungen zusammen und nennt GitHub Actions. Das ist ein wichtiger technischer Bestandteil. Ergänzend gehören kleine regelmäßig integrierte Änderungen und die Reaktion auf fehlgeschlagene Prüfungen zur Arbeitsweise.

Martin Fowlers [Fachartikel zu Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html) beschreibt diese Praxis einschließlich gemeinsamer Entwicklungslinie und selbstprüfendem Build. Der Artikel ist eine Primärquelle des Autors zur Arbeitsweise, keine Anweisung, einen konkreten Projektbranch ohne dessen vereinbarte Regeln zusammenzuführen. Eine Entwurfsprüfung und die spätere Integration bleiben bewusst organisierte Schritte.

## 3. Einfacher Vergleich aus dem Alltag

Mehrere Personen ergänzen regelmäßig einen gemeinsamen Bauplan. Nach jeder vorgesehenen Übernahme wird kontrolliert, ob die Teile weiterhin zusammenpassen. Kleine häufige Schritte machen Unterschiede eher sichtbar als ein großer Stapel lange getrennt entwickelter Pläne.

Die Grenze: Eine automatische Kontrolle kennt nur die tatsächlich hinterlegten Regeln. Ein formal passender Plan kann weiterhin eine übersehene fachliche Anforderung verfehlen. Auch ein dauerhaft rotes Warnlicht hilft wenig, wenn niemand die Ursache untersucht und den gemeinsamen Zustand wiederherstellt.

## 4. Wie funktioniert das?

Ein Projekt legt fest, welche Ereignisse welche Prüfungen starten. Das kann ein Push, ein Pull Request oder ein anderer vereinbarter Auslöser sein. Danach wird ein bestimmter Stand in einer geeigneten Umgebung bereitgestellt. Build, Tests und weitere Prüfungen erzeugen nachvollziehbare Ergebnisse.

Die [GitHub-Dokumentation zu CI](https://docs.github.com/en/actions/get-started/continuous-integration) beschreibt GitHub Actions als mögliche Plattform dafür. Welche Branches, Pfade und Bedingungen einen Lauf auslösen, hängt vom Workflow ab. „Bei jedem Push“ ist deshalb keine pauschale Garantie für jedes Repository. Übersprungene oder gar nicht konfigurierte Prüfungen sind keine bestandenen Tests.

Versionen und Umgebung beeinflussen die Ergebnisse. Ein nachvollziehbarer Lauf sollte erkennen lassen, welcher Commit und welche Werkzeuge beteiligt waren. Unterschiede zwischen lokalem System und Runner können echte Probleme oder Diagnosebedarf zeigen. Ein grüner Lauf gilt zunächst für die tatsächlich ausgeführten Schritte unter diesen Bedingungen.

Automatisierung braucht außerdem geeignete Befugnisse. Ein Prüflauf muss nicht jede Veröffentlichungsberechtigung erhalten. Vertrauliche Werte und fremd beeinflusster Code müssen nach dem vorgesehenen Plattformvertrag behandelt werden. CI ist kein Grund, unkontrolliert zusätzliche Rechte oder Secrets bereitzustellen.

## 5. Wo begegnet mir das unter Linux?

Viele Projekte verwenden Linux-Runner für Builds und Tests. Andere benötigen zusätzliche Zielumgebungen. Ein erfolgreicher Linux-Lauf beweist nicht automatisch alle Eigenschaften einer anderen Plattform oder einer grafischen Benutzerumgebung.

Auch Prüfungen im Pull Request gehören zu einem bestimmten Stand. Wird der Quellbranch aktualisiert, müssen die relevanten Ergebnisse dazu passen. Dieses Glossar richtet keinen Workflow ein, startet keinen manuellen Dienstlauf und verändert keine bestehende CI-Konfiguration.

## 6. Konkretes Beispiel Schritt für Schritt

Das folgende Gedankenbeispiel wurde nicht als CI-Workflow ausgeführt. Ein erfundenes Python-Projekt möchte seine Textverarbeitung vor einer vorgesehenen Übernahme prüfen. Es werden keine Runner, Konten oder Berechtigungen eingerichtet.

Zuerst legen die Beteiligten den erwarteten Umfang fest: Syntax und ausgewählte Lint-Regeln sowie passende eigene Funktionstests. Der geprüfte Commit soll eindeutig erkennbar sein. Eine spätere Veröffentlichung ist für diesen Ablauf nicht vorgesehen.

Danach würde der konfigurierte Auslöser den Stand bereitstellen und die vereinbarten Schritte ausführen. Schlägt ein Funktionstest fehl, ist das ein zu untersuchendes Ergebnis. Ein trotzdem erfolgreiches Formatprüfergebnis hebt den Testfehler nicht auf.

Anschließend wird eine Korrektur vorgenommen. Ein neuer Lauf muss den tatsächlich geänderten Stand prüfen. Ein älterer grüner Bericht gehört nicht automatisch zum neuen Commit. Ebenso darf ein ausgelassener Schritt nicht als erfolgreich ausgeführt beschrieben werden.

Schließlich entscheiden die Beteiligten anhand der aktuellen Ergebnisse und weiteren Prüfung über die Integration. Das Gedankenmodell behauptet weder einen realen GitHub-Actions-Lauf noch einen Merge, eine Veröffentlichung oder eine umfassende Projektabnahme.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein lokaler Test ist eine einzelne Prüfung. CI verbindet regelmäßige Integration mit automatischer Rückmeldung. Kontinuierliche Bereitstellung beziehungsweise Auslieferung betrifft zusätzliche Schritte und Entscheidungen. Ein Push kann einen Lauf auslösen, führt aber nicht allein dadurch jede dieser Aufgaben aus.

## 8. Häufige Missverständnisse

CI bedeutet nicht nur „irgendein automatischer Job“. Nicht jeder Push startet überall dieselben Prüfungen. Grün bedeutet nicht vollständig fehlerfrei. Und automatische Tests bedeuten keine automatische Erlaubnis zur Veröffentlichung oder Zusammenführung.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Halte Prüfumfang, Commitbezug und Fehlerzustand sichtbar. Begrenze Befugnisse auf die Aufgabe und untersuche Abweichungen. Dieses Dokument erstellt keine Workflowdateien und ändert weder Anwendung, Tests, Abhängigkeiten, Konten noch Veröffentlichungseinstellungen.
