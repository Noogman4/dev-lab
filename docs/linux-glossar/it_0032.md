# Build

## 1. Kurzbeschreibung

Ein Build ist der Vorgang, bei dem aus Projektquellen und festgelegten Eingaben bestimmte Softwareartefakte erzeugt werden. Das Wort kann auch das Ergebnis dieses Vorgangs bezeichnen. Ein Artefakt ist hier beispielsweise eine ausführbare Datei oder ein Paket. Der genaue Ablauf hängt von Sprache, Projekt und Zielplattform ab.

## 2. Was bedeutet der Begriff?

Ein Build beantwortet die Frage: „Welche Verarbeitung erzeugt aus diesem Ausgangsstand das gewünschte Ergebnis?“ Dazu gehören die Quellen, eine Build-Konfiguration, Werkzeuge und benötigte Abhängigkeiten. Der fertige Dateiname allein erklärt diese Voraussetzungen nicht.

Das Quellbeispiel eines installierbaren Pakets ist passend. Nicht jeder Build erzeugt jedoch dasselbe Format oder überhaupt ein Installationspaket. Manche Schritte erzeugen Bibliotheken, Dokumentation oder zusammengefasste Ressourcen. Welche Ergebnisse tatsächlich zum Build gehören, legt das Projekt fest.

## 3. Einfacher Vergleich aus dem Alltag

Beim Backen werden Zutaten anhand eines Rezepts mit bestimmten Geräten verarbeitet. Das entspricht ungefähr den Quellen, der Konfiguration und den Build-Werkzeugen. Das fertige Gebäck ist das erzeugte Artefakt.

Der Vergleich hat Grenzen: Softwareergebnisse können unter geeigneten Bedingungen bytegenau reproduziert werden. Dafür müssen weit mehr Eingaben bekannt sein als nur der sichtbare Quelltext. Werkzeugversionen, Plattformdetails oder eingebettete Zeitangaben können das Ergebnis verändern. Ein gleicher Produktname garantiert deshalb keinen identischen Dateiinhalt.

## 4. Wie funktioniert das?

Bei einem C-Projekt können Quelltexte zunächst übersetzt und anschließend zu einem ausführbaren Programm verbunden werden. GNU Make beschreibt im [offiziellen Einstieg zu Makefiles](https://www.gnu.org/software/make/manual/html_node/Introduction.html), wie Regeln und Abhängigkeiten dieses Vorgehen steuern. Bereits vorhandene Ergebnisse können unter passenden Voraussetzungen wiederverwendet werden; sie müssen zum aktuellen Ausgangsstand passen.

Bei Python kann ein Paketbau unter anderem eine Quelldistribution und ein Wheel erzeugen. Das [offizielle PyPA-Paketierungstutorial im Projektquelltext](https://raw.githubusercontent.com/pypa/packaging.python.org/main/source/tutorials/packaging-projects.rst) erklärt diese unterschiedlichen Archive. Ein Wheel muss nicht zwingend selbst kompilierten Maschinencode enthalten. „Gebaut“ und „aus C übersetzt“ sind daher keine austauschbaren Aussagen.

## 5. Wo begegnet mir das unter Linux?

Ein Projekt kann ein Debian-Paket, eine Bibliothek oder ein ausführbares Werkzeug bauen. Häufig führen lokale Skripte oder eine automatisierte Pipeline die Schritte aus. Welche Befehle vorgesehen sind, steht in den Projektanleitungen; sie sollten nicht aus einem ähnlich aufgebauten fremden Projekt übernommen werden.

Ein erfolgreicher Build bedeutet zunächst, dass die vorgesehenen Erzeugungsschritte abgeschlossen wurden. Er beweist nicht automatisch korrektes Anwendungsverhalten, erfolgreiche Installation oder Eignung für jede Linux-Distribution. Tests und Zielplattformprüfung müssen tatsächlich durchgeführt und getrennt berichtet werden.

## 6. Konkretes Beispiel Schritt für Schritt

Das folgende Gedankenbeispiel beschreibt den Ablauf eines erfundenen Python-Paketbaus:

```text
Quellen und Paketmetadaten
        -> festgelegtes Build-Werkzeug
        -> Paketarchive im Ausgabeordner
        -> gesonderte Installation und Funktionsprüfung
```

Zuerst bestimmst du den Quellenstand und die vorgesehenen Paketdaten. Danach werden die benötigten Werkzeugversionen und das Ausgabeformat festgelegt. Der Erzeugungsschritt schreibt neue Artefakte. Anschließend prüfst du, ob die erwarteten Dateien zum richtigen Stand gehören.

Eine Installation und ein Funktionstest sind weitere Arbeitsschritte. Werden sie nicht ausgeführt, dürfen sie nicht allein aus vorhandenen Paketdateien abgeleitet werden. Auch ein alter Ausgabeordner ist kein sicherer Beleg für einen neuen erfolgreichen Build.

Dieses Beispiel wurde nicht als Paketprojekt angelegt oder gebaut. Es erklärt die Rollen der Schritte und behauptet weder vorhandene Artefakte noch eine erfolgreiche Installation.

## 7. Abgrenzung zu ähnlichen Begriffen

Quellcode ist eine Eingabe. Kompilieren ist ein möglicher Build-Schritt. Paketieren stellt Dateien und Metadaten zusammen. Installieren richtet eine Software für die Verwendung ein. Ausführen verwendet die fertige Software. Ein Projekt kann diese Schritte automatisiert verknüpfen, ihre Ergebnisse bleiben dennoch unterschiedlich.

## 8. Häufige Missverständnisse

Eine Datei im Ausgabeordner muss nicht aus dem aktuellen Lauf stammen. Ein bestandener Build ersetzt keinen Test. Auch sind Ergebnisse nicht allein wegen desselben Versionsnamens identisch. Ein wiederverwendetes Zwischenergebnis ist nur sinnvoll, wenn seine Voraussetzungen weiterhin stimmen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Lies Build-Skripte vor ihrer Ausführung: Sie können beliebige Aktionen ausführen und Daten erzeugen oder entfernen. Verwende nachvollziehbare Quellen und überprüfte Werkzeuge. Für dieses Dokument wurde weder ein Projektbuild gestartet noch eine Abhängigkeit installiert oder eine bestehende Paketdatei verändert.
