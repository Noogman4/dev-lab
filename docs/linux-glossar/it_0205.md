# Git

## 1. Kurzbeschreibung

Git ist ein verteiltes Versionskontrollsystem. Es hält ausgewählte Projektstände und ihre Beziehungen in einer Historie fest. Dadurch lassen sich Änderungen nachvollziehen, vergleichen und gemeinsam weiterentwickeln. Git ist weder mit einem bestimmten Internetdienst identisch noch auf Programmcode beschränkt. Auch geeignete Textdokumente können damit versioniert werden.

## 2. Was bedeutet der Begriff?

Das Katalogbeispiel beschreibt den gespeicherten Projektverlauf. Git zeichnet dabei nicht jede Tastatureingabe automatisch auf. Die Beteiligten wählen aus, welche Inhalte in einen neuen gespeicherten Stand aufgenommen werden. Ungespeicherte oder nicht aufgenommene Änderungen gehören noch nicht zu diesem Stand.

Die [offizielle Git-Beschreibung](https://raw.githubusercontent.com/git/git/master/Documentation/git.adoc) bezeichnet Git als verteiltes Versionskontrollsystem. Eine normale lokale Kopie kann eine eigene Historie besitzen und ohne laufende Internetverbindung arbeiten. Welche entfernten Inhalte tatsächlich vorhanden sind, hängt unter anderem davon ab, wie das Repository angelegt oder kopiert wurde.

## 3. Einfacher Vergleich aus dem Alltag

Stell dir eine Folge bewusst abgelegter Arbeitsstände mit Notizen und nachvollziehbaren Vorgängern vor. Du kannst untersuchen, wann ein Absatz verändert wurde, und getrennte Entwicklungen miteinander vergleichen. Das ist wesentlich geordneter als Dateien namens „neu“, „neu2“ und „wirklich_final“.

Die Grenze: Git versteht nicht automatisch, welcher Text fachlich richtig ist. Es entscheidet auch nicht selbst, ob eine Änderung veröffentlicht werden darf. Außerdem werden Dateien außerhalb der erfassten Inhalte nicht allein durch die Existenz eines Repositorys gesichert.

## 4. Wie funktioniert das?

In einem üblichen Arbeitsablauf gibt es das Arbeitsverzeichnis, die vorgemerkten Inhalte im Index und gespeicherte Commits. Eine Datei kann nach dem Vormerken erneut verändert werden. Dann unterscheiden sich der vorgemerkte und der aktuelle Arbeitsstand. Ein Commit speichert den ausgewählten Stand mit Metadaten und gegebenenfalls Vorgängerbeziehungen.

Das [offizielle Git-Tutorial](https://raw.githubusercontent.com/git/git/master/Documentation/gittutorial.adoc) führt diese bewusste Auswahl und das Speichern ein. Branches ermöglichen benannte Entwicklungslinien. Entfernte Repositories können zur Zusammenarbeit dienen. Ein lokaler Commit lädt jedoch noch nichts zu einem solchen Ziel hoch.

Git speichert Projektstände technisch über Objekte und Referenzen. Es ist deshalb keine bloße fortlaufende Textdatei mit Änderungsnotizen. Gleichzeitig garantiert ein gespeicherter Commit weder eine erfolgreiche Prüfung noch einen sinnvollen Inhalt. Diese Bewertung bleibt Aufgabe der Beteiligten und ihrer Arbeitsabläufe.

## 5. Wo begegnet mir das unter Linux?

Viele Entwicklungsprojekte verwenden Git im Terminal oder über eine grafische Oberfläche. Auch dieses Dokument liegt in einem Git-Projekt. Git ist dabei das Versionskontrollwerkzeug; GitHub ist ein Dienst, der unter anderem Repositories und Zusammenarbeit anbietet.

Ein neuer Übungsbereich lässt sich lokal anlegen. Die [Dokumentation zu git init](https://raw.githubusercontent.com/git/git/master/Documentation/git-init.adoc) erklärt die Erstellung eines leeren Repositorys und den anfänglichen Branch. Das folgende Beispiel verwendet ausschließlich einen neu erzeugten temporären Ordner.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses vollständige Beispiel wurde mit Python 3.13 und Git 2.52.0 ausgeführt. Python steuert nur die lokalen Git-Aufrufe. Persönliche und systemweite Git-Konfiguration werden für diese Kindprozesse ausgeblendet; das Repository erhält keine Vorlagen. Die Identität gilt nur für die einzelnen Aufrufe.

```python
import os
from pathlib import Path
import subprocess
import tempfile

env = {k: v for k, v in os.environ.items() if not k.startswith("GIT_")}
env.update(GIT_CONFIG_GLOBAL="/dev/null", GIT_CONFIG_NOSYSTEM="1")
with tempfile.TemporaryDirectory() as ordner:
    repo = Path(ordner)
    def git(*args):
        return subprocess.run(
            ["git", "-c", "user.name=Glossar", "-c",
             "user.email=glossar@example.invalid", "-c",
             "commit.gpgsign=false", *args],
            cwd=repo, env=env, check=True, capture_output=True, text=True
        ).stdout
    git("init", "--template=", "-b", "probe")
    (repo / "notiz.txt").write_text("Erster Stand\n", encoding="utf-8")
    git("add", "notiz.txt")
    git("commit", "-m", "Eigene Probe")
    gespeichert = git("show", "HEAD:notiz.txt")
    assert gespeichert == "Erster Stand\n"
    assert git("status", "--porcelain") == ""
    print("Gespeicherter Inhalt:", gespeichert.strip())
    print("Arbeitsverzeichnis sauber:", True)
```

Geprüfte Ausgabe:

```text
Gespeicherter Inhalt: Erster Stand
Arbeitsverzeichnis sauber: True
```

Es wird genau eine eigene Datei aufgenommen und lokal gespeichert. Es gibt keine Netzwerkverbindung, keinen Push und keine Änderung am bestehenden Projekt durch diese Übung. Der temporäre Ordner wird anschließend entfernt.

## 7. Abgrenzung zu ähnlichen Begriffen

Git ist das Werkzeug. Ein Repository enthält dessen Versionsdaten. Ein Hostingdienst stellt zusätzliche Zusammenarbeit bereit. Eine Sicherungsstrategie muss außerdem berücksichtigen, welche Daten überhaupt erfasst und an unabhängige Orte kopiert wurden.

## 8. Häufige Missverständnisse

Ein Commit ist noch kein Push. Git speichert nicht automatisch jede neue Datei. Eine technisch erfolgreiche Zusammenführung beweist keine fachliche Richtigkeit. Und eine lokale Historie schützt nicht allein vor dem Verlust des gesamten Datenträgers.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe die ausgewählten Änderungen vor dem Commit. Zugangsdaten gehören nicht versehentlich in die Historie. Eine spätere Entfernung aus der aktuellen Datei beseitigt frühere gespeicherte Inhalte nicht automatisch. Die Übung verwendet ausschließlich selbst erzeugten harmlosen Text.
