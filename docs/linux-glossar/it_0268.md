# Blocking

## 1. Kurzbeschreibung

Blocking bedeutet, dass ein Aufruf den betroffenen Ausführungsablauf zunächst nicht weiterlaufen lässt. Er wartet beispielsweise auf Daten, eine Sperre oder den Abschluss einer Arbeit. Welche anderen Teile währenddessen fortfahren können, hängt vom Entwurf ab. Ein blockierender Thread bedeutet nicht automatisch, dass der ganze Rechner oder jedes andere Programm stillsteht.

## 2. Was bedeutet der Begriff?

Die Quelle nennt einen langen Ping, der eine GUI aufhalten kann. Das ist als mögliche Wirkung eines ungeeigneten synchronen Aufrufs verständlich. Maßgeblich ist, wo gewartet wird: Wenn die zentrale Ereignisverarbeitung währenddessen nicht weiterarbeitet, kann die Oberfläche nicht wie vorgesehen reagieren.

Auch ein bewusst blockierender Worker kann sinnvoll sein, wenn er auf neue Aufgaben wartet und dabei keine andere erforderliche Arbeit aufhält. Der Begriff allein ist deshalb kein allgemeines Qualitätsurteil. Vertrag, Dauer und Ausführungsort müssen zusammen betrachtet werden.

## 3. Einfacher Vergleich aus dem Alltag

Du rufst eine Auskunft an und wartest in der Leitung. Für diesen Gesprächsablauf geht es erst mit einer Antwort oder dem Ende des Wartens weiter. Andere Personen können währenddessen ihre eigenen Aufgaben erledigen.

Die Grenze: Software kennt unterschiedliche Ausführungsstränge und Ereignisverarbeitung. Ein Wartevorgang kann wenig Rechenzeit benötigen und trotzdem den vorgesehenen Fortschritt verhindern. Umgekehrt kann eine lange Berechnung den Ablauf aufhalten, obwohl sie nicht auf eine äußere Antwort wartet.

## 4. Wie funktioniert das?

Eine blockierende Schnittstelle liefert erst nach ihrem vorgesehenen Ereignis oder Ergebnis zurück. Je nach Vertrag kann eine Wartefrist oder ein Abbruch vorgesehen sein. Der aufrufende Code muss mit Erfolg, Zeitüberschreitung und anderen Fehlern passend umgehen.

Die [Python-Dokumentation zu Queue.get](https://docs.python.org/3.13/library/queue.html#queue.Queue.get) zeigt einen konkreten Unterschied: Mit blockierendem Aufruf kann auf einen Eintrag gewartet werden. Mit einer positiven Wartefrist wird bei ausbleibendem Eintrag Empty ausgelöst. Das ist ein erwarteter Zustand des Aufrufs, keine automatische Beschädigung der Queue.

Für einen Event Loop sind blockierende Aufrufe besonders relevant. Die [asyncio-Dokumentation zu blockierendem Code](https://docs.python.org/3.13/library/asyncio-dev.html#running-blocking-code) erklärt, dass lange direkte Verarbeitung andere Tasks und I/O-Arbeit verzögern kann. Eine Funktion wird nicht allein dadurch kooperativ, dass sie innerhalb einer Coroutine aufgerufen wird.

Ein anderer Thread oder Prozess kann geeignete Arbeit auslagern. Das macht die ursprüngliche Operation aber nicht unbedingt selbst nichtblockierend. Stattdessen findet ihr Warten an einem anderen Ort statt. Übergabe, Fehler und Ende bleiben zusätzliche Anforderungen. Eine Oberfläche kann weiterhin hängen, wenn sie sofort wieder ungeeignet auf den Worker wartet.

## 5. Wo begegnet mir das unter Linux?

Datei-, Netzwerk- und Sperraufrufe besitzen unterschiedliche Warteverträge. Auch die Anzeige einer Anwendung hängt von deren Ereignisverarbeitung ab. Ein Hänger sollte deshalb nicht nur anhand des sichtbaren Fensters beurteilt werden.

Für dieses Glossar wird kein Ping gestartet und keine echte Verbindung geöffnet. Der eigene Test wartet nur auf eine neu erzeugte leere Warteschlange. Es gibt eine kurze ausdrücklich gesetzte Wartefrist und keinen unbegrenzten blockierenden Aufruf.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Es demonstriert eine Queue-Ausnahme nach begrenztem Warten und anschließend einen erfolgreich verfügbaren eigenen Eintrag. Eine Leistungs- oder genaue Zeitmessung ist nicht vorgesehen.

```python
from queue import Empty, Queue

aufgaben = Queue()
zeitgrenze_erreicht = False
try:
    aufgaben.get(block=True, timeout=0.02)
except Empty:
    zeitgrenze_erreicht = True
assert zeitgrenze_erreicht
aufgaben.put("Probe")
ergebnis = aufgaben.get(block=True, timeout=0.02)
assert ergebnis == "Probe"
aufgaben.task_done()
print("Leeres begrenztes Warten beendet:", zeitgrenze_erreicht)
print("Verfügbarer Eintrag:", ergebnis)
```

Geprüfte Ausgabe:

```text
Leeres begrenztes Warten beendet: True
Verfügbarer Eintrag: Probe
```

Der erste Aufruf findet keinen Eintrag und endet nach seinem Wartevertrag mit Empty. Der zweite bekommt den eigenen verfügbaren Wert. Die tatsächliche verstrichene Zeit wird nicht gemessen. Das Beispiel prüft weder GUI-Reaktionsfähigkeit noch Netzwerkzeitgrenzen oder beliebige Abbruchmechanismen.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Deadlock ist eine festgefahrene Warteabhängigkeit. Blocking kann dagegen ein ganz normaler endlicher Aufruf sein. Async ermöglicht passende kooperative Wartepunkte. Ein Thread kann selbst blockieren, während andere Teile weiterlaufen. Diese Begriffe beschreiben unterschiedliche Eigenschaften.

## 8. Häufige Missverständnisse

Nicht jedes Warten ist ein Fehler. Ein blockierter Thread hält nicht automatisch den ganzen Rechner an. Ein Timeout beweist keine fachlich erfolgreiche Arbeit. Und Auslagern macht eine blockierende Operation nicht von selbst zu einer nichtblockierenden Schnittstelle.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Bestimme Ausführungsort, Wartevertrag und Fehlerweg ausdrücklich. Vermeide ungeeignetes Warten an zentralen Ereignisstellen. Die Ausführung verwendet nur eine eigene Speicherqueue und verändert keine Anwendungen, Dienste, Geräte oder Netzwerkeinstellungen.
