# Coverage

## 1. Kurzbeschreibung

Coverage bedeutet im Testkontext Abdeckung: Es wird gemessen, welche betrachteten Codebestandteile während einer Ausführung erreicht wurden. Häufig geht es um ausführbare Zeilen oder Verzweigungen. Die Messung zeigt Lücken und erreichte Stellen. Sie beweist nicht, dass das Verhalten dort richtig war oder dass die Tests geeignete Erwartungen geprüft haben.

## 2. Was bedeutet der Begriff?

Die Quelle nennt 80 Prozent Coverage und erklärt richtig, dass daraus keine Fehlerfreiheit folgt. Zusätzlich muss bekannt sein, worauf sich der Anteil bezieht. Dateien, ausgeschlossene Stellen und die gewählte Messart beeinflussen Zähler und Nenner.

Die [Autoren-Dokumentation zur Arbeitsweise von coverage.py](https://raw.githubusercontent.com/nedbat/coveragepy/master/doc/howitworks.rst) unterscheidet Ausführung, Analyse und Bericht. Eine sinnvolle Kennzahl entsteht also nicht allein dadurch, dass irgendein Code gelaufen ist. Das Werkzeug muss auch bestimmen, welche Stellen als betrachtete Möglichkeiten zählen.

## 3. Einfacher Vergleich aus dem Alltag

Du markierst auf einem Stadtplan die Straßen, die du entlanggefahren bist. Die Markierungen zeigen erreichte Wege und ausgelassene Bereiche. Sie sagen noch nicht, ob du unterwegs jede Hausnummer richtig erfasst oder jede Aufgabe korrekt erledigt hast.

Die Grenze: Software besitzt auch Verzweigungen und Bedingungen, die in einer einfachen Linienmarkierung nicht vollständig sichtbar werden. Ein einmal besuchter Ort kann mit verschiedenen Eingaben sehr unterschiedlich reagieren. Die Messung ist daher ein Hinweis auf Ausführung, kein vollständiges Qualitätsurteil.

## 4. Wie funktioniert das?

Während der Ausführung zeichnet ein Werkzeug geeignete Ereignisse auf. Danach werden sie den betrachteten Codebestandteilen zugeordnet. Ein Bericht kann erreichte und nicht erreichte Stellen darstellen. Bei einer prozentualen Angabe muss die zugrunde liegende Auswahl bekannt sein.

Die [coverage.py-Dokumentation zur Branch-Abdeckung](https://raw.githubusercontent.com/nedbat/coveragepy/master/doc/branch.rst) erklärt den Unterschied zu bloßer Statement-Abdeckung. Eine Bedingungszeile kann erreicht worden sein, obwohl nur einer ihrer möglichen Wege genommen wurde. Auch vollständig erreichte Verzweigungen decken nicht automatisch jede Kombination aller Eingabewerte ab.

Pythons Standardbibliothek bietet mit [trace.Trace](https://docs.python.org/3.13/library/trace.html#trace.Trace) eine einfachere Möglichkeit, ausgeführte Zeilen aufzuzeichnen. Das Beispiel verwendet sie für eine ausdrücklich selbst festgelegte kleine Zeilenmenge. Es behauptet keine gleichwertige vollständige coverage.py-Auswertung oder Branch-Messung.

Wichtig bleibt die Verbindung zu Assertions. Code kann ausgeführt werden und einen falschen Wert liefern, ohne dass ein fehlender Vergleich den Fehler meldet. Umgekehrt können wenige gut gewählte Fälle wichtige Eigenschaften prüfen. Abdeckung hilft beim Finden von Lücken, ersetzt aber nicht die Wahl sinnvoller Erwartungen.

## 5. Wo begegnet mir das unter Linux?

Entwicklungsprojekte können Coverage-Berichte lokal oder in CI erzeugen. Eine Schwelle kann dazu dienen, Veränderungen sichtbar zu machen. Sie sollte jedoch nicht losgelöst vom Prüfgegenstand als vollständige Freigabe verstanden werden.

Für dieses Glossar wird keine Messbibliothek installiert und keine bestehende Testsuite instrumentiert. Die Aufzeichnung beschränkt sich auf eine selbst erzeugte temporäre Datei. Es entsteht kein Projektbericht und keine Aussage zur Abdeckung der NetMon-Anwendung.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 ausgeführt. Die eigene Funktion soll im Gedankenvertrag Zahlen addieren, enthält aber absichtlich eine falsche Berechnung ihrer Anzahl. Alle ausgewählten ausführbaren Zeilen werden dennoch erreicht.

```python
from pathlib import Path
import tempfile
from trace import Trace

with tempfile.TemporaryDirectory() as ordner:
    datei = Path(ordner) / "eigene_probe.py"
    quelle = (
        "def summe(werte):\n"
        "    ergebnis = len(werte)\n"
        "    return ergebnis\n"
        "\n"
        "resultat = summe([2, 3])\n"
    )
    datei.write_text(quelle, encoding="utf-8")
    tracer = Trace(count=True, trace=False)
    namensraum = {"__file__": str(datei), "__name__": "eigene_probe"}
    tracer.runctx(compile(quelle, str(datei), "exec"), namensraum, namensraum)
    zaehler = tracer.results().counts
    betrachtet = {1, 2, 3, 5}
    erreicht = {n for n in betrachtet if zaehler.get((str(datei), n), 0) > 0}
    assert erreicht == betrachtet
    assert namensraum["resultat"] == 2 and namensraum["resultat"] != 5
    print("Erreichte betrachtete Zeilen:", len(erreicht), "von", len(betrachtet))
    print("Fachliches Ergebnis korrekt:", namensraum["resultat"] == 5)
```

Geprüfte Ausgabe:

```text
Erreichte betrachtete Zeilen: 4 von 4
Fachliches Ergebnis korrekt: False
```

Die Aufzeichnung erreicht den gesamten ausdrücklich betrachteten Ausschnitt. Der falsche Rückgabewert bleibt trotzdem falsch. Genau dieser Gegensatz wird geprüft. Das Beispiel führt nur eigenen Quelltext aus und entfernt seine temporäre Datei. Es misst keine Branch-Abdeckung oder allgemeine Fehlerquote.

## 7. Abgrenzung zu ähnlichen Begriffen

Coverage beschreibt erreichte Codebestandteile. Assertions vergleichen Erwartungen. Ein Review beurteilt weitere Zusammenhänge. Ein Leistungstest untersucht andere Eigenschaften. Keine dieser Aussagen lässt sich allein durch die Prozentzahl einer anderen Prüfung ersetzen.

## 8. Häufige Missverständnisse

100 Prozent Zeilenabdeckung bedeutet nicht fehlerfrei. Eine erreichte Bedingung beweist nicht beide Zweige. Ausgeschlossener Code kann den Anteil verändern. Und bloßer Aufruf ohne passende Erwartung prüft nicht automatisch das fachliche Ergebnis.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Nenne Messart, Umfang und ausgeschlossene Stellen. Nutze Berichte, um sinnvolle zusätzliche Fälle zu finden. Die Ausführung verändert keine Anwendung, Tests, Abhängigkeiten, CI-Dateien oder bestehenden Berichte.
