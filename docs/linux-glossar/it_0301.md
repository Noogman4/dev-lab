# Memory Leak

## 1. Kurzbeschreibung

Ein Memory Leak ist ein Speicherleck. Speicher bleibt länger belegt, als die Anwendung ihn für ihre Aufgabe braucht. Bei Wiederholung eines betroffenen Vorgangs kann der Verbrauch steigen. Die Ursache kann auch in einem Programm mit automatischer Speicherverwaltung liegen.

## 2. Was bedeutet der Begriff?

In einer Sprache mit manueller Verwaltung kann ein Programm den Verweis auf einen reservierten Bereich verlieren, ohne ihn freizugeben. In Python kann ein Objekt weiterhin erreichbar bleiben, etwa weil eine dauerhafte Liste jeden früheren Arbeitsschritt speichert. Der Speicherverwalter kann aus der Referenz allein nicht wissen, ob die Anwendung das Objekt fachlich noch braucht.

## 3. Einfacher Vergleich aus dem Alltag

In einem Lager landen leere Rückgabekisten immer wieder auf einem Regal. Obwohl niemand die Kisten später verwendet, steht das Regal weiter voll. Anders als im Lager kann eine Laufzeit intern freigegebenen Speicher zur schnelleren Wiederverwendung behalten. Der vom Betriebssystem gemeldete Verbrauch muss deshalb nicht sofort sinken.

## 4. Wie funktioniert das?

Suche nach einer wiederholbaren Tätigkeit und vergleiche mehrere Messpunkte. [tracemalloc](https://docs.python.org/3.13/library/tracemalloc.html) kann Snapshots bestimmter Python-Speicherzuweisungen vergleichen. Eine auffällige Stelle dort ist ein Einstieg in die Suche nach dem besitzenden Objekt oder der gehaltenen Referenz.

Der Prozessspeicher umfasst auch native Bibliotheken und andere Bereiche. Die [Linux-Referenz zu /proc/PID/status](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html) erklärt `VmRSS` und weist auf die Grenzen dieses Messwerts hin. RSS steht für den im Arbeitsspeicher vorgehaltenen Anteil eines Prozesses.

## 5. Wo begegnet mir das unter Linux?

Unter Linux lässt sich ein Wachstum zunächst auf Prozessebene beobachten. Für die Ursachenanalyse brauchst du gegebenenfalls Daten aus der Laufzeit oder aus einer nativen Komponente. Ein begrenzter Cache kann sich nach dem Start füllen und danach stabil bleiben.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses CPython-Beispiel zählt eigene Objekte anhand schwacher Referenzen. Eine schwache Referenz erlaubt eine Beobachtung, ohne das Objekt selbst am Leben zu halten.

```python
import weakref

class Notiz:
    pass

behalten = [Notiz() for _ in range(3)]
beobachtet = [weakref.ref(notiz) for notiz in behalten]
assert sum(ref() is not None for ref in beobachtet) == 3
print("Behalten:", len(behalten))

behalten.clear()
assert all(ref() is None for ref in beobachtet)
print("Nach Freigabe:", len(behalten))
```

Die erwartete Ausgabe lautet zuerst `Behalten: 3` und dann `Nach Freigabe: 0`. Die Prüfung zeigt das Ende der erreichbaren Objekte in diesem Modell.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein erwarteter Cache hat ein definiertes Ziel und möglichst eine Grenze. Ein Speicherleck hält unbeabsichtigt Ressourcen fest. Steigender Speicherverbrauch bei wachsender Nutzlast kann auch ein gewollter Effekt sein.

## 8. Häufige Missverständnisse

Ein niedrigerer RSS-Wert ist kein notwendiger Beweis dafür, dass ein Python-Objekt freigegeben wurde. Ein erzwungener Sammlungslauf kann erreichbare Objekte mit einer unbeabsichtigt gehaltenen starken Referenz nicht beseitigen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Vergleiche wiederholte gleichartige Abläufe mit geeigneten Messpunkten. Prüfe die Lebensdauer langlebiger Listen, Registrierungen und Rückruffunktionen. Untersuche Speicherabbilder nur in geeigneter Umgebung, weil sie Programmdaten enthalten können.
