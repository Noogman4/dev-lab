# Webhook

## 1. Kurzbeschreibung

Ein Webhook ist eine ereignisbezogene Benachrichtigung über einen eingerichteten HTTP-Zugang. Ein Dienst sendet beispielsweise nach einem Ereignis eine Anfrage an einen Empfänger. Dieser muss Inhalt, Herkunft und Verarbeitung nach dem vereinbarten Verfahren prüfen. Der Begriff garantiert weder ein einheitliches Datenformat noch genau eine Zustellung in unveränderlicher Reihenfolge.

## 2. Was bedeutet der Begriff?

Das Katalogbeispiel einer Meldung nach einem fertigen Build ist typisch. Die [GitHub-Einführung zu Webhooks](https://docs.github.com/en/webhooks/about-webhooks) beschreibt ein konkretes Ereignis- und Zustellmodell. Die Bedingungen dieses Anbieters sind aber nicht automatisch die Regeln aller anderen Dienste.

Ein Webhook unterscheidet sich vom wiederholten aktiven Nachfragen nach Änderungen. Der sendende Dienst stößt den Austausch bei einem passenden Ereignis an. Dafür muss ein entsprechendes Ziel vereinbart sein. Dieser Eintrag richtet kein solches Ziel ein und sendet keine Meldung.

## 3. Einfacher Vergleich aus dem Alltag

Eine Werkstatt vereinbart, nach Abschluss eines Auftrags eine Nachricht an eine hinterlegte Stelle zu schicken. Der Empfänger muss nicht ständig fragen, ob die Arbeit fertig ist. Er muss aber prüfen, ob die Nachricht zum richtigen Vorgang gehört.

Die Grenze: Technische Benachrichtigungen können verspätet, erneut oder mit Fehlern eintreffen. Ein Text mit „fertig“ ist außerdem kein verlässlicher Nachweis des Absenders. Empfangen, Bestätigen und fachlich Verarbeiten sind unterschiedliche Schritte.

## 4. Wie funktioniert das?

Ein Anbieter ordnet Ereignisse eingerichteten Empfängern zu. Er bildet eine passende Anfrage, häufig mit strukturierten Daten. Der Empfänger behandelt sie nach dem dokumentierten Vertrag. Die genaue Methode, Signatur und Wiederholungslogik sind anbieterspezifisch.

Die [GitHub-Empfehlungen für Webhooks](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks) behandeln beispielsweise Geheimnisse, zeitnahe Antworten und eindeutige Lieferkennungen. Solche Kennungen können helfen, wiederholt erhaltene Nachrichten bewusst einzuordnen. Eine Annahmebestätigung darf nicht mit der bereits vollständig abgeschlossenen Fachverarbeitung verwechselt werden.

Für eine Prüfung des Inhalts kann ein vereinbartes kryptografisches Verfahren verwendet werden. Es muss zu den tatsächlich gesendeten Bytes passen. Zusätzlich bleiben unter anderem erwarteter Ereignistyp, Zielbeziehung und Umgang mit Wiederholungen zu prüfen. Eine richtige Signatur allein ist keine vollständige Verarbeitungsstrategie.

## 5. Wo begegnet mir das unter Linux?

Programme und Dienste können Webhooks für Benachrichtigungen über Builds oder andere Ereignisse nutzen. Die empfangende Anwendung ist in diesem Austausch ein Server, während der auslösende Dienst einen Clientaufruf sendet. Eine grafische Oberfläche ist dafür nicht zwingend erforderlich.

Eine erreichbare URL ist allerdings nicht automatisch ein sicher eingerichteter Empfänger. Auch die Verarbeitung sollte den vereinbarten Umfang beachten. Der folgende lokale Versuch enthält keinen HTTP-Endpunkt und verwendet keinen Anbieter oder vorhandenen Schlüssel.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Ordner ausgeführt. Es demonstriert nur einen eigenen HMAC-Vergleich, kein vollständiges Webhook-Protokoll. Die [Python-Referenz zu compare_digest](https://docs.python.org/3.13/library/hmac.html#hmac.compare_digest) beschreibt den dafür vorgesehenen Vergleich.

```python
import hashlib
import hmac

schluessel = b"nur-fuer-diese-eigene-probe"
daten = b'{"ereignis":"build_fertig","id":"probe-1"}'
signatur = hmac.new(schluessel, daten, hashlib.sha256).hexdigest()


def passt(inhalt, vorgelegt):
    erwartet = hmac.new(schluessel, inhalt, hashlib.sha256).hexdigest()
    return hmac.compare_digest(erwartet, vorgelegt)


assert passt(daten, signatur)
assert not passt(daten + b" ", signatur)
print("Eigene Bytes passend:", passt(daten, signatur))
print("Veränderte Bytes abgelehnt:", not passt(daten + b" ", signatur))
```

Geprüfte Ausgabe:

```text
Eigene Bytes passend: True
Veränderte Bytes abgelehnt: True
```

Schon der zusätzliche Leerraum verändert hier die signierten Bytes, obwohl ein JSON-Parser den fachlichen Inhalt ähnlich lesen könnte. Deshalb darf ein vereinbarter Vergleich nicht unbesehen auf beliebig neu formatierten Text angewendet werden. Der feste Testschlüssel ist kein echter Zugang. Wiederholungs- oder Berechtigungsprüfung werden nicht getestet.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine API kann Anfragen zu beliebigen vorgesehenen Zeitpunkten erhalten. Ein Webhook beschreibt hier einen ereignisbezogenen Zustellweg. Polling fragt wiederholt nach. Eine Session hält einen anderen Nutzungskontext. Ein Token ist ein möglicher Nachweis, nicht selbst die gesamte Benachrichtigung.

## 8. Häufige Missverständnisse

Eine Meldung kommt nicht allgemein garantiert genau einmal. Ein erfolgreicher HTTP-Status beweist nicht automatisch abgeschlossene Folgearbeit. Ein bekannter Feldname bestätigt auch keinen Absender. JSON allein legt schließlich weder Signaturregeln noch Ereignissemantik fest.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Nutze die Dokumentation des konkreten Anbieters und prüfe erwartete Daten sowie Zustellkennungen. Behandle Folgeaktionen kontrolliert. Dieser Eintrag registriert keinen Webhook, betreibt keinen Empfänger und verändert keine Schlüssel, Dienste, Konten oder Konfigurationen.

## 10. Verwandte Begriffe

[HTTP](it_0145.md) trägt den Austausch. Der [Endpoint](it_0171.md) kann das Ziel bezeichnen. [Client](it_0183.md) und [Server](it_0184.md) beschreiben Rollen. [JSON](it_0175.md) ist ein mögliches Datenformat. Der [Token](it_0188.md) erfüllt eine getrennte Nachweisfunktion.
