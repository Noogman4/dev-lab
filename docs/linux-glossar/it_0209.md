# Merge

## 1. Kurzbeschreibung

Ein Merge führt in Git Entwicklungsgeschichten zusammen. Änderungen eines anderen Entwicklungsstands werden in den aktuellen Zweig integriert. Je nach Ausgangslage genügt ein Vorrücken des Branchverweises oder es entsteht ein neuer Merge-Commit. Ein Merge ist keine Garantie, dass das gemeinsame Ergebnis fachlich richtig oder getestet ist.

## 2. Was bedeutet der Begriff?

Das Katalogbeispiel beschreibt die Aufnahme eines Feature-Branches in `main`. Wichtig ist dabei die Richtung: Der aktuell ausgewählte Branch ist normalerweise das Ziel der Integration. Der andere Branch wird dadurch nicht automatisch gelöscht. Auch erfolgt keine Veröffentlichung an einen entfernten Dienst allein durch den lokalen Merge.

Die [offizielle Dokumentation zu git merge](https://raw.githubusercontent.com/git/git/master/Documentation/git-merge.adoc) erläutert die Zusammenführung und ihre verschiedenen Fälle. Ein Feature-Name legt nicht fest, was integriert wird; maßgeblich sind die tatsächlich bezeichneten Commits und die gewählten Optionen.

## 3. Einfacher Vergleich aus dem Alltag

Zwei Personen bearbeiten Kopien eines gemeinsamen Textstands. Bei der Zusammenführung wird betrachtet, was beide seit diesem Ausgangspunkt geändert haben. Änderungen an verschiedenen Abschnitten können leicht zusammenpassen. Widersprüchliche Änderungen am selben Satz brauchen dagegen eine bewusste Entscheidung.

Die Grenze: Konfliktfreiheit bedeutet nur, dass das Werkzeug die Änderungen nach seinen Regeln zusammenbringen konnte. Zwei getrennte Abschnitte können fachlich trotzdem nicht mehr zusammenpassen. Eine automatisch zusammengeführte Konfiguration kann beispielsweise syntaktisch korrekt und dennoch widersprüchlich sein.

## 4. Wie funktioniert das?

Häufig vergleicht Git die beteiligten Stände unter Berücksichtigung einer gemeinsamen Ausgangsbasis. Die [Dokumentation zu git merge-base](https://raw.githubusercontent.com/git/git/master/Documentation/git-merge-base.adoc) erklärt geeignete gemeinsame Vorgänger und auch die Möglichkeit mehrerer solcher Basen. Das vereinfachte Bild eines einzigen gemeinsamen Ausgangspunkts deckt daher nicht jede komplizierte Historie ab.

Ist der aktuelle Stand bereits ein Vorfahr des einzubeziehenden Stands, kann ein Fast-Forward den Branchverweis einfach vorrücken lassen. Sind beide Seiten weiterentwickelt worden, kann ein echter Zusammenführungscommit ihre Historien verbinden. Der gewöhnliche Merge zweier auseinanderentwickelter Linien hat dann zwei Eltern.

Entsteht ein Konflikt, muss die Anwendung der Änderungen gegebenenfalls angehalten und aufgelöst werden. Vorhandene offene Änderungen erschweren die Übersicht und können eine Rücknahme problematischer machen. Die offizielle Merge-Dokumentation empfiehlt deshalb einen geeigneten sauberen Ausgangsstand. Das folgende Beispiel erzeugt bewusst keine Konflikte.

## 5. Wo begegnet mir das unter Linux?

Teams integrieren Änderungen lokal oder über Funktionen eines Hostingdiensts. Ein Pull Request organisiert Prüfung und Diskussion, ist aber nicht selbst mit dem Git-Grundbegriff Merge identisch. Hostingdienste können unterschiedliche Integrationsverfahren anbieten.

Vor einem Merge helfen aktueller Branch, sauberer Status und eine Prüfung des geplanten Umfangs. Das eigentliche Projekt wird hier nicht zusammengeführt. Alle Beispielreferenzen und Dateien entstehen nur in einem eigenen temporären Repository.

## 6. Konkretes Beispiel Schritt für Schritt

Ausgeführt wurde das vollständige Beispiel mit Python 3.13 und Git 2.52.0. Persönliche und systemweite Git-Konfiguration sind für die Kindprozesse ausgeblendet. Das neue Repository verwendet keine Vorlagen; die Identität wird pro Aufruf gesetzt.

```python
import os
from pathlib import Path
import subprocess
import tempfile

env = {k: v for k, v in os.environ.items() if not k.startswith("GIT_")}
env.update(GIT_CONFIG_GLOBAL="/dev/null", GIT_CONFIG_NOSYSTEM="1")
with tempfile.TemporaryDirectory() as ordner:
    repo = Path(ordner)
    def git(*args):
        return subprocess.run(
            ["git", "-c", "user.name=Glossar", "-c",
             "user.email=glossar@example.invalid", "-c",
             "commit.gpgsign=false", *args],
            cwd=repo, env=env, check=True, capture_output=True, text=True
        ).stdout.strip()
    def speichern(datei, text):
        (repo / datei).write_text(text, encoding="utf-8")
        git("add", datei)
        git("commit", "-m", datei)
    git("init", "--template=", "-b", "basis")
    speichern("start.txt", "Gemeinsam\n")
    git("switch", "-c", "funktion")
    speichern("funktion.txt", "Neue Funktion\n")
    git("switch", "basis")
    speichern("hinweis.txt", "Neuer Hinweis\n")
    git("merge", "--no-edit", "funktion")
    eltern = git("rev-list", "--parents", "-n", "1", "HEAD").split()[1:]
    assert len(eltern) == 2
    assert (repo / "funktion.txt").read_text() == "Neue Funktion\n"
    assert (repo / "hinweis.txt").read_text() == "Neuer Hinweis\n"
    assert git("status", "--porcelain") == ""
    print("Eltern des Merge-Commits:", len(eltern))
    print("Beide Ergänzungen vorhanden:", True)
```

Geprüfte Ausgabe:

```text
Eltern des Merge-Commits: 2
Beide Ergänzungen vorhanden: True
```

Beide Zweige erhalten vor dem Merge einen eigenen Folgecommit. Die getrennten neuen Dateien lassen sich konfliktfrei zusammenführen. Geprüft werden zwei Eltern, beide Inhalte und der saubere Status. Es gibt keinen Netzwerkzugriff und keinen Merge des bestehenden Projektbranches.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Fast-Forward benötigt normalerweise keinen zusätzlichen Merge-Commit. Ein Rebase ordnet Commits in einer anderen Weise neu an. Ein bloßes Kopieren einer Datei verbindet keine Entwicklungsgeschichten. Ein Commit kann außerdem ohne Zusammenführung entstehen.

## 8. Häufige Missverständnisse

Nicht jeder Merge erzeugt einen neuen Commit. Konfliktfreiheit beweist keine fachliche Verträglichkeit. Der eingebundene Branch wird nicht automatisch entfernt. Und ein lokaler Merge ist noch kein Push oder eine Veröffentlichung.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe Zielzweig und Ausgangsstatus. Kontrolliere das gemeinsame Ergebnis und führe passende fachliche Tests aus. Dieses Beispiel testet nur die kleine konfliktfreie Git-Zusammenführung; Konfliktauflösung und produktive Integration sind nicht Gegenstand der Ausführung.

## 10. Verwandte Begriffe
