# CORS

## 1. Kurzbeschreibung

CORS bedeutet „Cross-Origin Resource Sharing“. Das Verfahren erlaubt einem Server, dem Browser mitzuteilen, unter welchen Bedingungen eine Antwort für eine andere Origin freigegeben werden darf. Eine Origin umfasst bei gewöhnlichen HTTP-Adressen Schema, Host und Port. „Andere Domain“ ist deshalb nur eine verkürzte und manchmal ungenaue Beschreibung.

## 2. Was bedeutet der Begriff?

Webseiten arbeiten in einem Sicherheitskontext. Der Browser beschränkt bestimmte Zugriffe zwischen unterschiedlichen Origins. Das [CORS-Protokoll im Fetch-Standard](https://fetch.spec.whatwg.org/#http-cors-protocol) beschreibt die vereinbarte Freigabe über HTTP-Felder.

Das Katalogbeispiel einer API und eines anderen Frontends ist unter diesen Bedingungen richtig: Browsercode möchte eine Antwort cross-origin nutzen. Daraus folgt nicht, dass jeder andere Client CORS benötigt. Ein gewöhnliches serverseitiges Programm wird nicht automatisch durch dieselbe Browserprüfung begrenzt.

## 3. Einfacher Vergleich aus dem Alltag

Eine Stelle legt fest, welche andere Stelle bestimmte Antworten einsehen darf. Eine Nachricht kann bereits angekommen sein, obwohl ihre Weitergabe an einen bestimmten Empfänger nicht erlaubt wird. Übermittlung und Einsichtsrecht sind verschiedene Schritte.

Die Grenze: CORS ist ein genau definiertes Browser- und HTTP-Verfahren. Es beurteilt keine menschliche Vertrauenswürdigkeit und ersetzt keine Anmeldung. Eine Freigabe für das Lesen einer Antwort bedeutet auch nicht automatisch, dass jede fachliche Aktion des anfragenden Benutzers zulässig ist.

## 4. Wie funktioniert das?

Der Browser berücksichtigt die anfragende Origin und die Art des Zugriffs. Der Server kann etwa mit `Access-Control-Allow-Origin` eine passende Freigabe mitteilen. Wenn ein CORS-Preflight erforderlich ist, verwendet die Voranfrage die Methode `OPTIONS`. `Access-Control-Request-Method` benennt die Methode der geplanten Anfrage. Ein passender Eintrag im Preflight-Cache kann eine erneute Voranfrage ersparen. [WHATWG Fetch zum CORS-Preflight](https://fetch.spec.whatwg.org/#cors-preflight-fetch)

Die Origin ist nicht bloß der Hostname. [RFC 6454 zur Origin](https://www.rfc-editor.org/rfc/rfc6454.html#section-4) beschreibt die Herleitung aus Schema, Host und Port für entsprechende URI-Fälle. Das gesamte Origin-Modell besitzt zusätzliche Sonderfälle; eine freie Zeichenkettenzerlegung ist kein vollständiger Ersatz für Browserregeln.

Wichtig ist außerdem die Trennung von Senden und Freigeben. Manche Anfragen können bereits übertragen werden, bevor die Antwort für den aufrufenden Code blockiert wird. Eine CORS-Fehlermeldung beweist daher nicht, dass auf dem Server keinerlei Wirkung entstanden ist. CORS ersetzt keinen Schutz gegen unerwünschte verändernde Anfragen.

## 5. Wo begegnet mir das unter Linux?

Browser unter Linux setzen entsprechende Webregeln um. Eine Frontend-Anwendung kann deshalb eine CORS-Meldung sehen, obwohl ein Kommandozeilenclient dieselbe API-Antwort lesen kann. Das ist nicht automatisch ein Widerspruch, sondern eine unterschiedliche Zugriffsprüfung.

Bei Anfragen mit Zugangsdaten gelten zusätzliche Regeln. Eine pauschale Sternfreigabe ist nicht für jeden solchen Fall verwendbar. Die konkrete Konfiguration muss zum tatsächlichen Origin- und Berechtigungsmodell passen. Das Abschalten von Browserprüfungen ist keine passende Abnahme einer API-Einrichtung.

## 6. Konkretes Beispiel Schritt für Schritt

Diese fiktiven HTTP-Adressen dienen nur dem Vergleich. Es wird kein Browser gestartet und kein Name aufgelöst.

| Erste Adresse | Zweite Adresse | Gleiche gewöhnliche Origin? |
| --- | --- | --- |
| https://app.beispiel.invalid | https://app.beispiel.invalid/hilfe | Ja |
| https://app.beispiel.invalid | https://api.beispiel.invalid | Nein |
| https://app.beispiel.invalid | https://app.beispiel.invalid:8443 | Nein |
| https://app.beispiel.invalid | http://app.beispiel.invalid | Nein |

Ein anderer Pfad allein erzeugt im ersten Fall keine neue Origin. Die weiteren Zeilen unterscheiden Host, Port oder Schema. Deshalb reicht die Frage nach „derselben Domain“ für die Einordnung nicht immer aus.

Eine mögliche Antwortfreigabe müsste die tatsächlich gewünschte Origin korrekt berücksichtigen. Die Tabelle ist aber weder ein vollständiger CORS-Konfigurationstest noch ein Ersatz für einen Browserversuch mit bekannten Bedingungen. Es werden keine realen Header oder Serverregeln verändert.

## 7. Abgrenzung zu ähnlichen Begriffen

Authentifizierung prüft eine Identität, Autorisierung die erlaubte Handlung. CORS betrifft die Freigabe bestimmter Antworten im Browserkontext. HTTPS schützt einen Kommunikationszusammenhang. Eine Firewall kontrolliert Verkehr auf anderen Regeln. Keines dieser Verfahren ist allein ein vollständiger Ersatz für die übrigen.

## 8. Häufige Missverständnisse

CORS ist kein allgemeiner API-Zugangsschutz gegen beliebige Programme. Ein blockierter Antwortzugriff bedeutet nicht immer eine ungesendete Anfrage. Nicht jeder Fall benötigt einen Preflight. Eine erfolgreiche Freigabe beweist schließlich keine richtige Fachantwort oder sicheren Benutzerzugriff.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Ermittle bei Problemen genaue Origins, Methode und Zugangsdatenmodus. Prüfe die beabsichtigte Freigabe statt pauschal alles zu erlauben. Dieser Eintrag sendet keine Anfragen, verändert keine Browserflags und bearbeitet weder CORS-Header noch Server- oder Proxykonfiguration.
