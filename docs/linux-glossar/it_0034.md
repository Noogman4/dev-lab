# Release

## 1. Kurzbeschreibung

Ein Release ist ein bewusst freigegebener Softwarestand, der einer vorgesehenen Nutzergruppe bereitgestellt wird. Häufig gehören eine Versionsbezeichnung, Hinweise zu Änderungen und passende Dateien dazu. Die Quelle nennt Version `1.0.0` als Beispiel. Eine Versionsnummer allein beweist jedoch noch nicht, dass der betreffende Stand tatsächlich veröffentlicht oder für einen bestimmten Einsatz freigegeben wurde.

## 2. Was bedeutet der Begriff?

Ein Release macht einen ausgewählten Stand als verwendbare Ausgabe erkennbar. Es beantwortet unter anderem, welche Änderungen enthalten sind und wo die dazugehörigen Artefakte zu finden sind. Die Zielgruppe kann öffentlich oder intern sein.

Der Ausdruck wird im Alltag auch für den Freigabevorgang verwendet. Für die Beurteilung eines konkreten Stands ist wichtig, ob von einer geplanten Version, einem Entwurf, einer Vorabversion oder einer tatsächlich veröffentlichten Ausgabe gesprochen wird. Diese Zustände sollten nicht allein aufgrund ähnlicher Namen gleichgesetzt werden.

## 3. Einfacher Vergleich aus dem Alltag

Bei einer neuen Buchauflage entscheidet ein Verlag, welcher Textstand als Ausgabe erscheinen soll. Die Auflage erhält eine Kennzeichnung, und Leser sollen die passenden Exemplare zuordnen können. Nicht jede zwischenzeitliche Manuskriptänderung ist bereits eine neue veröffentlichte Auflage.

Der Vergleich hat Grenzen: Software kann in unterschiedlichen Paketformaten für mehrere Plattformen erscheinen und anschließend Sicherheitsaktualisierungen erhalten. Außerdem kann ein Release intern bleiben oder nur für Tests gedacht sein. Eine große Öffentlichkeit gehört nicht zwingend zur Definition.

## 4. Wie funktioniert das?

Ein Projekt wählt einen Stand, erzeugt oder sammelt die vorgesehenen Artefakte und veröffentlicht Informationen zur Verwendung. Die genaue Freigaberegel hängt vom Projekt ab. Tests und Quellenstand sollten zu den tatsächlich ausgelieferten Dateien passen.

GitHub-Releases basieren auf Git-Tags und können Releasehinweise sowie Dateien verknüpfen. Die [offizielle GitHub-Beschreibung im Dokumentationsprojekt](https://raw.githubusercontent.com/github/docs/main/content/repositories/releasing-projects-on-github/about-releases.md) erläutert auch, dass Tagdatum und Releasedatum verschieden sein können. Ein Tag markiert also einen Stand, ist aber nicht mit sämtlichen Informationen und Freigabeschritten eines Releases identisch.

Auch Pflegephasen sind projektspezifisch. Python beschreibt in [PEP 602 zum Releasezyklus](https://peps.python.org/pep-0602/) seine Veröffentlichungskadenz und anschließende Wartung. Daraus folgt keine allgemeine Regel, dass jedes Linux-Projekt nach demselben Zeitplan arbeitet. Ein veröffentlichtes Release bedeutet insbesondere nicht, dass seine Wartung beendet ist.

## 5. Wo begegnet mir das unter Linux?

Ein Projekt kann Paketdateien über eine Release-Seite anbieten. Eine Distribution kann daraus eigene Pakete mit zusätzlicher Paketrevision erstellen. Der gleiche upstream benannte Softwarestand muss dadurch nicht in jedem Verteilungskanal byteidentische Dateien besitzen.

Vor der Verwendung solltest du prüfen, welche Plattform und welcher Einsatzzweck vorgesehen sind. Hinweise zu bekannten Einschränkungen sind Teil einer sinnvollen Einordnung. Ein Release mit einer vertraut aussehenden Nummer ist kein automatischer Nachweis, dass es zur eigenen Umgebung passt.

## 6. Konkretes Beispiel Schritt für Schritt

Das folgende Gedankenbeispiel beschreibt eine erfundene Ausgabe eines kleinen Werkzeugs:

```text
ausgewählter Quellenstand
    -> geprüfte Paketdatei
    -> Versionsbezeichnung 1.0.0
    -> Releasehinweise und Freigabe
    -> gesonderte Bereitstellung am Ziel
```

Zuerst wird der ausgewählte Stand eindeutig festgehalten. Danach wird die dazugehörige Paketdatei erzeugt und in der vorgesehenen Weise geprüft. Die Releasehinweise beschreiben Änderungen, Voraussetzungen und bekannte Grenzen. Erst eine tatsächlich erfolgte Freigabe macht aus dem vorbereiteten Entwurf die vorgesehene Ausgabe.

Die spätere Einrichtung auf einem Arbeitsplatz ist ein weiterer Vorgang. Ein veröffentlichtes Paket ist noch nicht automatisch auf jedem Ziel installiert. Ebenso beweist ein lokal laufender Entwicklungsstand nicht, dass seine Dateien bereits als Release bereitgestellt wurden.

Dieses Beispiel wurde nicht praktisch durchgeführt. Es wurde weder ein Release angelegt noch ein Tag gesetzt, ein Paket veröffentlicht oder ein Zielsystem aktualisiert.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine Version kennzeichnet einen Stand. Ein Build erzeugt Dateien. Ein Release gibt eine ausgewählte Ausgabe frei. Ein Deployment richtet Software für eine Zielumgebung ein. Diese Schritte können automatisiert verbunden sein, ihre jeweiligen Ergebnisse müssen trotzdem gesondert nachgewiesen werden.

## 8. Häufige Missverständnisse

Ein Tag ist nicht automatisch eine vollständige Releasebeschreibung. Ein Entwurf ist keine bereits erfolgte Freigabe. Eine neuere Versionsnummer garantiert nicht, dass alle bisherigen Schnittstellen unverändert bleiben. Auch können verschiedene Paketformate unterschiedliche Plattformvoraussetzungen besitzen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Lies Freigabehinweise und prüfe Herkunft sowie Zuordnung der Dateien. Verwechsle eine Vorabversion nicht mit einer für deinen Zweck geprüften Ausgabe. Dieses Dokument erklärt die Begriffe und verändert selbst keine Veröffentlichung oder installierte Version.
