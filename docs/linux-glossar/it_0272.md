# Abhängigkeiten

## 1. Kurzbeschreibung

Abhängigkeiten sind Komponenten, die Software für einen bestimmten Zweck voraussetzt. Dazu zählen Bibliotheken, externe Programme und manchmal eine geeignete Laufzeitumgebung. Ob du eine Komponente wirklich brauchst, hängt davon ab, welche Funktion du nutzen oder welchen Arbeitsschritt du ausführen willst.

## 2. Was bedeutet der Begriff?

„Extern“ beschreibt die Zuständigkeit. Eine Anwendung kann eine Funktion aus einer anderen Bibliothek verwenden, statt sie selbst mitzuliefern. Benötigt sie eine Mindestversion, gehört auch diese Anforderung zur Abhängigkeit. Der Komponentenname allein sagt noch nichts darüber aus, welche Ausgaben zusammenarbeiten.

## 3. Einfacher Vergleich aus dem Alltag

Ein Beamer braucht Strom, um ein Bild zu zeigen. Ein Lautsprecher ist für eine Vorführung mit Ton sinnvoll, für stumme Folien kann er entfallen. Software kann solche Unterschiede ausdrücklich in ihren Metadaten festhalten. Anders als bei einer Steckdose kann eine Bibliothek selbst weitere Bibliotheken anfordern.

## 4. Wie funktioniert das?

Debian unterscheidet etwa `Depends`, `Recommends` und `Suggests`. Die [Debian-Paketbeziehungen](https://www.debian.org/doc/debian-policy/ch-relationships.html) erklären, wann ein Eintrag in eines dieser Felder gehört. Eine Python-Distribution kann reguläre Abhängigkeiten und zusätzliche Gruppen für bestimmte Funktionen deklarieren. Die [PyPA-Spezifikation für pyproject.toml](https://packaging.python.org/en/latest/specifications/pyproject-toml/) beschreibt dafür `dependencies` und `optional-dependencies`.
Unterscheide direkte und transitive Abhängigkeiten. Deine Anwendung benutzt A direkt. Wenn A wiederum B benötigt, hängt die Anwendung indirekt von B ab. Ein Paketwerkzeug muss die gesamte Kette berücksichtigen. Unvereinbare Versionsanforderungen können die Auflösung verhindern.

## 5. Wo begegnet mir das unter Linux?

Unter Linux sind Build- und Laufzeitbedarf oft verschieden. Ein Compiler kann zur Erstellung einer Bibliothek erforderlich sein, während die installierte Anwendung nur deren Laufzeitdateien braucht. Welche Pakete dazugehören, hängt von Distribution und Paketformat ab.

## 6. Konkretes Beispiel Schritt für Schritt

Gedankenbeispiel ohne Installation. Eine erfundene Anwendung zeigt vorhandene Mitschnittdateien an und kann zusätzlich selbst Mitschnitte anstoßen.

1. Die Bibliothek zum Lesen des Dateiformats wird immer gebraucht und gehört zu den Kernvoraussetzungen.
2. Ein externes Mitschnittwerkzeug ist in diesem Entwurf nur für die Zusatzfunktion vorgesehen. Die Anwendung kann diesen Teil bei fehlendem Werkzeug gezielt deaktivieren und den Grund anzeigen.
3. Angenommen, das Werkzeug verlangt zusätzlich Rechte für eine Netzwerkschnittstelle. Die Installation allein würde diese Voraussetzungen nicht nachweisen. Für jede Funktion wäre ein eigener Test nötig.

Das Beispiel aus der Quelle mit Wireshark ist eine mögliche Zuordnung. Daraus lässt sich die tatsächliche Ausstattung eines NetMon-Pakets nicht ablesen.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine optionale Funktion kann eine zwingende Voraussetzung haben, sobald sie eingeschaltet wird. Eine Empfehlung drückt je nach Paketformat einen anderen Grad der Notwendigkeit aus. Eine Versionsangabe grenzt kompatible Ausgaben ein und ersetzt keine Funktionsprüfung.

## 8. Häufige Missverständnisse

Eine vorhandene Bibliothek muss zur Architektur und zur erwarteten Schnittstelle passen. Auch zwei Programme mit gleichnamigen Funktionen sind nicht automatisch austauschbar. Ein erfolgreicher Build weist nur nach, dass seine Voraussetzungen erfüllt waren.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Suche bei einer Fehlermeldung nach der konkreten fehlenden Komponente und der geforderten Version. Prüfe, wer sie verwaltet. Systempakete und Bibliotheken in einer Python-Umgebung landen in unterschiedlichen Zuständigkeitsbereichen.
