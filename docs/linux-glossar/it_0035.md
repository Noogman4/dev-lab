# Version

## 1. Kurzbeschreibung

Eine Version kennzeichnet einen bestimmten Stand von Software oder Daten. Häufig besteht die Kennzeichnung aus Zahlen wie `1.2.3`, manchmal aus einem Datum oder zusätzlichen Buchstaben. Die Bedeutung und Reihenfolge ergeben sich aus dem verwendeten Versionsschema. Eine vertraut aussehende Nummer ist kein allgemeiner Beweis für Kompatibilität, Qualität oder eine bereits erfolgte Veröffentlichung.

## 2. Was bedeutet der Begriff?

Versionsangaben helfen, Fehlerberichte, Abhängigkeiten und bereitgestellte Dateien einem Stand zuzuordnen. „Es funktioniert nicht“ wird aussagekräftiger, wenn klar ist, welche Version verwendet wurde. Bei Paketierung können außerdem die Version des ursprünglichen Projekts und eine zusätzliche Paketrevision relevant sein.

Zu einer Versionsnummer können mehrere Artefakte gehören, etwa Pakete für unterschiedliche Plattformen. Auch zwei Builds desselben Quellenstands können verschiedene Dateiinhalte ergeben. Für die genaue Zuordnung eines Artefakts helfen Quellenstand und Prüfsumme. Nach den [SemVer-Regeln](https://semver.org/spec/v2.0.0.html) brauchen Änderungen am Inhalt eines bereits veröffentlichten Pakets eine neue Versionsnummer.

## 3. Einfacher Vergleich aus dem Alltag

Eine nummerierte Auflage eines Handbuchs hilft, dieselbe Ausgabe zu erkennen. Die Seitenangabe einer älteren Auflage passt vielleicht nicht mehr zu einer späteren. Die Kennzeichnung schafft einen Bezug zwischen Hinweis und verwendetem Dokument.

Die Grenze des Vergleichs: Software kann mehrere Komponenten mit eigenen Versionen kombinieren. Außerdem können unterschiedliche Anbieter dasselbe Grundprodukt anders paketieren. Eine einzelne sichtbare Nummer erklärt daher nicht zwangsläufig den vollständigen Zustand der installierten Umgebung.

## 4. Wie funktioniert das?

Ein Versionsschema legt Form, Vergleich und gegebenenfalls Bedeutung einzelner Teile fest. Semantic Versioning 2.0.0 unterscheidet etwa Haupt-, Neben- und Korrekturversion und verbindet Änderungen mit einer deklarierten öffentlichen Schnittstelle. Die [offizielle SemVer-Spezifikation](https://semver.org/spec/v2.0.0.html) beschreibt diese Regeln einschließlich Vorabkennzeichnungen. Sie gelten nicht automatisch für jedes Projekt mit drei Zahlen.

Python-Paketversionen besitzen eigene Regeln, wie sie beispielsweise [PEP 440 im Versionsschema](https://peps.python.org/pep-0440/#version-scheme) beschreibt. Dazu gehören unter anderem Entwicklungs- und Vorabversionen sowie numerische Vergleichsregeln. Ein allgemeiner Textvergleich bildet solche Regeln nicht zuverlässig ab. Für tatsächliche Paketentscheidungen ist ein zum verwendeten Format passendes Werkzeug erforderlich.

## 5. Wo begegnet mir das unter Linux?

Paketverwaltungen, Anwendungsdialoge und Fehlerberichte zeigen Versionsangaben. Bei einer Diagnose können zusätzlich Interpreter, Bibliotheken und Distribution relevant sein. Zwei Nutzer derselben Anwendungsnummer müssen daher nicht dieselben Voraussetzungen haben.

Auch Abhängigkeiten können Mindest- oder Ausschlussversionen nennen. Eine größere Nummer bedeutet dabei nicht automatisch, dass jede ältere Schnittstelle erhalten bleibt. Lies die Regeln und Freigabehinweise des betroffenen Projekts, statt aus der Form der Zahl eine Kompatibilitätsgarantie abzuleiten.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Python-3-Beispiel demonstriert nur den Unterschied zwischen Text- und Zahlvergleich für zwei bereits festgelegte dreiteilige Zahlenfolgen:

```python
alt = "1.9.0"
neu = "1.10.0"
textvergleich = neu > alt
alt_zahlen = tuple(int(teil) for teil in alt.split("."))
neu_zahlen = tuple(int(teil) for teil in neu.split("."))
zahlenvergleich = neu_zahlen > alt_zahlen
assert textvergleich is False
assert zahlenvergleich is True
print(textvergleich)
print(zahlenvergleich)
```

Die Ausgabe lautet:

```text
False
True
```

Der Textvergleich betrachtet Zeichen und ordnet den Beginn `1.1` anders ein als `1.9`. Der Vergleich der Zahlentupel behandelt dagegen zehn als größer als neun. Das zeigt den Fallstrick, ist aber ausdrücklich kein vollständiger Versionsparser.

Das Beispiel unterstützt weder Vorabkennzeichnungen noch Paketrevisionen, lokale Versionsanteile oder beliebige fremde Eingaben. Es darf nicht als Ersatz für SemVer-, Python-Paket- oder Distributionsregeln übernommen werden.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine Version bezeichnet einen Stand. Ein Release gibt eine ausgewählte Ausgabe frei. Ein Build erzeugt ein bestimmtes Artefakt. Ein Commit kennzeichnet einen Stand in der Versionsverwaltung. Eine Prüfsumme beschreibt Dateiinhalte. Diese Angaben können zusammengehören, sind aber nicht austauschbar.

## 8. Häufige Missverständnisse

Drei Zahlen bedeuten nicht automatisch SemVer. Eine neue Hauptversion muss nicht abwärtskompatibel sein. Ein Datum ist ohne festgelegtes Format kein universell korrekt sortierbarer Versionswert. Auch ist eine lokale Entwicklungsänderung nicht automatisch durch die zuletzt veröffentlichte Versionsnummer vollständig beschrieben.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Notiere bei Berichten die tatsächlich verwendeten Stände. Verwende für echte Abhängigkeitsentscheidungen den vorgesehenen Versionsvergleich. Teste wichtige Schnittstellen nach Aktualisierungen. Das Lernbeispiel verarbeitet nur zwei feste eigene Texte und verändert keine Pakete oder installierten Versionen.
