# Response

## 1. Kurzbeschreibung

Eine Response ist eine Antwort auf eine Anfrage im jeweiligen Kommunikationsmodell. Sie kann ein Ergebnis, einen Fehler oder weitere Informationen enthalten. Bei HTTP gehören Status und Nachrichtenfelder dazu; Inhalt ist abhängig vom Fall möglich. Eine Response ist deshalb nicht einfach gleichbedeutend mit einer JSON-Zeichenkette oder einem vollständigen fachlichen Erfolg.

## 2. Was bedeutet der Begriff?

„Response“ bedeutet Antwort. Das Katalogbeispiel einer JSON-Antwort ist ein verbreiteter API-Fall. Andere Antworten können Text, Binärdaten oder nach den Protokollregeln keinen Inhalt enthalten. Format und Bedeutung müssen aus der Schnittstelle hervorgehen.

[RFC 9110 zum Nachrichteninhalt](https://www.rfc-editor.org/rfc/rfc9110.html#section-6.4) erläutert dessen Bedeutung abhängig von Methode und Status. Ein erfolgreich gelesener Körper ist also nicht automatisch das gesamte Ergebnis. Status und Felder können für die richtige Interpretation ebenso entscheidend sein.

## 3. Einfacher Vergleich aus dem Alltag

Auf einen Arbeitsauftrag kommt ein Antwortschreiben mit einer Einordnung und gegebenenfalls Anlagen zurück. „Auftrag abgelehnt“ ist ebenfalls eine Antwort, obwohl die gewünschte Leistung nicht erbracht wurde. Fehlt das Schreiben vollständig, ist die Situation nochmals anders.

Die Grenze: Protokolle definieren genaue Formate. Eine Antwort darf nicht allein nach einem freundlich klingenden Text beurteilt werden. Auch können technische Zwischenstellen Antworten liefern, bevor die eigentliche Anwendung den gewünschten Inhalt bereitstellt. Herkunft und Kontext bleiben wichtig.

## 4. Wie funktioniert das?

Eine Gegenstelle erstellt die passende Nachricht zur Verarbeitung einer Anfrage. Bei HTTP beschreibt der Status deren Einordnung. Felder können beispielsweise Inhaltstyp oder weitere Verarbeitungsbedingungen nennen. Die genaue Darstellung unterscheidet sich zwischen HTTP-Versionen.

[RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html) beschreibt die HTTP/1.1-Nachrichtensyntax mit Startzeile, Feldern und abgegrenztem Körper. Eine Darstellung als Text in einem Lernbeispiel ist deshalb nicht automatisch eine vollständige, korrekt übertragene Antwort jeder HTTP-Version.

Bei JSON muss anschließend zusätzlich die Datenstruktur zur API passen. Ein leeres Objekt kann syntaktisch gültig sein, aber erforderliche Fachfelder vermissen lassen. Transport, Nachrichtenformat und fachlicher Vertrag sind unterschiedliche Prüfebenen.

## 5. Wo begegnet mir das unter Linux?

Browser und Anwendungen verarbeiten Antworten verschiedener Dienste. Bibliotheken können Status, Felder und Inhalt getrennt zugänglich machen. Eine Fehlermeldung beim Verbindungsaufbau ist von einer tatsächlich empfangenen HTTP-Fehlerantwort zu unterscheiden.

Python bietet mit [http.client.parse_headers](https://docs.python.org/3.13/library/http.client.html#http.client.parse_headers) eine Funktion zum Lesen entsprechender Feldzeilen aus einem binären Datenstrom. Sie liest nicht selbst die HTTP-Startzeile und ist kein vollständiger HTTP-Client. Genau diese begrenzte Aufgabe wird unten verwendet.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Ordner ausgeführt. Alle Antwortbytes sind selbst erzeugt und liegen ausschließlich im Speicher. Kein Server und kein Socket sind beteiligt.

```python
from http.client import parse_headers
from io import BytesIO
import json

roh = (
    b"HTTP/1.1 200 OK\r\n"
    b"Content-Type: application/json\r\n"
    b"Content-Length: 2\r\n\r\n{}"
)
with BytesIO(roh) as quelle:
    start = quelle.readline()
    assert start == b"HTTP/1.1 200 OK\r\n"
    felder = parse_headers(quelle)
    inhalt = quelle.read()
assert felder["Content-Type"] == "application/json"
assert int(felder["Content-Length"]) == len(inhalt) == 2
assert json.loads(inhalt) == {}
print(start.decode("ascii").strip())
print(felder["Content-Type"])
print(inhalt.decode("ascii"))
```

Geprüfte Ausgabe:

```text
HTTP/1.1 200 OK
application/json
{}
```

Die Startzeile wird ausdrücklich getrennt gelesen. Danach verarbeitet die Bibliothek die Felder. Der eigene Inhalt umfasst genau zwei Byte und ist ein gültiges leeres JSON-Objekt. Das beweist keine echte API-Antwort und keine vollständige HTTP-Parserimplementierung für beliebige Eingaben. Eine fachliche Temperaturangabe wäre darin beispielsweise nicht enthalten.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Request ist die Anfrage, eine Response die Antwort. Ein Statuscode ist ein Teil der HTTP-Einordnung. JSON ist ein Datenformat. Ein Paket ist eine andere Übertragungseinheit und muss nicht eine ganze Antwort enthalten. Ein Prozess-Exit-Code gehört wiederum zu einer anderen Schnittstelle.

## 8. Häufige Missverständnisse

Eine Fehlerantwort ist nicht dasselbe wie gar keine Antwort. `200` beweist nicht automatisch richtige Fachwerte. Eine JSON-Antwort garantiert auch kein bestimmtes Objektschema. Ein leerer Körper darf schließlich nur im Zusammenhang mit den Regeln der jeweiligen Methode und Antwort interpretiert werden.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe Status, relevante Felder und Inhalt gemeinsam. Begrenze reale Eingaben und behandle Fehler nach dem Schnittstellenvertrag. Das Beispiel verarbeitet nur eigene Bytes und verändert weder Netzwerkverbindungen noch Konten, Dienste oder Anwendungsdaten.

## 10. Verwandte Begriffe

Der [Request](it_0172.md) ist der Ausgangspunkt des Austauschs. [HTTP](it_0145.md) definiert Nachrichtenregeln. Die [API](it_0169.md) beschreibt Fachanforderungen. Ein [Packet](it_0163.md) kann nur einen Teil der Übertragung enthalten. Der [Exit-Code](it_0137.md) ist kein HTTP-Status.
