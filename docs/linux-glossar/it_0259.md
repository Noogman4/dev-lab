# Thread

## 1. Kurzbeschreibung

Ein Thread ist ein Ausführungsstrang innerhalb eines Prozesses. Mehrere Threads können Aufgaben nebenläufig bearbeiten und dabei auf gemeinsamen Speicher zugreifen. Sie sind nicht automatisch voneinander isolierte Programme. Welche Arbeit tatsächlich parallel läuft und welche Synchronisierung nötig ist, hängt von Laufzeit, Aufgabe und gemeinsam verwendeten Daten ab.

## 2. Was bedeutet der Begriff?

Die Quelle nennt einen Hintergrundscan neben einer reagierenden GUI. Ein Thread kann dafür ein möglicher Baustein sein. Die Oberfläche bleibt aber nicht allein durch das Anlegen eines Threads automatisch korrekt und reaktionsfähig. Kommunikation, Zuständigkeiten und Beenden müssen passend umgesetzt werden.

Die [Linux-man-pages-Übersicht zu POSIX-Threads](https://man7.org/linux/man-pages/man7/pthreads.7.html) beschreibt gemeinsame Prozessressourcen und eigene Thread-Stacks. Ein eigener Ausführungsstrang besitzt somit einen eigenen Ablauf, während viele Ressourcen weiterhin zum selben Prozess gehören. Das erklärt sowohl effiziente Zusammenarbeit als auch mögliche gegenseitige Beeinflussung.

## 3. Einfacher Vergleich aus dem Alltag

Mehrere Personen arbeiten in derselben Werkstatt an verschiedenen Aufträgen. Jede hat ihren eigenen Ablauf, benutzt aber gemeinsame Werkzeuge und Bestände. Eine Person kann warten, während eine andere weiterarbeitet.

Die Grenze: Gemeinsame Materialien können zu Konflikten führen. Auch kann die Werkstatt nur eine bestimmte Anzahl von Aufgaben wirklich gleichzeitig bedienen. In Software entscheiden zusätzlich Betriebssystem und Laufzeit über die Ausführung. Mehr Beteiligte bedeuten daher nicht automatisch mehr Geschwindigkeit oder unabhängige Sicherheit.

## 4. Wie funktioniert das?

Ein Programm startet einen Thread mit einer vorgesehenen Aufgabe. Der Thread führt seinen Ablauf aus und kann Ergebnisse über einen vereinbarten Weg bereitstellen. Gemeinsame veränderliche Daten benötigen passende Regeln. Ein Ergebnis sollte nicht zufällig gelesen werden, bevor seine Bereitstellung abgeschlossen ist.

Für CPython erläutert die [Python-3.13-Dokumentation zu GIL und Leistung](https://docs.python.org/3.13/library/threading.html#gil-and-performance-considerations) die Einschränkung gleichzeitiger Python-Bytecodeausführung im üblichen GIL-Betrieb. I/O-geprägte Arbeit und bestimmte Erweiterungen sind anders zu betrachten. Zudem existieren in Python 3.13 experimentelle Free-Threaded-Builds. Eine pauschale Aussage über alle Python-Versionen und Builds wäre deshalb falsch.

Zum Abschluss kann ein anderer Thread warten. Die [Dokumentation zu Thread.join](https://docs.python.org/3.13/library/threading.html#threading.Thread.join) beschreibt auch Zeitgrenzen: Danach muss mit `is_alive` geprüft werden, ob der Thread tatsächlich beendet ist. `join` beendet ihn nicht gewaltsam und bedeutet nicht automatisch fachlichen Erfolg seiner Arbeit.

Auch unbehandelte Fehler benötigen einen vorgesehenen Meldeweg. Ein Thread kann beendet sein, weil seine Aufgabe gescheitert ist. Das folgende Beispiel prüft deshalb neben dem Ende auch das erwartete Ergebnis und die zugehörigen Kennungen.

## 5. Wo begegnet mir das unter Linux?

Anwendungen und Bibliotheken verwenden Threads für verschiedene Aufgaben. Ein Worker kann dabei innerhalb desselben Programms laufen. Ein eigener Thread ist weder ein eigener Betriebssystembenutzer noch eine vollständige Sicherheits-Sandbox.

Bei grafischen Programmen müssen Rückmeldungen über die vorgesehenen Frameworkwege erfolgen. Ein Hintergrundthread sollte nicht allein aus Bequemlichkeit beliebige Oberflächenobjekte verändern. Hier wird keine GUI gestartet und keine bestehende Threadstruktur der Anwendung untersucht.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Ein eigener Thread verarbeitet nur den Text „Probe“. Es werden keine Netzwerke, Dateien oder Dienste angesprochen.

```python
import os
from threading import Thread, get_ident

hauptprozess = os.getpid()
hauptthread = get_ident()
ergebnisse = []

def arbeiten():
    ergebnisse.append((os.getpid(), get_ident(), "Probe".upper()))

worker = Thread(target=arbeiten)
worker.start()
worker.join(timeout=1)
assert not worker.is_alive()
assert len(ergebnisse) == 1
prozess, thread, text = ergebnisse[0]
assert prozess == hauptprozess and thread != hauptthread
assert text == "PROBE"
print("Gleicher Prozess:", prozess == hauptprozess)
print("Anderer Thread:", thread != hauptthread)
print("Ergebnis:", text)
```

Geprüfte Ausgabe:

```text
Gleicher Prozess: True
Anderer Thread: True
Ergebnis: PROBE
```

Die Ergebnisliste wird hier erst nach kontrolliertem Threadende gelesen. Der Versuch zeigt einen eigenen Thread im selben Prozess und sein erwartetes Ergebnis. Er ist kein Leistungstest und kein allgemeiner Nachweis, dass beliebige gemeinsame Daten ohne Synchronisierung sicher verwendet werden könnten.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Prozess besitzt einen eigenen Ausführungskontext mit eigenen Grenzen. Ein Thread gehört zu einem Prozess und teilt viele Ressourcen. Ein Queue Worker beschreibt eine Arbeitsrolle, die durch einen Thread umgesetzt werden kann. Ein asynchroner Ablauf ist wiederum nicht automatisch ein zusätzlicher Thread.

## 8. Häufige Missverständnisse

Ein Thread ist keine automatische Prozessisolierung. Ein gestarteter Thread garantiert keine Beschleunigung. `join` mit Zeitgrenze garantiert kein erzwungenes Ende. Und ein beendeter Thread kann trotzdem einen Fehler erlebt haben.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Definiere Datenübergabe, Fehlerbehandlung und Beenden ausdrücklich. Prüfe tatsächlich erwartete Ergebnisse. Das Beispiel startet nur einen eigenen kurzlebigen Thread, kontrolliert dessen Ende und verändert keine bestehenden Programme, Geräte oder Dienste.
