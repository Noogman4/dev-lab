# Pull Request

## 1. Kurzbeschreibung

Ein Pull Request ist ein Vorschlag, Änderungen eines Entwicklungszweigs in einen anderen zu übernehmen. Ein Hostingdienst stellt dafür Vergleich, Beschreibung und Diskussion bereit. Die Beteiligten können den Inhalt prüfen und Änderungen verlangen. Das Eröffnen eines Pull Requests ist noch keine Integration in den Zielbranch und keine automatische Freigabe.

## 2. Was bedeutet der Begriff?

Die Quelle beschreibt einen Vorschlag, der geprüft und gemergt wird. Das ist ein möglicher erfolgreicher Ablauf. Ein Pull Request kann jedoch auch offen bleiben, überarbeitet oder ohne Übernahme geschlossen werden. Die eigentliche Entscheidung hängt vom Projekt und seinen Regeln ab.

Die [GitHub-Referenz zu Pull Requests](https://docs.github.com/en/pull-requests/reference/pull-requests) erläutert diesen Zusammenarbeitsvorgang. Er gehört zur Plattform, nicht zu den Grundobjekten des lokalen Git-Repositorys. Andere Dienste verwenden teilweise andere Namen und können abweichende Arbeitsabläufe anbieten. Hier beziehen sich konkrete Plattformangaben ausdrücklich auf GitHub.

## 3. Einfacher Vergleich aus dem Alltag

Eine Redaktion erhält einen Änderungsvorschlag für ihr Handbuch. Sie sieht die betroffenen Abschnitte, eine Begründung und gegebenenfalls Prüfergebnisse. Die Beteiligten können Rückfragen stellen, bevor die neue Fassung in die maßgebliche Ausgabe gelangt.

Die Grenze: Eine Plattformdiskussion ist kein automatisch bindender Vertrag und keine selbsttätige Fachprüfung. Ein grünes Prüfsymbol sagt nur etwas über die tatsächlich ausgeführten Prüfungen aus. Ob sie die relevante Anforderung abdecken, müssen die Beteiligten weiterhin beurteilen.

## 4. Wie funktioniert das?

Ein Pull Request vergleicht eine Quellseite mit einem Zielbranch. Auf GitHub werden dafür häufig die Begriffe Head und Base verwendet. Eine falsche Basis kann einen unpassenden Umfang zeigen. Deshalb müssen nicht nur Titel und einzelne Dateien, sondern auch Vergleichsrichtung und Ausgangspunkt stimmen.

Weitere Commits auf dem Quellbranch können den vorgeschlagenen Inhalt verändern. Ein Review bezieht sich daher auf einen konkreten Prüfstand; nach wesentlichen Änderungen kann erneute Prüfung nötig sein. Welche Freigaben technisch erforderlich sind, hängt von den eingestellten Regeln ab. Nicht jedes Repository verlangt dieselben Prüfungen.

GitHub unterscheidet außerdem Entwürfe und zur Prüfung bereite Pull Requests. Die [Dokumentation zum Wechsel des Bearbeitungsstands](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/changing-the-stage-of-a-pull-request) erläutert diese Zustände. „Ready for review“ heißt bereit für Rückmeldung, nicht bereits fachlich genehmigt. Ein späterer Integrationsschritt ist davon zu unterscheiden.

## 5. Wo begegnet mir das unter Linux?

Die lokale Arbeit erfolgt oft im Editor und mit Git. Der Pull Request wird zusätzlich auf einem Hostingdienst angezeigt oder über dessen Werkzeuge verwaltet. Ein lokaler Commit allein erzeugt keinen solchen Vorschlag.

Auch ein Push bedeutet nicht zwingend, dass ein neuer Pull Request eröffnet wurde. Er kann lediglich den Branch eines bereits bestehenden Vorschlags aktualisieren. Benachrichtigungen, Prüfabläufe und Berechtigungen gehören zur jeweiligen Dienstkonfiguration und werden hier nicht eingerichtet.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenbeispiel wurde nicht als neuer Plattformvorgang ausgeführt. Es beschreibt eine erfundene Handbuchkorrektur und enthält weder Nachrichtenversand noch Reviewer-Zuweisungen oder eine Integration.

Zuerst korrigiert eine Mitwirkende einen Tippfehler auf einem eigenen Branch. Sie prüft, dass nur die beabsichtigte Textdatei betroffen ist, und speichert einen Commit. Anschließend stellt sie diesen Branch am vereinbarten Austauschort bereit.

Danach formuliert sie einen Vorschlag: Welche Stelle war falsch, wie lautet die Korrektur, und was wurde geprüft? Als Quelle wird ihr Korrekturbranch gewählt, als Ziel der passende Handbuchbranch. Eine falsche Zielbasis könnte weitere, hier gar nicht gemeinte Änderungen in den Vergleich bringen.

Die Redaktion liest den Unterschied und entdeckt eine zweite betroffene Formulierung. Die Mitwirkende ergänzt einen weiteren Commit. Nun muss die aktualisierte Fassung geprüft werden; eine frühere Rückmeldung bezog sich noch nicht automatisch auf diesen zusätzlichen Inhalt.

Schließlich entscheidet die Redaktion über die Übernahme. Sie kann zustimmen, weitere Änderungen verlangen oder den Vorschlag schließen. Selbst eine Zustimmung muss nicht bedeuten, dass die technische Integration bereits erfolgt ist. Das Beispiel behauptet keine tatsächlich ausgeführte Prüfung oder Plattformaktion.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Commit ist ein Git-Objekt. Ein Branch bezeichnet einen Entwicklungsstand. Ein Push überträgt Versionsdaten. Ein Pull holt und integriert nach dem gewählten Verfahren. Ein Pull Request organisiert dagegen den Vorschlag und seine Prüfung auf einer Plattform. Der ähnliche Name macht ihn nicht zu einem bloßen `git pull`.

## 8. Häufige Missverständnisse

Ein Pull Request wird nicht immer gemergt. Ein Entwurf ist keine fachliche Freigabe. Ein bestandener automatischer Test ersetzt nicht alle Reviews. Und ein aktualisierter Quellbranch kann den bereits besprochenen Umfang nachträglich verändern.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Halte Ziel, Umfang und Prüfaussagen konkret. Kennzeichne offene Punkte und tatsächlich nicht ausgeführte Tests. Prüfe den aktuellen Unterschied vor einer Integration erneut. Für dieses Glossarbeispiel werden keine gemeinsamen Branches geändert und keine Plattformbenachrichtigungen ausgelöst.

## 10. Verwandte Begriffe

[Branch](it_0208.md) bezeichnet Quelle und Ziel. [Commit](it_0207.md) speichert Änderungen. [Push](it_0211.md) stellt Versionsarbeit bereit. [Merge](it_0209.md) ist ein Integrationsverfahren. [Fork](it_0213.md) kann den eigenen Ausgangsort bilden.
