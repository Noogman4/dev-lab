# Fremdschlüssel

## 1. Kurzbeschreibung

Ein Fremdschlüssel ist eine festgelegte Beziehung zwischen Datenbankwerten. Er verlangt, dass ein eingetragener Verweis zu einem zulässigen Schlüsselwert der referenzierten Tabelle passt. So lässt sich verhindern, dass beispielsweise eine Bestellung auf einen unbekannten Kunden verweist. Ein passender Spaltenname allein stellt diese Beziehung noch nicht her.

## 2. Was bedeutet der Begriff?

Im Katalog verweist `user_id` auf `users.id`. Das ist eine typische Modellierung: Eine Tabelle enthält die eigentlichen Benutzerangaben, eine andere deren Kennung als Verweis. Die referenzierte Kennung muss nach den Regeln des Datenbanksystems geeignet eindeutig sein; häufig ist sie ein Primärschlüssel.

Die [PostgreSQL-Dokumentation zu Fremdschlüsseln](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK) erläutert diese referenzielle Integrität. Sie beschreibt auch mehrteilige und selbstbezügliche Beziehungen. Ein Fremdschlüssel muss deshalb nicht immer auf eine andere Tabelle zeigen: Eine Hierarchie kann innerhalb derselben Tabelle auf einen übergeordneten Eintrag verweisen.

## 3. Einfacher Vergleich aus dem Alltag

Auf einem Ausleihzettel steht die Nummer einer vorhandenen Bibliothekskarte. Die Bibliothek kann prüfen, ob diese Nummer im Kartenverzeichnis existiert. Namen müssen nicht auf jedem Zettel erneut vollständig abgeschrieben werden.

Die Grenze: Eine existierende Karte beweist nicht, dass die richtige Person vor dir steht oder ausleihen darf. Ebenso prüft ein Fremdschlüssel eine definierte Datenbeziehung, keine vollständige fachliche Berechtigung. Ein technisch gültiger Verweis kann immer noch dem falschen Benutzer zugeordnet worden sein.

## 4. Wie funktioniert das?

Die Beziehung wird im Schema erklärt, etwa mit `REFERENCES`. Bei relevanten Änderungen kontrolliert die Datenbank die Bedingungen. Wann genau eine Prüfung erfolgt, kann vom System und einer ausdrücklich gewählten aufgeschobenen Prüfung abhängen. Das folgende Beispiel verwendet die unmittelbare Prüfung.

Fehlende Werte verdienen besondere Aufmerksamkeit. Ein nullable Fremdschlüssel kann eine noch nicht zugeordnete Beziehung ausdrücken. Soll eine Zuordnung verpflichtend sein, braucht sie zusätzliche Bedingungen wie `NOT NULL`. Außerdem bedeutet ein Fremdschlüssel nicht automatisch, dass abhängige Datensätze beim Löschen mitgelöscht werden. Solche Aktionen müssen passend festgelegt werden.

Die [SQLite-Dokumentation zu Fremdschlüsseln](https://www.sqlite.org/foreignkeys.html) erklärt die verbindungsbezogene Aktivierung mit `PRAGMA foreign_keys`. Auf einen vermuteten Standardwert sollte man sich nicht verlassen. Eine Änderung dieser Einstellung während einer laufenden Mehranweisungstransaktion hat dort keine Wirkung. Das Beispiel aktiviert und kontrolliert sie deshalb gleich nach dem Verbindungsaufbau.

## 5. Wo begegnet mir das unter Linux?

Lokale Anwendungen können zusammengehörige Angaben über Tabellen verteilen. Eine Fehlermeldung zu einer Fremdschlüsselbedingung kann auf eine fehlende zugehörige Kennung hindeuten. Sie ist kein Anlass, die Prüfung einfach abzuschalten.

Bei Importen oder Strukturänderungen müssen Daten und Beziehungen zusammenpassen. Das betrifft auch die Reihenfolge von Einfügungen. Hier werden ausschließlich eigene Speicherdaten verwendet; keine bestehenden Anwendungsdaten werden untersucht oder verändert.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel verwendet eine eigene Datenbank im Arbeitsspeicher. `autocommit=True` startet die Verbindung ohne offene Transaktion. So kann die Fremdschlüsselprüfung sofort aktiviert und abgefragt werden. Der Parameter ist ab Python 3.12 verfügbar. [Python-Dokumentation zu `sqlite3.connect`](https://docs.python.org/3.13/library/sqlite3.html#sqlite3.connect)

```python
from contextlib import closing
import sqlite3

with closing(sqlite3.connect(":memory:", autocommit=True)) as db:
    db.execute("PRAGMA foreign_keys = ON")
    assert db.execute("PRAGMA foreign_keys").fetchone() == (1,)
    db.execute("CREATE TABLE personen (id INTEGER PRIMARY KEY)")
    db.execute("""CREATE TABLE notizen (
        id INTEGER PRIMARY KEY,
        person_id INTEGER NOT NULL REFERENCES personen(id)
    )""")
    db.execute("INSERT INTO personen VALUES (1)")
    db.execute("INSERT INTO notizen VALUES (1, 1)")
    abgelehnt = False
    try:
        db.execute("INSERT INTO notizen VALUES (2, 999)")
    except sqlite3.IntegrityError:
        abgelehnt = True
    assert abgelehnt
    assert db.execute("SELECT person_id FROM notizen").fetchall() == [(1,)]
    print("Fremdschlüsselprüfung aktiv:", True)
    print("Unbekannte Person abgelehnt:", abgelehnt)
```

Geprüfte Ausgabe:

```text
Fremdschlüsselprüfung aktiv: True
Unbekannte Person abgelehnt: True
```

Die Kennung 1 ist vorhanden, 999 nicht. Das Beispiel prüft weder Löschkaskaden noch aufgeschobene Bedingungen, Importwerkzeuge oder Mehrbenutzerbetrieb.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Primärschlüssel identifiziert Zeilen der eigenen Tabelle. Ein Fremdschlüssel sichert einen Verweis ab. Ein JOIN verbindet Daten für ein Abfrageergebnis; er legt für sich genommen keine dauerhafte Fremdschlüsselbedingung an. Ein gewöhnlicher Index ist ebenfalls keine solche Beziehung.

## 8. Häufige Missverständnisse

`user_id` als Name reicht nicht aus. Ein Verweis ist keine Zugriffserlaubnis. Eine Beziehung muss nicht automatisch verpflichtend sein. Und eine vorhandene SQLite-Deklaration beweist ohne Prüfung der Verbindungseinstellung noch nicht, dass sie gerade durchgesetzt wird.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe Aktivierung, passende Schlüssel und Löschregeln zusammen. Fehler sollten an ihren Ursachen untersucht werden. Das Abschalten von Bedingungen kann verwaiste Verweise zulassen. Im Beispiel bleibt die Einstellung auf die neue temporäre Verbindung begrenzt.
