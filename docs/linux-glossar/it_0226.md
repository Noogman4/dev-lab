# Observer

## 1. Kurzbeschreibung

Observer bezeichnet ein Entwurfsmuster zur Benachrichtigung interessierter Teile über Änderungen oder Ereignisse. Beobachter melden ihr Interesse bei einer Quelle an. Die Quelle informiert sie nach einem vereinbarten Ablauf. Das kann wiederholtes Nachfragen vermeiden. Anmeldung, Zeitpunkt, Inhalt und Ende einer Verbindung müssen jedoch konkret geregelt sein.

## 2. Was bedeutet der Begriff?

Die Quelle nennt eine GUI, die sich bei einer Statusänderung aktualisiert. Dafür muss die Änderung an die Darstellung gelangen. Ein Observer-Ablauf kann diese Verbindung herstellen, ohne dass die Quelle sämtliche einzelnen Bildschirmdetails kennen muss.

Ein konkreter verwandter Mechanismus sind [Signale und Slots in Qt](https://doc.qt.io/qt-6/signalsandslots.html). Die Qt-Dokumentation beschreibt die Kommunikation zwischen Objekten und unterschiedliche Verbindungsarten. Das ist eine Frameworkumsetzung mit eigenen Regeln, kein Beleg dafür, dass jede selbst geschriebene Beobachterliste automatisch dieselben Garantien besitzt.

## 3. Einfacher Vergleich aus dem Alltag

Du meldest dich für eine Benachrichtigung an, sobald ein bestelltes Buch bereitliegt. Die Bibliothek informiert die angemeldeten Personen. Du musst nicht ständig selbst nachfragen, ob sich etwas geändert hat.

Die Grenze: Eine Softwarebenachrichtigung kann unmittelbar im selben Ablauf oder später über eine Warteschlange erfolgen. Es muss außerdem geklärt sein, was bei einer nicht erreichbaren oder fehlerhaften Empfängerseite geschieht. Die Anmeldung allein garantiert keine bestimmte Zustellzeit oder dauerhafte Speicherung der Nachricht.

## 4. Wie funktioniert das?

Die Quelle verwaltet interessierte Empfänger oder Verbindungen. Bei einer relevanten Änderung löst sie eine Benachrichtigung aus. Diese kann den neuen Wert enthalten oder nur signalisieren, dass der Empfänger aktuelle Daten abfragen soll. Welche Variante gilt, gehört zur Schnittstelle.

Auch unveränderte Werte brauchen eine Regel: Soll eine erneute Zuweisung desselben Werts eine weitere Nachricht erzeugen? Das Beispiel entscheidet sich dagegen. Das ist keine universelle Eigenschaft des Musters. Ebenso sind Reihenfolge, Fehlerbehandlung und Umgang mit An- oder Abmeldungen während der Benachrichtigung implementierungsabhängig.

Eine Verbindung sollte enden, wenn sie nicht mehr gebraucht wird. Die [Qt-Dokumentation zu QObject::disconnect](https://doc.qt.io/qt-6/qobject.html#disconnect) beschreibt dafür konkrete Funktionen und Überladungen. Bereits eingereihte Zustellungen und verschiedene Verbindungsarten müssen nach den Regeln der tatsächlich verwendeten Qt-Version betrachtet werden. Die eigene synchrone Python-Liste unten besitzt keine solche Warteschlange.

## 5. Wo begegnet mir das unter Linux?

Grafische Programme reagieren auf Statusänderungen, Eingaben oder neue Daten. Observer-ähnliche Mechanismen helfen, Verarbeitung und Anzeige zu verbinden. Eine Benachrichtigung bedeutet aber nicht automatisch, dass eine GUI aus beliebigen Threads sicher verändert werden darf. Dafür gelten zusätzliche Frameworkregeln.

Fehlende Abmeldungen oder unerwartet lange gehaltene Verbindungen können die Lebensdauer von Objekten beeinflussen. Doppelte Anmeldungen können außerdem zu mehrfacher Verarbeitung führen. Welche Fälle eine Bibliothek verhindert, muss konkret geprüft werden. Hier wird kein GUI- oder Threadverhalten abgenommen.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Es verwendet nur eigenen Speicherzustand und eine Liste gesammelter Meldungen. Die Wörter „scannt“ und „bereit“ sind Testwerte; es findet kein Scan statt.

```python
class Status:
    def __init__(self):
        self.wert = "bereit"
        self._beobachter = []

    def anmelden(self, funktion):
        self._beobachter.append(funktion)

    def abmelden(self, funktion):
        self._beobachter.remove(funktion)

    def setzen(self, wert):
        if wert == self.wert:
            return
        self.wert = wert
        for funktion in tuple(self._beobachter):
            funktion(wert)

meldungen = []
status = Status()
empfangen = meldungen.append
status.anmelden(empfangen)
status.setzen("scannt")
status.setzen("scannt")
status.setzen("bereit")
assert meldungen == ["scannt", "bereit"]
status.abmelden(empfangen)
status.setzen("pause")
assert meldungen == ["scannt", "bereit"] and status.wert == "pause"
print("Empfangene Änderungen:", len(meldungen))
print("Aktueller Zustand:", status.wert)
```

Geprüfte Ausgabe:

```text
Empfangene Änderungen: 2
Aktueller Zustand: pause
```

Die gleiche Zuweisung erzeugt hier keine zweite Meldung. Nach der Abmeldung wird die spätere Änderung nicht mehr gesammelt. Die einfache Liste implementiert keine vollständige Fehlerisolierung, Nebenläufigkeit oder Behandlung beliebiger Doppelanmeldungen. Ihre Ausführung ist synchron.

## 7. Abgrenzung zu ähnlichen Begriffen

Polling fragt wiederholt nach dem Zustand. Ein Observer lässt sich nach vereinbarten Regeln benachrichtigen. Eine Warteschlange kann Nachrichten zeitlich entkoppeln, ist aber nicht automatisch Bestandteil jedes Observers. MVC beschreibt eine weiter gefasste Rollenverteilung, in der Benachrichtigungen verwendet werden können.

## 8. Häufige Missverständnisse

Eine Anmeldung garantiert keine bestimmte Zustellzeit. Observer bedeutet nicht automatisch asynchron. Eine Statusmeldung startet keinen echten Scan. Und das Abmelden einer Verbindung hat nicht in jedem Framework dieselben Folgen für bereits geplante Zustellungen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Dokumentiere Lebensdauer, Nachricht und Ausführungsort. Kläre Fehler- und Abmelderegeln. Prüfe relevante Zustandsfolgen mit eigenen Daten. Das Beispiel ändert keine Dienste oder Geräte und verwendet keine installierte GUI-Bibliothek.
