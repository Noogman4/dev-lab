# Packet

## 1. Kurzbeschreibung

„Packet“ ist das englische Wort für Datenpaket. Gemeint ist eine abgegrenzte Übertragungseinheit innerhalb eines Netzwerkverfahrens. Ein Paket enthält Verwaltungsinformationen und gegebenenfalls Nutzdaten. Welche Felder und Grenzen gelten, hängt vom betrachteten Protokoll ab. Nicht jedes Paket entspricht einer vollständigen Nachricht, Datei oder einem einzelnen Funktionsaufruf einer Anwendung.

## 2. Was bedeutet der Begriff?

Im IP-Zusammenhang spricht man von IP-Paketen beziehungsweise Datagrammen. Die [IPv4-Grundspezifikation RFC 791](https://www.rfc-editor.org/rfc/rfc791.html) beschreibt dafür einen Kopf mit Angaben wie Version, Länge und Adressen. [RFC 8200](https://www.rfc-editor.org/rfc/rfc8200.html) definiert ein anderes Grundformat für IPv6.

Das Katalogbeispiel „Netzwerkdaten werden in Pakete zerlegt“ vermittelt die Grundidee. Ergänzend ist wichtig, welche Ebene betrachtet wird. Ein Ethernet-Rahmen, ein IP-Paket und eine Transportnachricht besitzen verschiedene Aufgaben und können ineinander eingebettet sein. Die alltägliche Bezeichnung „Paket“ wird dabei manchmal ungenau verwendet.

## 3. Einfacher Vergleich aus dem Alltag

Eine größere Sendung besteht aus einzelnen Umschlägen mit Zustellinformationen. In einem Umschlag kann wiederum eine anders beschriftete innere Sendung liegen. Die äußere und innere Verpackung erfüllen unterschiedliche Aufgaben.

Der Vergleich erklärt Verwaltungsdaten und Einbettung. Seine Grenze: Netzformate sind bitgenau definiert. Eine Dateigrenze ist außerdem nicht automatisch eine Paketgrenze. Verschlüsselung, Aufteilung und Wiederholung können dazu führen, dass der Inhalt einzelner Pakete nicht direkt als verständlicher Anwendungsauftrag lesbar ist.

## 4. Wie funktioniert das?

Ein Protokollkopf beschreibt, wie die nachfolgenden Daten einzuordnen sind. Beim Weiterreichen zwischen Ebenen kommen passende Angaben hinzu oder werden ausgewertet. Auf einer anderen Verbindung kann eine neue äußere Verpackung nötig sein, während der darüberliegende Kommunikationszusammenhang weiter besteht.

Größenbeschränkungen sind ebenfalls relevant. Je nach Protokoll und Weg muss eine Anwendung oder Netzwerkschicht damit umgehen. IPv4 und IPv6 besitzen unterschiedliche Fragmentierungsregeln: IPv6-Router führen die IPv4-artige Fragmentierung weitergeleiteter Pakete nicht einfach unverändert aus. Die Einzelheiten beschreibt RFC 8200.

Eine beobachtete Paketfolge ist deshalb nicht automatisch eine direkte Liste der Schreibaufrufe einer Anwendung. TCP stellt beispielsweise einen Bytestrom bereit, dessen Grenzen anders liegen können. Auch ein wiederholt übertragenes Stück bedeutet nicht zwingend, dass der Benutzer denselben Auftrag mehrfach abgeschickt hat.

## 5. Wo begegnet mir das unter Linux?

Netzwerkprogramme nutzen normalerweise Betriebssystemschnittstellen, statt jeden Kopf selbst zu bauen. Diagnosewerkzeuge können einzelne Einheiten und ihre Felder darstellen. Die angezeigte Struktur hängt dabei vom Aufzeichnungspunkt und den erkannten Protokollen ab.

Ein lesbarer Protokollkopf beweist keine vollständige Sicht auf den Anwendungsinhalt. Umgekehrt ist unlesbarer Inhalt nicht automatisch ein Fehler; er kann beispielsweise verschlüsselt oder binär kodiert sein. Für eine Interpretation müssen Protokoll und Kontext bekannt sein.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenmodell betrachtet ein vereinfachtes IPv4-Paket ohne Optionen. Es wurde nicht erzeugt oder gesendet. Für den UDP-Kopf beschreibt [RFC 768](https://www.rfc-editor.org/rfc/rfc768.html) vier Felder zu jeweils 16 Bit.

```text
IPv4-Kopf ohne Optionen: 20 Byte
UDP-Kopf:                8 Byte
Eigene Nutzdaten Probe:  5 Byte
Betrachtetes IP-Paket:  33 Byte
```

Die fünf ASCII-Zeichen von `Probe` benötigen in dieser Darstellung fünf Byte. Die Rechnung beschreibt nur die gewählte IP-Einheit. Ein zusätzlicher Ethernet-Rahmen und weitere Angaben auf der Verbindung sind darin nicht mitgezählt.

Das Modell ist kein vollständiger gültiger Paketbauplan. Prüfsummen, konkrete Feldwerte und eine reale Übertragung fehlen. Die Zahl 33 ist weder eine feste allgemeine Paketgröße noch eine Aussage über tatsächlich gemessenen Verkehr. Gerade diese Begrenzung zeigt, warum bei Größenangaben die betrachtete Ebene genannt werden muss.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Rahmen gehört zur jeweiligen Verbindungstechnik. Ein IP-Paket trägt Informationen für die Netzebene. TCP verwendet Segmente, UDP Datagramme. Eine Anwendung definiert darüber eigene Nachrichten. Dieselben Nutzdaten können auf diesen Ebenen unterschiedlich verpackt und aufgeteilt erscheinen.

## 8. Häufige Missverständnisse

Ein Paket enthält nicht automatisch eine ganze Webseite. Ein einzelner Sendeaufruf entspricht nicht immer einem späteren Empfangsblock. Alle Pakete haben außerdem nicht dieselbe Länge. Eine Prüfsumme garantiert schließlich nicht dieselbe Authentizität wie ein geeignetes kryptografisches Schutzverfahren.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Benenne bei einer Analyse Protokoll, Ebene und beobachteten Ausschnitt. Vermeide Schlussfolgerungen allein aus einer unbekannten Bytefolge. Dieser Eintrag zeichnet keinen Verkehr auf, verarbeitet keine fremden Daten und verändert keine Schnittstellen oder Geräteeinstellungen.

## 10. Verwandte Begriffe
