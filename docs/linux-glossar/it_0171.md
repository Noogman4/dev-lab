# Endpoint

## 1. Kurzbeschreibung

Ein Endpoint ist ein bestimmter Zugangspunkt einer Schnittstelle. Im Web-API-Kontext wird er häufig durch eine Zieladresse oder einen Pfad beschrieben. Für die genaue Operation sind aber auch Methode und Schnittstellenvertrag wichtig. Der gleiche Pfad kann je nach HTTP-Methode unterschiedliche Aufgaben haben. Ein vorhandener Adresstext beweist noch keinen erreichbaren Dienst.

## 2. Was bedeutet der Begriff?

„Endpoint“ bedeutet Endpunkt. Hier geht es entsprechend der Quelle um eine Web-API. In anderen Netzwerkzusammenhängen kann das Wort beispielsweise einen Transportendpunkt aus Adresse und Port bezeichnen. Diese Bedeutungen sind verwandt, aber nicht in jedem Detail gleich.

Die [OpenAPI-Spezifikation 3.1.1 zum Paths-Objekt](https://spec.openapis.org/oas/v3.1.1.html#paths-object) beschreibt relative Pfade zu Endpunkten und ihren Operationen. Der Pfad wird mit einer Serveradresse verbunden. Das Katalogbeispiel `/api/status` ist deshalb ein möglicher Pfad, allein aber noch keine vollständige entfernte Zieladresse.

## 3. Einfacher Vergleich aus dem Alltag

Eine Behörde hat verschiedene Schalter mit festgelegten Aufgaben. Die Anschrift führt zum Gebäude, die Schalternummer zum passenden Zugang. Welche Handlung dort angefordert wird, muss trotzdem zum vorgesehenen Verfahren passen.

Die Grenze: Ein Endpoint ist keine menschlich besetzte Stelle, die ungenaue Wünsche auslegt. Pfad, Methode, Eingabe und Berechtigung folgen technischen Regeln. Eine ähnlich aussehende Adresse muss daher weder dieselbe Funktion noch dieselben Zugriffsrechte besitzen.

## 4. Wie funktioniert das?

Ein Client bildet ein Ziel aus den benötigten Bestandteilen. Dazu können Schema, Host, Port, Basispfad, konkreter Pfad und Query-Angaben gehören. Die API beschreibt, welche Operation an welcher Stelle erwartet wird. Eine Pfadvorlage mit Parametern ist außerdem von einem konkret eingesetzten Wert zu unterscheiden.

Die HTTP-Methode ergänzt die Bedeutung. `GET /api/status` und `POST /api/status` wären zwei unterschiedliche Operationsbeschreibungen, sofern eine API beide tatsächlich definiert. Daraus folgt keine automatische Bedeutung des zweiten Aufrufs; sie müsste dokumentiert sein. Ein Pfadname allein ist kein verlässlicher Beleg für Nebenwirkungen.

## 5. Wo begegnet mir das unter Linux?

Anwendungen können entfernte APIs oder lokale HTTP-Schnittstellen nutzen. Konfigurationen enthalten dafür oft Basisadressen. Eine Entwicklungsumgebung kann einen anderen Host oder Port als die spätere Installation verwenden, obwohl derselbe Pfad vorkommt.

Ein Proxy kann die öffentliche Adresse außerdem auf eine interne Anwendung abbilden. Der vom Client sichtbare Endpoint ist dann nicht zwingend die direkte interne Prozessadresse. Für eine Diagnose sind gewünschte Operation, tatsächliches Ziel und konkrete Antwort getrennt zu betrachten.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Ordner ausgeführt. Es zerlegt ausschließlich eine eigene fiktive URL. Die [Python-Referenz zu urlsplit](https://docs.python.org/3.13/library/urllib.parse.html#urllib.parse.urlsplit) beschreibt diese Aufteilung.

```python
from urllib.parse import urlsplit

url = "https://dienst.beispiel.invalid:8443/api/status?detail=kurz"
teile = urlsplit(url)
assert teile.scheme == "https"
assert teile.hostname == "dienst.beispiel.invalid"
assert teile.port == 8443
assert teile.path == "/api/status"
assert teile.query == "detail=kurz"
assert teile.fragment == ""
print(teile.hostname)
print(teile.port)
print(teile.path)
```

Geprüfte Ausgabe:

```text
dienst.beispiel.invalid
8443
/api/status
```

Die Assertions prüfen getrennte Bestandteile. Sie beweisen weder eine gültige API-Beschreibung noch Erreichbarkeit, Vertrauenswürdigkeit oder Berechtigung. `urlsplit` stellt keine Verbindung her und ist kein vollständiger Sicherheitsvalidator für beliebige URLs. Eine HTTP-Methode ist im Beispiel ebenfalls nicht festgelegt oder ausgeführt.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine API umfasst mehr als einen einzelnen Endpoint. Eine Ressource bezeichnet den fachlichen Gegenstand, eine Operation den vereinbarten Zugriff. Ein Port ist Teil bestimmter Transportadressierung. Eine URL kann einen Endpoint beschreiben, enthält aber nicht allein alle Vertragsbedingungen wie erwartete Daten oder Authentifizierung.

## 8. Häufige Missverständnisse

Ein Pfad ist nicht immer eine vollständige Adresse. Gleiche Pfade auf verschiedenen Servern bedeuten nicht dieselbe Anwendung. Ein vorhandener Endpoint ist auch nicht zwangsläufig öffentlich oder ohne Anmeldung nutzbar. Der Name `status` garantiert schließlich keine bestimmte Antwortstruktur.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Dokumentiere Ziel, Methode und erwartete Eingaben gemeinsam. Prüfe Konfiguration und Umgebung, bevor du eine unerwartete Antwort interpretierst. Dieses Beispiel liest nur eine eigene Zeichenkette und verändert weder Anwendungsadressen noch Proxy-, Port- oder Netzwerkeinstellungen.

## 10. Verwandte Begriffe

Die [API](it_0169.md) definiert den übergeordneten Vertrag. [HTTP](it_0145.md) liefert Methodenregeln. Ein [Proxy](it_0162.md) kann vermitteln. Der [Hostname](it_0167.md) und [Port](it_0142.md) sind mögliche Zielbestandteile. [REST](it_0170.md) ist eine gesonderte Architekturfrage.
