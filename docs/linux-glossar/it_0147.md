# TLS

## 1. Kurzbeschreibung

TLS, Transport Layer Security, stellt Anwendungen einen kryptografisch geschützten Kommunikationskontext bereit. Dazu gehören Vertraulichkeit, Erkennung unzulässiger Veränderungen und eine passende Authentifizierung der Gegenstelle. Der tatsächlich erreichte Schutz hängt von Version, Einstellungen und korrekter Prüfung ab. TLS ist keine Garantie für richtige Anwendungsinhalte oder sichere Speicherung nach dem Empfang.

## 2. Was bedeutet der Begriff?

Die Spezifikation [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html) definiert TLS 1.3. Sie trennt einen Handshake zum Aushandeln und Herstellen der Sicherheitsparameter von der geschützten Datenübertragung. TLS ist nicht auf Webseiten beschränkt; verschiedene Anwendungen können es für ihre Kommunikation verwenden.

Das Katalogbeispiel HTTPS ist deshalb ein wichtiger Anwendungsfall. TLS und HTTPS sind aber keine Synonyme. HTTP legt weiterhin fest, welche Anfragen und Antworten ausgetauscht werden. TLS ergänzt einen Schutzkontext. Auch eine Benutzeranmeldung und die Berechtigung für eine Aktion bleiben eigene Fragen.

## 3. Einfacher Vergleich aus dem Alltag

Zwei Stellen vereinbaren einen geschützten Versandweg, prüfen passende Nachweise und verwenden anschließend gemeinsam festgelegte Schutzmittel. Ein fremder Beobachter soll die versendeten Inhalte nicht einfach lesen oder unbemerkt austauschen können.

Die Grenze: Es wird kein menschlich ausgewähltes gemeinsames Passwort ungeschützt durch die Leitung geschickt. Moderne Verfahren leiten Schlüssel nach definierten kryptografischen Regeln ab. Außerdem ist die Prüfung der richtigen Gegenstelle wesentlich. Eine geschützte Unterhaltung mit dem falschen Partner erfüllt nicht den gewünschten Zweck.

## 4. Wie funktioniert das?

Im Handshake werden Parameter und Schlüsselmaterial vereinbart und die vorgesehenen Identitätsnachweise verarbeitet. TLS 1.3 unterstützt unterschiedliche Verfahren, darunter Zertifikatsauthentifizierung und vorab vereinbarte Schlüssel. Deshalb ist ein Zertifikat nicht in jeder denkbaren TLS-Verwendung der einzige mögliche Nachweis.

Für die anschließenden Daten verwenden die Partner geeignete abgeleitete Schlüssel. Ein Zertifikat selbst ist weder der gesamte verschlüsselte Inhalt noch einfach der geheime Sitzungsschlüssel. Die genaue Rollenverteilung beschreibt RFC 8446.

Versionen und Algorithmen sind relevant. [RFC 9325](https://www.rfc-editor.org/rfc/rfc9325.html) gibt Empfehlungen zur sicheren Verwendung und schließt unter anderem TLS 1.0 und 1.1 als auszuhandelnde Versionen aus. Die bloße Beschriftung „TLS“ ersetzt deshalb keine Prüfung der tatsächlich vorgesehenen Konfiguration.

## 5. Wo begegnet mir das unter Linux?

Browser und andere Netzwerkprogramme nutzen TLS-Bibliotheken. Eine Anwendung muss dabei geeignete Prüfregeln und Vertrauensinformationen verwenden. Die Einstellungen können sich zwischen Werkzeugen unterscheiden. Ein funktionierender Zugriff in einem Programm beweist nicht automatisch eine identische Einrichtung aller anderen.

Python stellt einen Client-Kontext mit [PROTOCOL_TLS_CLIENT](https://docs.python.org/3.13/library/ssl.html#ssl.PROTOCOL_TLS_CLIENT) bereit. Die Dokumentation beschreibt dafür Zertifikats- und Namensprüfung als Voreinstellungen. Das ist eine konkrete Python-Schnittstelle, keine allgemeine Aussage über alle TLS-Bibliotheken.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Ordner ausgeführt. Es erzeugt ausschließlich ein neues Kontextobjekt und untersucht zwei Einstellungen. Es lädt keine eigenen Zertifikate und stellt keine Verbindung her.

```python
import ssl

kontext = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
assert kontext.verify_mode == ssl.CERT_REQUIRED
assert kontext.check_hostname is True
print("Zertifikatsprüfung erforderlich:", kontext.verify_mode == ssl.CERT_REQUIRED)
print("Namensprüfung aktiv:", kontext.check_hostname)
```

Geprüfte Ausgabe:

```text
Zertifikatsprüfung erforderlich: True
Namensprüfung aktiv: True
```

Damit ist nur die Konfiguration dieses Objekts geprüft. Für eine echte Verbindung wären unter anderem passende Vertrauensinformationen und eine erreichbare Gegenstelle nötig. Es wurde weder ein Zertifikat einer Gegenstelle akzeptiert noch verschlüsselter Nutzdatenverkehr gemessen. Der Code ist deshalb keine vollständige Verbindungsanleitung.

## 7. Abgrenzung zu ähnlichen Begriffen

TCP organisiert einen zuverlässigen Bytestrom, verschlüsselt ihn aber nicht automatisch. HTTPS verwendet TLS für HTTP-Kommunikation. Eine Prüfsumme erkennt bestimmte Veränderungen, beweist jedoch nicht dieselbe kryptografische Authentizität. Historisches SSL ist außerdem nicht einfach eine bedenkenlos austauschbare Bezeichnung aktueller TLS-Versionen.

## 8. Häufige Missverständnisse

Verschlüsselung ohne passende Gegenstellenprüfung genügt nicht immer. Ein gültiger Schutzkontext beweist auch keine vertrauenswürdige Fachantwort. TLS verbirgt nicht automatisch jede Verkehrseigenschaft, etwa die Existenz einer Kommunikation. Sicherheitsbehauptungen müssen deshalb den tatsächlich geschützten Bereich nennen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Verwende gepflegte Bibliotheken und dokumentierte sichere Einstellungen. Schalte Prüfungen nicht ungeprüft aus, um einen Fehler zu übergehen. Das Beispiel verändert ausschließlich ein eigenes Objekt im Prüfprozess; Zertifikatsablagen, Systemkonfiguration und bestehende Verbindungen bleiben unberührt.

## 10. Verwandte Begriffe

[HTTPS](it_0146.md) ist ein Anwendungsfall. [HTTP](it_0145.md) definiert weiterhin die Nachrichtenbedeutung. [TCP](it_0143.md) übernimmt andere Transportaufgaben. Eine [Exception](it_0091.md) kann bei einer tatsächlich misslungenen TLS-Verbindung auftreten, wurde hier aber nicht ausgelöst.
