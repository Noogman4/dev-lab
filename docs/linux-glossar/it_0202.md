# Transaktion

## 1. Kurzbeschreibung

Eine Transaktion fasst Datenbankarbeit zu einer kontrollierten Einheit zusammen. Sie wird bestätigt oder zurückgenommen. Damit lassen sich zusammengehörige Änderungen vor einem unerwünschten Teilzustand schützen. Entscheidend sind die tatsächlichen Transaktionsgrenzen und die Fehlerbehandlung. Nicht jeder Fehler setzt in jeder Datenbank automatisch alle vorherigen Schritte zurück.

## 2. Was bedeutet der Begriff?

Die Quelle beschreibt Operationen, die gemeinsam erfolgreich sein müssen. Das ist die richtige Grundidee: Zwei zusammengehörige Einfügungen sollen beispielsweise entweder beide erhalten bleiben oder gemeinsam verworfen werden. Ein erfolgreicher erster Befehl bedeutet noch nicht, dass die ganze Einheit bereits dauerhaft bestätigt wurde.

Das [PostgreSQL-Tutorial zu Transaktionen](https://www.postgresql.org/docs/current/tutorial-transactions.html) erklärt die Alles-oder-nichts-Idee anhand zusammengehöriger Änderungen. Welche Zwischenstände andere Transaktionen beobachten können, gehört zusätzlich zur Isolation und hängt von den jeweiligen Regeln ab. Das folgende Einzelverbindungsbeispiel prüft keine konkurrierenden Zugriffe.

## 3. Einfacher Vergleich aus dem Alltag

Du stellst ein Paket aus zwei zusammengehörigen Formularen zusammen. Erst wenn beide vollständig sind, gibst du das Paket verbindlich ab. Fehlt eines, behältst du beide zurück, statt einen unvollständigen Vorgang zu starten.

Die Grenze: Eine Datenbanktransaktion wirkt auf die beteiligten Datenbankoperationen. Ein schon verschickter Brief, eine ausgegebene Meldung oder eine externe Netzwerkanfrage wird dadurch nicht automatisch zurückgeholt. Eine Transaktion ersetzt keine Planung solcher äußeren Wirkungen.

## 4. Wie funktioniert das?

Eine Datenbank führt Änderungen innerhalb einer Transaktion aus. `COMMIT` bestätigt sie, `ROLLBACK` verwirft die noch nicht bestätigte Arbeit der betreffenden Transaktion. Wie eine Transaktion beginnt und welche automatischen Bestätigungen stattfinden, hängt von Datenbank, Schnittstelle und Einstellungen ab.

Die [SQLite-Dokumentation zur Transaktionssteuerung](https://www.sqlite.org/lang_transaction.html) beschreibt auch die Fehlerbehandlung: Bestimmte Fehler nehmen nur die aktuelle Anweisung zurück, andere können die ganze Transaktion betreffen. Die Quellaussage „Bei Fehler wird eine Transaktion zurückgerollt“ ist daher ohne Kontext zu pauschal. Eine Anwendung muss die vorgesehenen Regeln und ihren Fehlerpfad kennen.

Für Python erklärt die [Dokumentation des Verbindungs-Kontextmanagers](https://docs.python.org/3.13/library/sqlite3.html#how-to-use-the-connection-context-manager), wann beim Verlassen eines `with`-Blocks bestätigt oder zurückgenommen wird. Ein Fehler muss den Block verlassen, damit dessen entsprechende Fehlerbehandlung greift. Wer ihn vorher abfängt und verschluckt, kann ein anderes Verhalten erreichen. Der Kontextmanager schließt außerdem nicht automatisch die Verbindung.

## 5. Wo begegnet mir das unter Linux?

Anwendungen ändern häufig mehrere zusammengehörige Angaben, etwa einen Haupteintrag und seine Zuordnungen. Eine sauber begrenzte Transaktion kann verhindern, dass nur ein Teil gespeichert wird. Das Verhalten stammt aus dem Datenbanksystem und seiner Anbindung, nicht aus einem allgemeinen Linux-Schalter.

Eine offene Transaktion kann außerdem Ressourcen oder Sperren betreffen. Langes Warten auf Benutzereingaben innerhalb einer Schreibtransaktion kann deshalb ungünstig sein. Die genauen Auswirkungen hängen vom System ab. Hier werden weder laufende Dienste noch vorhandene Datenbanken berührt.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 und SQLite 3.46.1 in einem temporären Arbeitsordner ausgeführt. Die Verbindung verwendet ausdrücklich `autocommit=False` und nur eine eigene Speicherdatenbank.

```python
from contextlib import closing
import sqlite3

with closing(sqlite3.connect(":memory:", autocommit=False)) as db:
    db.execute("CREATE TABLE probe (id INTEGER PRIMARY KEY, text TEXT)")
    db.commit()
    fehler = False
    try:
        with db:
            db.execute("INSERT INTO probe VALUES (1, 'Erster')")
            db.execute("INSERT INTO probe VALUES (1, 'Doppelter')")
    except sqlite3.IntegrityError:
        fehler = True
    nach_fehler = db.execute("SELECT COUNT(*) FROM probe").fetchone()[0]
    assert fehler and nach_fehler == 0
    with db:
        db.execute("INSERT INTO probe VALUES (1, 'Erster')")
        db.execute("INSERT INTO probe VALUES (2, 'Zweiter')")
    nach_bestaetigung = db.execute("SELECT COUNT(*) FROM probe").fetchone()[0]
    assert nach_bestaetigung == 2
    print("Nach Fehler:", nach_fehler)
    print("Nach Bestätigung:", nach_bestaetigung)
```

Geprüfte Ausgabe:

```text
Nach Fehler: 0
Nach Bestätigung: 2
```

Der doppelte Primärschlüssel löst einen Fehler aus, der den ersten Block verlässt. Der Kontextmanager nimmt dessen Arbeit zurück. Der zweite Block wird erfolgreich bestätigt. Das kontrolliert genau diesen Fehlerpfad; weder Stromausfallfestigkeit noch Mehrbenutzerisolation werden damit getestet.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine einzelne SQL-Anweisung ist nicht automatisch die gesamte fachliche Transaktion. Eine Migration kann mehrere Änderungen benötigen und gegebenenfalls Transaktionen verwenden. Eine Sicherung ist wiederum ein gesondert aufbewahrter Datenstand und kein Ersatzwort für ROLLBACK.

## 8. Häufige Missverständnisse

Nicht jeder Fehler führt überall zur vollständigen Rücknahme. Ein abgefangener Fehler kann den Kontrollfluss verändern. Bereits bestätigte Arbeit wird durch eine spätere Rücknahme nicht beliebig rückgängig gemacht. Und eine Transaktion umfasst nicht automatisch externe Nebenwirkungen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Setze Grenzen und Fehlerbehandlung ausdrücklich. Prüfe auch den Fehlerfall mit eigenen Daten. Verlasse dich nicht nur auf den Erfolgspfad. Die Verbindung wird hier zusätzlich mit `closing` geschlossen; sämtliche Beispieldaten verschwinden danach.

## 10. Verwandte Begriffe

Die [Datenbank](it_0191.md) führt Arbeit aus. [SQL](it_0192.md) formuliert Anweisungen. Eine [Migration](it_0201.md) kann Transaktionen nutzen. Der [Primärschlüssel](it_0197.md) löst hier die Bedingungsverletzung aus. [Exception](it_0091.md) behandelt Fehler im Programmablauf.
