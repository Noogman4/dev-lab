# Process Fork

## 1. Kurzbeschreibung

Process Fork bezeichnet hier das Erzeugen eines Kindprozesses durch `fork` unter Linux beziehungsweise passenden POSIX-Systemen. Eltern- und Kindprozess setzen die Ausführung getrennt fort. Sie besitzen eigene Prozesskennungen und getrennte Speicherbereiche. Das ist nicht dasselbe wie ein weiterer Thread und auch nicht der Fork eines Repositorys auf einem Hostingdienst.

## 2. Was bedeutet der Begriff?

Die Quelle beschreibt das Kopieren eines Prozesses. Die [Linux-man-pages-Dokumentation zu fork](https://man7.org/linux/man-pages/man2/fork.2.html) erklärt den neuen Kindprozess und wichtige Unterschiede zum Elternprozess. Zum Zeitpunkt der Erzeugung besitzen ihre Speicherbereiche zunächst denselben Inhalt. Spätere gewöhnliche Änderungen einer Variablen werden aber nicht automatisch im anderen Prozess sichtbar.

„Kopieren“ bedeutet nicht zwingend, dass sofort jeder physische Speicherinhalt vollständig dupliziert wird. Linux verwendet dafür unter anderem Copy-on-write. Bestimmte Ressourcenbeziehungen wie geerbte Dateideskriptoren müssen außerdem gesondert betrachtet werden. Getrennter Speicher bedeutet nicht völlige Unabhängigkeit sämtlicher Wirkungen.

## 3. Einfacher Vergleich aus dem Alltag

Zwei Personen beginnen mit derselben Arbeitsnotiz. Anschließend bearbeiten sie ihre eigenen Fassungen. Wenn eine Person ihre Zahl auf 2 ändert, steht auf der anderen Notiz nicht automatisch ebenfalls 2. Informationen müssen über einen vereinbarten Weg ausgetauscht werden.

Die Grenze: Prozesse besitzen technische Vererbungs- und Ressourcenregeln. Manche Zugriffe beziehen sich weiterhin auf gemeinsame äußere Gegenstände. Zwei getrennte Notizen erklären deshalb nicht allein, wie geerbte offene Dateien oder weitere Systemressourcen zusammenwirken.

## 4. Wie funktioniert das?

Nach erfolgreichem `fork` gibt es zwei Ausführungspfade. Der Rückgabewert ist im Kind 0 und im Elternprozess die Kennung des Kindes. Bei Fehlern gelten die jeweiligen Schnittstellenregeln. Das Programm muss erkennen, welcher Pfad gerade ausgeführt wird.

Die [Python-3.13-Dokumentation zu os.fork](https://docs.python.org/3.13/library/os.html#os.fork) beschreibt diese Rückgabewerte und die Plattformabhängigkeit. Sie warnt außerdem vor der Kombination mit mehreren Threads. Ein Kindprozess übernimmt nicht einfach alle laufenden Threads in einem beliebig sicheren Zustand. Für echte Anwendungen müssen deshalb geeignete Prozessstartverfahren und Bibliotheksregeln beachtet werden.

Gewöhnliche Speicherwerte bleiben nach dem Fork getrennt. Für eine Nachricht kann beispielsweise eine eigens vorbereitete Pipe verwendet werden. Das ist ein ausdrücklicher Kommunikationsweg und kein Beweis für gemeinsamen Variablenspeicher. Geerbte Dateideskriptoren müssen auf den nicht benötigten Seiten passend geschlossen werden.

Auch das Kindende gehört zum Ablauf. Der Elternprozess sollte das vorgesehene Ende und den Status kontrollieren. Ein Kind nur zu starten und nie seinen Abschluss zu beachten, ist keine vollständige Prozessverwaltung. Das Beispiel wartet ausdrücklich auf seinen eigenen Kindprozess.

## 5. Wo begegnet mir das unter Linux?

Systemprogramme und Laufzeitbibliotheken können Prozesse erzeugen und anschließend andere Programme ausführen. Fork und das Ersetzen eines Programmbilds sind dabei verschiedene Schritte. Ein Fork allein startet nicht automatisch eine neue Shell oder ein anderes ausführbares Programm.

In Python ist ein direkter Fork keine universelle Empfehlung für jede Aufgabe oder Plattform. Das folgende Beispiel läuft ausschließlich als eigenes kleines Linux-Skript ohne zusätzlich gestartete Threads. Es greift nicht in einen bestehenden Anwendungsprozess ein.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 unter Linux in einem temporären Arbeitsordner ausgeführt. Es erzeugt genau einen eigenen Kindprozess und eine eigene Pipe. Bestehende Dateien, Dienste oder Netzwerke werden nicht angesprochen.

```python
import os

lesen, schreiben = os.pipe()
wert = 1
kind = os.fork()
if kind == 0:
    try:
        os.close(lesen)
        wert = 2
        os.write(schreiben, str(wert).encode("ascii"))
        os.close(schreiben)
    except BaseException:
        os._exit(1)
    os._exit(0)

os.close(schreiben)
with os.fdopen(lesen, "rb") as pipe:
    kindwert = int(pipe.read().decode("ascii"))
beendet, status = os.waitpid(kind, 0)
assert beendet == kind and os.waitstatus_to_exitcode(status) == 0
assert wert == 1 and kindwert == 2
assert kind != os.getpid()
print("Wert im Elternprozess:", wert)
print("Übertragener Wert aus dem Kind:", kindwert)
print("Kind kontrolliert beendet:", True)
```

Geprüfte Ausgabe:

```text
Wert im Elternprozess: 1
Übertragener Wert aus dem Kind: 2
Kind kontrolliert beendet: True
```

Die Variable im Elternprozess bleibt unverändert. Die 2 wird über die Pipe übertragen. Das Kind beendet nur seinen eigenen Pfad, und der Elternprozess kontrolliert dessen Status. Dieser kleine Versuch prüft keine komplexe Anwendung mit mehreren Threads oder geerbten Fremdressourcen.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Thread teilt viele Ressourcen innerhalb eines Prozesses. Fork erzeugt hier einen weiteren Prozess. Ein Programmwechsel ist ein zusätzlicher Vorgang. Ein Repository-Fork bezeichnet dagegen eine Projektabzweigung und keine Prozessverwaltung.

## 8. Häufige Missverständnisse

Fork ist nicht einfach ein weiterer Thread. Getrennte Variablen synchronisieren sich nicht von selbst. Geerbte Deskriptoren sind nicht automatisch unabhängige äußere Ressourcen. Und ein erfolgreicher Start ersetzt nicht die Kontrolle des Kindendes.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Nutze für reale Aufgaben passende Prozessschnittstellen und beachte Thread- und Bibliotheksregeln. Plane Kommunikation und Ende ausdrücklich. Der Versuch erzeugt nur seinen eigenen kurzlebigen Prozess und verändert keine Konten, Dienste oder Systemkonfiguration.
