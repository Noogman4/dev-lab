# Proxy

## 1. Kurzbeschreibung

Ein Proxy vermittelt Kommunikation für andere Beteiligte. Ein HTTP-Proxy kann Anfragen entgegennehmen und sie stellvertretend weitergeben oder aus einem geeigneten Zwischenspeicher beantworten. Welche Daten er sieht und welche Regeln gelten, hängt von seiner Rolle ab. „Zwischenstation“ bedeutet deshalb nicht automatisch Anonymisierung, Verschlüsselung oder uneingeschränkten Zugriff.

## 2. Was bedeutet der Begriff?

Das englische Wort bezeichnet eine Stellvertretung. Bei einem üblichen Forward Proxy wird die Vermittlung auf Clientseite ausgewählt. Ein Reverse Proxy tritt dagegen gegenüber Clients als Zugang zu serverseitigen Angeboten auf. Die [HTTP-Spezifikation zu Vermittlern](https://www.rfc-editor.org/rfc/rfc9110.html#section-3.7) unterscheidet solche Rollen sowie Tunnel.

Das Katalogbeispiel eines weiterleitenden HTTP-Proxys ist damit passend. Der Oberbegriff wird aber auch in anderen Protokollzusammenhängen verwendet. Die folgenden Einzelheiten betreffen HTTP und sind keine universelle Beschreibung jeder Software mit „Proxy“ im Namen.

## 3. Einfacher Vergleich aus dem Alltag

Eine Assistenz nimmt einen Auftrag entgegen und klärt ihn mit einer anderen Stelle. Für die anfragende Person ist zunächst die Assistenz der Ansprechpartner. Auf der anderen Seite kann sie mehrere Anfragen bündeln und Antworten zurückgeben.

Der Vergleich erklärt Stellvertretung. Seine Grenze: Ein Proxy interpretiert technisch definierte Nachrichten und folgt konkreten Regeln. Er kann nicht automatisch die Absicht eines unklaren Auftrags erkennen. Außerdem muss geklärt werden, ob er Nachrichten selbst verarbeitet oder nur einen Datenkanal vermittelt.

## 4. Wie funktioniert das?

Ein Client baut eine Verbindung zum Vermittler auf und übergibt eine passende Anfrage. Für gewöhnliche HTTP/1.1-Anfragen an einen Forward Proxy beschreibt [RFC 9112 die absolute Zielform](https://www.rfc-editor.org/rfc/rfc9112.html#section-3.2.2). Der Vermittler kann nach den HTTP-Regeln weiterarbeiten oder unter passenden Bedingungen einen Cache verwenden.

Ein Reverse Proxy kann serverseitige Ziele auswählen, ohne dass der Client jede interne Anwendung direkt kennen muss. Die öffentliche Zugangsrolle und die eigentliche Anwendung bleiben dabei verschiedene Funktionen. Ein Erfolg am Proxy beweist nicht automatisch, dass jeder dahinterliegende Dienst gesund ist.

Für Tunnel definiert [RFC 9110 die CONNECT-Methode](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.6). Nach erfolgreicher Einrichtung werden Daten entsprechend weitergeleitet. Eine darin aufgebaute TLS-Verbindung ist nicht automatisch vom Proxy entschlüsselt. Wird TLS dagegen an einer Zwischenstelle beendet, besitzt diese eine andere Sicht auf die Inhalte.

## 5. Wo begegnet mir das unter Linux?

Browser und Kommandozeilenprogramme können Proxy-Einstellungen verwenden. Nicht jede Anwendung übernimmt aber dieselben Einstellungen oder denselben Startkontext. Ein eingerichteter Proxy für ein Programm bedeutet deshalb nicht automatisch, dass alle Programme darüber kommunizieren.

Serveranwendungen können ebenfalls hinter einem Reverse Proxy arbeiten. Für die Fehlersuche sind dann mehrere Verbindungen zu unterscheiden: zum Vermittler und zwischen Vermittler und Zielanwendung. Eine Fehlermeldung kann auf einer dieser Ebenen entstehen, auch wenn eine andere bereits funktioniert.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenmodell zeigt eine fiktive HTTP-Vermittlung. Es wurde kein Proxy gestartet, keine Adresse aufgelöst und keine Anfrage ausgeführt.

```text
Client: möchte eine bestimmte Hilfeseite abrufen.
Forward Proxy: erhält die passende Anfrage des Clients.
Proxy: prüft seine Regeln und gegebenenfalls einen verwendbaren Cache.
Falls nötig: Proxy fragt die vorgesehene nächste Gegenstelle an.
Client: erhält die vermittelte Antwort oder eine konkrete Fehlermeldung.
```

Ein fehlender Zugriff kann hier beispielsweise auf eine Regel des Proxys oder auf ein Problem mit der nächsten Gegenstelle zurückgehen. Die Aussage „Webseite nicht erreichbar“ grenzt das noch nicht eindeutig ein.

Das Modell beschreibt keinen TLS-Tunnel und keine tatsächlichen Protokollbytes. Auch ist der Client nicht allein durch die Vermittlung unsichtbar. Welche Informationen protokolliert, weitergegeben oder durch Anmeldung zugeordnet werden, hängt von der konkreten Einrichtung ab. Es werden keine realen Protokolle untersucht.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Router leitet Pakete nach Netzwerkregeln weiter. NAT übersetzt bestimmte Adressangaben. Ein HTTP-Proxy arbeitet mit einer Stellvertretungsrolle für HTTP-Kommunikation. Ein VPN verbindet einen anderen Kommunikationszusammenhang. Diese Verfahren können kombiniert werden, sind jedoch keine austauschbaren Namen derselben Funktion.

## 8. Häufige Missverständnisse

Ein Proxy garantiert keine Anonymität. Er entschlüsselt auch nicht zwangsläufig jede HTTPS-Verbindung. Eine Proxy-Einstellung in einer Shell ist außerdem kein sicherer Beweis für die Verwendung durch jede grafische Anwendung. Ein Cacheinhalt muss schließlich nach passenden Regeln verwendet werden, statt beliebig jede Anfrage zu ersetzen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Bestimme bei einer Diagnose Rolle, betroffene Anwendung und genaue Fehlermeldung. Übernimm keine unbekannte Zwischenstelle als vermeintlich harmlose Reparatur. Der Eintrag verändert keine Proxy-, Browser- oder Vertrauenseinstellungen und greift auf keinen vermittelten Dienst zu.

## 10. Verwandte Begriffe
