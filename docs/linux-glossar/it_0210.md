# Pull

## 1. Kurzbeschreibung

Ein Pull holt in Git Daten aus einem anderen Repository und integriert anschließend einen ausgewählten Entwicklungsstand in den aktuellen Branch. Es ist damit mehr als ein reiner Abruf. Wie integriert wird, hängt von Optionen und Konfiguration ab. Der aktuelle Arbeitsstand und die beteiligten Historien müssen dazu passen.

## 2. Was bedeutet der Begriff?

Die Quelle beschreibt das Holen entfernter Änderungen und nennt `git pull`. Für Einsteiger ist die Ergänzung wichtig: Der Befehl kann nach dem Abruf den eigenen Branch und seine Arbeitsdateien verändern. Er ist nicht bloß eine unverbindliche Vorschau darauf, was andere bearbeitet haben.

Die [offizielle Dokumentation zu git pull](https://raw.githubusercontent.com/git/git/master/Documentation/git-pull.adoc) beschreibt zuerst den Fetch und dann die Integration. Ein anderes Repository muss dabei nicht zwingend auf einem Internetserver liegen. Auch ein lokaler Pfad kann als Quelle dienen. Das Beispiel nutzt genau diese Möglichkeit und benötigt keine Netzwerkverbindung.

## 3. Einfacher Vergleich aus dem Alltag

Du lässt dir zuerst die neu abgelegten Unterlagen einer anderen Arbeitsstelle geben. Danach bringst du deinen eigenen Arbeitsstand damit auf einen gemeinsamen Stand. Die Lieferung der Unterlagen und ihre Aufnahme in deine Arbeit sind zwei verschiedene Vorgänge.

Die Grenze: Git überträgt Objekte und aktualisiert Referenzen nach konkreten Regeln. Ein Pull überschreibt nicht einfach immer den gesamten Ordner mit einer entfernten Kopie. Bei auseinanderentwickelten Historien oder problematischen lokalen Änderungen kann eine Integration scheitern beziehungsweise eine zusätzliche Entscheidung verlangen.

## 4. Wie funktioniert das?

Der erste Teil entspricht einem Abruf. Die [Dokumentation zu git fetch](https://raw.githubusercontent.com/git/git/master/Documentation/git-fetch.adoc) erklärt das Holen von Objekten und Referenzen sowie die Aktualisierung entsprechender Remote-Tracking-Referenzen. Ein Fetch allein ist noch kein Merge in den gerade ausgecheckten lokalen Branch.

Anschließend integriert Pull den ausgewählten Stand. Möglich sind je nach Aufruf beispielsweise ein Fast-Forward, eine Merge-Integration oder ein Rebase. Welche Voreinstellung gilt, sollte anhand der tatsächlich verwendeten Git-Version und Konfiguration geprüft werden. Das Beispiel vermeidet diese Unklarheit durch `--ff-only`.

Mit dieser Option wird nur ein passendes Vorrücken erlaubt. Sind die beiden Entwicklungszweige auseinandergegangen, wird eine solche Integration verweigert. Das ersetzt weder die fachliche Prüfung des neuen Inhalts noch das Verständnis der beteiligten Branches. Ein konfliktfreier Fast-Forward kann weiterhin fehlerhaften Code enthalten.

## 5. Wo begegnet mir das unter Linux?

Entwickler aktualisieren lokale Arbeitsstände im Terminal oder über eine grafische Git-Oberfläche. Vorher sollten aktueller Branch, Quelle und offene Änderungen bekannt sein. Ein bloßes „Aktualisieren“ in einer Oberfläche kann mehr Arbeitsschritte umfassen, als die Beschriftung vermuten lässt.

Ein Remote-Name wie `origin` ist eine lokale Bezeichnung für eine konfigurierte Quelle. Er bedeutet nicht automatisch GitHub oder einen bestimmten vertrauenswürdigen Server. Hier benennt er ausschließlich das selbst erzeugte lokale Quellrepository.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 und Git 2.52.0 ausgeführt. Alle Daten entstehen in einem temporären Ordner. Persönliche und systemweite Git-Konfiguration werden für die Kindprozesse ausgeblendet; es werden keine Vorlagen übernommen.

```python
import os
from pathlib import Path
import subprocess
import tempfile

env = {k: v for k, v in os.environ.items() if not k.startswith("GIT_")}
env.update(GIT_CONFIG_GLOBAL="/dev/null", GIT_CONFIG_NOSYSTEM="1")
with tempfile.TemporaryDirectory() as ordner:
    basis = Path(ordner)
    quelle = basis / "quelle"
    lokal = basis / "lokal"
    quelle.mkdir()
    def git(repo, *args):
        return subprocess.run(
            ["git", "-c", "user.name=Glossar", "-c",
             "user.email=glossar@example.invalid", "-c",
             "commit.gpgsign=false", *args],
            cwd=repo, env=env, check=True, capture_output=True, text=True
        ).stdout.strip()
    git(quelle, "init", "--template=", "-b", "probe")
    datei = quelle / "notiz.txt"
    datei.write_text("Anfang\n", encoding="utf-8")
    git(quelle, "add", "notiz.txt")
    git(quelle, "commit", "-m", "Anfang")
    git(basis, "clone", "--template=", str(quelle), str(lokal))
    datei.write_text("Neuer Stand\n", encoding="utf-8")
    git(quelle, "add", "notiz.txt")
    git(quelle, "commit", "-m", "Ergänzung")
    assert (lokal / "notiz.txt").read_text() == "Anfang\n"
    git(lokal, "pull", "--ff-only", "origin", "probe")
    assert git(lokal, "rev-parse", "HEAD") == git(quelle, "rev-parse", "HEAD")
    assert (lokal / "notiz.txt").read_text() == "Neuer Stand\n"
    assert git(lokal, "status", "--porcelain") == ""
    print("Lokaler Inhalt:", (lokal / "notiz.txt").read_text().strip())
    print("Commitstände gleich:", True)
```

Geprüfte Ausgabe:

```text
Lokaler Inhalt: Neuer Stand
Commitstände gleich: True
```

Nach dem Kopieren erhält nur die Quelle einen weiteren Commit. Pull bringt die lokale Kopie per Fast-Forward auf diesen Stand. Geprüft werden Inhalt, Commitgleichheit und sauberer Status. Ein Konflikt- oder Rebase-Fall wird nicht ausgeführt. Beide Repositories werden anschließend entfernt.

## 7. Abgrenzung zu ähnlichen Begriffen

Fetch holt Daten und Referenzen. Pull verbindet Abruf und Integration. Ein Merge ist ein mögliches Integrationsverfahren. Ein lokaler Commit speichert eigene Arbeit. Keiner dieser Begriffe bedeutet automatisch, dass eigene Commits an einen entfernten Dienst gesendet wurden.

## 8. Häufige Missverständnisse

Pull ist nicht nur Herunterladen. `origin` ist kein fest eingebauter Internetanbieter. Die gewählte Integrationsart ist wichtig. Und `--ff-only` verspricht weder einen erfolgreichen Pull bei jeder Historie noch fachlich geprüfte Inhalte.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe Quelle, Zielbranch und offenen Status. Bei einer Verweigerung kläre die Ursache, statt Schutzregeln blind zu umgehen. Das Beispiel aktualisiert nur eine eigene Wegwerfkopie und führt keinen Pull im bestehenden Projekt aus.

## 10. Verwandte Begriffe
