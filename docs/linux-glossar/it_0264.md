# Race Condition

## 1. Kurzbeschreibung

Eine Race Condition liegt vor, wenn die Korrektheit eines Ablaufs von einer nicht ausreichend geregelten zeitlichen Reihenfolge abhängt. Mehrere Beteiligte verwenden beispielsweise gemeinsame Daten, ohne die notwendige gesamte Verarbeitung zusammenhängend abzusichern. Eine ungünstige Verschachtelung kann dann ein falsches Ergebnis erzeugen. Dafür ist keine exakt gleichzeitige Ausführung auf mehreren CPU-Kernen erforderlich.

## 2. Was bedeutet der Begriff?

Die Quelle nennt zwei Threads, die dieselbe Datei schreiben. Auch ein gewöhnlicher Zähler im Speicher kann betroffen sein: Beide Beteiligten lesen denselben alten Wert und schreiben anschließend jeweils ihre daraus berechnete Erhöhung. Eine Erhöhung geht logisch verloren, obwohl zwei Schreibvorgänge stattgefunden haben.

Die [MITRE-Beschreibung CWE-362](https://cwe.mitre.org/data/definitions/362.html) behandelt gemeinsame Ressourcen mit unzureichender Synchronisierung. Welche Folgen entstehen, hängt von Ressource, Vertrag und möglicher Reihenfolge ab. Nicht jede veränderliche zeitliche Reihenfolge ist automatisch ein Fehler; sie wird problematisch, wenn eine notwendige Eigenschaft verletzt wird.

## 3. Einfacher Vergleich aus dem Alltag

Zwei Personen lesen auf einer Liste den Lagerbestand 0. Beide wollen einen Artikel ergänzen und schreiben unabhängig 1 auf. Am Ende steht 1, obwohl insgesamt zwei Artikel dazugekommen sind. Die getrennten Schritte haben nicht als gemeinsame fachliche Einheit funktioniert.

Die Grenze: Software kann sehr viele andere Verschachtelungen und Speicherregeln besitzen. Der Vergleich erklärt einen verlorenen Aktualisierungsstand, aber nicht jede Art von Race Condition. Auch ein einzelner sichtbarer erfolgreicher Lauf beweist nicht, dass eine andere Reihenfolge ausgeschlossen ist.

## 4. Wie funktioniert das?

Ein logischer Vorgang besteht häufig aus Lesen, Entscheiden und Schreiben. Wenn andere Beteiligte dazwischen denselben relevanten Zustand verändern dürfen, kann die ursprüngliche Entscheidung überholt sein. Die benötigte Grenze muss deshalb nach dem fachlichen Vorgang gewählt werden, nicht allein nach einzelnen Variablenzugriffen.

Die [Python-Dokumentation zu Lock-Objekten](https://docs.python.org/3.13/library/threading.html#lock-objects) beschreibt exklusiven Zugang zu einem geschützten Abschnitt. Wenn jedoch nur das einzelne Lesen und einzelne Schreiben getrennt gesperrt sind, bleibt zwischen ihnen eine Lücke. Das Beispiel zeigt diesen Unterschied ausdrücklich.

Ein Lock hilft nur, wenn die Beteiligten denselben vorgesehenen Vertrag einhalten. Andere Techniken können unveränderliche Daten, Nachrichtenübergabe oder passende atomare beziehungsweise transaktionale Operationen verwenden. Welche Lösung geeignet ist, hängt von der Ressource und der gesamten Anforderung ab.

Der GIL ist ebenfalls keine pauschale Absicherung jeder mehrstufigen fachlichen Verarbeitung. Ein Programm sollte benötigte Eigenschaften ausdrücklich herstellen. Auch nebenläufige Tasks können an ihren Übergabepunkten logisch miteinander wechselwirken. Die konkrete Laufzeit und Ausführungsweise müssen berücksichtigt werden.

## 5. Wo begegnet mir das unter Linux?

Programme teilen Dateien, Datenbankzustände oder Speicherwerte. Probleme können nur unter bestimmten Abläufen auftreten und dadurch schwer wiederholbar erscheinen. Zufällig oft erfolgreiche Durchläufe sind kein ausreichender Beweis einer korrekten Koordination.

Für die Erklärung wird deshalb eine problematische Reihenfolge bewusst hergestellt. Es werden keine vorhandenen Dateien gleichzeitig bearbeitet und keine echten Anwendungszustände verändert. Der Versuch nutzt ausschließlich einen eigenen Speicherzähler und kurzlebige Threads.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Eine Barrier stellt sicher, dass beide Worker vor ihrem Schreiben denselben alten Wert gelesen haben. Die zweite Variante schützt dagegen den ganzen Aktualisierungsschritt.

```python
from threading import Barrier, Lock, Thread

zustand = {"wert": 0}
schutz = Lock()
gelesen = Barrier(2, timeout=2)

def fehlerhaft():
    with schutz:
        alt = zustand["wert"]
    gelesen.wait()
    with schutz:
        zustand["wert"] = alt + 1

def zusammenhaengend():
    with schutz:
        zustand["wert"] = zustand["wert"] + 1

def ausfuehren(funktion):
    threads = [Thread(target=funktion) for _ in range(2)]
    for thread in threads:
        thread.start()
    for thread in threads:
        thread.join(timeout=1)
    assert all(not thread.is_alive() for thread in threads)

ausfuehren(fehlerhaft)
verloren = zustand["wert"]
assert verloren == 1
zustand["wert"] = 0
ausfuehren(zusammenhaengend)
assert zustand["wert"] == 2
print("Getrennt geschützte Teilschritte:", verloren)
print("Geschützte gesamte Aktualisierung:", zustand["wert"])
```

Geprüfte Ausgabe:

```text
Getrennt geschützte Teilschritte: 1
Geschützte gesamte Aktualisierung: 2
```

Die erste Variante besitzt zwar Locks, schützt aber nicht die notwendige Einheit. Die zweite hält den zusammengehörigen Schritt unter derselben Sperre. Beide Durchläufe beenden ihre Worker. Der Versuch prüft genau diesen Ablauf und keine allgemeine Race-Freiheit einer Anwendung.

## 7. Abgrenzung zu ähnlichen Begriffen

Nebenläufigkeit erlaubt zeitliche Überlappung. Eine Race Condition ist eine daraus oder aus anderem Timing entstehende Korrektheitsabhängigkeit. Ein blockierender Vorgang ist nicht automatisch ein solcher Fehler. Ein erfolgreicher Test beobachtet wiederum nur seine kontrollierten Bedingungen.

## 8. Häufige Missverständnisse

Ein vorhandenes Lock schützt nicht automatisch die richtige Einheit. Ein GIL verhindert nicht jede fachliche Race Condition. Zwei physische Kerne sind nicht zwingend nötig. Und viele zufällig erfolgreiche Läufe beweisen keinen Ausschluss aller ungünstigen Reihenfolgen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Definiere die notwendige gemeinsame Eigenschaft und schütze den passenden Umfang. Prüfe relevante Verschachtelungen mit eigenen Daten. Die Ausführung verändert keine Dateien, Konten, Dienste, Netzwerke oder vorhandenen Anwendungsthreads.
