# Resolver

## 1. Kurzbeschreibung

Ein Resolver ist eine Komponente, die eine Namensanfrage bearbeitet und ein Ergebnis für die anfragende Anwendung beschafft. Im DNS-Zusammenhang können daran mehrere Resolverrollen beteiligt sein. Ein Resolver muss nicht bei jeder Anfrage neue entfernte DNS-Server kontaktieren: Er kann vorhandene gültige Antworten nutzen oder Arbeit an eine andere Komponente weitergeben.

## 2. Was bedeutet der Begriff?

„Resolve“ bedeutet hier auflösen. Die Anwendung möchte beispielsweise passende Adressinformationen zu einem Namen erhalten. Welche Arbeit der angesprochene Resolver selbst erledigt, hängt von seiner Rolle und Konfiguration ab.

Die aktuelle [DNS-Terminologie in RFC 9499](https://www.rfc-editor.org/rfc/rfc9499.html) unterscheidet unter anderem Stub-Resolver und rekursive Auflösung. Ein Stub-Resolver übernimmt nicht die gesamte Suche selbst, sondern verlässt sich gewöhnlich auf einen rekursiven Resolver. Die Quellaussage „fragt DNS-Server ab“ beschreibt somit einen möglichen Schritt, nicht die vollständige Definition jeder Resolverkomponente.

## 3. Einfacher Vergleich aus dem Alltag

Du fragst am Empfang nach einer zuständigen Person. Der Empfang kann eine aktuelle Auskunft bereits kennen oder eine zentrale Stelle damit beauftragen, sie zu beschaffen. Diese zentrale Stelle fragt gegebenenfalls weitere zuständige Büros.

So lassen sich verschiedene Rollen verstehen. Die Grenze: DNS-Anfragen und Antworten haben festgelegte Formate und Gültigkeitsregeln. Eine Auskunft wird nicht nach Menschenkenntnis bewertet. Außerdem ist eine empfangene Adresse noch kein Nachweis, dass die gewünschte Anwendung erreichbar oder die Verbindung passend geschützt ist.

## 4. Wie funktioniert das?

Ein Resolver erhält eine Frage zu einem Namen und einer gewünschten Information. Ein rekursiver Resolver kann aus einem Cache antworten oder weitere Anfragen veranlassen, bis ein Ergebnis oder Fehler feststeht. Er muss nicht für jeden Namen zwangsläufig den gesamten Weg von der Wurzel an neu durchlaufen. Gültige Zwischenergebnisse können Arbeit vermeiden.

Ein autoritativer Server hat dagegen eine Zuständigkeit für bestimmte DNS-Daten. Das ist eine andere Rolle als das Beschaffen einer Antwort im Auftrag eines Clients. Eine konkrete Software kann mehrere Rollen unterstützen; die Rollen dürfen trotzdem nicht als gleichbedeutend behandelt werden. RFC 9499 beschreibt diese Begriffe im Zusammenhang.

## 5. Wo begegnet mir das unter Linux?

Anwendungen können eine lokale Namensschnittstelle verwenden. Bei glibc beeinflusst der Name Service Switch, welche Quellen in welcher Reihenfolge berücksichtigt werden. Die [Linux-Handbuchseite zu nsswitch.conf](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html) beschreibt diese Auswahl, darunter die Kategorie für Rechnernamen.

Daraus folgt: Eine erfolgreiche Namensauflösung über eine Systemfunktion ist nicht automatisch der Beweis einer gerade gesendeten DNS-Anfrage. Lokale Daten oder andere konfigurierte Verfahren können beteiligt sein. Manche Anwendungen verwenden zudem eigene Auflösungswege. Der tatsächliche Ablauf muss für das konkrete Programm betrachtet werden, nicht nur für den Rechner insgesamt.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenmodell beschreibt eine mögliche Kette. Es wurde keine Anfrage gesendet und kein Cache untersucht.

```text
Eine Anwendung fragt nach einer Adresse zu hilfe.beispiel.invalid.
Eine lokale Anfragestelle gibt die DNS-Frage an einen rekursiven Resolver weiter.
Dieser besitzt bereits eine passende, noch gültige Antwort im Cache.
Er liefert diese Antwort zurück, ohne dafür erneut die zuständigen Server abzufragen.
Die Anwendung muss anschließend ihren eigenen Verbindungsaufbau behandeln.
```

Wäre keine passende Antwort vorhanden, könnte der rekursive Resolver zusätzliche Arbeit übernehmen. Das Beispiel behauptet aber weder eine bestimmte reale Serveradresse noch eine universelle Reihenfolge aller Systeme. Auch das Wort „lokal“ bezeichnet hier eine Rolle im Modell, keine festgestellte Installation.

Die Trennung hilft bei einer Diagnose: Eine Verzögerung könnte in der Auflösung liegen, während eine spätere Verbindungsverweigerung ein anderes Problem wäre. Ein einmal erfolgreicher Namensabruf beweist nicht beide Schritte zugleich.

## 7. Abgrenzung zu ähnlichen Begriffen

DNS ist das übergeordnete Namenssystem. Ein Resolver beschafft Ergebnisse. Ein autoritativer Server stellt Daten für einen Zuständigkeitsbereich bereit. Ein Cache hält zeitweise verwendbare Antworten. Eine Anwendung kann diese Bausteine nutzen, ist aber nicht allein deshalb selbst ein vollständiger rekursiver DNS-Dienst.

## 8. Häufige Missverständnisse

Ein Resolver ist nicht automatisch der Heimrouter, auch wenn dieser eine entsprechende Funktion anbieten kann. Ein anderer Resolver behebt nicht jede Netzwerkstörung. Eine alte Antwort im erlaubten Cachezeitraum muss außerdem nicht bedeuten, dass der aktuelle zuständige Server noch genau denselben Inhalt ausliefert.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Kläre bei Problemen zuerst den Auflösungsweg der konkreten Anwendung. Unterscheide Name, angefragten Typ, Ergebnis und anschließenden Zugriff. Ändere keine Resolveradresse allein auf Verdacht. Dieser Eintrag liest keine Systemdateien oder vorhandenen Cacheinhalte und verändert keine Namens- oder Netzkonfiguration.

## 10. Verwandte Begriffe

[DNS](it_0148.md) erklärt Daten und Hierarchie. Die [IP-Adresse](it_0139.md) ist ein mögliches Ergebnis. [HTTPS](it_0146.md) benötigt zusätzlich eine passende geschützte Gegenstelle. Ein [Service](it_0119.md) kann einen Resolver betreiben, muss aber von dessen fachlicher Rolle unterschieden werden.
