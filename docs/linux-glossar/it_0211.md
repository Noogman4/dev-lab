# Push

## 1. Kurzbeschreibung

Ein Push überträgt in Git benötigte Versionsobjekte zu einem anderen Repository und aktualisiert dort ausgewählte Referenzen. Er sendet nicht automatisch jede gerade bearbeitete Datei. Welche Branches oder Tags betroffen sind, hängt vom Aufruf und der Konfiguration ab. Ein erfolgreicher Push ist außerdem weder ein Merge noch eine fachliche Freigabe.

## 2. Was bedeutet der Begriff?

Die Quelle beschreibt das Senden lokaler Änderungen und nennt das Hochladen von Commits. Dabei ist „Änderungen“ als bereits gespeicherte Versionsarbeit zu verstehen. Eine Datei, die nur im Arbeitsverzeichnis verändert wurde, gehört nicht allein dadurch zu den übertragenen Commits.

Die [offizielle Dokumentation zu git push](https://raw.githubusercontent.com/git/git/master/Documentation/git-push.adoc) beschreibt die Aktualisierung von Branches, Tags und anderen Referenzen samt benötigten Objekten. Das Ziel muss nicht zwingend über das Internet erreichbar sein. Für das Beispiel genügt ein weiteres lokales Repository in einem temporären Ordner.

## 3. Einfacher Vergleich aus dem Alltag

Du gibst bewusst abgelegte Arbeitsstände an ein anderes Archiv weiter und aktualisierst dort das zugehörige Lesezeichen. Noch lose auf deinem Schreibtisch liegende Entwürfe werden nicht automatisch mitgeliefert. Auch entscheidet die Ablage allein nicht, ob jemand den neuen Stand bereits geprüft hat.

Die Grenze: Git überträgt nicht nach Papierlogik jede Datei einzeln neu. Bereits vorhandene Objekte und technische Referenzregeln spielen eine Rolle. Ein Push kann außerdem vom Ziel verweigert werden, etwa wegen fehlender Rechte, Schutzregeln oder einer unpassenden Historie.

## 4. Wie funktioniert das?

Ein Aufruf bestimmt Quelle und Ziel der Referenzaktualisierung. Beispielsweise kann ein lokaler Branch in den gleichnamigen Branch eines benannten Remotes übertragen werden. Ohne ausdrücklich genannte Zuordnung können Einstellungen das Verhalten beeinflussen. Deshalb ist es für Einsteiger sinnvoll, den geplanten Umfang genau zu prüfen.

Die [Dokumentation zu git remote](https://raw.githubusercontent.com/git/git/master/Documentation/git-remote.adoc) erklärt lokale Bezeichnungen für andere Repositories. Ein Name wie `origin` oder `ablage` ist eine Konfiguration des eigenen Repositorys. Er beweist weder einen bestimmten Anbieter noch eine passende Berechtigung. Das Hinzufügen des Namens überträgt für sich genommen noch keinen Commit.

Ein gewöhnlicher Push auf einen Branch schützt normalerweise vor einer nicht passenden Ersetzung seiner bisherigen Entwicklung. Eine Ablehnung kann bedeuten, dass zuerst weitere Arbeit berücksichtigt werden muss. Erzwingen ist keine allgemeine Reparatur. Außerdem können serverseitige Regeln strengere Bedingungen setzen. Das Beispiel verwendet weder Force-Optionen noch einen gemeinsam genutzten Server.

## 5. Wo begegnet mir das unter Linux?

Entwickler senden fertige lokale Commits zu einem Teamrepository oder einem eigenen Ziel. Grafische Oberflächen bieten dafür häufig eine Schaltfläche. Vorher sollten Zieladresse und Branchzuordnung klar sein. Die Anzeige eines lokalen Commit-Erfolgs beweist noch keine erfolgreiche Übertragung.

Ein Push kann in realen Projekten weitere Abläufe auslösen, etwa Prüfungen eines Hostingdiensts. Welche das sind, hängt von der Umgebung ab. Das folgende lokale Bare-Repository besitzt keine übernommenen Vorlagen; eine solche Dienstintegration wird nicht eingerichtet oder getestet.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 und Git 2.52.0 ausgeführt. Persönliche und systemweite Git-Konfiguration sind für die Kindprozesse ausgeblendet. Alle Repositorys und Daten entstehen im temporären Ordner, die Identität gilt nur pro Aufruf.

```python
import os
from pathlib import Path
import subprocess
import tempfile

env = {k: v for k, v in os.environ.items() if not k.startswith("GIT_")}
env.update(GIT_CONFIG_GLOBAL="/dev/null", GIT_CONFIG_NOSYSTEM="1")
with tempfile.TemporaryDirectory() as ordner:
    basis = Path(ordner)
    quelle = basis / "quelle"
    ziel = basis / "ziel.git"
    quelle.mkdir()
    def git(repo, *args):
        return subprocess.run(
            ["git", "-c", "user.name=Glossar", "-c",
             "user.email=glossar@example.invalid", "-c",
             "commit.gpgsign=false", *args],
            cwd=repo, env=env, check=True, capture_output=True, text=True
        ).stdout.strip()
    git(quelle, "init", "--template=", "-b", "probe")
    git(basis, "init", "--template=", "--bare", "-b", "probe", str(ziel))
    datei = quelle / "notiz.txt"
    datei.write_text("Gespeichert\n", encoding="utf-8")
    git(quelle, "add", "notiz.txt")
    git(quelle, "commit", "-m", "Eigener gespeicherter Stand")
    datei.write_text("Offen bearbeitet\n", encoding="utf-8")
    git(quelle, "remote", "add", "ablage", str(ziel))
    git(quelle, "push", "ablage", "probe:refs/heads/probe")
    assert git(quelle, "rev-parse", "HEAD") == git(ziel, "rev-parse", "refs/heads/probe")
    assert git(ziel, "show", "refs/heads/probe:notiz.txt") == "Gespeichert"
    assert datei.read_text() == "Offen bearbeitet\n"
    print("Im Ziel:", git(ziel, "show", "refs/heads/probe:notiz.txt"))
    print("Nur lokal offen:", datei.read_text().strip())
```

Geprüfte Ausgabe:

```text
Im Ziel: Gespeichert
Nur lokal offen: Offen bearbeitet
```

Übertragen wird der gespeicherte Commit. Die anschließende Bearbeitung bleibt ausschließlich im Quellarbeitsverzeichnis. Beide Repositories werden entfernt. Es gibt keinen Git-Netzwerktransport und keinen Push der Übungsdaten zum tatsächlichen Projekt.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Commit speichert lokal. Push aktualisiert ein anderes Repository. Pull holt und integriert einen anderen Stand. Ein Merge verbindet Historien. Eine Veröffentlichung oder Bereitstellung kann auf einem Push aufbauen, ist aber ein gesonderter Arbeitsablauf.

## 8. Häufige Missverständnisse

Push nimmt keine ungespeicherten Arbeitsdateien automatisch auf. Ein Remote-Name ist keine Vertrauensgarantie. Eine Ablehnung rechtfertigt keinen blinden Force-Push. Und übertragene Commits sind nicht allein deshalb fachlich geprüft oder im Hauptbranch integriert.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Kontrolliere Ziel, Branch und gespeicherten Umfang. Berücksichtige mögliche Auswirkungen des tatsächlichen Ziels. Die Übung schreibt nur in ein eigenes temporäres Bare-Repository und verändert weder gemeinsame Referenzen noch Konten oder Dienste.

## 10. Verwandte Begriffe

[Commit](it_0207.md) speichert den Stand. [Branch](it_0208.md) benennt die Entwicklung. [Pull](it_0210.md) arbeitet in der Gegenrichtung mit Integration. [Merge](it_0209.md) verbindet Historien. [Repository Git](it_0206.md) erklärt das Zielmodell.
