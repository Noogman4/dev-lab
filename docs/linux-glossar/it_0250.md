# Mock

## 1. Kurzbeschreibung

Ein Mock ist ein kontrollierbares Ersatzobjekt für Tests. Es kann vorgegebene Ergebnisse liefern, Fehler auslösen und Aufrufe aufzeichnen. Dadurch lässt sich prüfen, wie ein zu testender Teil mit einer Abhängigkeit zusammenarbeitet. Das Ersatzobjekt ist aber nicht automatisch eine vollständige Nachbildung des echten Diensts. Sein begrenzter Vertrag bestimmt die Aussage des Tests.

## 2. Was bedeutet der Begriff?

Die Quelle nennt einen ersetzten Netzwerkaufruf. Damit kann ein Test unabhängig von einem entfernten Server werden und auch seltene Fehler gezielt behandeln. Ein simulierter Timeout beweist jedoch weder eine echte Verbindung noch das Verhalten einer realen Zeitüberschreitung im Betrieb.

Die [Python-Dokumentation zu Autospeccing](https://docs.python.org/3.13/library/unittest.mock.html#auto-speccing) beschreibt kontrollierte Mock-Schnittstellen und typische Fehler zu freier Ersatzobjekte. Ein Mock kann sonst unter Umständen Methoden zulassen, die der echte Gegenstand gar nicht besitzt. Ein passender Schnittstellenabgleich hilft, ersetzt aber keine vollständige Verhaltensprüfung.

## 3. Einfacher Vergleich aus dem Alltag

Bei einer Probe nimmt eine Person bewusst die Rolle einer Auskunftsstelle ein. Sie gibt vereinbarte Antworten und notiert, welche Fragen gestellt wurden. So kann die anfragende Seite ihren Ablauf üben, ohne eine echte Außenstelle zu benötigen.

Die Grenze: Die Probenperson kennt nur die vereinbarten Fälle. Sie beweist nicht, dass der reale Betrieb dieselben Antworten, Zeiten und Fehler liefert. Ebenso darf ein Mock nicht stillschweigend als Abnahme des tatsächlich ersetzten Systems ausgegeben werden.

## 4. Wie funktioniert das?

Zunächst wird eine geeignete Austauschstelle benötigt. Eine Abhängigkeit kann beispielsweise ausdrücklich übergeben werden. Dann legt der Test Ergebnis oder Fehler des Ersatzes fest und führt den zu prüfenden Ablauf aus. Anschließend werden dessen beobachtbare Wirkung und gegebenenfalls relevante Aufrufe kontrolliert.

Die [Dokumentation zu Mock.side_effect](https://docs.python.org/3.13/library/unittest.mock.html#unittest.mock.Mock.side_effect) beschreibt unter anderem das Auslösen einer vorgegebenen Ausnahme. Damit können Fehlerpfade geprüft werden, ohne echte Störungen zu erzeugen. Der aufrufende Code muss den Fehler nach seinem Vertrag behandeln oder weitergeben.

Ein Rückgabewert allein prüft noch nicht die richtige Anfrage. Umgekehrt garantiert ein korrekt aufgezeichneter Aufruf nicht, dass die Anwendung dessen Ergebnis richtig verwendet. Beide Fragen sollten nach der Anforderung entschieden werden. Nicht jeder interne Hilfsaufruf muss dafür festgeschrieben werden.

Zu genaue Erwartungen an unwichtige interne Reihenfolgen können sinnvolle Änderungen erschweren. Zu freie Ersatzobjekte können dagegen echte Schnittstellenfehler verdecken. Ein guter Test wählt die relevante Grenze bewusst und ergänzt bei Bedarf passende Integrationsprüfungen mit echten Komponenten.

## 5. Wo begegnet mir das unter Linux?

Python-Tests können Datenzugriffe, Zeitquellen oder Meldungsfunktionen kontrolliert ersetzen. Das Standardmodul unittest.mock ist dafür verfügbar. Eine echte Netzwerkverbindung wird dadurch nicht benötigt, wenn der geprüfte Code die vorgesehene Ersatzstelle tatsächlich verwendet.

Bei nachträglichem Ersetzen vorhandener Namen muss außerdem die richtige Verwendungsstelle getroffen werden. Das folgende Beispiel hält die Abhängigkeit ausdrücklich als Parameter sichtbar. Es verändert keine Importe der Anwendung und greift nicht in eine bestehende Testsuite ein.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Es verwendet ausschließlich eine selbst erzeugte Schnittstelle und einen dazu passenden Mock. Ein realer Netzwerk- oder Dateidienst ist nicht beteiligt.

```python
from unittest.mock import create_autospec

def eigene_quelle(kennung):
    return f"Eigener Titel {kennung}"

def anzeigetitel(holen, kennung):
    return holen(kennung).strip()

ersatz = create_autospec(eigene_quelle, spec_set=True, return_value=" Probe ")
ergebnis = anzeigetitel(ersatz, 7)
assert ergebnis == "Probe"
ersatz.assert_called_once_with(7)

ersatz.reset_mock()
ersatz.side_effect = TimeoutError("Eigener Testfehler")
weitergegeben = False
try:
    anzeigetitel(ersatz, 7)
except TimeoutError:
    weitergegeben = True
assert weitergegeben
ersatz.assert_called_once_with(7)
print("Verarbeitetes Ergebnis:", ergebnis)
print("Simulierter Fehler weitergegeben:", weitergegeben)
```

Geprüfte Ausgabe:

```text
Verarbeitetes Ergebnis: Probe
Simulierter Fehler weitergegeben: True
```

Die vorgegebene Rückgabe wird verarbeitet und der Aufruf mit Kennung 7 kontrolliert. Nach dem Zurücksetzen wird ein bewusst simulierter Fehler weitergegeben. Die eigene Originalfunktion dient hier als Signaturvorlage und wird dadurch nicht als echte Integration geprüft. Eine tatsächliche Zeitüberschreitung findet nicht statt.

## 7. Abgrenzung zu ähnlichen Begriffen

Test Double ist ein allgemeiner Begriff für Ersatzteile. Ein Stub liefert typischerweise vorbereitete Antworten, ein Fake kann eine kleine funktionsfähige Ersatzimplementierung sein. Ein Mock unterstützt insbesondere kontrollierte Aufrufbeobachtung. Die Begriffe werden in Werkzeugen teilweise unterschiedlich verwendet; der konkrete Vertrag ist entscheidend.

## 8. Häufige Missverständnisse

Ein Mock ist keine automatische echte Integration. Eine simulierte Ausnahme testet nicht die wirkliche Netzwerkzeit. Richtige Aufrufargumente beweisen noch nicht richtige Ergebnisverarbeitung. Und beliebig erlaubte Methoden können eine unpassende Schnittstelle verbergen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Wähle Ersatzstellen nach der Anforderung und halte ihre Grenzen fest. Prüfe relevante Aufrufe und Ergebnisse. Das Beispiel verwendet keine fremden Daten, führt keine Netzwerkstörung herbei und verändert weder Anwendung, Testsuite noch Abhängigkeiten.
