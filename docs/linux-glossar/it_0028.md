# Refactoring

## 1. Kurzbeschreibung

Refactoring ist das Umgestalten der inneren Struktur von Software, während ihr vereinbartes beobachtbares Verhalten erhalten bleibt. Dadurch soll sich der Code leichter verstehen und weiterentwickeln lassen. Die Quelle nennt als Beispiel, eine lange Funktion in kleinere Funktionen aufzuteilen. Entscheidend ist nicht die neue Zahl der Funktionen, sondern die verständlichere Struktur bei erhaltener Wirkung.

## 2. Was bedeutet der Begriff?

Martin Fowler beschreibt Refactoring ausdrücklich als interne Strukturänderung ohne Änderung des beobachtbaren Verhaltens. Seine [Definition von Refactoring](https://martinfowler.com/bliki/DefinitionOfRefactoring.html) ist eine Primärquelle für diese Abgrenzung.

Dazu muss bekannt sein, was zum beobachtbaren Verhalten gehört: Ergebnisse, Ausgaben, Fehlermeldungen, Nebenwirkungen und gegebenenfalls zugesicherte Schnittstellen. Nur dieselbe Zahl zurückzugeben reicht nicht, wenn zusätzlich eine Datei anders überschrieben wird. Der relevante Beobachtungsrahmen sollte deshalb vor der Änderung feststehen.

## 3. Einfacher Vergleich aus dem Alltag

Du ordnest die Werkzeuge in einer Werkstatt neu, beschriftest Fächer und verkürzt Suchwege. Die Werkstatt kann danach dieselben Aufträge erfüllen, aber die Arbeit ist übersichtlicher organisiert.

Die Grenze des Vergleichs: Bei Software können schon kleine Umstellungen die Reihenfolge von Aktionen oder das Teilen von Daten verändern. Eine vermeintlich interne Änderung kann dadurch nach außen wirken. Das Ziel „Verhalten erhalten“ ist deshalb zu prüfen und nicht nur eine Bezeichnung für eine angenehmere neue Ordnung.

## 4. Wie funktioniert das?

Ein sinnvoller Ablauf beginnt mit dem Erfassen des bisherigen Verhaltens. Danach folgt eine kleine Strukturänderung und eine erneute Prüfung. Beispiele sind das Herausziehen eines klaren Teilablaufs in eine Hilfsfunktion oder das Umbenennen eines internen Namens.

Tests können ausgewählte Ergebnisse vor und nach der Umstellung vergleichen. Pythons Testbibliothek bietet etwa `assertEqual`; die [offizielle Dokumentation dieser Prüfung](https://docs.python.org/3.13/library/unittest.html#unittest.TestCase.assertEqual) beschreibt den Vergleich erwarteter Werte. Solche Tests sind Belege für ihre Fälle, kein mathematischer Nachweis jeder möglichen Verwendung. Ungeprüfte externe Nebenwirkungen müssen gesondert betrachtet werden.

## 5. Wo begegnet mir das unter Linux?

Ein Python-Projekt kann wiederholte Formatierungslogik in eine gemeinsame Funktion verschieben. In einem Hilfswerkzeug können reine Berechnungen von Dateizugriffen getrennt werden, damit sie leichter mit eigenen Daten geprüft werden können. Ob das tatsächlich hilfreich ist, hängt vom Code und seinen Aufgaben ab.

Ein großflächiger Neuaufbau einer Anwendung ist nicht automatisch ein Refactoring. Wenn gleichzeitig neue Funktionen hinzukommen, Fehler korrigiert und Schnittstellen verändert werden, ist die Wirkung schwerer zu beurteilen. Getrennte nachvollziehbare Schritte erleichtern die Prüfung.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Python-3-Beispiel zieht eine Formatierung in eine Hilfsfunktion heraus:

```python
def vorher(name):
    return "Name: " + name.strip().upper()

def normalisieren(name):
    return name.strip().upper()

def nachher(name):
    return "Name: " + normalisieren(name)

faelle = [" Sven ", "NetMon", ""]
for name in faelle:
    assert vorher(name) == nachher(name)
assert nachher(" Sven ") == "Name: SVEN"
print(nachher(" Sven "))
print("Vergleiche:", len(faelle))
```

Die Ausgabe lautet:

```text
Name: SVEN
Vergleiche: 3
```

Die äußere Funktion liefert weiterhin denselben Text. Das Bereinigen und Großschreiben erhält lediglich einen eigenen internen Namen. Die Vergleiche berücksichtigen Leerraum, einen normalen Text und eine leere Eingabe. Sie betreffen genau diese selbst gewählten Stringfälle; andere Eingabetypen oder eine reale Oberfläche werden nicht geprüft.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine Bugkorrektur ändert unerwünschtes Verhalten. Eine Erweiterung fügt Verhalten hinzu. Eine Optimierung zielt auf Eigenschaften wie Laufzeit oder Speicherverbrauch und muss die vereinbarten Grenzen berücksichtigen. Ein Refactoring kann spätere Verbesserungen erleichtern, ist aber nicht automatisch eine solche fachliche Änderung.

## 8. Häufige Missverständnisse

Mehr kleine Funktionen bedeuten nicht zwangsläufig besseren Code. Auch ein erfolgreiches Formatieren des Quelltexts beweist keine Verhaltenserhaltung. Umbenennungen können außen sichtbar sein, wenn Nutzer oder andere Module den betreffenden Namen als Schnittstelle verwenden. „Intern“ muss daher am tatsächlichen Gebrauch beurteilt werden.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Arbeite in kleinen Schritten und prüfe den Diff. Bewahre vorhandene Änderungen anderer Personen. Wenn ein Schritt Ergebnisse oder Schnittstellen bewusst verändert, dokumentiere ihn als eigene Verhaltensänderung. Das Beispiel verändert ausschließlich seine selbst definierten Funktionen im Lernskript; es refaktoriert keinen NetMon-Anwendungscode.
