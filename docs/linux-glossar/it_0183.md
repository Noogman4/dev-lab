# Client

## 1. Kurzbeschreibung

Ein Client ist ein Programm, das eine angebotene Leistung anfordert. Im Web kann ein Browser diese Rolle übernehmen. Ebenso können Kommandozeilenwerkzeuge oder andere Anwendungen Clients sein. Der Begriff beschreibt eine Rolle im Austausch, keine bestimmte Geräteklasse und keine notwendige grafische Oberfläche.

## 2. Was bedeutet der Begriff?

„Client“ bedeutet hier die anfragende Seite. Die [HTTP-Spezifikation zu Clients und Servern](https://www.rfc-editor.org/rfc/rfc9110.html#section-3.3) beschreibt einen Client als Programm, das Verbindungen für HTTP-Anfragen aufbaut. Das ist eine konkrete Definition im HTTP-Kontext; andere Protokolle besitzen eigene Abläufe.

Das Katalogbeispiel eines Browsers ist richtig. Der Mensch vor dem Browser ist jedoch nicht selbst das Protokollprogramm. Eine Eingabe kann im Browser mehrere technische Vorgänge auslösen. Umgekehrt kann ein Client automatisch arbeiten, ohne dass jemand jede einzelne Anfrage anklickt.

## 3. Einfacher Vergleich aus dem Alltag

Eine Stelle fordert eine Leistung bei einer anderen Stelle an. Für diesen Vorgang ist sie die anfragende Seite. Wenn sie anschließend selbst eine andere Leistung anbietet, übernimmt sie in einem anderen Vorgang eine andere Rolle.

Die Grenze: Programme verwenden genau definierte Schnittstellen. Eine Rolle ist keine Aussage darüber, welcher Beteiligte vertrauenswürdig ist oder wer alle Regeln bestimmen darf. Ein Client kann falsche Daten übermitteln; die Gegenstelle muss notwendige Bedingungen selbst prüfen.

## 4. Wie funktioniert das?

Ein Client bestimmt das gewünschte Ziel und bildet eine passende Anfrage. Bei HTTP gehören unter anderem Methode, Ziel und gegebenenfalls Nachrichtenfelder oder Inhalt dazu. Nach dem Austausch muss der Client Status und Daten nach dem Vertrag interpretieren.

Eine Bibliothek kann Teile dieser Arbeit übernehmen. Die [Python-Dokumentation zu urlopen](https://docs.python.org/3.13/library/urllib.request.html#urllib.request.urlopen) beschreibt beispielsweise eine Schnittstelle für entsprechende Zugriffe und Antworten. Ihr Vorhandensein bedeutet nicht, dass ein bloß erzeugtes Anfrageobjekt bereits gesendet wurde.

Zeitgrenzen, Fehler und eventuell nötige Wiederholungen sind weitere Fragen. Ein erfolgreicher Verbindungsaufbau ist noch keine fachlich passende Antwort. Eine Antwort ohne Transportfehler kann ebenso eine erlaubte Ablehnung oder einen Anwendungsfehler enthalten.

## 5. Wo begegnet mir das unter Linux?

Ein Browser, eine API-Abfrage oder ein Softwarewerkzeug kann als Client arbeiten. Die Rolle hängt nicht davon ab, ob das Programm im Terminal, als Dienst oder auf einem Notebook läuft. Auch ein Rechner, der andere Dienste bereitstellt, kann gleichzeitig Client einer weiteren Gegenstelle sein.

Bei einem Proxy wird das besonders sichtbar: Er nimmt auf einer Seite Anfragen an und stellt auf einer anderen Seite eigene Anfragen weiter. Daraus entsteht keine feste Trennung in reine Client- und reine Serverhardware für jeden Vorgang.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenmodell verwendet einen fiktiven Statusabruf. Es wurde keine Bibliotheksfunktion zum Senden aufgerufen und kein Dienst angesprochen.

```text
Ein Programm benötigt eine Statusdarstellung.
Es bestimmt Ziel, Methode und erwartetes Format.
Es stellt die passende Anfrage im beschriebenen Protokoll.
Eine Antwort oder ein konkreter Fehler wird entgegengenommen.
Das Ergebnis wird geprüft und an die weitere Anwendung weitergegeben.
```

Das Programm ist hier Client der Statusschnittstelle. Ob es das Ergebnis anschließend grafisch, als Text oder gar nicht unmittelbar anzeigt, ändert diese Rolle nicht. Die Darstellung gehört zu einer anderen Zuständigkeit.

Das Modell garantiert keine erfolgreiche Antwort. Ein echter Client müsste beispielsweise Berechtigungen und die Vertrauensprüfung der Verbindung berücksichtigen. Auch muss er eine ausbleibende Antwort von einer empfangenen Fehlerantwort unterscheiden. Es gibt hier keine tatsächlich gemessene Kommunikation oder installierte neue Clientsoftware.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Frontend ist eine nutzerseitige Anwendungsschicht. Ein Client ist eine Rolle beim Anfordern von Leistungen. Ein Browser kann beides verbinden. Eine API ist der Vertrag des Zugangs. Ein Request ist der konkrete Auftrag. Diese Begriffe betreffen verschiedene Ausschnitte desselben möglichen Ablaufs.

## 8. Häufige Missverständnisse

Client bedeutet nicht automatisch „Mensch“ oder „kleiner Rechner“. Eine grafische Oberfläche ist nicht erforderlich. Ein Client darf außerdem nicht allein deshalb jeden Zugriff ausführen, weil er eine korrekte Nachricht senden kann. Derselbe Prozess kann schließlich in verschiedenen Austauschbeziehungen unterschiedliche Rollen haben.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Beschreibe bei einer Diagnose das konkrete Programm, Ziel und Protokoll. Prüfe Antwortdaten statt nur das Ende des Aufrufs. Dieser Eintrag startet keinen Clientzugriff, installiert nichts und verändert weder Konten noch Dienste oder Netzwerkparameter.

## 10. Verwandte Begriffe

Das [Frontend](it_0181.md) betrifft die Nutzungsschicht. Ein [Request](it_0172.md) ist die Anfrage, eine [Response](it_0173.md) die Antwort. Der [Proxy](it_0162.md) kann mehrere Rollen verbinden. Die [API](it_0169.md) legt den Vertrag fest.
