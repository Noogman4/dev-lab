# Cookie

## 1. Kurzbeschreibung

Ein Cookie ist ein benannter Wert, den ein HTTP-Nutzeragent wie ein Browser nach bestimmten Regeln verwalten und bei passenden Anfragen mitsenden kann. Cookies können etwa eine Sitzungskennung oder eine Einstellung transportieren. Sie sind nicht automatisch die vollständige Sitzung, verschlüsselt oder nur für eine einzige Seite sichtbar.

## 2. Was bedeutet der Begriff?

[RFC 6265](https://www.rfc-editor.org/rfc/rfc6265.html) beschreibt die grundlegenden HTTP-Felder `Set-Cookie` und `Cookie`. Eine Antwort kann dem Browser einen Wert samt Attributen mitteilen. Ob und wie er gespeichert beziehungsweise gesendet wird, hängt von diesen Regeln und der Browserpolitik ab.

Die Quellbeschreibung einer kleinen im Browser gespeicherten Datenmenge ist damit ein brauchbarer Einstieg. Die konkrete Größe und Behandlung sind jedoch nicht beliebig. Das Katalogbeispiel einer Login-Sitzung sollte außerdem unterscheiden: Häufig identifiziert ein Cookie serverseitigen Sitzungszustand, statt alle dazugehörigen Daten selbst zu enthalten.

## 3. Einfacher Vergleich aus dem Alltag

Du erhältst eine Garderobenmarke und zeigst sie später wieder vor. Die Marke ermöglicht eine Zuordnung, enthält aber nicht selbst den abgegebenen Mantel. Ihre Bedeutung hängt von den Regeln der Ausgabestelle ab.

Die Grenze: Ein Cookie ist ein technischer Wert mit Übertragungs- und Gültigkeitsbedingungen. Nicht jeder Cookie dient als Zugangsnachweis. Falls ein Wert aber Zugang vermittelt, kann sein Verlust an die falsche Stelle relevant sein. Ein bloßer Name wie `session` garantiert keine sichere Umsetzung.

## 4. Wie funktioniert das?

Der Server setzt einen Wert mit gewünschten Attributen. Der Browser berücksichtigt unter anderem Host- beziehungsweise Domainbezug, Pfad und Gültigkeitsbedingungen. Bei passenden weiteren Anfragen kann er entsprechende Werte im Cookie-Feld übermitteln.

Die [Mozilla-Referenz zu Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) erläutert auch heutige Attribute wie `Secure`, `HttpOnly` und `SameSite`. Sie begrenzen unterschiedliche Aspekte: Übertragungsbedingungen, Zugriff über bestimmte Skriptschnittstellen und den Site-Kontext. Keines davon ist allein eine vollständige Zugriffsrichtlinie für die Anwendung.

Site und Origin sind dabei nicht derselbe Begriff. Außerdem können Browserregeln und Versionen Unterschiede verursachen. Ein gespeicherter Headertext ist deshalb kein Ersatz für die Prüfung, was ein konkreter Browser tatsächlich annimmt und sendet.

## 5. Wo begegnet mir das unter Linux?

Browser und HTTP-Bibliotheken können Cookieverwaltung verwenden. Ein Programm muss nicht dieselbe Speicherablage oder dieselben Regeln wie ein Browser besitzen. Ein reines Parserobjekt führt insbesondere noch keine Browserverwaltung aus.

Python stellt mit [SimpleCookie](https://docs.python.org/3.13/library/http.cookies.html#http.cookies.SimpleCookie) einen Zugang zum Verarbeiten entsprechender Werte bereit. Die Bibliothek und die vollständige aktuelle Browserpolitik sind aber nicht identisch. Der folgende Versuch prüft nur die ausgewählten selbst erzeugten Felder.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Ordner ausgeführt. Der Cookie-Wert ist erfunden und vermittelt keinen echten Zugriff. Kein Browserprofil wird geöffnet.

```python
from http.cookies import SimpleCookie

cookies = SimpleCookie()
cookies.load("probe=abc123; Path=/; Secure; HttpOnly; SameSite=Lax")
eintrag = cookies["probe"]
assert eintrag.value == "abc123"
assert eintrag["path"] == "/"
assert eintrag["secure"] is True
assert eintrag["httponly"] is True
assert eintrag["samesite"] == "Lax"
print(eintrag.key)
print(eintrag["path"])
print(eintrag["samesite"])
```

Geprüfte Ausgabe:

```text
probe
/
Lax
```

Die Assertions bestätigen die Interpretation dieser Attribute im Python-Objekt. Sie beweisen weder eine Browserannahme noch eine korrekte Sitzung oder einen gesicherten HTTPS-Austausch. Der Test speichert nichts in einem echten Cookiebestand und sendet keine Anfrage.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine Sitzung ist ein größerer Nutzungszusammenhang. Ein Token kann einen Zugriffsnachweis darstellen und über verschiedene Wege transportiert werden. Ein Cookie ist ein bestimmter HTTP-Zustandsmechanismus. Andere Browserablagen besitzen eigene APIs und werden nicht automatisch nach denselben Regeln mit Anfragen übertragen.

## 8. Häufige Missverständnisse

Ein Cookie ist nicht grundsätzlich ein Login. `HttpOnly` verschlüsselt den Wert nicht. Ein Pfadattribut ist auch keine vollständige Sicherheitsgrenze zwischen Anwendungen. Schließlich muss ein nicht dauerhaft gesetzter Cookie nicht unter allen Browser-Wiederherstellungsfunktionen genau dann verschwinden, wenn ein Fenster geschlossen wird.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Wähle Attribute passend zum tatsächlichen Einsatzzweck. Behandle echte Zugangskennungen vertraulich und prüfe Browserverhalten kontrolliert. Dieser Eintrag liest keine vorhandenen Cookies und verändert weder Profile, Konten, Sitzungen noch Dienste oder Servereinstellungen.

## 10. Verwandte Begriffe

[HTTP](it_0145.md) definiert den Kommunikationsrahmen. Die [Response](it_0173.md) kann Set-Cookie enthalten. Ein [Request](it_0172.md) kann passende Werte zurücksenden. [CORS](it_0185.md) betrifft eine andere Browserprüfung. [HTTPS](it_0146.md) ergänzt Verbindungsschutz.
