# Repository Git

## 1. Kurzbeschreibung

Ein Git-Repository enthält Versionsdaten eines Projekts, insbesondere gespeicherte Objekte und Verweise auf Entwicklungsstände. Häufig gehört ein Arbeitsverzeichnis dazu, in dem Dateien bearbeitet werden. Das ist jedoch nicht zwingend: Ein Bare-Repository besitzt kein eigenes gewöhnliches Arbeitsverzeichnis. Repository und gerade sichtbarer Projektordner sind deshalb nicht immer dieselbe Sache.

## 2. Was bedeutet der Begriff?

Das Katalogbeispiel nennt ein NetMon-Repository mit Code und Historie. Für den Alltag ist das anschaulich. Technisch muss man dennoch zwischen den Versionsdaten und den ausgecheckten Arbeitsdateien unterscheiden. Eine beliebige Kopie sichtbarer Dateien enthält nicht automatisch die zugehörige Git-Historie.

Die [offizielle Beschreibung des Repository-Aufbaus](https://raw.githubusercontent.com/git/git/master/Documentation/gitrepository-layout.adoc) erklärt gewöhnliche und Bare-Repositories. Sie nennt außerdem den Fall einer `.git`-Datei, die auf den eigentlichen Speicherort verweist. Die Regel „In jedem Projekt muss `.git` ein Unterverzeichnis sein“ wäre daher zu eng.

## 3. Einfacher Vergleich aus dem Alltag

Ein Archiv bewahrt abgelegte Arbeitsstände und ihre Zuordnungen auf. Auf einem Arbeitstisch liegt ein bestimmter daraus bereitgestellter Stand zur Bearbeitung. Das Archiv und der Tisch erfüllen verschiedene Aufgaben, auch wenn sie oft unmittelbar nebeneinander stehen.

Die Grenze: Git verwaltet technische Objekte und Referenzen statt Papierordner. Ein Arbeitsverzeichnis kann außerdem zusätzliche, noch nicht erfasste Dateien enthalten. Nicht alles, was auf dem Tisch liegt, gehört schon zum Archiv. Und ein Archiv kann existieren, ohne dass gerade ein Tisch eingerichtet ist.

## 4. Wie funktioniert das?

In einem üblichen Repository liegen Versionsdaten im Bereich `.git`. Dazu gehören beispielsweise Objektspeicher, Referenzen und lokale Einstellungen. Das Arbeitsverzeichnis zeigt die zur Bearbeitung bereitgestellten Dateien. Der Index beschreibt vorgemerkte Inhalte für einen nächsten Commit.

Ein Bare-Repository legt seine Git-Daten direkt im dafür vorgesehenen Verzeichnis ab und hat kein gewöhnliches Arbeitsverzeichnis. Es kann beispielsweise als Austauschziel dienen. „Bare“ bedeutet nicht „ohne Historie“ und auch nicht „automatisch im Internet erreichbar“. Ein neu angelegtes Repository kann dagegen unabhängig von seiner Form zunächst noch überhaupt keinen Commit besitzen.

Die [Dokumentation zu git init](https://raw.githubusercontent.com/git/git/master/Documentation/git-init.adoc) beschreibt die Anlage und die Option `--bare`. Sie erläutert auch den anfänglichen Branch ohne Commit. Sein Name allein beweist daher noch keinen gespeicherten Projektstand. Für die Strukturprüfung sind Git-Abfragen zuverlässiger als Annahmen aus einem Ordnernamen.

## 5. Wo begegnet mir das unter Linux?

Ein geklontes Entwicklungsprojekt erscheint oft als Verzeichnis mit Arbeitsdateien und `.git`. Ein lokal verwaltetes Austauschziel kann dagegen ein Bare-Repository sein. Die Endung `.git` wird dafür häufig verwendet, erzwingt aber selbst keinen bestimmten Inhalt.

Dateimanager blenden mit einem Punkt beginnende Namen häufig aus. Dadurch kann die Versionsverwaltung unsichtbar wirken. Versteckt bedeutet jedoch weder geschützt noch verschlüsselt. Git-Metadaten sollten ebenso sorgfältig behandelt werden wie der übrige Projektbestand.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 und Git 2.52.0 ausgeführt. Es legt zwei leere Übungsrepositories in einem neuen temporären Ordner an. Persönliche und systemweite Git-Konfiguration werden nur für die Kindprozesse ausgeblendet; Vorlagen werden nicht übernommen.

```python
import os
from pathlib import Path
import subprocess
import tempfile

env = {k: v for k, v in os.environ.items() if not k.startswith("GIT_")}
env.update(GIT_CONFIG_GLOBAL="/dev/null", GIT_CONFIG_NOSYSTEM="1")
with tempfile.TemporaryDirectory() as ordner:
    basis = Path(ordner)
    normal = basis / "normal"
    bare = basis / "austausch.git"
    def git(*args):
        return subprocess.run(
            ["git", *args], cwd=basis, env=env,
            check=True, capture_output=True, text=True
        ).stdout.strip()
    git("init", "--template=", "-b", "probe", str(normal))
    git("init", "--template=", "--bare", "-b", "probe", str(bare))
    normal_bare = git("-C", str(normal), "rev-parse", "--is-bare-repository")
    bare_bare = git("-C", str(bare), "rev-parse", "--is-bare-repository")
    assert normal_bare == "false" and bare_bare == "true"
    assert (normal / ".git").is_dir()
    assert (bare / "HEAD").is_file() and not (bare / ".git").exists()
    print("Normales Repository ist bare:", normal_bare)
    print("Austauschrepository ist bare:", bare_bare)
```

Geprüfte Ausgabe:

```text
Normales Repository ist bare: false
Austauschrepository ist bare: true
```

Die beiden Formen werden durch Git und ergänzende Strukturprüfungen unterschieden. Es werden keine Commits, Remotes oder Netzwerkverbindungen angelegt. Das Beispiel erstellt insbesondere kein zusätzliches Worktree des bestehenden Projekts. Beide Übungsrepositories werden danach entfernt.

## 7. Abgrenzung zu ähnlichen Begriffen

Git ist das Werkzeug. Das Repository hält Versionsdaten. Ein Arbeitsverzeichnis enthält bearbeitbare Dateien. Ein Hostingdienst bietet zusätzliche Verwaltung und Zusammenarbeit. Ein entfernter Ort ist eine Konfiguration beziehungsweise ein anderes Repository, nicht automatisch die Definition des eigenen.

## 8. Häufige Missverständnisse

Ein Repository benötigt nicht immer ein Arbeitsverzeichnis. `.git` muss nicht immer ein Verzeichnis sein. Ein neuer Branchname bedeutet noch keinen Commit. Und das Kopieren nur sichtbarer Dateien ist nicht automatisch eine vollständige Repository-Kopie.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Ändere Git-Metadaten nicht versuchsweise von Hand. Nutze die vorgesehenen Abfragen und Arbeitsabläufe. Eine Sicherung muss die tatsächlich benötigten Daten umfassen. Die Übung berührt weder das bestehende Projekt noch dessen entfernte Ziele.
