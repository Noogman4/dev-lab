# pyproject.toml

## 1. Kurzbeschreibung

`pyproject.toml` ist eine Projektdatei im TOML-Format. Python-Paketwerkzeuge verwenden sie unter anderem für die Auswahl des Build-Backends und für Metadaten. Auch einzelne Entwicklerwerkzeuge können eigene Einstellungen daraus lesen.

## 2. Was bedeutet der Begriff?

TOML gliedert Einstellungen in Tabellen und Schlüssel mit Werten. Eine Zeile wie `name = "notizbeispiel"` bekommt ihre Bedeutung aus der Tabelle, in der sie steht. Die [PyPA-Spezifikation zu pyproject.toml](https://packaging.python.org/en/latest/specifications/pyproject-toml/) definiert die Felder für Build-System und Projekt. Die Festlegung des Dateinamens macht daraus kein Python-Programm.

## 3. Einfacher Vergleich aus dem Alltag

Stell dir einen Auftragsordner mit getrennten Blättern vor. Auf einem steht, wer den Auftrag ausführen soll. Auf einem anderen stehen Produktname und Version. Die gemeinsamen Blätter können mehrere Teams lesen. Bei TOML müssen zusätzlich Schreibweise und Datentypen stimmen.

## 4. Wie funktioniert das?

`[build-system]` kann Anforderungen für den Build und den Namen des Backends festlegen. Ein Backend ist das Werkzeug, das die Artefakte erzeugt. Unter `[project]` stehen beispielsweise Name, reguläre Abhängigkeiten und Angaben zur unterstützten Python-Version. Wenn ein zulässiges Feld unter `dynamic` aufgeführt wird, kann sein Wert durch den Build bestimmt werden.

Unter `[tool]` verwenden Werkzeuge eigene Untertabellen. Eine Einstellung dort wirkt nur auf Programme, die genau diese Tabelle lesen. Es gibt keine Garantie, dass jedes Python-Projekt alle diese Tabellen benötigt oder dass ein beliebiges Backend sie gleich behandelt.

## 5. Wo begegnet mir das unter Linux?

Unter Linux liegt die Datei häufig neben Quelltext, Tests und README. Ein Paketwerkzeug kann aus einem Projektverzeichnis eine Python-Distribution erstellen. Eine IDE kann zugleich Einstellungen ihres Formatierungswerkzeugs aus derselben Datei lesen. Das Zusammenspiel hängt von den installierten Werkzeugen ab.

## 6. Konkretes Beispiel Schritt für Schritt

Das Beispiel untersucht ausschließlich Text. Es braucht Python ab 3.11, wie die [Dokumentation zu tomllib](https://docs.python.org/3.13/library/tomllib.html) angibt. Der erste Schritt liest TOML in verschachtelte Python-Dictionaries. Der zweite Schritt prüft, dass Build- und Projektangaben getrennt vorliegen.

```python
import tomllib

text = """
[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"

[project]
name = "Notizbeispiel"
version = "0.1.0"
"""
data = tomllib.loads(text)
assert data["build-system"]["requires"] == ["setuptools"]
assert data["project"]["version"] == "0.1.0"
print(data["project"]["name"], data["project"]["version"])
```

Die erwartete Ausgabe lautet `Notizbeispiel 0.1.0`. Dabei wird nur eine Zeichenkette verarbeitet.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine Sperrdatei hält je nach Werkzeug konkrete aufgelöste Versionen fest. Eine Projektdatei kann flexiblere Anforderungen ausdrücken. Die Metadaten im fertigen Paket sind ein weiterer Ort, an dem sich das Ergebnis kontrollieren lässt.

## 8. Häufige Missverständnisse

Gültiges TOML beweist keine fachlich gültige Paketbeschreibung. Ein fehlender Projektname oder eine unzulässige Versionsangabe kann erst dem Build-Werkzeug auffallen. Die Beispielprüfung überprüft nur die gezeigten Felder.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe bei einer Fehlermeldung zuerst den betroffenen Tabellennamen und anschließend die Dokumentation des zuständigen Werkzeugs. Wenn du die Datei veröffentlichst, bleiben ihre Werte für Leser sichtbar. Zugangsdaten gehören in dafür eingerichtete Mechanismen.
