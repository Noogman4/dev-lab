# Bug

## 1. Kurzbeschreibung

Ein Bug ist ein Defekt in Software, durch den sie unter bestimmten Umständen unerwünschtes oder falsches Verhalten zeigt. Das kann ein falsches Rechenergebnis, eine doppelt ausgeführte Aktion oder ein Absturz sein. Ein Bug muss nicht bei jedem Start sichtbar werden und nicht unbedingt eine Fehlermeldung auslösen.

## 2. Was bedeutet der Begriff?

Um einen Defekt zu beurteilen, braucht man eine nachvollziehbare Erwartung. „Der Knopf soll eine Aufgabe einmal anfordern“ ist überprüfbarer als „der Knopf funktioniert nicht“. Wenn derselbe Klick zwei Anforderungen erzeugt, liegt eine konkrete Abweichung vor.

Die Beobachtung allein erklärt jedoch noch nicht die Ursache. Vielleicht wurde die Aktion im Code doppelt registriert, vielleicht wurde ein Ereignis erneut zugestellt oder die Anzeige zählt falsch. Eine belastbare Diagnose trennt erwartetes Verhalten, tatsächliche Wirkung und vermuteten Defekt.

## 3. Einfacher Vergleich aus dem Alltag

Ein Getränkeautomat, der nach einmaligem Bezahlen zwei Bestellvorgänge auslöst, verhält sich anders als vorgesehen. Ein solcher Fehler kann in der Steuerung liegen, auch wenn das Gehäuse unbeschädigt aussieht.

Der Vergleich hat Grenzen: Softwarefehler betreffen keine abgebrochenen mechanischen Teile. Sie können aus dem Zusammenspiel von Zuständen, Eingaben und zeitlicher Reihenfolge entstehen. Auch ein korrektes Programm kann scheitern, wenn beispielsweise eine benötigte Ressource fehlt. Nicht jede Störung beweist deshalb einen Bug.

## 4. Wie funktioniert das?

Ein Defekt wird wirksam, wenn sein auslösender Fall erreicht wird. Eine falsch gewählte Grenze betrifft vielleicht nur genau einen Wert. Eine doppelte Ereignisbehandlung fällt unter Umständen erst auf, nachdem eine Ansicht mehrfach geöffnet wurde. Tests sollten deshalb auch den erforderlichen vorherigen Zustand erfassen.

Automatisierte Prüfungen können erwartete und beobachtete Werte vergleichen. Pythons `unittest` bietet dafür unter anderem `assertEqual`; die [offizielle Methodendokumentation](https://docs.python.org/3.13/library/unittest.html#unittest.TestCase.assertEqual) beschreibt das Scheitern bei ungleichen Werten. Ein bestandener Vergleich belegt aber nur den geprüften Fall, nicht die Fehlerfreiheit sämtlicher Abläufe.

## 5. Wo begegnet mir das unter Linux?

Ein grafisches Programm kann eine Aktion doppelt anstoßen; ein Hilfsskript kann bei leerer Eingabe abstürzen. Ein Fehler kann im Anwendungsprogramm, einer Bibliothek oder einer Systemkomponente liegen. Ohne Eingrenzung sollte nicht vorschnell die darunterliegende Plattform verantwortlich gemacht werden.

Für eine Meldung sind reproduzierbare Schritte, Versionen sowie erwartetes und tatsächliches Verhalten hilfreich. Die [Python-Anleitung zum Umgang mit Bugs](https://docs.python.org/3.13/bugs.html) verlangt solche Angaben für Python-Berichte und empfiehlt die Suche nach bereits bekannten Meldungen. Das sind nützliche Vorgehensweisen; die konkrete Meldestelle hängt selbstverständlich vom betroffenen Projekt ab.

## 6. Konkretes Beispiel Schritt für Schritt

Das Quellbeispiel mit zwei gestarteten Prozessen wird hier ungefährlich als doppelt gespeicherte Anforderung nachgebildet. Das vollständige Python-3-Skript startet keinen Prozess:

```python
def fehlerhaft(auftraege):
    auftraege.append("Start")
    auftraege.append("Start")

def korrigiert(auftraege):
    auftraege.append("Start")

alt = []
neu = []
fehlerhaft(alt)
korrigiert(neu)
assert alt == ["Start", "Start"]
assert neu == ["Start"]
print(len(alt))
print(len(neu))
```

Die Ausgabe lautet:

```text
2
1
```

Die erste Funktion verletzt die festgelegte Regel „ein Aufruf, eine Anforderung“. Die zweite erfüllt sie im gezeigten Fall. Die Zusicherungen prüfen beide Zustände ausdrücklich. Damit ist eine kleine Fehlerursache demonstriert, aber keine reale grafische Ereigniskette oder Prozesssteuerung getestet.

## 7. Abgrenzung zu ähnlichen Begriffen

Eine Ausnahme ist ein technischer Kontrollmechanismus und kann einen Bug anzeigen, muss es aber nicht. Eine fehlende Voraussetzung ist zunächst ein Umgebungsproblem. Eine neue Anforderung verändert das gewünschte Verhalten; eine Bugkorrektur stellt das bereits vereinbarte Verhalten her. Bei unklaren Anforderungen muss diese Abgrenzung gemeinsam geklärt werden.

## 8. Häufige Missverständnisse

Ein Bug muss nicht zuverlässig bei jedem Versuch auftreten. „Bei mir funktioniert es“ widerlegt keinen Fall mit anderen Voraussetzungen. Das Verbergen einer Meldung behebt keine Ursache. Auch können Tests selbst falsche Erwartungen enthalten; sie müssen zur tatsächlichen Anforderung passen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Erzeuge vor einer Korrektur einen kleinen nachvollziehbaren Fall. Prüfe danach die beabsichtigte Änderung und wichtige benachbarte Fälle. Bei Sicherheitsproblemen gehören vertrauliche Daten nicht in öffentliche Meldungen. Das Lernbeispiel verwendet nur eigene Listen und verändert keine Dienste oder echten Aufträge.
