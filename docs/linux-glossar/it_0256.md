# Code Review

## 1. Kurzbeschreibung

Ein Code Review ist die fachliche Durchsicht einer Änderung, häufig durch eine andere Person. Dabei werden Zweck, tatsächliche Wirkung und Einpassung in das Projekt beurteilt. Tests und automatische Werkzeuge liefern unterstützende Informationen. Ein Review ist dennoch eine eigene Tätigkeit mit einem konkreten Umfang und kein pauschaler Beweis, dass jeder denkbare Fehler ausgeschlossen ist.

## 2. Was bedeutet der Begriff?

Die Quelle nennt Fehlererkennung und bessere Lesbarkeit. Dazu gehört auch die Frage, ob der Code das beabsichtigte Problem sinnvoll löst. Eine Änderung kann formal sauber und erfolgreich getestet sein, während sie eine wichtige Anforderung noch verfehlt.

Googles [Beschreibung relevanter Review-Aspekte](https://google.github.io/eng-practices/review/reviewer/looking-for.html) behandelt unter anderem Entwurf, Funktionalität, Verständlichkeit und Tests. Das ist eine Primärquelle zu Googles eigenen Engineering-Praktiken, keine universell verbindliche Prozessvorschrift für jedes Projekt. Die konkreten Regeln muss das jeweilige Team festlegen.

## 3. Einfacher Vergleich aus dem Alltag

Eine zweite Redaktion liest eine überarbeitete Anleitung. Sie betrachtet nicht nur Tippfehler, sondern auch, ob die Schritte verständlich, vollständig und mit dem Zweck vereinbar sind. Ein Rechtschreibprogramm kann dabei helfen, übernimmt diese fachliche Durchsicht aber nicht.

Die Grenze: Eine zweite Person kann ebenfalls etwas übersehen. Sie benötigt Kontext, passende Zeit und klare Erwartungen. Auch ein gut formulierter Kommentar ist noch keine ausgeführte Änderung. Beobachtung, Diskussion und tatsächlicher neuer Stand müssen unterschieden werden.

## 4. Wie funktioniert das?

Zunächst wird der Änderungskontext bereitgestellt: Welches Problem wird gelöst, was soll danach anders sein und welche Prüfungen wurden tatsächlich ausgeführt? Die prüfende Person betrachtet den Unterschied und bei Bedarf den umgebenden Code. Nur einzelne Zeilen ohne ihren Vertrag zu lesen, kann wichtige Zusammenhänge verbergen.

Anschließend werden konkrete Beobachtungen und begründete Fragen festgehalten. Ein hilfreicher Hinweis verbindet eine Stelle mit einer möglichen Wirkung. Persönliche Stilvorlieben sollten von notwendigen Korrekturen erkennbar unterschieden werden. Automatisch festgelegte Formatregeln können wiederkehrende Detaildiskussionen verringern.

Googles [Standard für Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html) beschreibt die Abwägung zwischen Verbesserung der Codequalität und sinnvollem Fortschritt. Daraus folgt nicht, dass jede beliebige Einschränkung akzeptiert werden soll. Entscheidungen sollen auf Anforderungen, Qualität und nachvollziehbaren Argumenten beruhen.

Weitere Änderungen können eine erneute Betrachtung nötig machen. Ein Review bezieht sich auf einen bestimmten Stand. Wird danach zusätzliche Logik ergänzt, ist sie nicht allein durch eine ältere Zustimmung automatisch geprüft. Auch verbleibende Unsicherheiten sollten erkennbar dokumentiert werden.

## 5. Wo begegnet mir das unter Linux?

Teams prüfen Änderungen lokal oder über Hostingdienste. Ein Pull Request kann Diskussion, Unterschiede und Prüfergebnisse zusammenführen. Die Oberfläche organisiert den Vorgang, beurteilt aber nicht selbst jede fachliche Aussage.

Bei diesem Glossar bleibt die unabhängige inhaltliche Prüfung ausdrücklich offen. Die Autorenprüfung von Quellen, Struktur und Beispielen ist nicht mit einer zweiten unabhängigen Freigabe gleichzusetzen. Dieser Eintrag fordert keine Reviewer an und versendet keine Kommentare oder Nachrichten.

## 6. Konkretes Beispiel Schritt für Schritt

Das folgende Gedankenbeispiel wurde nicht als tatsächliches Review ausgeführt. Eine erfundene Änderung soll einen geladenen Notiztitel anzeigen. Die Beschreibung meldet, dass die Speicheranfrage keinen Fehler ausgelöst hat.

Zuerst betrachtet die prüfende Person die Anforderung: Der Nutzer soll den tatsächlich geladenen Titel sehen. Sie erkennt dann im gedachten Code, dass zwar Daten angefordert werden, die Anzeige aber immer nur „OK“ zurückgibt. Eine Prüfung auf bloßen Aufruferfolg würde diese Abweichung nicht entdecken.

Danach formuliert sie eine konkrete Rückfrage: Wie wird der geladene Titel an die Darstellung übergeben, und welcher Test beobachtet diesen Wert? Die Frage richtet sich auf die Wirkung und den Nachweis, nicht nur auf die persönliche Vorliebe für einen Variablennamen.

Anschließend würde die Änderung überarbeitet und mit einem passenden eigenen Test geprüft. Der neue Unterschied müsste erneut betrachtet werden. Ein nur mündlich angekündigter Fix wäre noch kein überprüfbarer neuer Stand.

Schließlich würde festgehalten, was wirklich beurteilt wurde und welche Teile offen bleiben. Dieses Modell behauptet keine existierende fehlerhafte Projektstelle, keinen versandten Kommentar und keine fachliche Freigabe eines tatsächlichen Pull Requests.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Test führt ausgewählte Fälle aus. Linting untersucht definierte Auffälligkeiten. Ein Formatter vereinheitlicht Darstellung. Ein Review beurteilt weitere Zusammenhänge durch Menschen. Eine abschließende Produktabnahme kann wiederum andere Anforderungen und Rollen besitzen.

## 8. Häufige Missverständnisse

Eine grüne Testsuite ersetzt nicht jede fachliche Durchsicht. Eine Zustimmung gilt nicht automatisch für später ergänzten Code. Ein Stilwunsch ist nicht immer ein Fehler. Und eine Autorenprüfung ist keine unabhängige Zweitprüfung.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Beschreibe Zweck, Umfang und Prüfergebnisse konkret. Formuliere Hinweise sachlich und begründet. Mache offene Punkte sichtbar. Dieses Gedankenbeispiel verändert keine Anwendung, weist niemandem ein Review zu und behauptet keine Reader- oder Zweitprüfungsabnahme.
