# Autorisierung

## 1. Kurzbeschreibung

Autorisierung entscheidet, ob eine bestimmte handelnde Identität eine bestimmte Aktion an einer bestimmten Ressource ausführen darf. Dabei können Rollen, Zuständigkeiten und weitere Bedingungen berücksichtigt werden. Eine erfolgreiche Anmeldung allein beantwortet diese Frage nicht vollständig. Auch die Kenntnis einer Objektkennung oder das Anzeigen eines Knopfs ist noch keine passende Berechtigung.

## 2. Was bedeutet der Begriff?

Die Quelle nennt Einstellungen, die nur Administratoren ändern dürfen. Das ist ein mögliches Rollenmodell. Andere Regeln unterscheiden beispielsweise zwischen eigenen und fremden Dokumenten. Auch öffentlich zugängliche Inhalte können bewusst ohne vorherige Anmeldung erlaubt sein.

Der [OWASP-Leitfaden zur Autorisierung](https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/Authorization_Cheat_Sheet.md) grenzt die Berechtigungsentscheidung von Authentifizierung ab. Er erläutert unter anderem zurückhaltende Standardentscheidungen und die Prüfung relevanter Anfragen. Welche Regeln gelten sollen, muss zur konkreten Anwendung passen. Der Begriff „Admin“ ist kein universeller Freibrief für jede technische Handlung.

## 3. Einfacher Vergleich aus dem Alltag

Ein Mitarbeiterausweis zeigt, zu wem ein Ausweis gehört. Ob diese Person ein bestimmtes Archiv betreten darf, richtet sich zusätzlich nach ihrer Zugangsberechtigung. Derselbe Ausweis kann für einen Bereich ausreichen und für einen anderen nicht.

Die Grenze: Software muss Rechte an den maßgeblichen Zugriffspunkten tatsächlich prüfen. Ein Warnschild oder ein ausgeblendeter Menüpunkt verhindert keinen anders ausgelösten Aufruf. Außerdem können Rechte geändert werden. Ein früher erlaubter Zugriff ist daher nicht automatisch für jede spätere Aktion weiter gültig.

## 4. Wie funktioniert das?

Eine Entscheidung benötigt die relevante Identität, die gewünschte Aktion und das betroffene Objekt beziehungsweise den Bereich. Danach wird die vorgesehene Regel angewendet. Eine Anwendung kann beispielsweise prüfen, ob eine Notiz der handelnden Identität zugeordnet ist. Andere Systeme verwenden zusätzliche Rollen oder Attribute.

Der [OWASP-Leitfaden zu direkten Objektreferenzen](https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.md) beschreibt Probleme fehlender objektbezogener Zugriffskontrolle. Eine erratene oder bekannte Kennung darf die Berechtigungsprüfung nicht ersetzen. Auch eine schwer zu erratende Kennung allein ist keine vollständige Autorisierung.

Die Prüfung muss zu den tatsächlich verwendeten Daten passen. Vom Anfragenden frei gelieferte Rollen oder Benutzerkennungen sind nicht automatisch vertrauenswürdige Identitätsinformationen. Die Herkunft solcher Angaben gehört zum gesamten Sicherheitsentwurf. Im Beispiel werden Identitäten nur als eigene Testvorgaben eingesetzt; es implementiert keine reale Anmeldung.

## 5. Wo begegnet mir das unter Linux?

Dateizugriffe, Dienste und Anwendungen besitzen unterschiedliche Berechtigungsmodelle. Eine erlaubte Aktion innerhalb einer Anwendung ist nicht mit Root-Rechten auf dem Betriebssystem gleichzusetzen. Umgekehrt sollte ein Programm nicht allein aus einem angezeigten Benutzernamen auf sämtliche notwendigen Rechte schließen.

Bei einer Anwendung können Lesen und Ändern außerdem verschiedene Bedingungen haben. Wer einen Inhalt sehen darf, darf ihn nicht zwangsläufig löschen. Dieses Dokument verändert keine Rechte, Konten oder Dateien und untersucht keine fremden Benutzerbestände.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Alle Identitäten und Notizen sind erfunden. Es prüft nur eine eigene Regel im Speicher: Lesen ist für die zugeordnete Identität erlaubt.

```python
notizen = {
    1: {"besitzer": "probe_a", "text": "Probe A"},
    2: {"besitzer": "probe_b", "text": "Probe B"},
}

def lesen(identitaet, kennung):
    notiz = notizen.get(kennung)
    if notiz is None or notiz["besitzer"] != identitaet:
        raise PermissionError("Nicht erlaubt")
    return notiz["text"]

eigene = lesen("probe_a", 1)
assert eigene == "Probe A"
abgelehnt = 0
for identitaet, kennung in [("probe_a", 2), ("probe_a", 999), ("unbekannt", 1)]:
    try:
        lesen(identitaet, kennung)
    except PermissionError:
        abgelehnt += 1
assert abgelehnt == 3
print("Eigene Notiz:", eigene)
print("Abgelehnte Zugriffe:", abgelehnt)
```

Geprüfte Ausgabe:

```text
Eigene Notiz: Probe A
Abgelehnte Zugriffe: 3
```

Der bekannte fremde Schlüssel 2 reicht nicht zum Lesen. Auch ein unbekanntes Objekt und eine unpassende Identität werden abgelehnt. Diese lokale Testfunktion ist kein produktionsreifes Zugriffssystem: Vertrauenswürdige Identitätsbindung, konkurrierende Änderungen, Rollenverwaltung und weitere Aktionen sind nicht umgesetzt oder abgenommen.

## 7. Abgrenzung zu ähnlichen Begriffen

Authentifizierung prüft zugeordnete Nachweise einer Identität. Autorisierung entscheidet über Aktionen. Ein Feature Flag wählt Funktionsvarianten. Ein Primärschlüssel identifiziert einen Datensatz. Keiner dieser anderen Bausteine ersetzt für sich genommen die passende objektbezogene Berechtigungsentscheidung.

## 8. Häufige Missverständnisse

Angemeldet bedeutet nicht uneingeschränkt berechtigt. Ein ausgeblendeter Knopf ist keine vollständige Zugriffskontrolle. Eine zufällige Kennung ist kein allgemeiner Berechtigungsnachweis. Und Leserechte erlauben nicht automatisch Änderungen oder Löschungen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Formuliere Regeln für Aktion und Objekt ausdrücklich. Prüfe erlaubte und abgelehnte Fälle mit eigenen Daten. Nutze Identitätsinformationen aus dem vorgesehenen vertrauenswürdigen Ablauf. Die Übung führt keinerlei Zugriffe auf reale Konten oder fremde Ressourcen aus.
