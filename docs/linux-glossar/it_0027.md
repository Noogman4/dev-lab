# Debugging

## 1. Kurzbeschreibung

Debugging ist das systematische Untersuchen und Eingrenzen von Softwarefehlern. Ziel ist, eine Ursache zu verstehen und eine nachvollziehbare Korrektur zu ermöglichen. Dazu können kleine Tests, Protokollausgaben oder ein Debugger dienen. Das bloße Verändern verdächtiger Zeilen ohne überprüfbare Vermutung ist noch keine verlässliche Fehlersuche.

## 2. Was bedeutet der Begriff?

Am Anfang steht eine konkrete Abweichung: Was sollte geschehen, was geschah tatsächlich und unter welchen Voraussetzungen? Danach wird die Aufgabe möglichst klein reproduziert. Eine Vermutung sollte so formuliert sein, dass eine Beobachtung sie bestätigen oder widerlegen kann.

Ein Werkzeug kann dabei Zustände sichtbar machen, aber nicht die fachliche Erwartung bestimmen. Wenn eine Rechnung den falschen Grenzwert verwendet, musst du zuerst wissen, welche Regel gelten soll. Mehr Ausgaben allein ersetzen diese Klärung nicht.

## 3. Einfacher Vergleich aus dem Alltag

Bei einer nicht leuchtenden Lampe prüfst du nacheinander Stromversorgung, Schalter und Leuchtmittel. Du tauschst nicht gleichzeitig alle Teile aus, wenn du verstehen willst, wo die Störung lag.

Die Grenze des Vergleichs: Software kann auf zeitliche Abläufe und gemeinsam verwendete Zustände reagieren. Zusätzliche Protokollausgaben oder Pausen können einen Fehler sogar beeinflussen. Ein unter Beobachtung verschwundenes Problem ist deshalb nicht automatisch behoben. Reproduzierbare Eingaben und dokumentierte Bedingungen bleiben wichtig.

## 4. Wie funktioniert das?

Ein Debugger kann die Ausführung an einem Haltepunkt anhalten. Dann lassen sich lokale Werte und Aufrufstellen untersuchen oder einzelne Schritte ausführen. Pythons eingebautes Modul `pdb` bietet solche Funktionen; die [offizielle pdb-Dokumentation](https://docs.python.org/3.13/library/pdb.html) beschreibt Haltepunkte, Einzelschritte und die Untersuchung des Aufrufstapels.

`breakpoint()` kann einen Debugger am Aufrufort aufrufen. Standardmäßig führt der Python-Hook zu `pdb`, er kann jedoch konfiguriert oder ersetzt sein. Die [Referenz zu breakpoint](https://docs.python.org/3.13/library/functions.html#breakpoint) erläutert diese Abhängigkeit. Ein stehen gebliebenes Programm kann daher lediglich auf eine interaktive Debuggereingabe warten, statt abgestürzt zu sein.

## 5. Wo begegnet mir das unter Linux?

Bei Python-Skripten können gezielte Ausgaben einen falsch berechneten Zwischenstand zeigen. In einer grafischen Anwendung kann ein Debugger helfen, die auslösende Ereigniskette zu untersuchen. Bei externen Diensten müssen zusätzlich deren Schnittstellen und Betriebsbedingungen betrachtet werden.

Entscheidend ist, Beobachtung und Reparatur zu trennen. Ein verdächtiger Wert liefert eine Spur, aber noch keinen vollständigen Ursachenbeweis. Nach einer Korrektur sollte der ursprüngliche Fall erneut geprüft werden. Sonst bleibt unklar, ob sich lediglich die sichtbare Meldung verändert hat.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Python-3-Beispiel sucht einen einfachen Fehler mit gezielten Ausgaben. Es startet keine interaktive Debuggersitzung:

```python
werte = [2, 4, 6]
summe = sum(werte)
teiler = len(werte) + 1
falscher_mittelwert = summe / teiler
print("Zwischenstand:", summe, teiler)
assert falscher_mittelwert == 3.0
teiler = len(werte)
mittelwert = summe / teiler
assert mittelwert == 4.0
print("Korrigiert:", mittelwert)
```

Die Ausgabe lautet:

```text
Zwischenstand: 12 4
Korrigiert: 4.0
```

Drei Werte werden fälschlich durch vier geteilt. Die Ausgabe legt genau diesen Zwischenstand offen. Mit der tatsächlichen Anzahl ergibt sich der erwartete Mittelwert. Die Zusicherungen machen beide Beobachtungen überprüfbar. Der Fall einer leeren Liste wäre eine zusätzliche Anforderung; dieses Beispiel legt ausdrücklich eine nichtleere Liste fest.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Test beobachtet Verhalten und vergleicht es mit Erwartungen. Debugging untersucht die Ursache einer Abweichung. Logging zeichnet Zustände oder Ereignisse auf und kann dafür Material liefern. Eine Korrektur verändert das Programm; anschließend muss geprüft werden, ob sie tatsächlich das gewünschte Verhalten herstellt.

## 8. Häufige Missverständnisse

Ein Debugger behebt keinen Fehler automatisch. Viele ungezielte Ausgaben sind nicht zwangsläufig hilfreicher als wenige gezielte. Ein einmal bestandener Fall beweist außerdem keine vollständige Fehlerfreiheit. Das Unterdrücken einer Ausnahme erklärt nicht, weshalb sie entstand.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Arbeite mit kleinen eigenen Daten. Protokolle können vertrauliche Werte enthalten; gib deshalb nur notwendige Angaben aus. Debugger können untersuchten Code weiter ausführen und damit echte Nebenwirkungen auslösen. Die hier beschriebene interaktive Debuggernutzung wurde nicht praktisch ausgeführt; geprüft wurde ausschließlich das vollständige Rechenbeispiel mit Ausgaben.
