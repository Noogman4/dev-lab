# Request

## 1. Kurzbeschreibung

Ein Request ist eine Anfrage, mit der ein Programm einen anderen Bestandteil um eine definierte Leistung bittet. Das kann ein Abruf oder ein Auftrag zur Verarbeitung sein. Im Web-Kontext verwendet man dafür häufig HTTP. Das Erzeugen einer Anfrage, ihr Senden und die erfolgreiche Ausführung sind jedoch verschiedene Schritte.

## 2. Was bedeutet der Begriff?

„Request“ bedeutet Anfrage oder Anforderung. Seine technische Form richtet sich nach der Schnittstelle. Ein lokaler Dienst kann andere Nachrichten verwenden als eine entfernte HTTP-API. Die folgenden konkreten Beispiele betreffen HTTP, ohne den allgemeinen Begriff darauf zu beschränken.

[RFC 9110 zur HTTP-Nachrichtenabstraktion](https://www.rfc-editor.org/rfc/rfc9110.html#section-6) beschreibt Steuerdaten, Felder und möglichen Inhalt. Zur Anfrage gehören insbesondere die gewünschte Methode und das Ziel. Ein URL-Text allein enthält deshalb nicht schon jede Aussage darüber, welche Operation verlangt wird.

## 3. Einfacher Vergleich aus dem Alltag

Du füllst einen Arbeitsauftrag aus. Darin stehen die zuständige Stelle, die gewünschte Handlung und die nötigen Angaben. Das fertige Formular auf deinem Schreibtisch ist noch kein zugestellter oder bereits ausgeführter Auftrag.

Die Grenze: Technische Schnittstellen akzeptieren genau definierte Formen. Sie ergänzen fehlende Angaben nicht nach Menschenkenntnis. Auch kann nach dem Absenden unklar bleiben, ob der Auftrag bereits verarbeitet wurde, wenn die Rückmeldung verloren geht. Diese Unsicherheit muss die Anwendung berücksichtigen.

## 4. Wie funktioniert das?

Ein Client stellt die Anfrage nach den Schnittstellenregeln zusammen. Bei HTTP können Methode, Ziel, Nachrichtenfelder und ein optionaler Inhalt beteiligt sein. Die konkrete Übertragung hängt von der HTTP-Version und dem Transport ab. Die Bedeutung des Auftrags bleibt davon zu unterscheiden.

Die Gegenstelle kann die Anfrage prüfen, ablehnen, weiterleiten oder verarbeiten. Authentifizierung, Berechtigung und fachliche Gültigkeit sind dabei eigene Bedingungen. Ein syntaktisch korrektes Dokument ist nicht automatisch ein erlaubter Auftrag.

Wiederholungen benötigen ebenfalls klare Regeln. [RFC 9110 zu idempotenten Methoden](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) beschreibt, wann die beabsichtigte Wirkung einer Wiederholung der einmaligen Ausführung entspricht. Eine fehlende Antwort ist deshalb kein allgemeiner Freibrief, jeden verändernden Auftrag beliebig erneut zu senden.

## 5. Wo begegnet mir das unter Linux?

Browser und andere Anwendungen stellen Anfragen, um Daten oder Funktionen zu nutzen. Auch eine Bibliothek kann dafür ein Anfrageobjekt bereitstellen. Erst eine geeignete Sendeoperation löst den tatsächlichen Austausch aus.

Python beschreibt [urllib.request.Request](https://docs.python.org/3.13/library/urllib.request.html#urllib.request.Request) als Abstraktion einer URL-Anfrage. Ein solches Objekt kann Ziel, Felder und Methode halten. Seine Existenz ist kein Nachweis einer Netzwerkverbindung, eines gültigen Zertifikats oder einer Antwort des Servers.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Ordner ausgeführt. Es erzeugt nur ein eigenes Objekt im Speicher. Es gibt bewusst keinen Aufruf zum Öffnen oder Senden.

```python
from urllib.request import Request

url = "https://dienst.beispiel.invalid/api/status"
anfrage = Request(url, headers={"Accept": "application/json"}, method="GET")
assert anfrage.get_method() == "GET"
assert anfrage.full_url == url
assert anfrage.get_header("Accept") == "application/json"
assert anfrage.data is None
print(anfrage.get_method())
print(anfrage.get_header("Accept"))
print(anfrage.data is None)
```

Geprüfte Ausgabe:

```text
GET
application/json
True
```

Die Assertions prüfen die ausdrücklich gewählte Methode, das fiktive Ziel und das gewünschte Antwortformat. Das Accept-Feld ist eine Präferenz des Clients, keine gemessene Zusage eines Servers. Der letzte Wert zeigt den hier nicht gesetzten Anfrageinhalt. Keine der Prüfungen bestätigt eine tatsächliche Dienstfunktion oder eine erfolgreiche HTTPS-Verbindung.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Endpoint bezeichnet einen Zugang. Ein Request ist die konkrete Anforderung. Eine Response ist die zugehörige Antwort im verwendeten Austauschmodell. Ein Netzwerkpaket wiederum ist eine Übertragungseinheit auf einer anderen Ebene. Ein Request kann sich über mehrere Pakete erstrecken.

## 8. Häufige Missverständnisse

Nicht jede Anfrage liefert JSON. Ein `GET`-Text im Quellcode bedeutet auch nicht, dass bereits etwas gesendet wurde. Eine Zeitüberschreitung beweist nicht automatisch, dass ein Server nichts ausgeführt hat. Umgekehrt garantiert eine empfangene Antwort nicht, dass der fachlich gewünschte Erfolg eingetreten ist.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe Methode, Ziel, Daten und Berechtigung gemeinsam. Plane Zeitgrenzen und Wiederholungen nach dem Schnittstellenvertrag. Das Beispiel arbeitet nur mit selbst gewählten Werten und verändert weder Dienste noch Konten, Verbindungen oder Anwendungseinstellungen.

## 10. Verwandte Begriffe

Der [Endpoint](it_0171.md) beschreibt den Zugang. Die [API](it_0169.md) legt den Vertrag fest. [HTTP](it_0145.md) definiert konkrete Nachrichtenregeln. Ein [Packet](it_0163.md) ist eine andere Übertragungseinheit. [HTTPS](it_0146.md) ergänzt gegebenenfalls den Schutzkontext.
