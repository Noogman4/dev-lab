# Multithreading

## 1. Kurzbeschreibung

Multithreading bedeutet, mehrere Threads innerhalb eines Prozesses zu verwenden. Ihre Aufgaben können sich zeitlich überlappen. Je nach Laufzeit und Hardware können bestimmte Arbeiten auch tatsächlich parallel ausgeführt werden. Mehrere Threads sind aber keine automatische Beschleunigung. Gemeinsamer Speicher, Koordination und kontrolliertes Beenden gehören zum Entwurf.

## 2. Was bedeutet der Begriff?

Die Quelle spricht von scheinbarer Gleichzeitigkeit und nennt GUI plus Netzwerkprüfung. Nebenläufigkeit kann tatsächlich so umgesetzt werden, dass die Oberfläche während anderer Arbeit reagiert. Die korrekte Übergabe von Ergebnissen und die Regeln der Oberfläche müssen dafür zusätzlich eingehalten werden.

Für CPython beschreibt die [Python-3.13-Dokumentation zu GIL und Leistung](https://docs.python.org/3.13/library/threading.html#gil-and-performance-considerations) wichtige Grenzen gleichzeitiger Python-Bytecodeausführung im üblichen GIL-Betrieb. Sie nennt auch experimentelle Free-Threaded-Builds. „Immer nur scheinbar gleichzeitig“ wäre daher ebenso zu pauschal wie „mehr Threads nutzen automatisch alle Kerne optimal“.

## 3. Einfacher Vergleich aus dem Alltag

Zwei Personen bereiten verschiedene Teile einer Mahlzeit vor. Während eine auf den Ofen wartet, kann die andere Gemüse schneiden. Benötigen beide dasselbe Werkzeug, müssen sie sich abstimmen. Für manche Aufgaben entsteht ein Vorteil, für andere nur zusätzlicher Abstimmungsaufwand.

Die Grenze: Softwarethreads teilen konkrete Datenstrukturen und werden vom System eingeplant. Eine zufällige Reihenfolge darf nicht als verlässliche Regel behandelt werden. Auch können Fehler in einem gemeinsamen Prozess weitere Arbeit beeinflussen. Der Vergleich erklärt mögliche Überlappung, keine feste Zeitersparnis.

## 4. Wie funktioniert das?

Ein Programm teilt geeignete Aufgaben auf Threads auf. Gemeinsame Daten werden über vereinbarte Mechanismen übergeben. Die [Dokumentation zu Lock-Objekten](https://docs.python.org/3.13/library/threading.html#lock-objects) beschreibt einen solchen Schutz für ausgewählte gemeinsam verwendete Abschnitte. Ein Lock wirkt nur dort, wo die Beteiligten die Regel tatsächlich einhalten.

Zur Abstimmung gibt es weitere Bausteine. Ein [Event](https://docs.python.org/3.13/library/threading.html#event-objects) kann eine Freigabe signalisieren. Eine [Barrier](https://docs.python.org/3.13/library/threading.html#barrier-objects) lässt eine festgelegte Zahl von Beteiligten aufeinander warten. Diese Werkzeuge haben unterschiedliche Verträge und sind nicht bloß austauschbare Pausenschalter.

Die Reihenfolge der Fertigstellung kann trotz gleicher Startbedingungen verschieden sein. Ein Test sollte deshalb nur eine Reihenfolge verlangen, wenn sie tatsächlich zum Vertrag gehört. Auch ein aufgeräumtes Ende muss geprüft werden: Ein wartender Hauptthread und noch laufende Worker sind nicht automatisch dasselbe wie abgeschlossene Arbeit.

Zusätzliche Threads können Speicher und Koordinationsaufwand benötigen. CPU-geprägte und I/O-geprägte Aufgaben sind unterschiedlich zu beurteilen. Eine passende Messung wäre nötig, um konkrete Leistungsaussagen zu treffen. Der folgende Versuch prüft nur Ablauf und Ergebnisse.

## 5. Wo begegnet mir das unter Linux?

Programme verwenden mehrere Threads für Verarbeitung, Warteschlangen oder Bibliotheksaufgaben. Eine GUI kann einen vorgesehenen Hintergrundweg nutzen. Das bedeutet nicht, dass jeder Worker beliebige GUI-Objekte direkt verändern darf; dafür gelten die jeweiligen Frameworkregeln.

Auch eine threadfähige Datenstruktur löst nicht automatisch alle fachlichen Reihenfolgen. Mehrere einzeln erlaubte Schritte können zusammen eine zusätzliche Koordination benötigen. Dieses Beispiel verwendet nur eigene Daten und berührt keine vorhandene Anwendung oder Netzwerkprüfung.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Zwei Worker verarbeiten eigene Texte. Barrier und Event stimmen den Ablauf ab; die Ergebnisliste wird beim Schreiben mit einem Lock geschützt.

```python
from threading import Barrier, Event, Lock, Thread

bereit = Barrier(3, timeout=2)
freigabe = Event()
schutz = Lock()
ergebnisse = []

def arbeiten(text):
    bereit.wait()
    if not freigabe.wait(timeout=2):
        raise RuntimeError("Eigene Freigabe fehlt")
    with schutz:
        ergebnisse.append(text.upper())

worker = [Thread(target=arbeiten, args=(text,)) for text in ["alpha", "beta"]]
for thread in worker:
    thread.start()
bereit.wait()
assert all(thread.is_alive() for thread in worker)
freigabe.set()
for thread in worker:
    thread.join(timeout=1)
assert all(not thread.is_alive() for thread in worker)
assert sorted(ergebnisse) == ["ALPHA", "BETA"]
print("Beendete Worker:", len(worker))
print("Ergebnisse:", ", ".join(sorted(ergebnisse)))
```

Geprüfte Ausgabe:

```text
Beendete Worker: 2
Ergebnisse: ALPHA, BETA
```

Die Hauptausführung zählt als dritter Barrier-Teilnehmer. Erst nach dem gemeinsamen Punkt wird die separate Freigabe gesetzt. Die Ergebnisreihenfolge wird bewusst nicht vorausgesetzt. Beide Threadenden und Werte werden kontrolliert. Echte CPU-Parallelität, Beschleunigung oder GUI-Reaktionsfähigkeit werden nicht gemessen.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Thread ist ein einzelner Ausführungsstrang. Multithreading verwendet mehrere davon. Mehrere Prozesse besitzen andere Grenzen und Kommunikationswege. Ein asynchrones Programm kann wiederum nebenläufige Aufgaben ohne einen zusätzlichen Thread pro Aufgabe organisieren.

## 8. Häufige Missverständnisse

Mehr Threads bedeuten nicht automatisch mehr Geschwindigkeit. Nebenläufigkeit ist nicht immer echte gleichzeitige CPU-Ausführung. Ein gemeinsamer Start garantiert keine Fertigstellungsreihenfolge. Und ein Lock schützt nicht magisch sämtliche ungeprüften Zugriffe des Programms.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Lege Übergabe, gemeinsame Daten und Ende ausdrücklich fest. Prüfe Fehlerwege passend zur Aufgabe. Das Beispiel startet nur zwei eigene kurzlebige Worker, kontrolliert deren Ende und verändert keine Dateien, Dienste oder Netzwerkeinstellungen.
