# Token

## 1. Kurzbeschreibung

Ein Token ist im API- und Sicherheitskontext ein digitaler Wert, der nach einem bestimmten Verfahren einen Nachweis oder Zugriff vermitteln kann. Seine Wirkung entsteht durch die Prüfung der zuständigen Gegenstelle. Ein beliebig erzeugter Text besitzt nicht automatisch Berechtigungen. Der Begriff umfasst unterschiedliche Arten und ist keine Zusage eines einheitlichen Formats.

## 2. Was bedeutet der Begriff?

Das Katalogbeispiel nennt ein API-Token. Im passenden Verfahren kann es erlaubte Zugriffe repräsentieren. Es muss jedoch geklärt sein, für welche Gegenstelle, welche Aufgaben und welche Zeit ein Wert gilt. Ein Token ist nicht automatisch ein vollständiger Identitätsnachweis für jede andere Anwendung.

[RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html) beschreibt Bearer Tokens für OAuth. Bei diesem Modell kann der Besitz eines gültigen Werts zur Nutzung der zugehörigen Rechte genügen. Diese Eigenschaft ist wichtig, darf aber nicht jeder anderen Tokenart ungeprüft zugeschrieben werden.

## 3. Einfacher Vergleich aus dem Alltag

Eine Eintrittskarte erlaubt nach den Regeln der Veranstaltung einen bestimmten Zutritt. Ihr Aufdruck allein entscheidet nicht über jede mögliche Veranstaltung. Manche Karten werden zusätzlich an eine Person oder weitere Bedingungen gebunden.

Die Grenze: Digitale Werte können kopiert werden, und der Empfänger muss sie technisch prüfen. Eine gut aussehende Zeichenfolge ersetzt weder eine gültige Ausgabe noch eine passende Berechtigung. Ein verlorener zugangsrelevanter Wert muss außerdem nach dem verwendeten Verfahren behandelt werden können.

## 4. Wie funktioniert das?

Ein System erzeugt oder stellt einen Wert aus und verbindet ihn mit Regeln. Ein anderes System kann ihn bei einem Zugriff übermitteln. Die empfangende Stelle prüft unter anderem Gültigkeit und erlaubte Nutzung nach dem Vertrag. Schutz beim Transport und Umgang mit Protokollen sind dabei relevant.

Tokens können undurchsichtige Kennungen oder strukturierte Darstellungen sein. [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html) beschreibt JSON Web Tokens als ein konkretes Format. Daraus folgt nicht, dass jedes API-Token ein JWT sein muss. Eine lesbare beziehungsweise kodierte Darstellung ist auch nicht automatisch verschlüsselt.

Die Prüfung darf sich nicht darauf beschränken, dass ein Text syntaktisch zum Format passt. Ein strukturierter Wert benötigt die vorgesehenen Vertrauens- und Gültigkeitsprüfungen. Eine zufällige Kennung benötigt eine passende Zuordnung. Beide Verfahren müssen zum eigentlichen Zugriffsmodell gehören.

## 5. Wo begegnet mir das unter Linux?

Programme können API-Tokens für entfernte Dienste verwenden. Der Speicher- und Übertragungsweg hängt von Anwendung und Bibliothek ab. Eine Datei oder Umgebungsvariable macht einen Wert nicht automatisch geschützt. Ein Token sollte nicht allein aus Bequemlichkeit in öffentliche Beispiele oder unnötige Logs gelangen.

Für die Erzeugung eigener zufälliger Werte bietet Python [secrets.token_urlsafe](https://docs.python.org/3.13/library/secrets.html#secrets.token_urlsafe). Die Funktion erzeugt eine Darstellung geeigneter Zufallsbytes. Sie meldet nichts bei einem Dienst an und richtet keine Zugriffsberechtigung ein.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Ordner ausgeführt. Es erzeugt nur einen neuen Testwert und gibt dessen Inhalt bewusst nicht aus. Der Wert gehört zu keinem Konto oder Dienst.

```python
import base64
import re
import secrets

probe = secrets.token_urlsafe(16)
assert re.fullmatch(r"[A-Za-z0-9_-]+", probe)
assert len(probe) == 22
roh = base64.urlsafe_b64decode(probe + "==")
assert len(roh) == 16
print(len(roh))
print(len(probe))
```

Geprüfte Ausgabe:

```text
16
22
```

Die Assertions prüfen Byteumfang und gewählte Darstellung. Sie beweisen keine erteilte Berechtigung und keine vollständige Tokenverwaltung. Auch lässt sich aus einer einzelnen erzeugten Probe keine statistische Sicherheitsabnahme des Gesamtsystems ableiten. Es wird nichts dauerhaft gespeichert oder an eine Gegenstelle gesendet.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Cookie ist ein möglicher Übertragungsmechanismus. Eine Session ist ein zusammenhängender Nutzungskontext. Ein Passwort ist eine andere Form von Geheimnis beziehungsweise Anmeldeinformation. Ein JWT bezeichnet ein bestimmtes strukturiertes Format. Der allgemeine Tokenbegriff ersetzt keine dieser genaueren Einordnungen.

## 8. Häufige Missverständnisse

Eine lange Zeichenfolge ist nicht automatisch gültig. Kodierung ist nicht Verschlüsselung. Ein Access Token beweist auch nicht zwangsläufig die Identität einer Person gegenüber jedem Empfänger. Ein erfolgreich geparster Wert ist schließlich nicht dasselbe wie ein nach allen Regeln akzeptierter Zugriff.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Behandle echte zugangsrelevante Werte vertraulich. Nutze dokumentierte Verfahren für Gültigkeit, begrenzte Rechte und gegebenenfalls Widerruf. Das Beispiel liest keine bestehenden Tokens oder Kontendaten und verändert weder Berechtigungen noch Dienste oder Konfigurationen.

## 10. Verwandte Begriffe

Die [API](it_0169.md) legt den Zugang fest. Ein [Cookie](it_0186.md) kann Werte transportieren. Eine [Session](it_0187.md) ist der größere Zusammenhang. [HTTPS](it_0146.md) schützt einen Kommunikationsabschnitt. [JSON](it_0175.md) ist ein mögliches Darstellungsformat.
