# HTTP

## 1. Kurzbeschreibung

HTTP, das Hypertext Transfer Protocol, beschreibt den Austausch von Anfragen und Antworten zwischen beteiligten Anwendungen. Es wird für Webseiten, Dateien und Programmierschnittstellen verwendet. HTTP legt unter anderem Methoden, Statuscodes und die Bedeutung von Nachrichtenfeldern fest. Es ist nicht mit HTML, einem Browser oder einem bestimmten Transportprotokoll gleichzusetzen.

## 2. Was bedeutet der Begriff?

Ein Client stellt eine Anfrage zu einer Ressource. Ein Server antwortet mit einem Status und gegebenenfalls Inhalt. Eine Ressource kann beispielsweise eine Hilfeseite oder eine API-Darstellung sein. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) definiert die gemeinsame HTTP-Semantik, die unabhängig von der genauen Nachrichtendarstellung einer Version betrachtet wird.

Das Katalogbeispiel `http://example.com` zeigt das URI-Schema `http`. Der Text ist hier nur eine Schreibweise, kein aufgerufener Link. Das Schema benennt einen Zugriffskontext; es garantiert weder einen vorhandenen Inhalt noch eine vertrauenswürdige Antwort. Für geschützte Übertragung wird gewöhnlich das gesondert definierte Schema `https` verwendet.

## 3. Einfacher Vergleich aus dem Alltag

An einem Auskunftsschalter formulierst du einen Auftrag: „Gib mir die Beschreibung zu diesem Thema.“ Die Antwort enthält eine Einordnung wie „gefunden“ oder „nicht vorhanden“ und gegebenenfalls die Unterlagen. Die gemeinsamen Regeln helfen beiden Seiten, das Ergebnis zu verstehen.

Die Grenze: HTTP versteht keine Alltagssprache und prüft nicht selbst die Wahrheit des Inhalts. Ein Statuscode ist eine technische Aussage nach der implementierten Schnittstelle. Ein erfolgreich beantworteter Abruf beweist deshalb nicht, dass der gelieferte Text fachlich korrekt oder aktuell ist.

## 4. Wie funktioniert das?

Eine Anfrage enthält eine Methode wie `GET` und ein Ziel. Felder ergänzen Informationen, etwa gewünschte Darstellungsarten. Eine Antwort enthält einen Statuscode, weitere Felder und je nach Fall einen Nachrichtenkörper. Die Bedeutung einzelner Methoden und Statuscodes steht in RFC 9110.

HTTP wird dort als zustandsloses Protokoll beschrieben. Daraus folgt nicht, dass Anwendungen keine Anmeldung oder Sitzung verwalten dürfen. Zusätzliche Mechanismen können Anfragen miteinander verknüpfen. Diese Anwendungszustände müssen von einer einzelnen Transportverbindung unterschieden werden.

Die konkrete Übertragung unterscheidet sich zwischen Versionen. [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html) definiert das Nachrichtenformat von HTTP/1.1. HTTP/2 und HTTP/3 haben andere Übertragungsformen. Ein lesbarer HTTP/1.1-Dialog ist daher kein vollständiges Abbild jeder heutigen Webverbindung.

## 5. Wo begegnet mir das unter Linux?

Browser, Entwicklungswerkzeuge und Anwendungen können HTTP-basierte Dienste nutzen. Auch ein lokales Programm kann eine entsprechende Schnittstelle anbieten. Der HTTP-Status ist dabei eine andere Ebene als ein Prozess-Exit-Code oder ein erfolgreicher TCP-Verbindungsaufbau.

Eine Antwort `404` bedeutet beispielsweise, dass die angefragte Ressource nach der HTTP-Antwort nicht gefunden wurde; sie bedeutet nicht einfach „kein Netzwerk“. Die Antwort selbst wurde ja empfangen. Ein Fehler muss deshalb auf der tatsächlich betroffenen Ebene betrachtet werden.

## 6. Konkretes Beispiel Schritt für Schritt

Dieser fiktive HTTP/1.1-Dialog wurde nicht gesendet. Die Blöcke dienen dem Lesen; sie sind keine vollständige bytegenaue Aufzeichnung. Auf der Leitung verwendet HTTP/1.1 definierte Zeilenenden, gewöhnlich CRLF.

```text
GET /hilfe HTTP/1.1
Host: beispiel.invalid

```

Eine denkbare Antwort:

```text
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 5

Hallo
```

Die Methode fragt hier eine Darstellung von `/hilfe` ab. Das Host-Feld ordnet das Ziel ein. In der Antwort steht `200` für die erfolgreiche Behandlung im beschriebenen Kontext. `Content-Type` beschreibt die Darstellung. Die Länge fünf bezieht sich auf die fünf UTF-8-Bytes von `Hallo`, nicht auf einen zusätzlichen Zeilenumbruch der Markdown-Darstellung.

Ein echter Client müsste das Nachrichtenformat und die vollständige Antwort korrekt verarbeiten. Der Beispielname bezeichnet keine getestete Anwendung. Es wurde weder ein Server gestartet noch ein Abruf vorgenommen.

## 7. Abgrenzung zu ähnlichen Begriffen

HTML ist eine mögliche Beschreibungssprache für Inhalte. HTTP ist das Kommunikationsprotokoll. TCP und QUIC bieten darunterliegende Transportmechanismen. Ein Browser kann mehrere solche Verfahren und weitere Inhalte kombinieren. Eine URL ist wiederum eine Zielangabe, kein vollständiger Netzwerkdialog.

## 8. Häufige Missverständnisse

HTTP transportiert nicht nur Webseiten. Ein Status `200` garantiert keine richtige Fachantwort. „Zustandslos“ verbietet außerdem keine Benutzersitzungen. Schließlich ist ein sichtbarer Nachrichtenkörper nicht immer HTML; er kann etwa Text, JSON oder andere Daten enthalten.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe bei einer Schnittstelle Methode, Status, Felder und Inhalt gemeinsam. Verwende für vertrauliche Kommunikation einen passenden geschützten Zugriff. Dieser Eintrag führt keine Anfragen aus und verändert keine Dienste oder Daten einer Anwendung.

## 10. Verwandte Begriffe

[TCP](it_0143.md) ist ein möglicher Transport. Ein [Port](it_0142.md) ergänzt den Endpunkt. Ein [Service](it_0119.md) stellt die Funktion bereit. Ein [Exit-Code](it_0137.md) gehört dagegen zum Prozessabschluss und ist kein HTTP-Status.
