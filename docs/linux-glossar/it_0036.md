# Changelog

## 1. Kurzbeschreibung

Ein Changelog ist eine geordnete Übersicht wichtiger Änderungen eines Projekts, üblicherweise nach Versionen gegliedert. Es hilft Nutzern und Mitwirkenden zu verstehen, was sich geändert hat und welche Folgen ein Wechsel haben kann. Die Quelle nennt NetMons Änderungen als Beispiel. Ein Changelog sollte dabei tatsächliche Änderungen beschreiben, nicht bloß geplante Verbesserungen als bereits ausgeliefert darstellen.

## 2. Was bedeutet der Begriff?

Ein guter Eintrag verbindet eine konkrete Änderung mit ihrer erkennbaren Auswirkung. „Anzeige verbessert“ ist weniger hilfreich als eine genaue Beschreibung, welche Anzeige unter welchen Umständen anders funktioniert. Details sollten zur Zielgruppe passen; nicht jeder interne Umsetzungsschritt gehört in eine nutzerorientierte Übersicht.

Das Projekt [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) definiert ein Changelog als kuratierte chronologische Liste bemerkenswerter Änderungen je Version. „Kuratiert“ bedeutet hier bewusst ausgewählt und verständlich aufbereitet. Es ist eine verbreitete Konvention, aber kein verpflichtendes Dateiformat sämtlicher Linux-Projekte.

## 3. Einfacher Vergleich aus dem Alltag

Ein Änderungsblatt zu einem Haushaltsgerät erklärt, welche Funktionen eine neue Ausgabe ergänzt und welche Hinweise nicht mehr gelten. Es soll den Umstieg erleichtern, statt sämtliche internen Arbeitsschritte der Hersteller aufzuzählen.

Die Grenze des Vergleichs: Software kann häufige kleine Versionen, Vorabstände und parallel gepflegte Zweige besitzen. Ein einzelnes Blatt ohne eindeutige Zuordnung kann deshalb irreführend sein. Auch ist eine beschriebene Korrektur noch kein eigener Nachweis, dass jeder betroffene Fall erfolgreich getestet wurde.

## 4. Wie funktioniert das?

Änderungen werden unter einer Version oder einem klar bezeichneten noch unveröffentlichten Abschnitt gesammelt. Keep a Changelog empfiehlt Gruppen wie hinzugefügt, geändert, veraltet, entfernt, korrigiert und sicherheitsrelevant. Eine Abkündigung beschreibt dabei eine künftig nicht mehr empfohlene Nutzung, nicht automatisch eine bereits entfernte Funktion.

Die Commit-Historie erfüllt eine andere Aufgabe. `git log` zeigt die aufgezeichneten Commits; die [offizielle Git-Dokumentation](https://raw.githubusercontent.com/git/git/master/Documentation/git-log.adoc) beschreibt dieses Werkzeug. Ein Changelogeintrag kann dagegen die Wirkung mehrerer Commits zusammenfassen. Eine unbearbeitete Historienliste ist deshalb nicht automatisch eine verständliche Änderungsübersicht für Anwender.

## 5. Wo begegnet mir das unter Linux?

Projekte führen häufig Dateien oder Release-Seiten mit Änderungshinweisen. Distributionspakete können zusätzlich eigene Paketierungsänderungen dokumentieren. Ein Hinweis zum ursprünglichen Projekt und ein Hinweis zur Paketrevision betreffen dann unterschiedliche Ebenen.

Vor einem Update können solche Texte auf geänderte Voraussetzungen, entfernte Schnittstellen oder notwendige Anpassungen hinweisen. Entscheidend ist, dass die gelesenen Hinweise zum tatsächlich verwendeten Ausgangs- und Zielstand passen. Eine alte Übersicht ist kein vollständiger Nachweis aller späteren Änderungen.

## 6. Konkretes Beispiel Schritt für Schritt

Das folgende erfundene Gedankenbeispiel ist kein Auszug aus NetMons tatsächlicher Änderungshistorie:

```text
Unveröffentlicht
  Geändert: Geplante kompaktere Darstellung der Ergebnisliste.

1.2.0 – 2026-11-01
  Hinzugefügt: Suche innerhalb der Ergebnisliste.
  Korrigiert: Leere Suchergebnisse zeigen nun einen Hinweis.
```

Zuerst wird geprüft, zu welchem Stand die Änderung gehört. Die Suche ist im Beispiel bereits einer veröffentlichten Version zugeordnet. Die kompaktere Darstellung steht dagegen unter „Unveröffentlicht“ und darf nicht als bereits ausgelieferte Eigenschaft dieser Version gelesen werden.

Danach wird die Wirkung beurteilt: Der Hinweis zu leeren Ergebnissen erklärt einen konkreten Fall. Für eine tatsächliche Freigabe müsste diese Aussage mit dem gebauten und geprüften Stand übereinstimmen. Ein Testbericht könnte zusätzliche Evidenz liefern, hätte aber eine andere Rolle als die Änderungsübersicht.

Dieses Beispiel wurde ausschließlich redaktionell betrachtet. Es wurde keine Version erzeugt, veröffentlicht oder anhand dieser erfundenen Funktionen getestet.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Changelog ordnet relevante Änderungen über Versionen. Release Notes können eine bestimmte Ausgabe ausführlicher erklären. Ein Commit-Protokoll zeigt Entwicklungsschritte. Ein Testbericht beschreibt tatsächlich ausgeführte Prüfungen. Ein Aufgabenplan nennt zukünftige Arbeit. Diese Dokumentarten können sich ergänzen, sollten aber nicht dieselben Behauptungen ersetzen.

## 8. Häufige Missverständnisse

Eine lange Commit-Liste ist nicht zwangsläufig ein gutes Changelog. „Geplant“ bedeutet nicht „ausgeliefert“. „Korrigiert“ ohne nachvollziehbaren Kontext erklärt die Auswirkung nur unzureichend. Ein fehlender Eintrag beweist zudem nicht, dass es tatsächlich keine relevante Änderung gab.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Halte Versionszuordnung und Freigabestatus eindeutig. Beschreibe wichtige entfernte oder geänderte Schnittstellen verständlich. Veröffentliche keine vertraulichen Diagnosedaten in Änderungshinweisen. Das Beispiel bearbeitet keine bestehende Projekthistorie und behauptet keine reale NetMon-Änderung.
