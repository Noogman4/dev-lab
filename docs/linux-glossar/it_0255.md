# Formatter

## 1. Kurzbeschreibung

Ein Formatter ist ein Werkzeug, das Quellcode nach festgelegten Darstellungsregeln anordnet. Dazu gehören beispielsweise Leerzeichen und Zeilenumbrüche. Ziel ist eine konsistente lesbare Form. Ein Formatter entscheidet nicht automatisch, ob die fachliche Berechnung oder der gesamte Programmablauf richtig ist. Prüfung und tatsächliche Änderung können außerdem unterschiedliche Betriebsarten sein.

## 2. Was bedeutet der Begriff?

Die Quelle nennt Black für Python. Dieses Werkzeug trifft bewusst viele Stilentscheidungen selbst. Dadurch müssen Beteiligte nicht jede einzelne Formatfrage immer wieder manuell abstimmen. Welche Ausgabe entsteht, hängt dennoch von Version, Konfiguration und gegebenenfalls aktivierten Vorschaufunktionen ab.

Die [offizielle Beschreibung des Black-Codestils](https://raw.githubusercontent.com/psf/black/main/docs/the_black_code_style/current_style.md) erläutert die angestrebte einheitliche Darstellung und die begrenzten Einstellmöglichkeiten. Diese Regeln gehören zu Black und sind nicht automatisch die vollständige Formatpolitik jeder Sprache oder jedes anderen Werkzeugs.

## 3. Einfacher Vergleich aus dem Alltag

Eine Textverarbeitung vereinheitlicht Einzüge und Zeilenabstände nach einer Vorlage. Dadurch wirkt ein Dokument konsistenter. Die Vorlage prüft jedoch nicht von selbst, ob die Zahlen eines Vertrags oder die fachlichen Aussagen stimmen.

Die Grenze: Ein Codeformatter muss die Sprache verstehen und ihre Struktur erhalten. Er ist daher mehr als ein blindes Ersetzen von Leerzeichen. Trotzdem ist eine erwartete Darstellungsänderung keine allgemeine Freigabe beliebiger logischer Änderungen.

## 4. Wie funktioniert das?

Das Werkzeug liest den Code, erkennt seine Struktur und erzeugt eine Darstellung nach seinem Stil. In einem schreibenden Modus kann es die Datei verändern. In einem reinen Prüfmodus meldet es dagegen, ob eine Abweichung vom gewünschten Format vorliegt.

Die [Black-Dokumentation zu Aufrufen und Optionen](https://raw.githubusercontent.com/psf/black/main/docs/usage_and_configuration/the_basics.md) beschreibt unter anderem `--check`, Konfiguration und Rückgabewerte. Ein Exitcode, der eine notwendige Formatierung meldet, ist nicht dasselbe wie ein Syntax- oder Laufzeitfehler der Anwendung. Der konkrete Aufruf muss dazu gelesen werden.

Für nachvollziehbare Ergebnisse sind dieselbe Version und passende Einstellungen hilfreich. Unterschiedliche Werkzeugversionen können andernfalls zusätzliche Änderungen erzeugen. Außerdem können ignorierte Abschnitte oder ausgeschlossene Dateien den Umfang beeinflussen. Ein sauberer Lauf bedeutet nur, dass die tatsächlich geprüften Inhalte die gewählte Prüfung erfüllen.

Eine Formatierung sollte von fachlichen Änderungen unterscheidbar bleiben. Das erleichtert Review und Fehlersuche. Im Beispiel wird die eigene Darstellung verändert und zusätzlich der abstrakte Syntaxbaum verglichen. Das ist eine begrenzte Kontrolle dieses Codes, kein Ersatz für alle fachlichen Tests.

## 5. Wo begegnet mir das unter Linux?

Python-Projekte können Black im Editor, vor einem Commit oder in automatisierten Abläufen einsetzen. Der Editor kann automatisch schreiben, während eine andere Umgebung nur prüft. Diese Unterschiede sollten bekannt sein, bevor ein Werkzeug auf vorhandene Dateien angewendet wird.

Das Beispiel setzt ein vorhandenes Black voraus. Es verwendet nur eine selbst erzeugte Datei und eine eigene temporäre Konfiguration. Pro Aufruf wird genau eine Quelldatei übergeben. Es gibt keine Installation und keine Formatierung von Anwendungs- oder Testdateien.

## 6. Konkretes Beispiel Schritt für Schritt

`BLACK_BIN` kann auf das vorhandene Werkzeug zeigen. Ist die Variable leer oder fehlt sie, sucht das Skript `black` im Suchpfad. Ein relativer Treffer wird im ursprünglichen Arbeitsverzeichnis absolut gemacht, bevor der Aufruf in das temporäre Verzeichnis wechselt. Der Cache ist ausgeschaltet. Die Prüfungen bleiben auch unter `-O` aktiv. [Python `shutil.which`](https://docs.python.org/3.13/library/shutil.html#shutil.which) · [Python `subprocess.Popen`](https://docs.python.org/3.13/library/subprocess.html#subprocess.Popen)

```python
# Black-Prüfung mit vorhandenem Werkzeug
import ast
import os
from pathlib import Path
import shutil
import subprocess
import tempfile

black = shutil.which(os.environ.get("BLACK_BIN") or "black")
if black is None:
    raise RuntimeError("Ein vorhandenes Black-Werkzeug wird benötigt")
black = str(Path(black).absolute())
with tempfile.TemporaryDirectory() as ordner:
    basis = Path(ordner)
    config = basis / "black.toml"
    config.write_text("[tool.black]\nline-length = 88\n", encoding="utf-8")
    datei = basis / "eigene_probe.py"
    vorher = "werte=[1,2,3]\n"
    datei.write_text(vorher, encoding="utf-8")
    def ausfuehren(*optionen):
        return subprocess.run(
            [black, "--config", str(config), "--no-cache", "--quiet",
             *optionen, str(datei)],
            cwd=basis, capture_output=True, text=True, timeout=5
        )
    if ausfuehren("--check").returncode != 1:
        raise RuntimeError("Der Prüfmodus meldete keinen Formatierungsbedarf")
    if ausfuehren().returncode != 0:
        raise RuntimeError("Black konnte die Beispieldatei nicht formatieren")
    nachher = datei.read_text(encoding="utf-8")
    if nachher != "werte = [1, 2, 3]\n":
        raise RuntimeError("Die Formatierung weicht vom erwarteten Ergebnis ab")
    if ast.dump(ast.parse(vorher)) != ast.dump(ast.parse(nachher)):
        raise RuntimeError("Die Formatierung hat den Syntaxbaum verändert")
    if ausfuehren("--check").returncode != 0:
        raise RuntimeError("Die formatierte Datei hat die erneute Prüfung nicht bestanden")
    print("Format geändert:", True)
    print("Syntaxbaum gleich:", True)
    print("Erneuter Prüfmodus erfolgreich:", True)
```

Geprüfte Ausgabe:

```text
Format geändert: True
Syntaxbaum gleich: True
Erneuter Prüfmodus erfolgreich: True
```

Zuerst erkennt der Prüfmodus die Abweichung. Danach wird nur die eigene Datei formatiert. Der erneute Prüfmodus akzeptiert sie. Der Syntaxbaum bleibt für dieses Beispiel gleich. Der Code wird nicht als Anwendung ausgeführt; die temporären Dateien werden entfernt.

## 7. Abgrenzung zu ähnlichen Begriffen

Linting sucht nach ausgewählten Auffälligkeiten. Formatierung vereinheitlicht Darstellung. Ein Test prüft Verhalten unter Bedingungen. Ein Review beurteilt weitere Zusammenhänge. Ein Werkzeug kann mehrere dieser Aufgaben anbieten, ohne sie in jedem Aufruf gemeinsam auszuführen.

## 8. Häufige Missverständnisse

Einheitliches Format bedeutet nicht fehlerfreie Logik. Ein Prüfmodus schreibt nicht zwingend Dateien. Ein Formatierungsbedarf ist kein automatischer Laufzeitfehler. Und ein grüner Lauf umfasst nicht jede ausgeschlossene Datei oder andere Konfiguration.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Nutze nachvollziehbare Versionen und einen klaren Umfang. Kontrolliere tatsächliche Änderungen im Review. Die Ausführung verändert nur ihre eigene temporäre Datei und keine Anwendung, Testsuite, Abhängigkeiten oder Projektkonfiguration.
