# NoSQL

## 1. Kurzbeschreibung

NoSQL ist ein Sammelbegriff für verschiedene Datenbankansätze jenseits des klassischen relationalen Modells. Dazu zählen unter anderem Dokument-, Schlüssel-Wert-, Graph- und bestimmte spaltenorientierte Modelle. Der Begriff benennt keine einzelne Software und keinen einheitlichen Funktionsumfang. Für eine Entscheidung muss deshalb das konkrete System mit seinen Regeln betrachtet werden.

## 2. Was bedeutet der Begriff?

Die Quelle nennt JSON-ähnliche Dokumente als Beispiel. Eine Dokumentdatenbank kann zusammengehörige Angaben verschachtelt speichern, statt sie ausschließlich in mehrere relationale Tabellen aufzuteilen. Das ist ein möglicher NoSQL-Ansatz, nicht die Definition aller NoSQL-Systeme.

Die [MongoDB-Dokumentation zur Datenmodellierung](https://www.mongodb.com/docs/manual/data-modeling/) erläutert flexible Dokumentstrukturen sowie Entscheidungen zwischen Einbettung und Verweisen. Flexibel bedeutet dabei nicht „ohne Datenmodell“. Welche Angaben zusammengehören und welche Abfragen häufig sind, bleibt eine wichtige Entwurfsfrage. Auch eine JSON-Datei ist allein noch kein Datenbankmanagementsystem.

## 3. Einfacher Vergleich aus dem Alltag

Ein relationales Modell erinnert vereinfacht an mehrere sauber abgestimmte Register. Ein Dokumentmodell kann eher einer Akte gleichen, die zusammengehörige Angaben gesammelt enthält. Für den Blick auf eine vollständige Akte kann das praktisch sein.

Die Grenze: Dieselbe Angabe kann in mehreren Akten vorkommen und bei Änderungen auseinanderlaufen. Außerdem lassen sich Dokumente nicht beliebig mit beliebigen anderen NoSQL-Modellen gleichsetzen. Ein Schlüssel-Wert-Speicher und eine Graphdatenbank haben andere Zugriffsmodelle. Der Vergleich ist eine Orientierung, kein Wettbewerb mit einem grundsätzlich besten Modell.

## 4. Wie funktioniert das?

Das jeweilige System legt fest, wie Daten adressiert, abgefragt und verändert werden. Eine Dokumentdatenbank arbeitet beispielsweise mit Dokumenten und ihren Feldern. Ein Schlüssel-Wert-System ordnet einem Schlüssel einen Wert zu. Eine Graphdatenbank stellt Knoten und Beziehungen in den Mittelpunkt.

Das Wort NoSQL bedeutet auch nicht, dass es nirgends Tabellen oder SQL-ähnliche Sprachen geben könne. Die [Architekturübersicht von Apache Cassandra](https://cassandra.apache.org/doc/latest/cassandra/architecture/overview.html) beschreibt CQL, Tabellen, typisierte Spalten und Partitionierung. Gleichzeitig gelten andere Modellierungs- und Abfragegrenzen als bei einer klassischen relationalen Datenbank. Der Sammelbegriff verdeckt diese Unterschiede leicht.

Ebenso wäre „NoSQL hat keine Transaktionen“ zu pauschal. Die [MongoDB-Dokumentation zu Transaktionen](https://www.mongodb.com/docs/manual/core/transactions/) beschreibt Transaktionen über mehrere Dokumente in unterstützten Bereitstellungen. Welche Garantien und Einschränkungen gelten, muss für Produkt, Version und Betriebsform geprüft werden. Daraus folgt keine entsprechende Zusicherung für ein beliebiges anderes System.

## 5. Wo begegnet mir das unter Linux?

Serveranwendungen können Dokumentdatenbanken, Zwischenspeicher oder andere spezialisierte Datenbanken verwenden. Ein Linux-Rechner kann darauf zugreifen oder solche Systeme betreiben. Das Betriebssystem allein bestimmt aber weder Datenmodell noch Konsistenzregeln.

Für eine lokale Anwendung ist ein zusätzlicher Datenbankserver nicht automatisch nötig. Anforderungen an Abfragen, Datenmenge, Sicherung und Betrieb entscheiden mit. Hier wird kein NoSQL-System installiert oder gestartet. Auch eine bestehende Anwendung wird nicht auf eine andere Speicherung umgestellt.

## 6. Konkretes Beispiel Schritt für Schritt

Das folgende Gedankenbeispiel wurde nicht an einer Datenbank ausgeführt. Es zeigt lediglich zwei selbst erfundene Dokumentformen in JSON-Schreibweise, keine vollständigen produktbezogenen Speicheroperationen.

```text
{"name": "Probe", "kontakte": [{"art": "mail", "wert": "probe@example.invalid"}]}
{"name": "Zweite Probe", "notiz": "Noch keine Kontaktangabe"}
```

Zuerst betrachten wir die gemeinsame Angabe `name`. Danach sehen wir eine eingebettete Liste im ersten Dokument. Im zweiten fehlt diese Liste; stattdessen gibt es eine Notiz. Ein Dokumentmodell kann solche unterschiedlichen Formen ermöglichen. Ob ein konkretes Schema sie zulässt, hängt von dessen Prüfung ab.

Nun entsteht die fachliche Frage: Bedeutet das fehlende Feld „keine Kontakte“, „noch nicht erfasst“ oder „unbekannt“? Diese Bedeutung wird durch flexible Speicherung nicht automatisch geklärt. Schließlich muss die Anwendung entscheiden, wie sie beide Formen liest und nach Kontaktarten sucht. Das Beispiel liefert keine Abfrage, kein Messergebnis und keine Zusage zu einer bestimmten Produktversion.

## 7. Abgrenzung zu ähnlichen Begriffen

JSON ist ein Austauschformat. Eine Dokumentdatenbank bietet darüber hinaus Speicher-, Abfrage- und Verwaltungsfunktionen. SQL ist eine Sprache mit verschiedenen Implementierungen. NoSQL ist eine grobe Gruppe von Ansätzen. Diese Begriffe liegen auf unterschiedlichen Ebenen und ersetzen einander nicht.

## 8. Häufige Missverständnisse

NoSQL bedeutet nicht automatisch schemalos, schneller oder einfacher zu betreiben. Dokumente benötigen weiterhin fachliche Regeln. Transaktions- und Konsistenzgarantien sind produktabhängig. Und eine SQL-ähnliche Abfragesprache allein macht zwei Systeme nicht austauschbar.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Beginne bei Zugriffsmustern und fachlichen Bedingungen. Prüfe danach die konkreten Garantien, Grenzen und Wiederherstellungswege des Systems. Flexibilität kann Arbeit in die Anwendung verlagern. Dieses Dokument enthält keine installierbare Anleitung und behauptet keine praktische NoSQL-Abnahme.

## 10. Verwandte Begriffe

Die [Datenbank](it_0191.md) ist der übergeordnete Begriff. [JSON](it_0175.md) erklärt das Austauschformat. [SQL](it_0192.md) behandelt die Sprache. Eine [Query](it_0200.md) fragt Daten ab. Die [Transaktion](it_0202.md) fasst Arbeit zusammen.
