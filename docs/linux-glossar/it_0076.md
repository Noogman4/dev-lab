# Event

## 1. Kurzbeschreibung

Ein Event ist ein Ereignis, auf das ein Programm reagieren kann. Es kann etwa einen Eingabevorgang, einen Timer oder eine interne Benachrichtigung darstellen. Die Quelle nennt einen Mausklick als Beispiel. Ereignisse müssen jedoch nicht von Menschen stammen und sind nicht auf grafische Oberflächen beschränkt.

## 2. Was bedeutet der Begriff?

Ein Ereignis beschreibt, dass etwas für den vorgesehenen Ablauf Relevantes geschehen ist. Es kann zusätzliche Informationen tragen, beispielsweise Zielobjekt, Ereignisart oder Eingabedaten. Welche Angaben verfügbar sind, entscheidet die konkrete Schnittstelle.

Pythons [Tkinter-Erklärung zu Bindings und Events](https://docs.python.org/3.13/library/tkinter.html#bindings-and-events) unterscheidet physische Ereignisse von anwendungsdefinierten virtuellen Ereignissen. Bei einer passenden Bindung erhält die aufgerufene Funktion ein Ereignisobjekt. Ein Ereignis und die darauf reagierende Funktion sind daher unterschiedliche Bestandteile.

## 3. Einfacher Vergleich aus dem Alltag

Ein Türsignal meldet, dass jemand geklingelt hat. Das Signal ist nicht selbst die anschließende Handlung, die Tür zu öffnen. Eine Reaktion kann von Zustand, Zuständigkeit und weiteren Informationen abhängen.

Die Grenze des Vergleichs: Eine Software kann Signale selbst erzeugen, weiterleiten oder gesammelt verarbeiten. Ein Ereignis belegt nicht automatisch, dass der zugrunde liegende fachliche Vorgang erfolgreich war. Auch können mehrere Ereignisse zu einer einzigen sichtbaren Benutzerhandlung gehören.

## 4. Wie funktioniert das?

Das Programm oder Toolkit erkennt oder erzeugt ein Ereignis. Eine registrierte Zuordnung bestimmt, welches passende Verhalten angestoßen wird. Manche Ereignisse werden eingereiht und später verarbeitet; andere Schnittstellen können ihre Verarbeitung unmittelbarer auslösen.

Das [offizielle Tk-Handbuch zu bind](https://raw.githubusercontent.com/tcltk/tk/core-8-6-branch/doc/bind.n) beschreibt die Verbindung zwischen Ereignismustern, Zielbereichen und aufzurufendem Code. Mehrere Bindungen und ihre Reihenfolge besitzen konkrete Regeln. Ein neuer Handler darf deshalb nicht unbemerkt andere benötigte Reaktionen verdrängen.

Die Bedeutung des Ereignisses gehört zum Anwendungsvertrag. „Daten aktualisiert“ kann etwa bedeuten, dass ein neuer Stand bereitsteht. Ob er gültig ist und welche Ansicht betroffen ist, muss die Verarbeitung zusätzlich prüfen.

## 5. Wo begegnet mir das unter Linux?

GUI-Anwendungen reagieren auf Eingaben und Fensteränderungen. Andere Programme können Benachrichtigungen über eigene asynchrone Schnittstellen erhalten. Die dazugehörigen Datenformate und Garantien sind nicht alle identisch.

Ein programmgesteuert erzeugtes Oberflächenereignis ist zudem kein Nachweis einer menschlichen Eingabe oder Berechtigung. Für Tests ist diese Trennung hilfreich: Ein gezieltes Ereignis kann eine Reaktion prüfen, ohne einen echten Mausklick oder eine äußere Systemänderung auszuführen.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Python-3-Beispiel erzeugt ausschließlich ein eigenes virtuelles Tk-Ereignis unter dem vorhandenen virtuellen Bildschirm:

```python
# GUI-Prüfung im virtuellen Bildschirm
import tkinter as tk

root = tk.Tk()
root.withdraw()
try:
    root.update()
    beobachtet = []
    root.bind("<<Probe>>", lambda ereignis: beobachtet.append(ereignis.widget))
    root.event_generate("<<Probe>>", when="tail")
    assert beobachtet == []
    root.update()
    assert beobachtet == [root]
    print(len(beobachtet))
finally:
    root.destroy()
```

Die Ausgabe lautet:

```text
1
```

Die eigene Bindung registriert die Reaktion. Das Ereignis wird ausdrücklich ans Ende der Warteschlange gestellt. Vor deren Verarbeitung ist die Beobachtungsliste leer; danach enthält sie das erwartete Zielobjekt. Geprüft ist dieser konkrete eingereihte Ablauf, keine universelle Zustellregel für alle Ereignissysteme.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Callback ist aufrufbarer Code für eine Reaktion. Ein Ereignis beschreibt den Anlass. Eine Warteschlange kann mehrere Anlässe aufnehmen. Ein Methodenaufruf kann dagegen direkt erfolgen, ohne ein gesondertes Ereignis einzureihen. Ein Protokolleintrag kann ein Ereignis dokumentieren, ist aber nicht zwingend dessen Zustellmechanismus.

## 8. Häufige Missverständnisse

Ein Ereignis beweist keinen erfolgreichen Abschluss. Ein virtueller Klick ist nicht dasselbe wie eine echte Personeneingabe. Ereignisse werden nicht in jeder Schnittstelle gleich behandelt. Eine Registrierung ist außerdem noch kein ausgeführter Callback und kann andere Bindungen je nach API ersetzen oder ergänzen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Definiere Ereignisart, Ziel und benötigte Daten. Prüfe Zustellreihenfolge und veraltete Zustände, wenn sie relevant sind. Das Beispiel testet nur eine eigene virtuelle Tk-Benachrichtigung; echte Eingaben, Systemereignisse und NetMon-Reaktionen wurden nicht praktisch geprüft.
