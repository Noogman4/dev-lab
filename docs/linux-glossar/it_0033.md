# Deployment

## 1. Kurzbeschreibung

Deployment bedeutet, Software auf einem vorgesehenen Zielsystem bereitzustellen. Dazu können das Übertragen oder Installieren eines Artefakts, passende Einstellungen, ein kontrollierter Start und die Prüfung der Erreichbarkeit gehören. Die Quelle nennt eine neue Serverversion als Beispiel. Bereitstellung ist jedoch nicht auf öffentlich erreichbare Server beschränkt.

## 2. Was bedeutet der Begriff?

Ein Deployment verbindet einen bestimmten Softwarestand mit einer bestimmten Umgebung. Ein fertiges Paket ist dafür eine mögliche Eingabe. Das Ziel kann eine Testumgebung, ein einzelner Arbeitsplatz oder ein Produktivsystem sein. Welche Aktionen nötig sind, bestimmt die Architektur des Projekts.

„Bereitgestellt“ sollte ein überprüfbares Ergebnis bezeichnen. Eine erfolgreich kopierte Datei beweist noch nicht, dass die Anwendung startet und ihre Aufgabe erfüllt. Ebenso bedeutet eine intern bereitgestellte Testversion nicht automatisch eine öffentliche Freigabe für alle Nutzer.

## 3. Einfacher Vergleich aus dem Alltag

Eine vorbereitete Ausstellung muss an ihren vorgesehenen Ort gebracht, aufgebaut und auf Funktionsfähigkeit geprüft werden. Die fertigen Ausstellungsstücke allein ergeben noch keine geöffnete Ausstellung. Der Einsatzort und seine Voraussetzungen gehören zur Vorbereitung.

Der Vergleich hat Grenzen: Bei Software können Daten und laufende Verbindungen von einer alten Version abhängen. Auch lassen sich nicht alle Änderungen durch einfaches Zurückstellen einer Datei rückgängig machen. Ein geänderter Datenbestand kann besondere Vorbereitungen und eine eigene Rückkehrstrategie erfordern.

## 4. Wie funktioniert das?

Ein kontrollierter Ablauf legt Artefakt, Zielumgebung, Einstellungen und Erfolgskriterien fest. Anschließend wird der Zustand hergestellt und geprüft. Ein Teil kann automatisiert sein, doch die Automatisierung muss die tatsächlichen Anforderungen abbilden.

Django unterscheidet ausdrücklich Entwicklungseinstellungen von solchen für den vorgesehenen Betrieb. Die [offizielle Deployment-Anleitung im Django-Projekt](https://raw.githubusercontent.com/django/django/stable/5.2.x/docs/howto/deployment/checklist.txt) erläutert dies für Django 5.2. Daraus folgt keine Pflicht, dass jedes Projekt Django oder dieselben Einstellungen verwendet; es zeigt die Bedeutung der Zielumgebung.

Kubernetes verwendet zusätzlich `Deployment` als Namen einer konkreten Ressourcenart. Sie beschreibt einen gewünschten Zustand und steuert dessen Herstellung für die betreffenden Anwendungsinstanzen. Das erläutert die [offizielle Kubernetes-Dokumentation](https://raw.githubusercontent.com/kubernetes/website/main/content/en/docs/concepts/workloads/controllers/deployment.md). Dieser Produktbegriff ist enger als der allgemeine Vorgang des Bereitstellens.

## 5. Wo begegnet mir das unter Linux?

Eine Anwendung kann als Paket auf einem Arbeitsplatz eingerichtet oder als Dienst in einer Testumgebung bereitgestellt werden. Dabei müssen benötigte Bibliotheken, Dateien und Einstellungen zur vorgesehenen Version passen. Auch Start und Verhalten sollten unter den tatsächlichen Bedingungen geprüft werden.

Ein laufender Prozess allein ist noch kein Funktionsnachweis. Eine repräsentative Anfrage oder ein sinnvoller Anwendungstest liefert stärkere Evidenz. Umgekehrt kann ein laufender Dienst nach einem späteren Neustart fehlen, wenn sein Start nur für die aktuelle Sitzung eingerichtet wurde.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenbeispiel beschreibt eine erfundene interne Anwendung. Es enthält keine auszuführenden Bereitstellungsbefehle:

```text
Version auswählen
    -> Testumgebung vorbereiten
    -> Artefakt bereitstellen
    -> Anwendung starten
    -> vereinbarte Beispielanfrage prüfen
    -> Ergebnis dokumentieren
```

Zuerst wird festgehalten, welcher Stand verwendet werden soll. Danach werden die Voraussetzungen des Ziels geprüft. Das Artefakt wird an seinen vorgesehenen Platz gebracht, und die Anwendung startet mit passenden Einstellungen.

Erst eine erfolgreiche Beispielanfrage beantwortet, ob der ausgewählte Ablauf funktioniert. Ein späterer Schritt in eine andere Umgebung wäre ein weiteres Deployment mit eigenen Voraussetzungen. Die Prüfung einer Testumgebung darf deshalb nicht automatisch als Nachweis für den Produktivbetrieb ausgegeben werden.

Dieses Beispiel wurde nicht praktisch durchgeführt. Es wurden keine Dateien installiert, Dienste gestartet oder echten Netzwerkkonfigurationen geändert.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Build erzeugt ein Artefakt. Ein Deployment stellt Software für ein Ziel bereit. Eine Veröffentlichung bezeichnet eine Freigabe oder Zugänglichmachung und kann ein eigener Schritt sein. Installation ist häufig ein Teil der Bereitstellung, erklärt aber noch nicht alle Einstellungen und Funktionsprüfungen.

## 8. Häufige Missverständnisse

Ein erfolgreicher Dateitransfer garantiert kein funktionierendes System. Ein neuer Prozess garantiert nicht die gewünschte Version. Ein Rückwechsel der Programmdatei stellt einen geänderten Datenbestand nicht zwangsläufig wieder her. Auch ein Kubernetes-Deployment bedeutet nicht automatisch, dass jede fehlerhafte Änderung selbsttätig zurückgerollt wird.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Lege Ziel, Prüfung und gegebenenfalls Rückkehrweg vor echten Änderungen fest. Schütze vertrauliche Einstellungen und behalte bestehende Daten im Blick. Dieses Glossardokument beschreibt den Vorgang; es nimmt selbst keine Bereitstellung vor und verändert keine Umgebung.
