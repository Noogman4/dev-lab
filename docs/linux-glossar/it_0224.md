# Singleton

## 1. Kurzbeschreibung

Singleton bezeichnet ein Entwurfsmuster, das eine einzige gemeinsame Instanz einer Klasse innerhalb des vorgesehenen Geltungsbereichs sicherstellen und zugänglich machen soll. Dabei muss klar sein, wo diese Einzigkeit gilt. Eine gemeinsame Instanz in einem Prozess ist nicht automatisch dieselbe Instanz in anderen Prozessen oder auf anderen Rechnern.

## 2. Was bedeutet der Begriff?

Die Quelle nennt einen möglichen ConfigManager. Eine gemeinsame Konfigurationsinstanz kann dafür sorgen, dass mehrere Teile denselben Zustand verwenden. Das ist aber eine Entwurfsentscheidung, keine zwingende Eigenschaft jeder Konfigurationsverwaltung. Auch kann ein einmal erzeugtes und ausdrücklich weitergegebenes Objekt genügen, ohne dass seine Klasse jede weitere Erzeugung grundsätzlich verhindert.

Der Begriff erscheint außerdem als Lebensdauerangabe in Containern. Die [Microsoft-Dokumentation zu Dienstlebensdauern](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/service-lifetimes) beschreibt die Singleton-Wiederverwendung einer Registrierung im Container. Diese konkrete Verwaltungsregel muss vom klassischen klassenbezogenen Muster unterschieden werden. Sie begründet keine universelle Einzigkeit über sämtliche getrennten Container und Programme hinweg.

## 3. Einfacher Vergleich aus dem Alltag

Ein Team verwendet ein gemeinsames Whiteboard für seinen aktuellen Plan. Alle Mitglieder sehen Änderungen an demselben Brett. Es gibt dadurch nicht bei jeder Nachfrage eine neue unabhängige Planfassung.

Die Grenze: Ein anderes Team kann ein anderes Whiteboard besitzen. Auch verhindert ein einziges Brett nicht, dass zwei Personen gleichzeitig widersprüchlich darauf schreiben. Ebenso lösen gemeinsame Softwareobjekte weder Nebenläufigkeit noch fachliche Abstimmung automatisch. Der Geltungsbereich und die Zugriffsmöglichkeiten bleiben entscheidend.

## 4. Wie funktioniert das?

Beim klassischen Muster wird die Erzeugung kontrolliert und ein gemeinsamer Zugriff auf die vorgesehene Instanz angeboten. In anderen Umsetzungen verwaltet eine zentrale Zusammensetzung oder ein Container die Wiederverwendung. Welche weiteren Erzeugungswege bestehen und wann die Instanz initialisiert wird, hängt von der konkreten Umsetzung ab.

Ein verwandtes, aber enger begrenztes Verhalten zeigt eine Namensregistrierung. Die [Python-Dokumentation zu logging.getLogger](https://docs.python.org/3.13/library/logging.html#logging.getLogger) garantiert bei gleichem Namen dieselbe Logger-Instanz. Unterschiedliche Namen können verschiedene Logger bezeichnen. Das ist deshalb kein Beweis, dass die gesamte Klasse Logger nur eine einzige Instanz besitzen könne.

Gemeinsamer veränderlicher Zustand schafft Abhängigkeiten zwischen Benutzern. Tests können sich beispielsweise beeinflussen, wenn sie dieselbe Instanz umkonfigurieren. Auch die erstmalige Erzeugung und spätere Zugriffe müssen bei Nebenläufigkeit passend geregelt werden. Ein Singleton-Name oder eine einzige Variable macht die Verarbeitung nicht automatisch threadsicher.

## 5. Wo begegnet mir das unter Linux?

Anwendungen verwenden gemeinsame Registrierungen, Konfigurationen oder Dienste innerhalb einer Laufzeit. Davon zu unterscheiden ist ein Programm, das nur einmal gestartet werden soll. Die Verhinderung einer zweiten Programminstanz braucht einen eigenen prozessübergreifenden Mechanismus und folgt nicht automatisch aus einem gewöhnlichen Objektmuster.

Bei Fehlersuche hilft daher die Frage: Welche Benutzer teilen tatsächlich welches Objekt? Zwei getrennte laufende Programme besitzen normalerweise getrennte Speicherzustände. Das Beispiel bleibt in einem einzigen neu gestarteten Python-Prozess und verändert keine vorhandene Anwendungskonfiguration.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Es prüft nur die dokumentierte Wiederverwendung pro Loggername. Es richtet keine Ausgabeziele ein und schreibt keine Logdatei.

```python
import logging

a = logging.getLogger("glossar.eigene_probe")
b = logging.getLogger("glossar.eigene_probe")
c = logging.getLogger("glossar.andere_probe")
assert a is b
assert a is not c
assert a.name == b.name == "glossar.eigene_probe"
assert c.name == "glossar.andere_probe"
print("Gleicher Name, gleiches Objekt:", a is b)
print("Anderer Name, gleiches Objekt:", a is c)
```

Geprüfte Ausgabe:

```text
Gleicher Name, gleiches Objekt: True
Anderer Name, gleiches Objekt: False
```

Die Prüfung verwendet Identität statt nur gleicher Werte. Sie zeigt eine klar begrenzte Wiederverwendung. Sie implementiert keinen eigenen klassischen Singleton, testet keine Container-Lebensdauer und weist keine Threadsicherheit oder prozessübergreifende Einzigkeit nach.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein globaler Variablenname verhindert nicht automatisch weitere Instanzen. Ein Container-Singleton ist eine Verwaltungsregel im jeweiligen Geltungsbereich. Eine Registrierung kann eine Instanz pro Schlüssel wiederverwenden. Dependency Injection kann eine gemeinsame Instanz ausdrücklich übergeben, ohne einen versteckten globalen Zugriff einzuführen.

## 8. Häufige Missverständnisse

Ein Singleton ist nicht automatisch threadsicher. Ein Prozessobjekt wird nicht dadurch weltweit eindeutig. Gemeinsamer Zustand macht Tests nicht von selbst leichter. Und ein gleichnamiger Logger beweist keine einzelne Instanz seiner gesamten Klasse.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Benenne Geltungsbereich, Lebensdauer und Veränderbarkeit. Prüfe, ob ausdrückliche Übergabe einer gemeinsamen Instanz ausreicht. Das Beispiel bleibt bei eigenen Loggernamen im Testprozess und verändert keine Konten, Dienste oder vorhandenen Konfigurationsdateien.
