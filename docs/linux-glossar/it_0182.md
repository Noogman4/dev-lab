# Backend

## 1. Kurzbeschreibung

Das Backend ist die Verarbeitungsschicht einer Anwendung hinter ihrem benutzerseitigen Zugang. Es kann fachliche Regeln, Zugriffskontrollen und den Umgang mit Daten übernehmen. „Hintergrundteil“ beschreibt dabei eine Architekturrolle und bedeutet nicht automatisch Hintergrundprozess, Thread oder bestimmter Rechner. Auch eine Datenbank ist nicht für jedes Backend zwingend nötig.

## 2. Was bedeutet der Begriff?

Die Grenze zwischen Frontend und Backend ordnet Zuständigkeiten. Ein Frontend kann Eingaben aufnehmen, während eine andere Schicht entscheidet, ob ein Auftrag zulässig und fachlich sinnvoll ist. Die Komponenten können auf unterschiedlichen Systemen oder innerhalb einer gemeinsamen Anwendung liegen.

Die [Django-Übersicht für Version 5.2](https://docs.djangoproject.com/en/5.2/intro/overview/) zeigt als konkretes Webbeispiel das Zusammenwirken von Datenmodellen, URL-Zuordnung und Verarbeitung. Das ist ein Framework-Modell, keine Pflichtarchitektur aller Backends. Das Katalogbeispiel mit Datenbankzugriff und API-Logik nennt typische Aufgaben, nicht die vollständige Definition.

## 3. Einfacher Vergleich aus dem Alltag

Ein Schalter nimmt einen Auftrag entgegen. Die zuständige Fachstelle prüft anschließend Regeln, bearbeitet den Vorgang und liefert ein Ergebnis. Die Fachstelle muss nicht sichtbar am Schalter sitzen, um entscheidend für die Leistung zu sein.

Die Grenze: Ein Backend beurteilt nur die implementierten Regeln. Es erkennt nicht automatisch jede falsche Fachannahme. Außerdem kann ein Auftrag auch ohne die ursprüngliche Oberfläche eintreffen. Deshalb darf die Prüfung nicht allein voraussetzen, dass ein bestimmtes Eingabefeld vorher korrekt bedient wurde.

## 4. Wie funktioniert das?

Eine Verarbeitungsschicht erhält Daten über eine vereinbarte Schnittstelle. Sie prüft Eingabeform, Berechtigung und fachliche Bedingungen, soweit diese zu ihrer Zuständigkeit gehören. Danach führt sie die vorgesehene Operation aus oder liefert einen passenden Fehler.

Die [W3C-Anleitung zur Formularvalidierung](https://www.w3.org/WAI/tutorials/forms/validation/) erklärt, warum alleinige Clientprüfungen keine Sicherheit gewährleisten. Eine frühere Oberflächenprüfung kann Bedienung erleichtern, ersetzt aber die notwendige Prüfung an der verantwortlichen Stelle nicht.

Bei einer tatsächlichen Anwendung kommen je nach Aufgabe Speicherung, Nebenwirkungen und Fehlerbehandlung hinzu. Ein Erfolg sollte erst gemeldet werden, wenn die zugesagte Operation den vereinbarten Zustand erreicht hat. Die genaue Zusage ist Teil des Schnittstellenvertrags.

## 5. Wo begegnet mir das unter Linux?

Ein Webdienst kann ein Backend auf einem Linux-Server betreiben. Eine Desktopanwendung kann ihre Verarbeitung ebenso in getrennten Modulen organisieren. Der Begriff entscheidet nicht allein, ob ein eigenständiger Dienst oder eine Netzwerkverbindung nötig ist.

Auch Fehlersuche profitiert von dieser Trennung. Ein korrekt berechnetes Ergebnis kann falsch angezeigt werden. Eine schöne Anzeige kann umgekehrt unzutreffende Daten enthalten. Beide Seiten benötigen passende Prüfungen, ohne dass jeder Fehler automatisch der anderen Seite zugeschrieben wird.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Ordner ausgeführt. Die Funktion modelliert nur eine kleine Eingabegrenze und eine Berechnung. Sie ist kein gestarteter Backendserver.

```python
def quadrat_anfordern(daten):
    if not isinstance(daten, dict) or set(daten) != {"zahl"}:
        raise ValueError("Unpassende Struktur")
    zahl = daten["zahl"]
    if type(zahl) is not int or abs(zahl) > 10:
        raise ValueError("Zahl außerhalb des Vertrags")
    return {"quadrat": zahl * zahl}


ergebnis = quadrat_anfordern({"zahl": 3})
assert ergebnis == {"quadrat": 9}
abgelehnt = 0
for eingabe in [{"zahl": "3"}, {"zahl": True}, {"zahl": 11}]:
    try:
        quadrat_anfordern(eingabe)
    except ValueError:
        abgelehnt += 1
assert abgelehnt == 3
print(ergebnis["quadrat"])
print("Abgelehnte Eingaben:", abgelehnt)
```

Geprüfte Ausgabe:

```text
9
Abgelehnte Eingaben: 3
```

Die Grenzen sind ausdrücklich selbst gewählte Vertragsregeln. Die Funktion akzeptiert hier nur echte Integer im kleinen Bereich und behandelt den Boolean nicht als passende Zahl. Geprüft werden konkrete lokale Fälle. Authentifizierung, Datenbankzugriff und HTTP-Verarbeitung sind nicht implementiert oder getestet.

## 7. Abgrenzung zu ähnlichen Begriffen

Das Frontend bildet den benutzerseitigen Zugang. Eine API definiert einen programmatischen Vertrag. Ein Server stellt einen Dienst bereit. Ein Daemon beschreibt einen Hintergrunddienstprozess. Ein Backend kann diese Techniken nutzen, ist aber nicht allein durch eine dieser Bezeichnungen vollständig beschrieben.

## 8. Häufige Missverständnisse

Backend heißt nicht automatisch Datenbank. Eine ausgeblendete Schaltfläche schützt die Fachfunktion nicht ausreichend. Gültige JSON-Syntax beweist außerdem keine passenden Fachwerte. Ein Rückgabecode des Prozesses ist schließlich nicht dieselbe Zusage wie ein erfolgreich gespeicherter Auftrag.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Definiere Zuständigkeiten und Eingabegrenzen klar. Prüfe notwendige Berechtigungen unabhängig von einer Oberfläche. Der Versuch verwendet nur eigene Speicherwerte und verändert keine Anwendung, Datenbank, Konten, Dienste oder Netzwerkparameter.

## 10. Verwandte Begriffe

Das [Frontend](it_0181.md) übernimmt andere Aufgaben. Die [API](it_0169.md) definiert Zugänge. Ein [Datentyp](it_0006.md) gehört zur Eingabeprüfung. Eine [Exception](it_0091.md) kann Ablehnung signalisieren. Der [Daemon](it_0117.md) ist eine andere Rollenbeschreibung.
