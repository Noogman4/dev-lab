# Dependency

## 1. Kurzbeschreibung

Eine Dependency ist eine Abhängigkeit: Ein Teil einer Software benötigt etwas anderes, um eine bestimmte Aufgabe zu erfüllen. Das kann beispielsweise eine Bibliothek, eine Laufzeitumgebung oder ein externes Programm sein. Welche Abhängigkeiten nötig sind, hängt vom Arbeitsumfang und von der Umgebung ab. Nicht jede gehört in jedem Fall zum Grundbetrieb.

## 2. Was bedeutet der Begriff?

Das Katalogbeispiel nennt `requests` als mögliche Python-Abhängigkeit. Ob ein konkretes Projekt diese Bibliothek benötigt, muss aus seinem Code und seiner Beschreibung hervorgehen. Der bloße Name im Glossar bedeutet weder, dass sie hier installiert ist, noch dass sie nachinstalliert werden soll.

Die [PyPA-Spezifikation für Abhängigkeitsangaben](https://raw.githubusercontent.com/pypa/packaging.python.org/main/source/specifications/dependency-specifiers.rst) beschreibt Paketnamen, Versionsbedingungen, Extras und Umgebungsbedingungen. Das ist eine konkrete Regelwelt für Python-Pakete. Betriebssystempakete und andere Ökosysteme verwenden eigene Formate und Werkzeuge. Ihre Angaben sind nicht beliebig austauschbar.

## 3. Einfacher Vergleich aus dem Alltag

Für ein Gericht brauchst du bestimmte Zutaten. Eine fertige Gewürzmischung kann weitere Zutaten enthalten, die nicht einzeln auf deiner ursprünglichen Einkaufsliste standen. Eine optionale Beilage wird dagegen nur für eine besondere Variante benötigt.

Die Grenze: Softwareabhängigkeiten haben genaue technische Beziehungen. Eine neue Version kann sich anders verhalten, und mehrere Beteiligte können unvereinbare Anforderungen stellen. Ein gleich klingender Name oder eine vorhandene Datei garantiert keine passende Schnittstelle. Der Vergleich erklärt nur direkte, indirekte und optionale Bedürfnisse.

## 4. Wie funktioniert das?

Eine direkte Abhängigkeit wird vom Projekt unmittelbar benötigt. Verwendet diese wiederum weitere Pakete, entstehen indirekte beziehungsweise transitive Abhängigkeiten. Die gesamte Beziehung ist daher oft ein Netz statt einer einzigen flachen Liste. Paketwerkzeuge versuchen, dafür gemeinsam passende Versionen zu bestimmen.

Außerdem unterscheiden sich Zwecke. Manche Werkzeuge werden zum Bauen benötigt, andere nur zum Testen. Eine Bibliothek für eine optionale Exportfunktion muss nicht zwingend in jeder Installationsvariante gebraucht werden. Umgebungsbedingungen können festlegen, dass eine Anforderung beispielsweise nur für bestimmte Plattformen relevant ist.

Die [Python-Dokumentation zu Distributionsanforderungen](https://docs.python.org/3.13/library/importlib.metadata.html#distribution-requirements) erklärt das Lesen deklarierter Anforderungen installierter Distributionen. Solche Metadaten sind nützlich, aber keine vollständige Laufzeitprüfung sämtlicher Funktionen. Die Funktion liefert auch nicht einfach die Garantie, dass jede indirekte Beziehung und jede externe Systemvoraussetzung bereits korrekt erfüllt ist.

## 5. Wo begegnet mir das unter Linux?

Ein Python-Projekt kann Paketabhängigkeiten beschreiben und zusätzlich Systembibliotheken benötigen. Welche Umgebung tatsächlich verwendet wird, ist wichtig: Ein Paket in einer anderen Python-Umgebung steht dem laufenden Programm nicht automatisch zur Verfügung. Auch Distributionsname und Importname müssen nicht identisch sein.

Bei einem Fehler sollte deshalb zuerst geklärt werden, welche Anforderung in welcher Umgebung fehlt oder nicht passt. Eine pauschale Installation beliebiger Pakete kann die Lage verschlechtern. Dieses Dokument verändert weder Python-Umgebungen noch Systempakete oder Projektabhängigkeiten.

## 6. Konkretes Beispiel Schritt für Schritt

Das folgende Gedankenbeispiel wurde nicht installiert oder mit einem Paketauflöser ausgeführt. Die Namen „Beispiel-Notiz“, „Beispiel-Export“ und „Beispiel-Texthelfer“ bezeichnen erfundene Pakete.

Zuerst benötigt das Notizprogramm für einen gewünschten Export die Exportbibliothek. Das ist aus Sicht dieser Variante eine direkte Abhängigkeit. Die Exportbibliothek braucht ihrerseits einen Texthelfer. Dieser ist für das Notizprogramm indirekt erforderlich, obwohl dessen eigener Code ihn möglicherweise nicht unmittelbar importiert.

Danach ergänzt die Projektbeschreibung eine Versionsbedingung. Eine beispielhafte Angabe `beispiel-export>=1.0,<2.0` würde geeignete Versionen ab 1.0 vor 2.0 zulassen. Sie benennt noch keine einzige konkret ausgewählte Version und behauptet keine tatsächliche Verfügbarkeit dieser erfundenen Pakete.

Nun fordert eine weitere Erweiterung einen unvereinbaren Versionsbereich desselben Helfers. Der Konflikt kann nicht sinnvoll durch bloßes Ignorieren einer Fehlermeldung gelöst werden. Die Anforderungen und ihre Verträglichkeit müssen geklärt werden.

Schließlich wird entschieden, ob der Export überhaupt zur gewählten Variante gehört. Eine optionale Funktion kann andere Anforderungen haben als der Grundbetrieb. Das Beispiel prüft weder Paketauflösung noch Installation oder tatsächliche Kompatibilität; es macht die Beziehungen und Entscheidungen sichtbar.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Plugin erweitert eine Anwendung über einen vorgesehenen Mechanismus. Eine Dependency bezeichnet allgemeiner etwas Benötigtes. Ein Modul ist ein Codebaustein. Eine Versionsbedingung beschreibt erlaubte Möglichkeiten, während eine konkret festgehaltene Auswahl zusätzliche Reproduzierbarkeit unterstützen kann. Das sind unterschiedliche Ebenen.

## 8. Häufige Missverständnisse

Nicht jede Abhängigkeit wird direkt importiert. Optionale und zum Bauen benötigte Pakete sind nicht automatisch Laufzeitvoraussetzungen jeder Variante. Ein Versionsbereich ist keine einzelne feste Version. Und „irgendwo installiert“ bedeutet nicht „in der richtigen Umgebung verfügbar“.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Dokumentiere Zweck, Umgebung und zulässige Versionen. Prüfe Änderungen mit den tatsächlich betroffenen Funktionen. Betrachte auch indirekte Anforderungen. Das Gedankenmodell enthält keine Installationsanweisung und verändert keine vorhandene Paket- oder Laufzeitkonfiguration.
