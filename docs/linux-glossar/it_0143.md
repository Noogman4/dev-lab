# TCP

## 1. Kurzbeschreibung

TCP, das Transmission Control Protocol, stellt Anwendungen einen zuverlässigen, geordneten Bytestrom zwischen verbundenen Endpunkten bereit. Es kümmert sich unter anderem um verlorene Daten und ihre Reihenfolge. Das bedeutet keine Garantie für den fachlichen Erfolg einer Anwendung: Eine Verbindung kann scheitern, und empfangene Bytes müssen noch sinnvoll verarbeitet werden.

## 2. Was bedeutet der Begriff?

TCP ist ein Transportprotokoll über IP. Seine grundlegende aktuelle Spezifikation ist [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html). Dort werden Zuverlässigkeit, Reihenfolge und der Bytestrom als zentrale Eigenschaften beschrieben. Anwendungen müssen dafür nicht jede verlorene Übertragung selbst auf der Ebene einzelner TCP-Segmente ersetzen.

Ein Bytestrom hat jedoch keine eingebauten Grenzen der Anwendungsnachrichten. Zwei Schreibaufrufe sind nicht automatisch zwei gleich große Empfangsaufrufe. Das verwendete Anwendungsprotokoll muss beispielsweise Länge oder Trennzeichen seiner Nachrichten festlegen.

## 3. Einfacher Vergleich aus dem Alltag

Eine umfangreiche Lieferung kommt in nummerierten Teilen. Eine Annahmestelle erkennt fehlende Stücke, fordert Ersatz an und stellt die vereinbarte Reihenfolge her. Die nachfolgende Arbeitsstation soll einen geordneten Bestand erhalten.

Das erklärt Reihenfolge und Wiederholung. Die Grenze: TCP-Nummern beziehen sich auf den Bytestrom, nicht einfach auf menschlich lesbare Paketzettel. Außerdem kann die Verbindung dauerhaft ausfallen. Und selbst eine vollständige Lieferung beweist nicht, dass die empfangende Anwendung ihren Inhalt gespeichert oder den gewünschten Auftrag ausgeführt hat.

## 4. Wie funktioniert das?

TCP baut einen Verbindungszustand zwischen Endpunkten auf. Sequenzinformationen ordnen Daten, Bestätigungen melden Empfang innerhalb des Transportverfahrens. Fehlende beziehungsweise als verloren bewertete Daten können erneut übertragen werden. Diese Aufgaben beschreibt RFC 9293 ausführlich.

Zusätzlich berücksichtigt TCP die Aufnahmefähigkeit der Gegenstelle und die Belastung des Übertragungswegs. Das begrenzt, wie viel ohne weitere Rückmeldung gesendet werden kann. „Zuverlässig“ bedeutet daher nicht „immer sofort“ oder „ohne Wartezeiten“. Die konkrete Anwendung muss weiterhin Zeitgrenzen, Verbindungsende und Fehler behandeln.

## 5. Wo begegnet mir das unter Linux?

Programme können TCP über Netzwerk-Sockets nutzen. Die Linux-Implementierung übernimmt die Transportarbeit, während die Anwendung ihre Nachrichten definiert. Ein erfolgreicher Verbindungsaufbau zeigt zunächst nur, dass die betreffenden Endpunkte eine Verbindung hergestellt haben.

Das Katalogbeispiel „Webseiten über HTTPS nutzen TCP“ braucht eine Einschränkung. Viele HTTPS-Verbindungen verwenden TCP, doch [HTTP/3 nach RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html) nutzt QUIC. [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html) definiert QUIC auf UDP-Basis. HTTPS ist deshalb kein verlässlicher alleiniger Beweis dafür, dass der Transport TCP verwendet.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenmodell betrachtet nur fünf Nutzdatenbytes. Es ist keine aufgezeichnete TCP-Verbindung und keine Simulation der vollständigen Protokollmaschine. Die Positionen sind vereinfachte relative Bytepositionen.

```text
Gewünschter Bytestrom: HALLO
Relativer Bereich 0–1: HA
Relativer Bereich 2–4: LLO
Der zweite Bereich kommt zuerst an.
Erst wenn der fehlende Anfang vorhanden ist, steht der vollständige Strom HALLO bereit.
```

Die empfangende Anwendung soll nicht einfach aufgrund der Ankunftsreihenfolge `LLOHA` erhalten. TCP organisiert die geordnete Bereitstellung. Welche Stückgrößen die Anwendung beim Lesen sieht, ist trotzdem eine andere Frage: Sie könnte etwa erst zwei und später drei Bytes lesen oder alle fünf gemeinsam erhalten.

Auch fehlt in diesem Modell jede Aussage zur fachlichen Bedeutung. Wenn `HALLO` einen Auftrag darstellen soll, müsste die Anwendung dessen Format und Ergebnis selbst regeln. Der Text versendet keine Pakete und öffnet keinen TCP-Port. Ein lokaler Unix-Socket-Test wäre dafür ebenfalls kein Nachweis einer tatsächlichen TCP-Übertragung.

## 7. Abgrenzung zu ähnlichen Begriffen

IP übernimmt grundlegende Paketadressierung und Weiterleitung. TCP ergänzt ein verbindungsorientiertes Transportmodell. UDP bietet ein anderes, datagrammorientiertes Modell. HTTP beschreibt Anwendungskommunikation, während TLS unter passenden Voraussetzungen Vertraulichkeit und Authentifizierung ergänzen kann. TCP allein ist keine Verschlüsselung.

## 8. Häufige Missverständnisse

Eine Transportbestätigung ist keine Bestätigung einer ausgeführten Bestellung oder gespeicherten Datei. Ein einzelnes `send` garantiert keine identische Empfangsblockgröße. Ebenso bedeutet ein verbundenes Socket nicht, dass die Gegenstelle für immer erreichbar bleibt. Der Verbindungszustand und die fachliche Bereitschaft bleiben getrennte Prüffragen.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Definiere Nachrichtengrenzen und Anwendungsbestätigungen ausdrücklich. Plane Fehler und Zeitüberschreitungen ein. Verwende für echte vertrauliche Kommunikation passende zusätzliche Schutzverfahren. Dieser Eintrag bleibt ein Gedankenmodell und verändert keine Prozesse, Ports oder Netzwerkeinstellungen.
