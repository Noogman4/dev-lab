# venv

## 1. Kurzbeschreibung

`venv` ist ein Python-Standardmodul zum Erzeugen virtueller Python-Umgebungen. Diese können projektbezogene Pakete vom gewöhnlichen Installationsbestand des Basisinterpreters trennen. Die Quelle nennt den üblichen Erzeugungsaufruf. Die Trennung ist jedoch keine allgemeine Sicherheitsisolation und kein Ersatz für Betriebssystemrechte oder einen Container.

## 2. Was bedeutet der Begriff?

Mehrere Projekte können unterschiedliche Abhängigkeiten benötigen. Eine virtuelle Umgebung stellt dafür einen eigenen Kontext mit passendem Interpreterzugang und Paketverzeichnis bereit. Sie ist normalerweise an einen vorhandenen Basisinterpreter gekoppelt, nicht eine völlig unabhängige neue Sprache.

Die [offizielle venv-Einführung](https://docs.python.org/3.13/library/venv.html#creating-virtual-environments) beschreibt die Erzeugung und die vorgesehenen Bestandteile. Ob Systempakete sichtbar sind und ob pip eingerichtet wird, hängt von den gewählten Optionen ab. „Virtuell“ bedeutet deshalb nicht automatisch „alle denkbaren äußeren Einflüsse ausgeschlossen“.

## 3. Einfacher Vergleich aus dem Alltag

Ein Projekt erhält einen eigenen beschrifteten Werkzeugbereich. Dadurch werden seine Bausteine nicht einfach mit denen anderer Projekte vermischt. Die gemeinsame Werkstattinfrastruktur bleibt trotzdem vorhanden.

Die Grenze des Vergleichs: Eine venv kann weiterhin Dateien lesen, Prozesse starten oder Netzwerke verwenden, soweit der ausführende Prozess dazu berechtigt ist. Sie schützt nicht von selbst vor schädlichem Code. Auch können Umgebungsvariablen und weitere Pfade das Verhalten beeinflussen.

## 4. Wie funktioniert das?

Eine Umgebung enthält Konfigurationsdaten und einen passenden Python-Zugang, je nach Plattform als Kopie oder Verknüpfung. Zusätzliche Pakete können in ihrem eigenen Verzeichnis liegen. Der verwendete Interpreter bestimmt, welcher Kontext bei einem Aufruf tatsächlich gilt.

Die [Referenz zu venv.EnvBuilder](https://docs.python.org/3.13/library/venv.html#venv.EnvBuilder) beschreibt Optionen wie gemeinsame Systempakete, Verknüpfungen und pip-Einrichtung. Das folgende Beispiel setzt `with_pip=False`, sodass es keine Paketverwaltung einrichtet und keine Pakete installiert.

Eine Shell-Aktivierung erleichtert die Auswahl über den Suchpfad. Sie ist nicht die einzige Verwendungsmöglichkeit: Der Interpreter kann ausdrücklich über seinen eigenen Pfad gestartet werden. Eine gesetzte Anzeige im Shellprompt ist außerdem kein vollständiger Funktionsnachweis der benötigten Projektabhängigkeiten.

## 5. Wo begegnet mir das unter Linux?

Python-Projekte verwenden häufig ein Verzeichnis wie `.venv`. Der Name ist eine Konvention, keine vorgeschriebene besondere Funktion des Linux-Dateisystems. Das Projekt dokumentiert, welcher Interpreter und welche Abhängigkeiten vorgesehen sind.

Eine vorbereitete venv sollte nicht ungeprüft als beliebig verschiebbar oder auf jedem anderen System verwendbar angesehen werden. Interpreterpfade und Plattformvoraussetzungen können sich unterscheiden. Reproduzierbare Einrichtungsanweisungen sind deshalb wichtiger als allein ein vorhandener Ordnername.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Python-3-Beispiel erzeugt unter Linux nur eine eigene kurzlebige Umgebung ohne pip:

```python
from pathlib import Path
import subprocess
import tempfile
import venv

with tempfile.TemporaryDirectory() as ordner:
    ziel = Path(ordner) / "probe"
    venv.EnvBuilder(with_pip=False, symlinks=True).create(ziel)
    assert (ziel / "pyvenv.cfg").is_file()
    config = (ziel / "pyvenv.cfg").read_text(encoding="utf-8")
    assert "include-system-site-packages = false" in config
    code = "import sys; print(sys.prefix != sys.base_prefix)"
    ergebnis = subprocess.run([str(ziel / "bin" / "python"), "-c", code],
                              capture_output=True, text=True, check=True, timeout=5)
    assert ergebnis.stdout == "True\n"
    print(ergebnis.stdout, end="")
```

Die Ausgabe lautet:

```text
True
```

Der eigene Interpreterzugang erkennt den getrennten Umgebungspräfix. Die Konfiguration und die Ausführung werden tatsächlich geprüft. Das Beispiel installiert keine Abhängigkeiten und entfernt danach ausschließlich den selbst erzeugten temporären Bereich. Es beweist keine vollständige Projekt- oder Sicherheitsisolation.

## 7. Abgrenzung zu ähnlichen Begriffen

pip installiert Distributionen. venv stellt einen Python-Umgebungskontext bereit. Ein Container oder eine virtuelle Maschine besitzt andere Isolationsmechanismen. Ein Git-Branch bezeichnet einen Quellstand. Ein Projektverzeichnis allein richtet noch keine passende Python-Umgebung ein.

## 8. Häufige Missverständnisse

Aktivierung bedeutet keine Sicherheitsgrenze. Eine venv installiert nicht automatisch jede Projektabhängigkeit. Derselbe Ordnername garantiert keinen identischen Bestand. Auch sollte eine fehlende Bibliothek nicht ohne Prüfung in irgendeinen anderen Interpreter installiert werden.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe den tatsächlich gestarteten Interpreter und dokumentierte Anforderungen. Bewahre bestehende Projektumgebungen. Der Test verändert weder `.venv` im Repository noch den Basisinterpreter und richtet keine zusätzliche Paketverwaltung ein.
