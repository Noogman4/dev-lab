# Semaphore

## 1. Kurzbeschreibung

Eine Semaphore verwaltet einen Zähler verfügbarer Zugänge. Ein erfolgreicher Erwerb verringert ihn, eine Freigabe erhöht ihn. Ist keine Kapazität verfügbar, kann ein passender Aufruf warten oder unmittelbar scheitern. Damit lassen sich beispielsweise höchstens drei gleichzeitige Nutzer einer Ressource vorsehen. Der Zähler führt die eigentliche Arbeit aber nicht selbst aus.

## 2. Was bedeutet der Begriff?

Die Quelle nennt drei gleichzeitige Downloads. Eine Semaphore könnte dafür drei Zugänge verwalten. Jede relevante Aufgabe muss den Zugang vor ihrer Arbeit erwerben und danach nach den vorgesehenen Regeln wieder freigeben. Wer diese Vereinbarung umgeht, wird nicht allein durch die Existenz des Zählers begrenzt.

Die [Python-Dokumentation zu Semaphore-Objekten](https://docs.python.org/3.13/library/threading.html#semaphore-objects) erklärt Erwerb, Freigabe und Warten. Das sind konkrete Schnittstellen für die Zusammenarbeit von Threads. Ein gleichnamiger Mechanismus für asynchrone Tasks oder andere Prozesse kann andere Regeln besitzen.

## 3. Einfacher Vergleich aus dem Alltag

Eine Werkstatt besitzt drei Zugangskarten für einen begrenzten Arbeitsbereich. Sind alle ausgegeben, muss eine weitere Person warten oder später wiederkommen. Wird eine Karte zurückgegeben, ist wieder ein Zugang möglich.

Die Grenze: Die Karten zählen nur Erlaubnisse. Sie garantieren nicht, dass die jeweilige Arbeit richtig erfolgt oder dass niemand eine Karte vergisst. Auch ersetzt ein solcher Zähler keine vollständige Prüfung, welcher Benutzer eine bestimmte Ressource überhaupt verwenden darf.

## 4. Wie funktioniert das?

Eine Anfangskapazität beschreibt die verfügbaren Zugänge. Vor der Arbeit wird ein Zugang erworben. Ein blockierender Aufruf kann bei Kapazität 0 warten. Eine nicht blockierende Variante meldet stattdessen unmittelbar, dass gerade kein Zugang verfügbar ist. Nach der Arbeit wird die Kapazität passend zurückgegeben.

Eine überzählige Freigabe kann ein Fehler sein. Die [Dokumentation zu BoundedSemaphore](https://docs.python.org/3.13/library/threading.html#threading.BoundedSemaphore) beschreibt deshalb eine Variante, deren Zähler nicht über den Anfangswert wachsen darf. Diese Kontrolle ist kein vollständiger Nachweis, dass jede konkrete Ressource der richtigen Aufgabe zugeordnet wurde. Sie erkennt eine bestimmte Art falscher Verwaltung.

Die [Linux-man-pages-Übersicht zu POSIX-Semaphoren](https://man7.org/linux/man-pages/man7/sem_overview.7.html) beschreibt außerdem benannte und unbenannte Formen für passende Prozess- und Threadzusammenarbeit. Das macht nicht jedes gewöhnliche Python-threading-Objekt automatisch zu einer gemeinsamen prozessübergreifenden Ressource. Der Geltungsbereich muss zur verwendeten Schnittstelle passen.

Auch Fehler- und Abbruchpfade müssen erworbene Zugänge korrekt behandeln. Eine vergessene Rückgabe kann spätere Arbeit dauerhaft warten lassen. Eine zu frühe Rückgabe kann mehr gleichzeitig aktive Arbeit erlauben als beabsichtigt. Die Freigabe muss daher zur tatsächlichen Lebensdauer der geschützten Tätigkeit passen.

## 5. Wo begegnet mir das unter Linux?

Programme begrenzen damit beispielsweise gleichzeitig verwendete Verbindungen oder andere knappe Ressourcen. Welche Kapazität sinnvoll ist, hängt von der Aufgabe ab. Ein größerer Wert führt nicht automatisch zu besserer Leistung und kann zusätzliche Belastung erzeugen.

Dieses Beispiel verwaltet nur eigene Zählerzugänge im Speicher. Es startet keine Downloads, öffnet keine Verbindungen und legt keine benannten Betriebssystem-Semaphoren an. Eine reale Ressourcenverwaltung wird dadurch nicht abgenommen.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 in einem temporären Arbeitsordner ausgeführt. Sämtliche Erwerbsversuche sind nicht blockierend. Die Anfangskapazität beträgt für dieses Modell 3.

```python
from threading import BoundedSemaphore

zugang = BoundedSemaphore(3)
erste = [zugang.acquire(blocking=False) for _ in range(3)]
assert erste == [True, True, True]
vierter = zugang.acquire(blocking=False)
assert not vierter
zugang.release()
erneut = zugang.acquire(blocking=False)
assert erneut
for _ in range(3):
    zugang.release()
ueberzaehlig_abgelehnt = False
try:
    zugang.release()
except ValueError:
    ueberzaehlig_abgelehnt = True
assert ueberzaehlig_abgelehnt
print("Anfänglich vergebene Zugänge:", sum(erste))
print("Vierter Zugang verfügbar:", vierter)
print("Nach Rückgabe wieder verfügbar:", erneut)
print("Überzählige Freigabe abgelehnt:", ueberzaehlig_abgelehnt)
```

Geprüfte Ausgabe:

```text
Anfänglich vergebene Zugänge: 3
Vierter Zugang verfügbar: False
Nach Rückgabe wieder verfügbar: True
Überzählige Freigabe abgelehnt: True
```

Nach dem erneuten Erwerb sind wieder drei Zugänge vergeben. Ihre drei Freigaben stellen die Anfangskapazität her. Der zusätzliche Versuch wird wie erwartet abgelehnt. Das prüft die Zählerregeln, keine reale gleichzeitige Downloadzahl, Fairness oder Prozesssynchronisierung.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Mutex erlaubt typischerweise einen exklusiven Abschnitt. Eine Semaphore verwaltet eine gewählte Kapazität. Ein Event signalisiert eine Bedingung. Eine Warteschlange hält Aufgaben. Diese Bausteine können zusammenarbeiten, sind aber nicht dieselbe Datenstruktur oder Berechtigungsentscheidung.

## 8. Häufige Missverständnisse

Die Semaphore führt keine Downloads selbst aus. Ein Zähler garantiert keine faire Reihenfolge. Eine begrenzte Variante erkennt nicht jeden Verwaltungsfehler. Und ein Threadobjekt ist nicht automatisch zwischen beliebigen Prozessen gemeinsam nutzbar.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Definiere Kapazität und Rückgabe passend zur Ressource. Prüfe Abbrüche und überzählige Freigaben. Die Ausführung bleibt bei einem eigenen Speicherobjekt und verändert keine Dateien, Konten, Dienste oder Netzwerkeinstellungen.
