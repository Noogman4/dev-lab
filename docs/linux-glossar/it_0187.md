# Session

## 1. Kurzbeschreibung

Eine Session ist ein zusammengehöriger Nutzungskontext über mehrere Interaktionen. In Webanwendungen kann sie beispielsweise eine Anmeldung oder vorübergehende Einstellungen verbinden. Die Sitzung ist nicht einfach ein einzelner HTTP-Request oder eine dauerhaft offene TCP-Verbindung. Zustandsdaten, Kennung und Lebensdauer müssen passend organisiert werden.

## 2. Was bedeutet der Begriff?

„Session“ bedeutet Sitzung. Der Begriff wird auch außerhalb des Webs verwendet, etwa für andere Benutzer- oder Arbeitssitzungen. Hier steht der Webkontext der Quelle im Vordergrund. Das Katalogbeispiel einer Sitzung nach einem Login ist häufig, aber Sitzungen können auch ohne angemeldeten Benutzer existieren.

Die [Django-Dokumentation zu Sessions in Version 5.2](https://docs.djangoproject.com/en/5.2/topics/http/sessions/) beschreibt verschiedene Speicherverfahren. Darunter sind serverseitige Daten und signierte Cookievarianten. Deshalb ist weder „alle Sitzungsdaten liegen immer im Browser“ noch „alle liegen ausnahmslos auf dem Server“ eine allgemeine Definition.

## 3. Einfacher Vergleich aus dem Alltag

Ein Vorgang wird über mehrere Besuche unter einer gemeinsamen Zuordnung bearbeitet. Eine Marke oder Nummer kann helfen, den richtigen Vorgang wiederzufinden. Der Vorgang umfasst aber mehr als diese Nummer.

Die Grenze: Eine Sitzungskennung ist ein technischer Wert. Wer sie in bestimmten Verfahren besitzt, kann möglicherweise den zugeordneten Zugriff nutzen. Sie ist nicht automatisch ein sicherer Identitätsbeweis unabhängig von Ablauf, Schutz und Prüfung. Auch darf ein längerer Nutzungskontext nicht mit einem unbefristeten Recht verwechselt werden.

## 4. Wie funktioniert das?

Eine Anwendung ordnet mehrere Anfragen einem Zusammenhang zu. Häufig wird dafür eine Kennung über ein Cookie transportiert. Serverseitige Verfahren können damit gespeicherte Daten nachschlagen. Andere Verfahren führen geschützte Zustandsinformationen beim Client mit. Signieren und Verschlüsseln sind dabei unterschiedliche Eigenschaften.

Der [OWASP-Leitfaden zum Sitzungsmanagement](https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/Session_Management_Cheat_Sheet.md) behandelt unter anderem Kennungen, Erneuerung und Ablauf. Solche Regeln sind wichtig, damit ein alter oder unberechtigt übernommener Zusammenhang nicht unbegrenzt nutzbar bleibt.

Abmeldung und Ablauf müssen zum Verfahren passen. Das bloße Entfernen eines sichtbaren Buttons macht eine Sitzung nicht ungültig. Auch das Löschen eines Browserwerts ist nicht ohne Weiteres der Nachweis, dass jeder serverseitige oder anderweitig gültige Zustand beendet wurde.

## 5. Wo begegnet mir das unter Linux?

Browser und Webanwendungen können Sitzungen verwenden, unabhängig vom Betriebssystem. Eine Linux-Anwendung kann entsprechend einen Webdienst nutzen. Das System selbst kennt daneben andere Arten von Sitzungen, die nicht automatisch identisch mit einer HTTP-Anmeldung sind.

Eine Verbindung kann zudem zwischen einzelnen Anfragen geschlossen und später neu aufgebaut werden, während der Anwendungskontext weiter besteht. Umgekehrt bedeutet eine bestehende Verbindung nicht, dass ein Benutzer angemeldet oder für eine bestimmte Aktion berechtigt ist.

## 6. Konkretes Beispiel Schritt für Schritt

Dieses Gedankenmodell beschreibt einen fiktiven Ablauf. Es wird keine Anmeldung durchgeführt und keine Sitzungskennung erzeugt.

```text
Vor der Anmeldung besteht noch kein entsprechender bestätigter Benutzerkontext.
Nach erfolgreicher Prüfung richtet die Anwendung den vorgesehenen Zusammenhang ein.
Weitere Anfragen werden nach dessen Regeln zugeordnet.
Für jede geschützte Aktion gelten weiterhin passende Berechtigungsprüfungen.
Abmeldung oder Ablauf machen den betreffenden Zugriff nach dem Verfahren ungültig.
```

Die Schritte zeigen Zuständigkeiten, keinen vollständigen sicheren Loginbauplan. Insbesondere fehlen konkrete Kennungserzeugung, Speicherregeln und Transportdetails. Es wird daher keine produktive Sicherheitsfunktion behauptet.

Ein Warenkorb oder eine vorübergehende Auswahl könnte außerdem schon vor einer Anmeldung existieren. „Session vorhanden“ und „Benutzer erfolgreich authentifiziert“ sind somit verschiedene Aussagen. Auch eine Antwort aus einem alten Kontext müsste nach den tatsächlichen Gültigkeitsregeln eingeordnet werden. Das Modell greift auf keine echten Konten oder Browserdaten zu.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Cookie ist ein möglicher Transport- und Zustandsmechanismus. Eine Session ist der größere Nutzungskontext. Ein Token kann einen bestimmten Nachweis darstellen. Eine HTTP-Verbindung trägt Nachrichten. Eine Betriebssystem-Anmeldesitzung ist wiederum ein anderer Kontext mit eigenen Verwaltungsregeln.

## 8. Häufige Missverständnisse

Eine Session ist nicht immer ein Login. Ein Cookie enthält nicht zwangsläufig die gesamten Sitzungsdaten. Eine signierte Darstellung ist außerdem nicht automatisch geheim. Schließlich darf eine sichtbar erfolgreiche Abmeldung nicht ohne Prüfung als universelle Ungültigkeit aller vorherigen Zugänge verstanden werden.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Verwende bei echten Anwendungen dokumentierte Verfahren für Kennung, Ablauf und Beendigung. Behandle zugangsrelevante Werte vertraulich. Dieser Eintrag liest oder verändert keine Sessions, Konten, Cookies, Schlüssel oder Dienste und führt keine Authentifizierung aus.

## 10. Verwandte Begriffe

Der [Cookie](it_0186.md) kann eine Kennung transportieren. [HTTP](it_0145.md) bleibt das Nachrichtenprotokoll. Ein [Request](it_0172.md) wird dem Kontext zugeordnet. Das [Backend](it_0182.md) übernimmt Prüfungen. [HTTPS](it_0146.md) ergänzt Verbindungsschutz.
