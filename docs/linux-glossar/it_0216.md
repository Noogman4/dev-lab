# Tag

## 1. Kurzbeschreibung

Ein Tag markiert in Git einen benannten Stand, häufig einen Commit für eine Version. Anders als ein gewöhnlicher Arbeitsbranch rückt ein Tag beim nächsten Commit nicht automatisch weiter. Es gibt einfache und annotierte Tags. Ein Tagname allein garantiert weder eine getestete Veröffentlichung noch die Unveränderlichkeit des Namens unter allen Umständen.

## 2. Was bedeutet der Begriff?

Der Katalog nennt `v1.0.0` als möglichen Release-Tag. Das ist eine verbreitete Benennung. Git leitet daraus jedoch keine fachliche Bedeutung wie „stabil“ oder „für alle Nutzer freigegeben“ ab. Dafür braucht ein Projekt eigene Regeln und eine entsprechende Prüfung.

Die [offizielle Dokumentation zu git tag](https://raw.githubusercontent.com/git/git/master/Documentation/git-tag.adoc) unterscheidet Lightweight-Tags und annotierte Tags. Ein einfacher Tag ist ein unmittelbarer Verweis auf ein Objekt. Ein annotierter Tag besitzt ein eigenes Tag-Objekt mit zusätzlichen Angaben, beispielsweise einer Nachricht und Tagger-Metadaten. Häufig zeigt dieses wiederum auf den gewünschten Commit.

## 3. Einfacher Vergleich aus dem Alltag

Ein Klebezettel markiert eine bestimmte abgelegte Fassung. Ein ausführlicher Begleitzettel enthält zusätzlich, wer die Markierung vorgenommen hat und was sie bedeuten soll. Beide können denselben Arbeitsstand kennzeichnen, haben aber nicht denselben Informationsumfang.

Die Grenze: Git-Tags sind technische Referenzen und gegebenenfalls Objekte. Ein beschrifteter Zettel beweist keine fachliche Abnahme. Auch kann ein Name unter bestimmten Voraussetzungen ersetzt oder gelöscht werden. Für verlässliche veröffentlichte Versionen braucht es deshalb gemeinsame Regeln statt nur eine hübsche Bezeichnung.

## 4. Wie funktioniert das?

Beim Anlegen wird ein Name im Tag-Namensraum auf ein Ziel bezogen. Ohne besondere Angabe wird häufig der aktuelle Commit gewählt. Ein annotierter Tag speichert zusätzlich ein Tag-Objekt; mit einer passenden Option kann dieses auch signiert werden. Eine Signatur ist wiederum nur im Rahmen ihrer technischen Prüfung und des Vertrauens in den Schlüssel aussagekräftig.

Ein neuer Folgecommit verschiebt den vorhandenen Tag nicht automatisch. Das unterscheidet den typischen Zweck vom Arbeitsbranch. Dennoch bedeutet „bleibt stehen“ keine technische Unmöglichkeit jeder späteren Änderung. Die Tag-Dokumentation behandelt ausdrücklich auch das Ersetzen bestehender Markierungen und die dabei entstehenden Probleme für andere Kopien.

Ein lokaler Tag ist außerdem nicht allein durch seine Anlage überall vorhanden. Die [Dokumentation zu git push](https://raw.githubusercontent.com/git/git/master/Documentation/git-push.adoc) beschreibt die gezielte Übertragung von Referenzen und Tag-Optionen. Ein gewöhnlicher Branch-Push darf nicht pauschal als Übertragung sämtlicher lokaler Tags verstanden werden. Eine Release-Seite eines Hostingdiensts ist noch einmal ein zusätzlicher Dienstvorgang.

## 5. Wo begegnet mir das unter Linux?

Projektarchive verwenden Tags, um bestimmte Stände wiederzufinden. Paketbau oder Fehlersuche können sich auf einen solchen Stand beziehen. Ob die Markierung tatsächlich zur installierten Software passt, muss anhand des jeweiligen Veröffentlichungs- und Paketierungswegs beurteilt werden.

Wer einen Tag auswählt, arbeitet nicht automatisch auf einem gewöhnlichen beweglichen Branch. Für eigene Weiterentwicklung sollte der Zustand bewusst geprüft werden. Das folgende Beispiel legt jedoch nur Markierungen an und wechselt keinen bestehenden Projektstand.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 und Git 2.52.0 ausgeführt. Es verwendet ein neues temporäres Repository ohne Vorlagen. Persönliche und systemweite Git-Konfiguration sind für die Kindprozesse ausgeblendet; die Identität gilt nur pro Aufruf.

```python
import os
from pathlib import Path
import subprocess
import tempfile

env = {k: v for k, v in os.environ.items() if not k.startswith("GIT_")}
env.update(GIT_CONFIG_GLOBAL="/dev/null", GIT_CONFIG_NOSYSTEM="1")
with tempfile.TemporaryDirectory() as ordner:
    repo = Path(ordner)
    def git(*args):
        return subprocess.run(
            ["git", "-c", "user.name=Glossar", "-c",
             "user.email=glossar@example.invalid", "-c",
             "commit.gpgsign=false", *args],
            cwd=repo, env=env, check=True, capture_output=True, text=True
        ).stdout.strip()
    git("init", "--template=", "-b", "probe")
    (repo / "notiz.txt").write_text("Eigener Stand\n", encoding="utf-8")
    git("add", "notiz.txt")
    git("commit", "-m", "Eigener Ausgangsstand")
    git("tag", "probe-leicht")
    git("tag", "-a", "probe-annotiert", "-m", "Eigene Markierung")
    leicht = git("cat-file", "-t", "refs/tags/probe-leicht")
    annotiert = git("cat-file", "-t", "refs/tags/probe-annotiert")
    assert leicht == "commit" and annotiert == "tag"
    assert git("rev-parse", "refs/tags/probe-annotiert^{}") == git("rev-parse", "HEAD")
    print("Einfacher Verweis zeigt auf:", leicht)
    print("Annotierter Verweis zeigt auf:", annotiert)
```

Geprüfte Ausgabe:

```text
Einfacher Verweis zeigt auf: commit
Annotierter Verweis zeigt auf: tag
```

Beide Markierungen gehören zum selben Commitstand. Eine führt direkt zum Commit, die andere über ein Tag-Objekt. Das Beispiel prüft keine Signatur, veröffentlicht keine Version und überträgt keine Tags. Der temporäre Bereich wird entfernt.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Branch schreitet bei eigener Entwicklung gewöhnlich fort. Ein Commit ist der gespeicherte Stand selbst. Ein Tag benennt ein Ziel. Eine Release-Seite kann zusätzliche Texte und Dateien anbieten. Gleichnamige Schlagwörter in anderen Anwendungen sind ein anderer Gebrauch des Worts.

## 8. Häufige Missverständnisse

Ein Tagname garantiert keine Stabilität. Nicht jeder Tag enthält eine Nachricht oder Signatur. Ein neuer Commit verschiebt Tags nicht automatisch. Und lokal angelegte Markierungen sind nicht automatisch auf jedem entfernten Repository vorhanden.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Dokumentiere die Bedeutung veröffentlichter Tags. Ersetze gemeinsam genutzte Versionsmarkierungen nicht beiläufig. Prüfe bei Bedarf Zielobjekt und Signatur getrennt. Die Übung verändert ausschließlich eigene Wegwerfmarkierungen und keine Projektversionen.

## 10. Verwandte Begriffe

[Commit](it_0207.md) bezeichnet den gespeicherten Stand. [Branch](it_0208.md) verwaltet die fortschreitende Linie. [Push](it_0211.md) überträgt Referenzen. [Repository Git](it_0206.md) enthält die Objekte. [Clone](it_0212.md) übernimmt Versionsdaten nach seinen Optionen.
