# Lockfile

## 1. Kurzbeschreibung

Ein Lockfile ist eine Datei, die ein Programm als Teil eines Sperrverfahrens verwendet. Damit können zusammenarbeitende Programme beispielsweise verhindern, dass dieselbe Aufgabe gleichzeitig mehrfach ausgeführt wird. Die Datei allein bewirkt das nicht: Entscheidend ist ein korrektes Verfahren zum Beanspruchen, Prüfen und Freigeben der Sperre.

## 2. Was bedeutet der Begriff?

„Lock“ bedeutet Sperre. Je nach Implementierung kann eine atomar angelegte Datei einen Anspruch kennzeichnen oder eine Betriebssystemsperre an einer geöffneten Datei verwendet werden. Diese Verfahren sind nicht identisch und haben unterschiedliche Regeln für Fehlerfälle und Lebensdauer.

Ein konkretes Linux-Verfahren ist `flock`. Die [offizielle Linux-Handbuchseite](https://man7.org/linux/man-pages/man2/flock.2.html) beschreibt gemeinsame und exklusive Sperren auf geöffneten Dateien. Der folgende Text und Versuch konzentrieren sich auf eine solche exklusive Sperre. Andere Bedeutungen von „Lockfile“, etwa festgeschriebene Paketversionen in manchen Projektwerkzeugen, sind davon zu unterscheiden.

## 3. Einfacher Vergleich aus dem Alltag

An einem gemeinsam verwendeten Arbeitsraum hängt ein Belegungsplan. Alle Beteiligten prüfen und befolgen dieselbe Regel, bevor sie den Raum benutzen. Ein bloß herumliegender Zettel schützt den Raum dagegen nicht vor gleichzeitigem Betreten.

Das erklärt die notwendige Zusammenarbeit. Die Grenze: Ein korrektes Sperrverfahren muss den Anspruch technisch eindeutig vergeben. Ein nacheinander ausgeführtes „nachsehen, dann Zettel hinlegen“ genügt bei gleichzeitig eintreffenden Personen nicht. Ebenso können zwei Prozesse zwischen einer Existenzprüfung und dem Anlegen einer Datei denselben scheinbar freien Zustand sehen.

## 4. Wie funktioniert das?

Bei einem exklusiven `flock` beansprucht ein Zugriff die Sperre. Ein anderer unabhängiger Zugriff auf dieselbe Datei kann die widersprechende Sperre nicht gleichzeitig erwerben. Mit einer nicht blockierenden Anforderung lässt sich sofort feststellen, dass die Sperre gerade nicht erhältlich ist.

Die [Python-Referenz zu fcntl.flock](https://docs.python.org/3.13/library/fcntl.html#fcntl.flock) stellt diese Operationen bereit. Die genaue Wirkung hängt auch vom System und Dateisystem ab. Bei gewöhnlichen lokalen Linux-Dateisystemen handelt es sich um ein kooperatives, sogenanntes advisory Verfahren: Andere Programme müssen die Sperrregel beachten. Es ersetzt keine Dateizugriffsrechte.

## 5. Wo begegnet mir das unter Linux?

Lockfiles werden beispielsweise zur Koordination gemeinsamer Ressourcen oder für einen Eininstanzbetrieb verwendet. Das Katalogbeispiel nennt eine mögliche Single-Instance-Regel für NetMon. Ob eine konkrete Anwendung so arbeitet und ob ihre Implementierung korrekt ist, wird durch diese Begriffserklärung nicht geprüft.

Eine PID in einer Datei ist ebenfalls nicht automatisch eine aktive Sperre. Ein Prozess kann beendet und seine Kennung später neu vergeben worden sein. Bei einem Dateisystem-Lock kann umgekehrt der Dateiname weiterhin existieren, obwohl die Sperre schon freigegeben ist. Dateiinhalt, Existenz und Sperrzustand sind getrennte Informationen.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 unter Linux in einem temporären Ordner ausgeführt. Zwei unabhängige Öffnungen derselben eigenen Datei konkurrieren innerhalb eines Prüfprozesses um `flock`.

```python
import fcntl
from pathlib import Path
import tempfile

with tempfile.TemporaryDirectory() as ordner:
    pfad = Path(ordner) / "probe.lock"
    with pfad.open("a+") as erstes, pfad.open("a+") as zweites:
        fcntl.flock(erstes, fcntl.LOCK_EX | fcntl.LOCK_NB)
        blockiert = False
        try:
            fcntl.flock(zweites, fcntl.LOCK_EX | fcntl.LOCK_NB)
        except BlockingIOError:
            blockiert = True
        finally:
            fcntl.flock(erstes, fcntl.LOCK_UN)
        assert blockiert
        fcntl.flock(zweites, fcntl.LOCK_EX | fcntl.LOCK_NB)
        fcntl.flock(zweites, fcntl.LOCK_UN)
        print("Zweiter Zugriff zunächst blockiert:", blockiert)
    assert pfad.exists()
    print("Datei bleibt nach Freigabe vorhanden:", pfad.exists())
```

Geprüfte Ausgabe:

```text
Zweiter Zugriff zunächst blockiert: True
Datei bleibt nach Freigabe vorhanden: True
```

Nach der Freigabe gelingt die zweite Sperranforderung. Die Datei existiert trotzdem weiter. Der Test prüft lokale Sperroperationen, keinen Mehrprozessstart einer Anwendung und kein Netzwerkdateisystem.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein PID-File hält zunächst eine Prozesskennung fest. Eine Datei mit festgeschriebenen Abhängigkeitsversionen hat eine andere Aufgabe. Dateirechte regeln zulässige Zugriffe, während eine kooperative Sperre deren zeitliche Abstimmung unterstützt. Diese Mechanismen können gemeinsam verwendet werden, sind aber nicht austauschbar.

## 8. Häufige Missverständnisse

Eine vorhandene Datei bedeutet nicht immer „Programm läuft“. Eine fehlende Datei beweist ebenfalls keine globale Sicherheit gegen Parallelstarts. Ein Lockfile sollte deshalb nicht ungeprüft gelöscht werden: Beteiligte könnten anschließend unter demselben Namen mit verschiedenen Dateiobjekten arbeiten und die gewünschte Koordination verlieren.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Verwende ein dokumentiertes Verfahren statt einer losen Existenzprüfung. Plane Freigabe und Fehlerbehandlung passend zur Sperrart. Der Versuch verändert ausschließlich eigene temporäre Daten und entfernt keine fremden Sperren. Eine tatsächliche Eininstanz-Abnahme bleibt offen.

## 10. Verwandte Begriffe

Ein [Prozess](it_0115.md) kann eine koordinierte Aufgabe ausführen. Die [PID](it_0116.md) kennzeichnet seine aktuelle Instanz. [Dateirechte](it_0112.md) bleiben für erlaubte Zugriffe relevant, auch wenn eine Sperre verwendet wird.
