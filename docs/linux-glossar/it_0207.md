# Commit

## 1. Kurzbeschreibung

Ein Commit ist ein gespeicherter Projektstand in Git mit zugehörigen Metadaten und Verweisen auf Vorgänger. Er erhält eine Objektkennung. Ein gewöhnlicher Commit übernimmt den vorbereiteten Inhalt des Index. Eine danach weiterbearbeitete Datei kann deshalb im Arbeitsverzeichnis anders aussehen als im gerade gespeicherten Commit.

## 2. Was bedeutet der Begriff?

Die Quelle nennt einen gespeicherten Änderungsstand und empfiehlt eine abgeschlossene Änderung. Das ist ein sinnvolles Arbeitsziel: Ein Commit sollte eine nachvollziehbare Einheit bilden. Git kann jedoch nicht selbst beurteilen, ob der Inhalt fachlich vollständig, getestet oder fehlerfrei ist.

Die [offizielle Dokumentation zu git commit](https://raw.githubusercontent.com/git/git/master/Documentation/git-commit.adoc) erklärt die Übernahme des Index und die Commit-Nachricht. Sie beschreibt auch besondere Aufrufformen mit abweichender Inhaltsauswahl. Hier behandeln wir den normalen Ablauf mit ausdrücklich vorgemerkten Dateien und anschließendem Commit ohne solche Sonderoptionen.

## 3. Einfacher Vergleich aus dem Alltag

Du stellst Unterlagen für eine datierte Ablage zusammen. Nach der Auswahl bearbeitest du eine Kopie auf deinem Schreibtisch weiter. Die abgelegte Zusammenstellung enthält dann weiterhin die ausgewählte Fassung, nicht automatisch die neueste Schreibtischfassung.

Die Grenze: Git legt keine unabhängige Fotokopie jedes gesamten Ordners nach Papierlogik an. Es verwendet Objekte und Verweise. Außerdem sind Autorangaben zunächst Metadaten und kein allgemeiner Identitätsnachweis. Eine technische Kennung oder eine Beschreibung ersetzt keine inhaltliche Prüfung.

## 4. Wie funktioniert das?

Mit `git add` wird der gewünschte Dateiinhalt vorgemerkt. Die [Dokumentation zu git add](https://raw.githubusercontent.com/git/git/master/Documentation/git-add.adoc) betont, dass spätere Bearbeitungen erneut aufgenommen werden müssen, wenn auch sie in den nächsten normalen Commit sollen. Das Vormerken ist kein dauerhafter Auftrag, alle künftigen Änderungen dieser Datei automatisch zu übernehmen.

Der Commit verweist auf den gespeicherten Projektbaum. Er enthält unter anderem eine Nachricht sowie Autor- und Committer-Angaben. Ein erster Commit besitzt keinen Vorgänger, ein gewöhnlicher Folgecommit typischerweise einen. Ein Merge-Commit kann mehrere Vorgänger haben. Die Historie ist daher nicht grundsätzlich nur eine einfache nummerierte Liste.

Die Objektkennung ist kein selbst gewählter Versionsname. Ihre genaue Form hängt vom verwendeten Objektformat ab. Wird ein Commit mit geändertem Inhalt oder geänderten Metadaten neu erzeugt, ist das ein anderes Objekt. Ein Branchname kann dagegen später auf einen anderen Commit zeigen.

## 5. Wo begegnet mir das unter Linux?

Entwicklungswerkzeuge zeigen Commits als Historie mit Nachrichten und Änderungen an. Ein lokaler Commit funktioniert ohne Hostingdienst. Er veröffentlicht nichts automatisch im entfernten Repository.

Vor dem Speichern sind der vorgemerkte Unterschied und der allgemeine Status hilfreich. Ein sauberer Arbeitsstand bedeutet anschließend nur, dass Git in diesem Bereich keine entsprechenden offenen Änderungen meldet. Er beweist keine bestandenen Tests oder erfolgreiche Ausführung des Projekts.

## 6. Konkretes Beispiel Schritt für Schritt

Das vollständige Beispiel wurde mit Python 3.13 und Git 2.52.0 ausgeführt. Es nutzt ein eigenes temporäres Repository ohne Vorlagen und blendet persönliche sowie systemweite Git-Konfiguration für die Kindprozesse aus. Die Identität wird ausschließlich pro Aufruf angegeben.

```python
import os
from pathlib import Path
import subprocess
import tempfile

env = {k: v for k, v in os.environ.items() if not k.startswith("GIT_")}
env.update(GIT_CONFIG_GLOBAL="/dev/null", GIT_CONFIG_NOSYSTEM="1")
with tempfile.TemporaryDirectory() as ordner:
    repo = Path(ordner)
    def git(*args):
        return subprocess.run(
            ["git", "-c", "user.name=Glossar", "-c",
             "user.email=glossar@example.invalid", "-c",
             "commit.gpgsign=false", *args],
            cwd=repo, env=env, check=True, capture_output=True, text=True
        ).stdout
    git("init", "--template=", "-b", "probe")
    datei = repo / "notiz.txt"
    datei.write_text("Vorgemerkt\n", encoding="utf-8")
    git("add", "notiz.txt")
    datei.write_text("Später bearbeitet\n", encoding="utf-8")
    git("commit", "-m", "Vorgemerkte Fassung speichern")
    gespeichert = git("show", "HEAD:notiz.txt").strip()
    aktuell = datei.read_text(encoding="utf-8").strip()
    assert gespeichert == "Vorgemerkt" and aktuell == "Später bearbeitet"
    assert git("diff", "--cached") == ""
    assert git("diff", "--name-only").strip() == "notiz.txt"
    print("Im Commit:", gespeichert)
    print("Im Arbeitsverzeichnis:", aktuell)
```

Geprüfte Ausgabe:

```text
Im Commit: Vorgemerkt
Im Arbeitsverzeichnis: Später bearbeitet
```

Der Commit enthält genau die vor der zweiten Bearbeitung aufgenommene Fassung. Die spätere Änderung bleibt offen. Das Beispiel erzeugt weder einen Push noch eine Änderung am eigentlichen Projekt. Sein temporäres Repository wird danach entfernt.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Commit ist ein gespeichertes Objekt. Ein Branch ist eine bewegliche Referenz auf einen Entwicklungsstand. Der Index bereitet Inhalte vor. Das Arbeitsverzeichnis enthält bearbeitbare Dateien. Das Übertragen von Commits an ein anderes Repository ist ein eigener Schritt.

## 8. Häufige Missverständnisse

Speichern im Editor erzeugt keinen Git-Commit. Vormerken speichert nicht automatisch spätere Bearbeitungen mit. Eine Commit-Nachricht garantiert keine fachliche Vollständigkeit. Und ein lokaler Commit ist noch keine Veröffentlichung oder unabhängige Sicherung.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Prüfe Inhalt und Umfang vor dem Commit. Beschreibe Zweck und Zusammenhang verständlich. Beachte, dass versehentlich aufgenommene vertrauliche Inhalte in der Historie liegen können. Die Übung verwendet nur zwei harmlose selbst erzeugte Textfassungen.
