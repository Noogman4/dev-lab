# Manifest

## 1. Kurzbeschreibung

Ein Manifest ist eine strukturierte Beschreibung eines Projekts, Pakets oder Artefakts. Es kann Namen, Versionen oder Anforderungen festhalten. Welche Felder gelten und welches Werkzeug sie liest, ergibt sich aus dem zugehörigen Format.

## 2. Was bedeutet der Begriff?

Der Begriff bezeichnet die Rolle einer Datei oder eines Metadatenblocks. In einem Python-Projekt kann `pyproject.toml` Projektangaben enthalten. Die [PyPA-Spezifikation](https://packaging.python.org/en/latest/specifications/pyproject-toml/) ordnet sie unter anderem der Tabelle `[project]` zu. Debian kennt für seine eigenen Paketformate [Kontrolldateien und Kontrollfelder](https://www.debian.org/doc/debian-policy/ch-controlfields.html), etwa Paketname, Version und Beschreibung.

## 3. Einfacher Vergleich aus dem Alltag

Eine Packliste beschreibt den Inhalt und den Bestimmungsort einer Sendung. Manifestangaben erfüllen eine ähnliche Aufgabe für Werkzeuge und Menschen. Die Grenze liegt in der genauen Semantik. Eine Software kann beispielsweise eine Versionsbedingung auswerten und dadurch einen Arbeitsschritt ablehnen.

## 4. Wie funktioniert das?

Ein Leser lädt ein Manifest im erwarteten Dateiformat und deutet die Felder nach seinem Schema. Syntax bestimmt, wie Zahlen, Listen oder Text geschrieben werden. Das Schema gibt an, welche Namen gültig sind und welche Werte ein Feld annehmen kann. Eine Datei kann syntaktisch korrekt sein und trotzdem eine Pflichtangabe vermissen lassen.

Manche Formate erlauben berechnete Angaben. Eine Version kann bei einem Build ermittelt werden, soweit das Format das ausdrücklich vorsieht. Maßgeblich ist dann auch, was im gebauten Artefakt steht.

## 5. Wo begegnet mir das unter Linux?

Bei der Paketarbeit unter Linux begegnest du solchen Metadaten etwa im Quellverzeichnis und in Paketwerkzeugen. Ähnlich benannte Felder können unterschiedliche Regeln haben. Die Debian-Versionssyntax und die einer Python-Distribution lassen sich nicht durch Umbenennen eines Feldes ineinander übertragen.

## 6. Konkretes Beispiel Schritt für Schritt

Gedankenbeispiel ohne Dateierstellung. Eine Notizanwendung soll in zwei Paketökosystemen erscheinen.

1. Das Team benennt Projekt, veröffentlichte Version und Laufzeitbedarf.
2. Für Python ordnet es diese Angaben den Projektfeldern der `pyproject.toml` zu. Für Debian wählt es die dort vorgesehenen Kontrollfelder und Paketbezeichnungen.
3. Bei der Kontrolle vergleicht es in beiden Artefakten die veröffentlichte Version mit der beabsichtigten Version. Die Paketnamen dürfen sich nach den Konventionen des jeweiligen Systems unterscheiden.
4. Eine separate Prüfung würde zeigen, ob die Anwendung mit den deklarierten Voraussetzungen tatsächlich startet.

## 7. Abgrenzung zu ähnlichen Begriffen

Ein Manifest beschreibt definierte Eigenschaften. Eine Sperrdatei kann konkrete aufgelöste Versionen festhalten. Eine Prüfsummenliste ermöglicht den Abgleich bestimmter Dateibytes. Manche Ökosysteme vereinen Funktionen, andere verwenden getrennte Dateien.

## 8. Häufige Missverständnisse

Der Name „Manifest“ verrät weder den Dateinamen noch das Format. Auch ein Eintrag, der im Text plausibel aussieht, gilt nur, wenn ihn das zuständige Werkzeug in der vorgesehenen Form interpretiert.

## 9. Praktische Hinweise und gegebenenfalls Risiken

Kläre vor einer Änderung, welches Werkzeug die Datei erzeugt und liest. Prüfe dynamisch ermittelte Angaben am fertigen Artefakt. Metadaten eines ausgelieferten Pakets sind für Empfänger zugänglich und eignen sich daher nicht für Zugriffsschlüssel.

## 10. Verwandte Begriffe

Die Python-Projektdatei pyproject.toml ist ein Beispiel für dieses Formatprinzip. [Paketierung](it_0270.md) erklärt den Gesamtprozess. [Abhängigkeiten](it_0272.md) erläutert die Voraussetzungen, die ein Manifest deklarieren kann.
