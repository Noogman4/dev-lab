## Ergebnis

- Der `netmon/`-App-Code entspricht jetzt wieder weitgehend dem Paketstand `1.1.14`.
- Ein Syntaxcheck fuer die zurueckgezogenen Kern-Dateien lief sauber.
- Ein kompletter `pytest`-Lauf ist trotzdem nicht gruen, weil die aktuell vorhandenen Tests ein anderer, neuerer oder uncommitteter Stand sind.
- Ein eingegrenzter `pytest`-Lauf gegen einen zur Deb passenden Testkern endete mit:
  - `94 failed, 420 passed`

## Wichtige Befunde

- `git ls-files tests` liefert aktuell nur:
  - `tests/test_hello.py`
- Die restlichen ausgefuehrten Tests sind untracked.
- `git ls-files netmon | wc -l` ergibt `54`.
- `find netmon -type f | wc -l` ergibt `269`.
- Die untracked Tests stammen aus mehreren Wellen zwischen `2026-04-03` und `2026-06-28`.
- Die Deb `1.1.14` enthaelt viele Features bis `2026-06-28`, aber die Testdateien sind nicht als gemeinsamer Git-Stand vorhanden.

## Fehlerklassen aus dem eingegrenzten Testlauf

- Sprach- und Textdrift:
  - Viele Assertions erwarten deutsche Texte, waehrend die Deb-Basis englische Fallbacks oder neue `tr(...)`-Wege liefert.
  - Beispiele:
    - `Fehler:` vs. `Error:`
    - `Land` vs. `Country`
    - `DoT: aktiv / Test ok` vs. `DoT: active / test ok`
- Dummy-/Testobjekte ohne `tr`:
  - Mehrere Controller und `app.py` setzen inzwischen `self.tr(...)` voraus.
  - Aeltere oder lose Test-Dummies liefern diese Methode nicht und brechen deshalb mit `AttributeError`.
- UI-/Source-Assertions gegen anderen Wortlaut:
  - Einige Tests pruefen konkrete deutsche Literale im Quelltext.
  - Die Deb-Basis verwendet dort bereits andere Strings oder uebersetzte Fallbacks.
- Funktionsstand neuer als Test oder Test neuer als Funktionsstand:
  - Zeitstempel zeigen gemischte Richtungen.
  - Ein Teil der Tests ist aelter als die passende Feature-Datei, ein anderer Teil ist neuer.

## Schlussfolgerung

- Das Problem ist nicht nur "kaputter Code".
- Das Problem ist vor allem ein auseinander gelaufener Stand zwischen:
  - Git
  - Paketbasis `.deb`
  - untracked Arbeitsdateien
  - untracked Tests

## Naechster sinnvoller Schritt

1. Den Paketstand `1.1.14` als Baseline behandeln.
2. Klären, welche untracked Tests wirklich zu `1.1.14` gehoeren.
3. Danach den neueren Funktions- und Teststand blockweise wieder aufbauen.
4. Am sinnvollsten zuerst einen konsistenten Block herstellen:
   - entweder "Deb-Code + passende Tests"
   - oder "aktuellerer Code + aktuellerer Testsatz"
